# EasyOrange 技术债务清单

> 主动列出"已知但选择不还"的技术债。**主动承认技术债 = 工程成熟标志**，比假装"完美无瑕"更可信。
>
> 不主动还债的判断标准：当还债的工程成本 > 债务当前造成的实际损失时，选择不还并文档化。

## 一、债务分类说明

| 级别 | 含义 | 处置策略 |
|---|---|---|
| **接受** | 已知债，当前不还，有明确理由 | 文档化，定期复盘 |
| **待评估** | 短期可接受，中期需还 | 标注触发条件 |
| **必须还** | 影响生产稳定性或安全 | 进入下个迭代 |

## 二、债务清单

### 测试与 CI

**TD-001 · 集成测试真实基础设施覆盖（已还）**
`*IT` 从「Testcontainers 依赖 → 静默跳过」改为 **Spring Boot docker-compose 复用 dev 栈**：`AbstractIntegrationTest` 去掉 `@Testcontainers` / `@ServiceConnection` / `@DynamicPropertySource`，由 `spring-boot-docker-compose`（`spring.docker.compose.file` 指向根 `compose.yaml`，`lifecycle-management: start-only`）保证基础设施运行，连接走 `application-it.yaml` 显式 localhost 直连；failsafe 绑定 `mvn verify`。
**结论**：弃用 Testcontainers 的理由是 ryuk sidecar 在无代理 Docker 下拉取失败，`disabledWithoutDocker=true` 会**静默跳过**、掩盖真实装配错误（`DatabaseConnectivityIT` 此前从未真正运行）。迁移时修出两处被掩盖的缺陷：`PaymentGatewayAdapter` / `MockSmsSenderAdapter` 原为 `@Profile("dev")` 门控，it profile 下无 bean。
**遗留**：IT 复用开发者持久 dev 库（非一次性），跨运行存在数据残留；完整隔离式测试库可作后续增强。

**TD-002 · JaCoCo 覆盖率门禁未在本地强制（接受）**
本地只在 `prepare-package` 生成报告，门禁在 CI（保本地编译速度）。代价是提交前看不到覆盖率红线。本地补跑命令见 [工程指标.md §2.1](./工程指标.md)。

### 基础设施依赖

**TD-003 · Elasticsearch 标记为可选依赖（接受）**
`@ConditionalOnProperty(easyorange.search.elasticsearch.enabled)` 控制装配（基文件默认 false）；关闭时 `KnowledgeFallbackAdapter` / `ProductSearchIndexAdapter` 接管。prod / dev 显式 true。
**代价**：ES 路径在无 ES 环境无法验证；降级走 MySQL LIKE，只能命中字面重叠，召回质量差。
**已有缓解**：① `ProdSearchGuard`（`@Profile("prod")`）在环境变量把开关覆盖回 false 时**中止启动**，ES 启用但不可达时 `ElasticsearchIndexManager` 的 `@PostConstruct` 建索引失败同样中止；② `KnowledgeFallbackAdapter` 启动打 WARN + 按调用累计 `easyorange.ai.rag.degraded`，`RagHealthIndicator` 在 `/actuator/health` 报 UNKNOWN 并标注「LIKE 兜底」；③ `ai-eval.yml`（按需 dispatch）起 ES 真实跑知识库召回；④ `ElasticsearchProductSearchIT`（商品检索 DSL）可本地跑。
**残留**：it 及裸跑基文件仍可无 ES 运行；商品检索 DSL 无 CI 覆盖——**这是 CI 覆盖缺口而非闭环**。
**触发重评估**：若未来支持「无 ES 的生产部署」，必须先落地召回的替代实现（进程内向量检索 / VectorStore）并纳入门禁，否则不能移除 `ProdSearchGuard`。

**TD-004 · Redis 单点 + 未做哨兵/集群（待评估）**
单实例足够 demo。代价：Redis 故障时 `RateLimitFilter` 与 `AiRateLimitInterceptor` 均 fail-open（可用性下降但不阻塞）。**触发**：进入生产时升级 Sentinel 或 Cluster。

### AI 工程化

**TD-005 · Token 成本治理（已还）**
`@TokenBudget` 注解 + `TokenBudgetAspect` + `InMemoryTokenBudgetStore` 已落地（计数维度 scenario + 日期，无用户维度）。**存储两版**（`easyorange.ai.budget.store`，默认 memory）：多实例场景切 `RedisTokenBudgetStore`（`HINCRBY` 原子累加，判定式与内存版一致，fail-open），代码侧已无缺口。**仍缺**：按用户 / 租户维度的计数（需要时才加）。

**TD-006 · Prompt 版本化（已还）**
`PromptRegistry` + `YamlPromptRegistry` + `PromptTemplate` 已落地：**5 个模板全在** `src/main/resources/prompts/*.yml`，模板即 system prompt，业务变量由服务内联 `String.format` 填充；prompt 修改无需重新编译部署。搜索增强的三个工具 prompt 已从 Java 常量移入 YAML 并纳入注入防护断言覆盖。

**TD-007 · AI 失败降级策略单一（接受）**
AI 调用失败仅 fail-open（返回 null 或 stale 缓存），用户感知不到降级提示。理由：AI 增强非必需，失败不影响主流程。缓解：Spring AI Observation 暴露成功率/延迟指标，降级频率可在监控面板观察。

### 安全与运维

**TD-008 · JWT 密钥从配置文件读取（接受）**
未接 Vault / Secrets Manager，轮换需重启、多实例需手动同步。缓解：prod profile 强制环境变量注入。**触发**：进入生产部署时接 Vault 或云厂商密钥服务。

**TD-009 · 文件上传未做病毒扫描（待评估）**
头像 / 商品图只校验 MIME 与大小。**触发**：进入生产时接 ClamAV 或云厂商内容安全服务。

### 工程化

**TD-010 · Lombok 在 JDK 25 下产生 unsafe 警告（接受）**
日志噪音；未来 JDK 可能移除 `sun.misc.Unsafe` 导致 Lombok 失效。缓解：JVM 参数已配 `--sun-misc-unsafe-memory-access=allow`。**触发**：Lombok 支持 JDK 25 后移除该参数。

**TD-011 · 跨模块 `<optional>` 未强制（已还）**
`.github/scripts/check-optional-deps.py` 接入 `backend-ci.yml`——除组合根 `easyorange-application` 外，任意模块依赖其他领域模块必须声明 `<optional>true</optional>`，违规即失败。本地复跑：`python3 .github/scripts/check-optional-deps.py easyorange-backend`。

**TD-012 · Flyway 只有一个 V1 初始化脚本（已还）**
表结构演进已切换为增量脚本：V2（收藏价格快照）/ V3（消息与订单扫描索引）/ V4（库存流水）/ V5（枚举码完整性）/ V6（AI 调用日志 token 用量）/ V7（商品 AI 建议价），`V1__init_schema.sql` 保持不动。**注**：开发阶段曾拆出 V2~V9 再在收口时合并回单文件 V1，未上线时属合理操作，上线后禁止。

### 文档与叙事

**TD-013 · 部分 README 数据未跑实测核对（待评估）**
JaCoCo / PIT / API 性能均已实测（见 [工程指标.md](./工程指标.md)）；"LLM 调用 p99 / 限流拒绝次数 / token 消耗"等 **AI 运行时指标仍为待补**——需真实 LLM key + Prometheus 采集，dev 环境密钥为占位（AI 调用走 fail-open，无法产生真实观测值）。**触发**：配置真实 key 启动后按 §2.2 采集并从"待补"替换为实测值。

**TD-014 · AI 成本治理是静态预估口径（已还）**
改为**按供应商回报的真实用量记账**：`AiModelSupport.recordBudgetUsage` 调后取 `ChatResponse` 的 usage，有真实 input/output 就按真实值累加；供应商不回报（embedding / 流式未带 usage）时退化为场景配置的单次上限，避免预算恒为 0 而静默失效。`TokenBudgetAspect` 相应退化为纯前置检查。

**TD-015 · 语义缓存命中率不可测 + 成本可见性不完整（部分已还）**
**已还**：`eo_ai_call_log` 补 `token_input` / `token_output`（供应商真实回报，未回报记 0、**不估算**）与 `subject_id`（调用主体，可空）+ `idx_ai_call_log_subject`（迁移 V6）；`AiCostReportService` + `GET /api/admin/ai/cost-report?hours=24` 可按场景聚合调用数 / token 入出 / 平均耗时 / 失败数。
**仍存在**：① `SemanticCacheService` 无 hit/miss 计数器，命中率不可测；其查询向量化走**不带 scope** 的 `AiModelSupport.embed`，既不计入日预算也不落调用日志（命中一次就是一次真实供应商调用，账面看不见）；② 预算计数默认在单 JVM 内存（key = 场景:日期，无 TTL，重启清空）——多实例改配置切 Redis 版即口径正确，未切时各算各的；③ embedding 调用 token 在成本报表里记 0（供应商不回报 usage）——embedding 成本仍是账外项。未命中路径的重复向量化已消除（端口拆成 `embedQuery` / `lookUp` / `store`，共用同一次向量化）。
**记账刻意留空的理由**：embedding 接口不回报 usage，纳入预算只能按场景上限估算，而 chat / qa 的单次上限是 1500 / 1000 token——给一次 1024 维 embedding 记上千 token 会让日预算被虚高用量提前打满，比不记更糟。
**触发重评估**：需要按用户 / 租户计费或更细的缓存收益核算时——加命中计数器、把 embedding 拆成独立预算场景（预算计数的 Redis 化已就位）。
