## 商品状态机

状态定义在 `ProductStatus.java`：枚举按生命周期声明（`DRAFT → PENDING_REVIEW → REJECTED → ONLINE → OFFLINE → SOLD`），合法转换集中在一张 `ALLOWED_TRANSITIONS` 表（单一事实来源），聚合根经 `transitionTo(target)` 统一守卫，终端状态用 `isTerminal()`（仅 SOLD）判断。

| 视角 | 转换 |
|---|---|
| 资产方 | `DRAFT → submitForReview → PENDING_REVIEW → approve → ONLINE`；被拒后 `REJECTED → submitForReview`（循环）；`ONLINE → takeOffline → OFFLINE` |
| 管理员 | `DRAFT` / `OFFLINE → putOnline → ONLINE`（绕过审核直接上架，端点受 `@PreAuthorize("hasRole('ADMIN')")`） |
| 系统 | `ONLINE → markAsSold → SOLD`（订单完成时由订单生命周期事件消费者触发） |

- 前端 C 端只展示 submitForReview 按钮；审核结果触发站内消息通知（AUDIT_SUCCESS / AUDIT_REJECTED）；审核记录落 `eo_product_audit_log`（action: 1 通过 / 2 拒绝 / 3 重提交，含维度 JSON + 前后状态快照）
- **进入 ONLINE 只有 `approve` 和 `putOnline` 两条路径**，统一经 `Product.validateOnline()`（isComplete + hasValidPrice + hasStock）守卫，禁止新增第三条绕过校验的上架路径
- `delete` 不改变 status，单独由 `canDelete()` 守卫（SOLD 不可删，保留订单追溯）；库存恢复不变量 `canRestoreStock()`（SOLD/OFFLINE 不可恢复）由 `Product.restoreStock()` 调用

## 订单状态机与生命周期

动作驱动设计：`OrderAction` 枚举是**唯一事实来源**（每个动作声明前置状态集合 / 目标状态 / 目标支付状态 / 关闭归因类型 / 错误码 / paymentGuard），聚合根统一经私有 `transitionTo(action, reason)` 守卫——一处校验合法性 + 一处应用副作用，**禁止绕过守卫直接改状态**。`OrderStatus.canTransitionTo()` 由动作定义派生。

```
PENDING_PAYMENT ──PAY──→ PAID ──SHIP──→ SHIPPED ──CONFIRM_RECEIPT──→ COMPLETED
       │                   │  │                     │
       │                   │  └──FORCE_CANCEL──→    │
       │                   └──REFUND──→            └──REFUND──→
   CANCEL──→ CANCELLED            │                              REFUNDED
       │        ▲                 │
       └────────┴──FORCE_CANCEL───┘
```

| 视角 | 转换 |
|---|---|
| 买家 | `PENDING_PAYMENT → CANCEL → CANCELLED`（仅待付款，必须附原因）；`PAID`/`SHIPPED → REFUND → REFUNDED`（支付状态须为已支付） |
| 卖家 | `PAID → SHIP → SHIPPED`；`SHIPPED → CONFIRM_RECEIPT → COMPLETED`（买家或系统自动确认） |
| 管理端 | `PENDING_PAYMENT`/`PAID → FORCE_CANCEL → CANCELLED`（必须附原因） |
| 系统 | `PENDING_PAYMENT → CANCELLED`（超时取消，`OrderTimeoutTask` 每 5 分钟扫描）；`SHIPPED → COMPLETED`（自动确认收货，`OrderAutoConfirmTask` 每日，`order.auto-confirm.*` 独立配置） |

- 两个定时任务均按订单加分布式锁（非阻塞，拿不到即跳过）+ 本地事务 + Outbox 事件原子提交；**聚合根重建必须带行项**，否则事件 `productIds`（完成事件）/ `items`（取消、退款事件）为空，库存恢复 / 售出标记会静默失效
- 订单完成事件触发 `ProductInventoryPort.markAsSold`；取消 / 退款事件触发 `restoreStock(orderId, productId, quantity)`，数量取事件明细且与下单扣减对称
- 库存变更统一落流水（`eo_stock_ledger`，唯一键 `(change_type, biz_id, product_id)` 承载幂等）：重复投递只生效一次；`StockReconcileScheduler` 每日对账余额与流水快照，漂移告警但不自动改数
- 下单链路（锁 → 准备 → 建单 + Outbox → 扣库存 → 建支付，单事务原子提交）见 [ADR-0007](../adr/0007-order-local-tx-over-saga.md)

### 支付-订单状态联动

订单置 `PAID` **唯一由「支付成功」事件驱动**：`PUT /api/orders/{id}/pay` 校验买家与 `canPay()` 后经 `PaymentGatewayPort.pay` 委托支付模块两阶段支付（PENDING → PAYING → SUCCESS），不直接置 PAID。`Payment.confirmPay` 发布 `PaymentSucceededEvent`（含 orderId，Outbox 同事务原子）→ RabbitMQ `payment.succeeded` → `PaymentSucceededEventConsumer` → `OrderCommandHandler.onPaymentSucceeded` 经 `PAY` 守卫置 `PAID` 并发布 `OrderPaidEvent`。mock 回调（`/mock-payment/success`、`/mock-payment/process`）与真实网关回调（`POST /api/payments/callback`）同路径发布事件。消费按 eventId 幂等，订单已支付则跳过。

**取消补偿**：支付成功事件到达时订单已取消（超时 / 买家取消 / 管理端强制取消）→ 订单保持 `CANCELLED` 不再流转（库存已在取消时恢复），并触发自动退款：`PaymentGatewayPort.refundPayment(orderId, …)` → payment 两阶段退款（SUCCESS → REFUNDING → REFUNDED，发 `PaymentRefundedEvent`）。退款失败经容器重试进 DLQ / terminal 人工介入；订单已是 `REFUNDED` 等非法状态仍由 `PAY` 守卫抛 `ORDER_STATUS_ERROR`（防重复支付事件重复退款）。

## 举报处理工作流

状态机：`PENDING(0) → PROCESSING(1) → RESOLVED(2)` / `DISMISSED(3)`

- 用户提交举报（选类型 + 填描述），24h 内同一用户对同一商品不可重复举报
- 管理员可单条 / 批量处理：**resolve** 通过 / **dismiss** 驳回 / IGNORE / PRODUCT_OFFLINE / WARN_SENDER / BAN_PRODUCT
- 每次处理操作记录到 `eo_report_handle_history`（action / remark / operator_id）
- 处理完成后 `ReportProcessedEvent` → 异步发站内信通知举报人
- 用户可查看自己的举报列表（分页）与详情（含处理结果）
