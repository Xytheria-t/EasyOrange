# 工单：发布助手（拍照识别）失败可观测

> 交给实施方（另一个 AI 会话，在本仓库内工作）：先读本文件全部内容，再动手。所有 file:line 都已核实。

## 一句话任务

把「发布助手拍照识别」的**静默失败**改成显式失败：后端返回明确业务错误码，前端据此提示用户；失败路径补测试。

## 背景（已核实的事实，勿重复摸索）

- 后端 `easyorange-ai/src/main/java/com/cartethyia/easyorange/ai/application/service/AutoListingService.java:31-58`：`analyzeImages`（`@TokenBudget(scenario="auto_listing")`）在三种运行期失败下**都 `return null`**：
  - ① 视觉模型返回空 → `:41-44`；
  - ② 结构化解析失败（`callJsonAs` 返回 empty）→ `:46-50`；
  - ③ 任意异常（供应商不可用等）→ `:52-57`（catch 后 `return null`）。
- 控制器 `easyorange-application/src/main/java/com/cartethyia/easyorange/adapter/inbound/web/controller/AiListingController.java:31-34` 无条件 `Result.success(...)` → **HTTP 200 + `data: null`**。
- 前端 `easyorange-frontend/src/hooks/useAutoListing.ts:26-36`：只有 `if (result.data)` 分支（弹成功提示 + 自动填充）；`data` 为 null 时**什么都不发生**——用户点了按钮、等一会儿、零反馈。
- 对照范式：对话链路已有正确做法（`AiChatService` 返回 200 + `ChatAnswer.degraded=true` + 人话文案，因为那里还有「部分可用结果」）。发布助手没有部分结果可言，所以走**业务错误码**更贴切。
- 前端请求层已经就绪：`easyorange-frontend/src/api/core/request.ts:182` 对非成功码 `throw new ApiClientError(data.message, data.code, data.data)`；`useAutoListing` 现有 `catch` 已会弹 error toast。
- 错误码空间：`easyorange-ai/src/main/java/com/cartethyia/easyorange/ai/domain/constant/AiResultCode.java` 目前只有 `TOKEN_BUDGET_EXCEEDED("B8001", ...)`；**B8002 空闲**（实施前 `grep -rn "B8002" --include=*.java .` 确认一次）。

## 目标与验收

1. `AiResultCode` 新增：`AI_UNAVAILABLE("B8002", "AI 服务暂时不可用，请稍后重试")`。
2. `AutoListingService.analyzeImages` 的三条运行期失败路径改为抛 `BusinessException.of(AiResultCode.AI_UNAVAILABLE)`；原有 `log.warn/error` 的上下文日志全部保留；方法签名与控制器保持「单表达式透传」不变（异常由全局异常处理转成 `Result` 的错误码）。
3. **保持不动**：`promptRegistry.require(...)` 的 fail-fast（模板缺失 = 部署期配置错误，`:32-34` 注释已写明语义，不要把它并入降级）。
4. 前端 `useAutoListing` 的 `catch` 改为**优先展示后端 message**（`ApiClientError` 的 `message`，即 B8002 的中文文案），取不到时回落现有「AI 识别失败，请稍后重试」。成功与失败两条分支都必须给出 toast。
5. 测试：
   - 后端 `easyorange-ai/src/test/java/.../AutoListingServiceTest.java`：为三条失败路径各加一条用例，断言抛出的 `BusinessException` 的 `getCode()` 为 `"B8002"`；成功路径用例不变。
   - 前端：若已有 `useAutoListing` / 发布页测试则补一条「后端返回业务错误 → 弹错误提示且文案来自后端」；没有就新建最小用例（参考同目录既有 hook 测试写法）。
6. 验收命令（全绿）：
   ```bash
   cd easyorange-backend && ./mvnw -o -pl easyorange-ai test -Dtest=AutoListingServiceTest
   cd easyorange-backend && ./mvnw -o -Pci -pl easyorange-ai verify -DskipITs=true   # spotless 必过
   cd easyorange-frontend && npm test && npm run lint:check && npm run typecheck
   ```
7. 手工验证（无需有效 AI key 即可完成）：起 dev 栈时**不要 `source .env`**（让 key 为空，模型装配成 `UnconfiguredChatModel`，失败是秒级的）→ 前端发布页上传图片点识别 → 应出现错误 toast「AI 服务暂时不可用，请稍后重试」，而不再是毫无反应。若需要启动应用：先 `cd easyorange-backend && ./mvnw install -DskipTests`，再 `./mvnw spring-boot:run -pl easyorange-application`。

## 明确不做

- **不改** provider 超时/重试配置（`easyorange.ai.qwen-vl.timeout` 等）。空 key 时秒级失败；**失效但仍非空的 key** 会有秒级以上的供应商超时 + 重试（实测一次 40s+），那是供应商侧行为，不在本工单范围。
- 不改响应体形状（不加 `degraded` 字段、不动 `AutoListingResult`）；不动 `AiChatService` 的 degraded 范式。
- 不新增「一码一类」的叶子异常；语义一律走 `AiResultCode` + `BusinessException.of(...)`。
- 不顺手改分块、prompt、前端视觉。

## 仓库规范（必须遵守）

- 异常：必须继承 `BaseBusinessException`；用 `BusinessException.of(...)`；用模块专属 `ResultCode`（禁止回退全局 `B0002`）；**每个业务模块只保留一个统一领域异常**。
- 提交：`fix(ai): ...`（后端）与 `fix(frontend): ...`（前端，如独立改动），一个逻辑单元一个提交；禁止 `git add -A`；spotless 与 pre-commit 必须绿；不重写已推送历史。
- 增量验证：只跑涉及模块的单测，不刷新覆盖率、不改 `doc/工程指标.md` 的数字。
- 前端提交前跑 `npm run lint:check` 与 `npm run typecheck`（CI 会跑同样三项）。

## 回报格式

改动文件 + 提交 hash；`AutoListingServiceTest` 的用例输出；前端用例输出；手工验证的实际 toast 文案；遗留问题（若有）。
