# 工单：易变结构计数治理（单点 + 自动校准）

> 交给实施方（另一个 AI 会话，在本仓库内工作）：先读本文件全部内容，再动手。所有 file:line 都已核实，可直接按图索骥。

## 一句话任务

把随代码频繁变动的「结构计数」收敛到**单一落点**，并提供**一条命令自动校准**；其余文档改为链接引用，从此改代码不再需要手工同步文档里的数字。

## 背景（已核实的事实，勿重复摸索）

- 触发原因：仓库迭代频繁（数周数百次提交），文档里散落的计数（Port 数、表数、消费者数、测试数…）每次都要人工同步，耗费 token 且已经漂移。
- **已存在的漂移实例**：`README.md:5` 写 49 Port，而自称 SSOT 的 `doc/工程指标.md:27` 写 **48**（代码事实 49）。
- 现有机制：`.githooks/check-metrics-drift.py` 从代码事实计算 9 类计数并校验文档中的 66 处文字，已在 pre-commit 与 CI 生效。**正向校验保留**；痛点是数字分散在多份文档，要过校验就得人工逐处改。
- **已知漏检**：正则不匹配 Markdown 加粗数字，所以 `doc/工程指标.md:39/41/82` 的前端测试文件数写 108（事实 106）长期未被拦住；`**48**` 这种写法同样漏过。
- 受管制的 9 类计数（脚本当前计算值，仅供参照，勿写死）：modules=11 / ports=49 / adrs=12 / consumers=9 / tables=27 / archunit_rules=12 / prompt_templates=5 / frontend_test_files=106 / golden_set_cases=35。

## 目标与验收

1. **单点落位**：在 `doc/工程指标.md` 顶部（紧跟标题与说明之后）新增一节 `## 结构计数（脚本生成，勿手改）`，用一个 fenced code block 列出全部 9 类计数的 `名称: 数字`，并附生成命令。**该区块是这 9 个数字在全仓的唯一落点**。
2. **其余位置去数字**：根 `README.md`、`easyorange-frontend/README.md`、`doc/interview/*.md`、`doc/agents/*.md`、`doc/技术栈.md`、`doc/技术债务清单.md`、`doc/迭代路线.md`、根 `AGENTS.md`、`easyorange-backend/AGENTS.md` 中这 9 类计数的具体数字，改为：链接 `doc/工程指标.md#结构计数` 或定性表述（例：「11 Maven 模块」→ 见下方豁免）。
   **豁免（允许保留）**：① modules 模块总数（低变动，且是简历硬点，可留可留一处）；② 版本号（由 `check-version-drift.py` 单独管，不动）；③ 实测类数字（QPS / 延迟分位 / 覆盖率 / PIT 分数 / k6 结果——是测量值不是派生计数，维持现状约定：带口径与日期）。
3. **脚本改造** `.githooks/check-metrics-drift.py`：
   - 新增 `--fix`：从代码事实重算并原地回写单点区块；**幂等**（连跑两次无 diff）。
   - 修正正则，使 `**49**`、`**106** 文件` 这类加粗数字也能被识别为待校验数字。
   - 校验失败时的错误信息里**直接给修复命令**：`python3 .githooks/check-metrics-drift.py --fix`。
   - 反向检查（加强项）：若 9 类计数出现在单点区块之外，报错并指出 `文件:行`。
4. **规则落笔**：根 `AGENTS.md` 的「实现偏好（跨项目）」或「参考索引」段落加一句：结构计数只在 `doc/工程指标.md` 单点维护，改代码后跑 `python3 .githooks/check-metrics-drift.py --fix`。（根 AGENTS.md 有 6500 字符预算、当前约 5836，加一行安全；pre-commit 会校验预算。）
5. **验收命令**（全绿才算完成）：
   ```bash
   python3 .githooks/check-metrics-drift.py            # 应 OK
   python3 .githooks/check-metrics-drift.py --fix      # 幂等：第二次 diff 为空
   git add -A --dry-run >/dev/null && git commit       # pre-commit 通过（按仓库规范提交，见下）
   grep -rn "个 Port\|48 个\|49 个\|108 文件\|106 文件\|个消费者\|张表" README.md doc/ *.md easyorange-backend/AGENTS.md \
     | grep -v "工程指标.md"                            # 应无命中（豁免项除外）
   ```

## 明确不做

- 不新增钩子或 CI 步骤；不改 `check-version-drift.py` / `check-test-tier-drift.py` / `check-context-budget.py` 的行为。
- 不做文档重排、不改目录名（`doc/` 保持不变，**不要**改成 `docs/`）。
- 不动 `doc/agent诊断与升级路线.md`（内部交接文档）。
- 不为了让校验变绿而删掉真实信息；只做「数字 → 链接/定性」的等价替换。

## 仓库规范（必须遵守）

- 提交：小步 + Conventional Commits（`<type>[(scope)]: 一句话中文`）；只含文档的提交 type 用 `docs`；一个逻辑单元一个提交；**禁止 `git add -A` 盲提**；钩子已启用（`core.hooksPath=.githooks`），pre-commit 必须绿。
- 脚本为纯标准库 Python，无第三方依赖；改完自测。
- 不重写已推送历史。

## 建议步骤

1. 先 `cat .githooks/check-metrics-drift.py` 读清 66 处分布与计算逻辑，再 `python3 .githooks/check-metrics-drift.py` 跑一次。
2. 重构脚本：抽出「计算事实」与「渲染单点区块」两个纯函数；`--fix` 只写单点区块，其余位置仍走校验。
3. 写单点区块；逐个文件把散落数字替换为链接/定性表述（每改一处 grep 确认残留）。
4. 修正则 + 报错信息带修复命令。
5. 跑验收命令 → 提交（建议 1 个提交：脚本与文档互为前提，合成一个逻辑单元）。

## 回报格式

列改动文件与提交 hash；贴 `--fix` 幂等证明（两次 diff 为空）；贴最终脚本输出；列仍保留的数字及理由（豁免项）。
