### 2.2 1 分钟版 · 模型应用工程师 / AI Agent 方向

> 我做了 EasyOrange 项目，定位是 **LLM 应用工程化 × DDD：RAG 检索增强 + 轻量级 Agent 编排 + 评估闭环**。
>
> 核心矛盾：LLM 调用贵且不稳定，必须限流降级 + 可观测 + 预算治理，同时 DDD 铁律要求 domain 层零框架依赖。我的解法是 **AI 基础设施全面框架化为 Spring AI 2.0**（[ADR-0008](../adr/0008-ai-spring-ai-framework.md)，Supersedes ADR-0003）——删掉自研 `LlmPort` / `VisionPort` / `CachingLlmAdapter` / `AiMetricsService`，六个业务服务直接注入 Spring AI `ChatModel` / `EmbeddingModel` bean（`chatModel` @Primary DeepSeek / `visionChatModel` Qwen-VL / `embeddingModel` DashScope text-embedding-v3，统一 OpenAI 兼容线协议）；保留业务级治理：`AiRateLimitInterceptor` Redisson 令牌桶按端点限流、超限返回 stale 缓存不是 429；`@TokenBudget` AOP 日预算 + Prompt 6 个 YAML 版本化。**6 个 AI 决策点（估值/文案/信用画像/找货/评估/审核）全链路 8 件套工程化**。
>
> RAG 侧我做了**真实检索链路**：`SemanticSearchService` 用 `text-embedding-v3` 把查询转 1024 维向量，ES kNN + BM25 混合召回 Top-50，Java 原生 Cosine 重排收口，索引侧 `nameEmbedding` best-effort 写入（失败降级 null 不阻塞主链路）——SKU < 10 万不引 Milvus，量级分界线讲得清楚。
>
> 质量侧我做了**评估闭环**：每次 LLM 调用落 `eo_ai_call_log`（scope/model/prompt_hash/响应/耗时/成败），`AiEvalScheduler` 每天用 ChatModel 当评审员按「相关性/完整性/格式/语气」四维打分回写，`AVG(judge_score) GROUP BY scope` 量化 prompt/模型改动的质量回归——AI 输出好不好从「感觉」变成「可量化」。
>
> 编排侧写了**轻量级 Agent Planner**（`AiSearchEnhancerAdapter`），基于 Spring AI `ChatModel`，无 LangChain4j 黑盒：自然语言查询走 4 路 CompletableFuture 并行 Tool Calling（LLM 意图识别路由 / 规则引擎打标签 / 市场分析 / 建议问题生成），单步骤 5s 超时降级不影响整体，每路 Tool 复用同一套模型 + 限流/预算链路。

### 2.3 1 分钟版 · Java 架构师 / 高级后端方向

> 我做了 EasyOrange，定位 **LLM × DDD：Java 架构工程化实战**。11 个 Maven 模块全解耦，35 个 Port 接口做编译期隔离，ArchUnit 10 条规则在 CI 阶段守住 DDD 分层不被破坏。
>
> 下单链路一致性我选 **本地单事务 + Redisson 分布式锁 + Outbox**，**拒绝 Saga**（见 [ADR-0007](../adr/0007-order-local-tx-over-saga.md)，同样拒绝 2PC/XA/Seata AT/TCC，原由见 [ADR-0001](../adr/0001-order-saga-vs-2pc.md) Superseded）：`OrderCommandHandler.handle(CreateOrderCommand)` 按 productId 排序获取分布式锁（key=`eo:order:lock:product:{productId}`，10s 是获取等待超时；持有期由 watchdog 续期、事务提交后释放，锁等待在事务外不占数据库连接）防死锁防超卖 → 事务内创建订单 + 发布 `OrderCreatedEvent`（Outbox 同事务原子）→ `ProductInventoryPort.decreaseStock()` 同步扣库存 → 创建支付记录；任一步失败事务整体回滚，抛 `OrderCreationException`，**无补偿路径**。取消/退款恢复库存、完成标记售出等跨模块副作用由 `OrderLifecycleEventConsumer` 消费订单生命周期事件异步触发。
>
> 事件驱动可靠性靠三层：① **Spring Modulith Outbox** — 业务表 + `EVENT_PUBLICATION` 表同事务原子写入，崩溃重启自动重发，不丢事件；② **DLQ 三级重试** — 消费失败进 DLQ，`DlqRetryScheduler` 每 5min 扫 + 指数退避 1/5/15min 重投，超过 max 转储 `eo.dlq.terminal` 等人工；③ **幂等** — `EventIdempotencyChecker` Redis SETNX 按 `consumerId:eventType:eventId` 去重，多消费者监听同一事件不阻塞；再加 **全链路 traceId**（HTTP → MDC → @Async → RabbitMQ header → 消费者 MDC）。
>
> 架构治理靠 ADR + ArchUnit + PIT 三板斧：10 条 ADR 每条都记「为什么选 + 拒绝了什么」，ArchUnit CI 阻断违规依赖，PIT 变异测试验证 JaCoCo 行覆盖不是假的（order 模块 mutation 70% / test strength 89%）。**11 模块 / 10 ADR / 35 Port / 2,400+ 测试，Domain 层 84.1% 行覆盖 + 71.5% 分支覆盖**。

### 2.4 3 分钟版（深度面 / 让你主动讲项目细节时）

> 1min 版本（§2.2 或 §2.3）+ 展开一个「被拒绝方案」的对比——比如 AI 方向展开「为什么不用 LangChain4j 自己手写 Tool Registry」或「从 ES 轻量 RAG 演进到完整 RAG 管线（分块 → 评测集 → rerank 模型）」；架构师方向展开「为什么单库下单不用 Saga（拒绝 Saga 的决策）」+ Seata AT/TCC 技术对比。讲完停一下，抛一句「这块要不要我再展开某个细节？」把节奏交给面试官。

## 三、高频追问应答

### 3.1 模型应用工程师 / AI Agent 方向

**问：为什么框架化到 Spring AI 2.0，而不是继续用自研 Port/Adapter？**
> 我做过完整评估（[ADR-0003](../adr/0003-ai-port-adapter-decorator.md) → [ADR-0008](../adr/0008-ai-spring-ai-framework.md) 决策翻转）：
> - ADR-0003 决策时（2025-11）Spring AI 1.0 尚未稳定，自研 Port/Adapter + 装饰器是合理选择；Spring AI 2.0.0 GA（2026）稳定后，自研 `LlmPort`/`VisionPort`/`CachingLlmAdapter`/`AiMetricsService` 就成了与框架重复的"手写代码"
> - 项目 STP 规范明确"零新增自定义代码是最优方案——删掉手写代码，换成框架配置即可"，迁移后六个 service 直接注入 `ChatModel`/`EmbeddingModel` bean，供应商切换只需改 `AiModelConfig` 的 baseUrl/apiKey/model
> - `AiSearchEnhancerAdapter` 的 4 路并行编排保留手写（框架黑盒），但每路 Tool 的 LLM 调用走框架 bean——**编排自己写、模型调用用框架**，两类复杂度各归其位

**问：RAG / 向量检索为什么不用 Milvus / PGVector？**
> （拒绝项第 5 条）量不够——现在 SKU 维度 < 10 万，Milvus/PGVector 引入向量索引构建、ANN 参数调优（HNSW ef_search / nprobe）、运维监控告警一整套东西，ROI 太低。我们用 **ES kNN 轻量 RAG**：`SemanticSearchService` 用 DashScope `text-embedding-v3`（1024 维）生成查询向量，索引侧商品名 `nameEmbedding` 由 `ElasticsearchProductSearchIndexAdapter` best-effort 写入（dims=1024 与 ES `dense_vector` 映射对齐），ES kNN + BM25 混合召回，LLM 做语义排序增强，P95 延迟 < 300ms 完全够用，等 SKU 到 500 万以上再平滑迁 Milvus。

**问：TokenBudget AOP 具体怎么管的？**
> `@TokenBudget` 注解加在 6 个 AI Service 方法上，Spring AOP `@Around` 切面在调用前检查 `累计预估用量 + maxTokensPerCall > dailyTokenLimit`（`TokenBudgetStore` 日累计），超过抛 `TokenBudgetExceededException` 走统一降级；`application.yaml` 的 `easyorange.ai.budget.scenarios` 可按场景热更新覆盖注解默认值（注解是编译期契约，配置是运行期旋钮）。预估用量以 `maxTokensPerCall` 计，不引入精确 token 计数器（YAGNI）。

**问：多模态 Vision 调用跟 LLM 是一条链路吗？**
> 是，同一套 Spring AI 链路——`visionChatModel` bean（Qwen-VL `qwen-vl-max`，DashScope compatible-mode 线协议）用 `AiModelSupport.analyzeImages`（多图 Media + `UserMessage.builder`）识别拍照上架图片，`@TokenBudget(scope=AUTO_LISTING)` 单独管预算。**换供应商只改 `AiModelConfig` 的 options**。

**问：搜索增强的 4 路并行是怎么组织的？有 Tool 抽象吗？**
> 有，我把它做成了 **Tool Registry 模式**：`SearchTool<T>` 接口（`name() / description() / kind() / run(context)`），4 个工具 Spring 自动收集进 `SearchToolRegistry`（构造期防重名冲突，新增工具零改动注册）：
> - `intent_detection`（LLM）— 意图识别
> - `product_tagging`（RULE）— 规则引擎打标签，零 LLM 成本亚毫秒
> - `market_analysis`（LLM）— 市场分析
> - `question_suggestion`（LLM）— 猜你想问
>
> `AiSearchEnhancerAdapter` 从 Registry 按 name 取工具，4 路 `CompletableFuture` 并行，5s 总超时，单路失败降级不影响整体。`name/description` 对应 OpenAI Function Calling 的 function name/description——未来要把工具暴露给模型自主调用，基于它们生成 JSON Schema 即可，抽象已经就位。

**问：怎么判断 AI 输出质量？（LLM-as-Judge）**
> 我把「AI 输出质量」从感觉变成了可量化：每次 LLM/Embedding 调用经 `AiCallLogRecorder` 落一条 `eo_ai_call_log`（scope/model/prompt_hash/response/耗时/成功与否，Flyway V3 建表），记录失败只告警不阻塞主链路。`AiEvalScheduler` 定时（默认每天 3 点，`easyorange.ai.eval.*` 配置）用 ChatModel 当评审员，按「相关性/完整性/格式/语气」四维打 1-5 分 + 一句评语回写。这样 prompt 版本或模型改动后，`SELECT AVG(judge_score) GROUP BY scope` 就能看到质量回归——回答「AI 输出好不好」这个 AI 岗必问题。

**问：RAG 你们现在做到哪一步了？往深做先做什么？**
> 现状（已落地两条线）：**① 商品标题级轻量 RAG**——`SemanticSearchService` 用 text-embedding-v3 生成 1024 维查询向量，ES kNN + BM25 混合召回 Top-50 + Java 原生 Cosine 重排；**② 知识库完整链路**——文档摄入管线（`KnowledgeIngestionService` 解析→分块 500 字 + overlap 50、切点优先落换行→逐块 embed→ES `knowledge_docs` 索引，best-effort 写入 + 启动补索引重试 PENDING）+ 混合召回（kNN num_candidates=100 + BM25 title^2/content）→ Cosine 重排收口 → 回答带 [来源:标题] 引用溯源（`AiChatService`）。
> 检索质量有量化：金标准集 10 条检索用例（gold_doc_ids 引用种子文档 kb-0001~0005）跑 hit@5 / MRR，逐条落 `eo_retrieval_metric`，`RetrievalEvalScheduler` 每日回归（默认关闭）。
> 还没做的是 **模型 rerank**（Cross-Encoder 替代 Cosine，双塔 vs 交叉编码的成本权衡我讲得清）——量级不到不需要，触发条件是检索指标下滑或知识库文档量级上涨，诚实标注演进方向。

**问：你的系统支持流式输出吗？设计一个流式问答？**
> **已支持**（AI Playground 页面落地）：`POST /api/ai/chat/stream` 用 SseEmitter + Spring AI `ChatModel.stream(Prompt)`（Flux），事件协议 token / sources / done / error，前端 fetch + ReadableStream 逐帧消费（选 fetch 而不是原生 EventSource，因为 EventSource 只支持 GET 且不能带 Authorization 头，我们的鉴权在 localStorage）。
> 设计时解决的工程点：**① 预算兼容**——流式方法在流结束前就返回，`@TokenBudget` AOP 拦不住，`AiChatService` 手动执行同一套预算检查，超限 onError 降级；② **调用日志不缺流**——`AiModelSupport.callTextStream` 阻塞收流后把完整拼接结果落 eo_ai_call_log（Judge 数据源不缺流式调用）；③ **引用来源先于正文**——检索结果在生成前就绪，先推 sources 事件让前端先渲染来源区；④ **断流兜底**——网络异常 onError 推送降级文案，前端展示错误气泡。
> 首字延迟（streaming 首 token 时间）目前未做专项指标采集，是诚实标注的待办。

**问：Agent 记忆 / 多轮对话怎么设计？**
> **已实现**（`AiChatService`，前端 Playground 多轮会话）：**短期记忆** = Redis List 会话窗口（key `eo:chat:session:{sessionId}`，TTL 24h，裁剪到最近 N 轮，`ChatSessionStore`），历史以「用户:…/助手:…」注入 prompt；**长期记忆** = `eo_user_preference` 用户画像表（跨会话持久，工具决策步骤顺带从对话提取偏好写入，聊天时注入 prompt）；**推理循环** = 单步 ReAct（工具决策器输出 JSON `{"tool":"knowledge_search"|"none","query":…,"preference":…}` → 执行检索 → 带引用生成回答）。
> 设计取舍：**记忆读写都 fail-open**——Redis 挂了丢记忆不阻塞回答；**单步 ReAct 是刻意简化**（决策点都是单次调用），多步推理循环（思考→调工具→观察→再思考）的抽象已就位：`SearchTool` 的 name/description 对齐 Function Calling JSON Schema，暴露给模型自主调用只需生成 schema。

**问：LLM-as-Judge 有什么局限？评估体系怎么补？**
> 局限：① **自评偏差**——Judge 和生成用同一个模型，偏好趋同；② 顺序 / 长度偏差（长答案容易得高分）；③ 打分离散、维度主观，不同 prompt 版本之间的分数差不可直接比。
> **已落地**：客观指标（检索层 hit rate / MRR 自动算，落 `eo_retrieval_metric`）+ 金标准集（30 条人工标注用例，`eval/golden-set.yaml`）+ **分数进 CI 门禁**（`EvalGate` 低于基线 -0.3 卡 build，`GoldenSetRegressionIT` 跑真实 LLM 回归，像 JaCoCo/PIT 一样卡门禁）。
> **演进中**：faithfulness（答案与检索内容一致性）未做；自评偏差的缓解（换 Judge 模型 / 人工抽检）未做；反馈飞轮已落地（👍/👎 → 导出评测集自动扩充）。

### 3.2 Java 架构师方向

**问：下单为什么不用 Saga？Seata 的 AT/TCC 不是更标准吗？**
> 分两层答——**为什么拒绝 Saga**（决策，见 [ADR-0007](../adr/0007-order-local-tx-over-saga.md)）和 **为什么不用 Seata**（技术对比，原 ADR-0001 结论保留）。
>
> **（一）为什么单库下单不用 Saga**：我们单库部署（MySQL 8.4），`OrderCommandHandler.handle(CreateOrderCommand)` 一个本地 `@Transactional` 就把订单 / 库存扣减（`ProductInventoryPort.decreaseStock`）/ 支付创建 / Outbox 事件全部包进**同一 MySQL 事务**，任一步失败数据库整体回滚——本地事务比 Saga 的最终一致更强、成本更低。Saga 的补偿要么与回滚重复、要么在进程崩溃后无法重建，`eo_saga` 表留下的只是一行失败状态码，观测价值低于写路径成本。所以我在 [ADR-0007](../adr/0007-order-local-tx-over-saga.md) 明确**拒绝 Saga**：单库场景正确识别过度设计，比挂一个失效状态机更能体现架构判断力。真正的演进触发条件是 product/payment 模块拆分独立数据源 / 独立部署，那时才重新评估真 Saga / 事务性 Outbox 补偿。
>
> **（二）为什么不用 Seata（知识保留）**：
> ① **Seata AT 模式** 要代理数据源 + undo_log 表 + TC/TM/RM 三角色独立部署，跟我们的 `@ConditionalOnProperty RabbitMQ` 降级模式不兼容——RabbitMQ 没了能起应用，Seata TC 挂了直接连不上；
> ② **TCC 模式** 3× try-confirm-cancel 样板代码，每个参与模块都要写 Try/Confirm/Cancel 三个接口，侵入大、维护成本爆炸；
> ③ 我们平台不经手资金，没有 double-spend 风险，本地单事务的强一致已经覆盖，Seata 强一致 ROI 太低；
> ④ 2PC/XA 需要全局事务协调器、穿透 Port/Adapter 边界、锁等待长——这条理由现在覆盖**整个 Saga 家族**（2PC/XA/Seata AT/TCC/Saga 编排），全都以同样理由被拒绝。

**问：为什么用 RabbitMQ 不用 Kafka？Kafka 不是更标准吗？**
> 这个问题我评估过 5 种 MQ（Rabbit / Kafka / Pulsar / NATS JetStream / Redis Streams），最后按 4 个维度打分选的 Rabbit，不是不知道 Kafka，是场景和成本都没到（见 [ADR-0005](../adr/0005-messaging-rabbitmq.md)）：
> ① **DLQ + 重试（40% 权重）Kafka 不原生**：我们有 `DlqRetryScheduler` 三级重试 + terminal 毒消息转储，RabbitMQ 的队列级 `x-dead-letter-exchange` 是声明式的，两个参数搞定；Kafka 根本没有「死信」概念，消费失败要自己手动发 dlq topic、自己调度器重投、自己配位点提交逻辑，成本翻倍；
> ② **模型（30%）不匹配**：我们是 1 个事件 → 10 个独立下游各消费各的（AI 要估值、订单生命周期要恢复库存 / 标记售出、审计要写库、通知要发消息），RabbitMQ 的「Exchange → 多独立队列」是原生的；Kafka 得搞 10 个不同 consumer group，每个 group 自己维护 offset + 重试，分散难讲还容易出 bug；
> ③ **成本（20%）和运维（10%）失衡**：Kafka 高吞吐优势是百万 msg/s 才显现，我们每天几万条事件，RabbitMQ 单节点 10k msg/s 完全够——杀鸡用牛刀，分区/副本/consumer group lag 带来的运维复杂度是纯负担；
> ④ **兜底方案**：我保留了 `MessageBus` Port 抽象，NATS JetStream 做了备选实现（`@ConditionalOnProperty` 切换），真哪天量到了换 Kafka 改 Adapter 就行，domain/application 层一行不用动。

**问：NATS JetStream 和 Kafka 你们如果真要二选一改哪个？**
> 选 NATS。两个原因：① **DLQ 原生**（`max_deliver + discard policy=dead`，和 Rabbit 的声明式粒度最接近，现有 `DlqRetryScheduler` 最容易迁移）；② **运维最轻**（`nats:2.10 -js` 单容器 50MB 镜像，Kafka KRaft 模式单节点也重得多）。Kafka 的唯一优势是「大众认知广 + 简历好看」，但从「替换成本最低、模型最贴合」的架构视角选，肯定 NATS。

**问：CQRS 为什么只在 4 个模块做，favorite/user 不做？**
> 见 [ADR-0002](../adr/0002-cqrs-scope-4-modules.md)。CQRS 的核心收益是「读多写少 + 查询聚合跨多个聚合根 + 读写模型可以独立优化」。product（读多写少，ES 全文搜索 + 列表聚合）、order（列表页跨 product+payment 聚合）、payment（对账查询独立索引）、message（消息会话列表 + 未读数查询维度独立）这 4 个满足条件。
>
> 但这 4 个**深度不同**：product / order 有独立 ReadModel（`product/application/query/readmodel/`、`order/application/query/readmodel/OrderReadModel` + `OrderQueryRepository`），payment / message 只做 **Command/Query Handler 级分离 + 独立查询仓储**（`PaymentQueryRepository`、`MessageQueryRepository`），没有单独的 ReadModel 类。
>
> 为什么 message 不做 ReadModel、favorite 完全不做？message 的**聊天消息本身读写比 1:1**（用户发一条对方读一条），读模型独立优化的收益接近 0，所以只用 Handler 级分离把「会话列表 / 未读数 / 历史消息」的查询维度独立出来就够了；favorite 收藏列表最多几千条，DB 单表 `WHERE user_id = ?` 加索引够用。CQRS 不是银弹，每个模块都拆 Command/Query Repository 多一倍代码量，收益 < 维护成本就坚决不做。

**问：ArchUnit 具体守了什么？你们 CI 真的能阻断吗？**
> `ArchitectureRulesTest` **10 条** `@ArchTest` 规则（`ArchitectureRulesTest.java` javadoc 也写 10；旧口径「11 条」是过时的）：
> 1. `domain` 白名单准入：`domain` 只允许依赖 JDK + `common`（零框架 / 不依赖 controller / mapper / DTO，合并为 1 条）
> 2. `*CommandHandler` 不能依赖 `*QueryHandler`（CQRS 写侧不依赖读侧）
> 3. `*QueryHandler` 也不能依赖 `*CommandHandler`（CQRS 读侧不依赖写侧）
> 4. 业务模块（order/product/message/favorite）间只能通过 `*.domain.port.*` 和 `*.domain.valueobject.*` 包通信（ACL 端口隔离）
> 5. 每个 `*Port` 接口必须有 `adapter.outbound` 适配器实现（端口必有适配器，白名单已清零）
> 6. 禁止出现 `*.infrastructure.*` 包（统一用 `adapter/outbound/`）
> 7. domain/application 禁止反向依赖 adapter（`FreezingArchRule` 冻结已知历史豁免，其余零例外）
> 8. Controller 禁止直连 `mapper`（必须经由 application 服务）
> 9. 禁止 `System.out` / `System.err`（统一 SLF4J）
> 10. 禁止 `e.printStackTrace()`（统一 SLF4J）
>
> 测试挂在 `easyorange-application` 模块的 `./mvnw test` 里，CI GitHub Actions 的 build-and-test job 只要失败就红，PR 合不进来，真能阻断。

**问：PIT 变异测试是什么？跟 JaCoCo 区别？**
> JaCoCo 行覆盖只看「代码被执行过没」，不管「测试能不能发现 bug」——把一个 `if (a > 0)` 改成 `if (a >= 0)`，JaCoCo 还是绿的，但实际上逻辑变了。PIT 在编译后的 bytecode 里注入**变异**（mutations）：比如把 `<` 改成 `<=`、把 `+` 改成 `-`、把 `return x` 改成 `return null`，然后跑现有测试，如果测试还全绿，说明这个变异**没被杀掉（存活）**，对应位置的测试没覆盖到真实逻辑。
>
> 我们只对 domain 层做（聚合根状态机 / 领域服务 / 值对象），**2026-08-14 全量实测：735 变异 2 分 26 秒**（比预估的 3-5 分钟还快，CI nightly 完全跑得起）——order 模块 mutation 74%（杀掉的比例）、test strength 78%、line 92%；product 281 变异 mutation 63%、test strength 73%。JaCoCo + PIT 双门禁互补，避免写「为了覆盖率的空测试」。

**问：Outbox 怎么保证事务一致的？崩溃了真的不丢事件？**
> Spring Modulith 的 Outbox 实现在 `org.springframework.modulith:spring-modulith-events-core`，核心就是**同事务双写**：
> 1. 业务 Service 方法 `@Transactional` 里先写业务表（比如 INSERT eo_order）
> 2. 再把 `DomainEvent` 序列化成 JSON 写入 `EVENT_PUBLICATION` 表（事件 ID / 类型 / completion_date = null）——**这两条 SQL 在同一个本地事务里**，要么都成功要么都回滚
> 3. 事务 commit 之后，`ApplicationListenerMethodAdapter` 异步从 `EVENT_PUBLICATION` 表捞 `completion_date is null` 的事件，一条一条发 RabbitMQ，发成功 UPDATE completion_date = NOW()
> 4. 崩溃重启时，`spring.modulith.events.republish-outstanding-events-on-restart=true` 会重新扫所有未完成事件，再发一次
>
> 关键是**至少一次投递** + **消费者幂等**配合：Modulith 保证不丢（可能重复），`EventIdempotencyChecker` 保证重复投递也只处理一次。

### 3.3 通用高频追问

**问：Redisson 分布式锁的 watchdog 到底怎么工作的？你们锁的 leaseTime 设了多少？**
> 我们下单锁在 `DistributedRedissonLockAdapter`，调的是 `lock.tryLock(waitTime, -1, TimeUnit.SECONDS)` 三参版本——**leaseTime 传 -1，由 Redisson watchdog 自动续期**：Redisson 默认锁 30s，后台每 10s（1/3 lease）检查锁是否仍被当前线程持有，是就续期回 30s，保证锁不会在下单流程结束前自动过期。watchdog 同时防止「持锁线程崩溃导致锁永不释放」（靠 Redis 端 PTTL 检测 + 看门狗线程续期）。另外锁**释放推迟到事务提交/回滚之后**（`DistributedRedissonLockAdapter` 用 `TransactionSynchronization#afterCompletion`）——若提前释放，后一个请求会在前一个事务尚未提交时读到旧库存快照，击穿防超卖（e268c59e 修复）。
> 场景差异：**短事务（我们的下单）用 watchdog（leaseTime=-1）**，不用手工估算锁时长、不怕租约提前过期；**明确不想被续期的场景**（如限定时长互斥）才传显式 leaseTime。
> 另外两个细节：① 多商品锁按 productId 排序后逐个获取（`DistributedRedissonLockAdapter`），防 AB-BA 死锁；② 释放时检查 `isHeldByCurrentThread()` 再 unlock，防「锁已过期被他人持有」时误删别人的锁。

**问：EventIdempotencyChecker 幂等为什么用纯 SETNX 就够了？不需要「锁 + done 标记」两级吗？**
> 不需要锁——`SET NX EX` 是**一条原子命令**，同时完成「检查 key 不存在 + 写入 + 设 TTL」，不存在查-写竞态窗口，锁是给多命令序列用的，这里单命令就原子了。key 命名空间 `consumerId:eventType:eventId` 隔离多消费者。两个细节：① 处理**失败**时 `unmark` 撤销标记，让容器重试 / DLQ 重投能重新执行——宁可重试不可漏处理；② 标记 TTL 24h 覆盖 DLQ 三级重试最长窗口（快速 3 次 + 退避 1/5/15min ≈ 20min），进程在标记后、处理完成前崩溃的残留窗口由业务副作用幂等（条件更新）兜底。

**问：ES 语义搜索怎么做的？为什么不引入 Milvus / PGVector？**
> 我们直接用的 **ES kNN 查询**，不是重排那套。链路：`SemanticSearchService` 用 DashScope `text-embedding-v3`（1024 维）把关键词转成查询向量，`ElasticsearchProductSearchQueryAdapter` 在语义模式下构造 ES 的 `knn` 查询（字段 `nameEmbedding`，`num_candidates=100`，`k=size*2`）+ BM25 `multi_match` 混合召回，LLM 对结果做增强（打标签/猜你想问，`AiSearchEnhancerAdapter`），P95 延迟 < 300ms 够用。为什么不用独立向量库？——SKU < 10 万，ES 自带 kNN + HNSW 索引完全够，Milvus / PGVector 引入向量索引构建 + ANN 调参 + 运维监控一整套东西，ROI 太低。真正的分界线是数据规模：SKU 到百万级、向量索引成为瓶颈时再切独立向量库。

**问：令牌桶和固定窗口的差异具体在哪？你们的 RRateLimiter 参数怎么定的？**
> 固定窗口（`increment+expire`）的问题：窗口边界突刺——59:59 用满 30 次，00:01 又能用 30 次，1 秒内理论上能打 60 次；且原子性缺口（increment 和 expire 两条命令非原子，需要 Lua）。Redisson `RRateLimiter` 是真正按「rate/interval 令牌补充速率」的令牌桶：`tryAcquire` 按补充速率发放，无边界突刺。我们按端点配 5-30 次/分（`AiRateLimitInterceptor` 表），配置在 `AiCallScope` 枚举 + yaml；Redis 不可用时 fail-open 直接放行——限流是保护手段，不能成为可用性单点。

**问：Flyway 你们怎么演进的？只有初始脚本吗？**
> 不是。项目有过真实演进：`V1__init_schema.sql` 是开发阶段两次合并后的单文件完整 DDL（V1~V6、V1~V9 收口）——折叠过删表迁移（遗留幂等键表 eo_idempotency_key，死代码创建的表，幂等改由 `IdempotencyKeyFilter` + Redis 承载）、删列迁移（eo_audit_log.oper_location）、加列迁移（eo_order.refund_reason/refund_time），并入 AI 观测/知识库/画像表（eo_ai_call_log 等 5 张）。约定：**禁止修改已执行的迁移脚本**（上线后），新增按 V{N+1} 递增；DDL 用 MySQL 8 原生 INPLACE 算法（非阻塞在线执行）；新增字段必须可空或有默认值。开发阶段合并迁移是项目未上线、无生产历史时的合理操作，上线后绝对禁止。

**问：性能数据？压测过吗？**
> 压过。k6 50 VUs × 30s 混合只读流量（列表 60% + 分类 20% + 搜索 20%），本地单实例开发栈：**640 req/s，avg 6ms，p95 9.2ms，p99 13ms，0 失败**——比脚本内置阈值（p95<500ms / p99<1s）低一个数量级。另外做过限流开关对比：默认限流（200 次/60s/IP）下同参数压测 84.8% 返回 **429 而非 500**，证明限流器真实生效、后端零错误。写路径（下单 + 分布式锁）压测还没做，需要认证 token + 库存编排，成本较高，是我列的待办。

**被问"业务复杂度这么低有意义吗？"（防守型话术）**
> 我同意业务本身不是重点——我特意选了 C2C 资产流转做载体，因为它刚好能完整展示 DDD 的 4 个核心聚合根（Product / Order / Payment / User）、跨模块一致性架构决策（拒绝 Saga → 本地单事务 + 分布式锁 + Outbox）、读多写少场景（CQRS）、实时通信（WebSocket）这几个架构模式。**如果业务做复杂了，比如再加议价 / 阶梯降价 / 优惠券，状态机就有几十种转换，面试时间根本讲不完**，反而侵蚀 DDD/AI 工程化的主线叙事。
>
> 真正的复杂度我刻意放在架构与 AI 工程化上：11 模块 + 35 Port 编译期隔离 / 拒绝 Saga 的 ADR 决策（本地单事务 + 分布式锁 + Outbox）/ Outbox + DLQ 三级重试 / traceId 全链路 / LLM 调用 8 件套工程化 + ADR+ArchUnit+PIT 治理三板斧，这些才是 Java 架构师 / AI Agent 岗真正关心的。

## 五、知识盲区标注（面试前必须复习或提前想好「怎么绕」）

> ⚠️ 这是**最重要的一节**。下面这些点是文档叙事里提到但真实项目可能没做到 100% 的，面试官追问时别翻车。

| 追问方向 | 叙事里提到的 | 实际项目需要确认 | 回答不上时的「绕法」 |
|---|---|---|---|
| **LangChain4j / Spring AI 源码细节** | 「拒绝了 LangChain4j」 | 你是不是真的读过这俩框架源码？Tool 反射调用是怎么走的？ | 老实答「我没有深入到 Spring AI 的 Bean 注册源码，但对比评估了它们的 Tool 抽象——LangChain4j 的 @Tool 是编译期生成 GPT JSON Schema，Spring AI 的 FunctionCallback 是运行时反射，都不如我自己写的 CompletableFuture 并行 Tool 灵活，调试也能直接在 AiSearchEnhancerAdapter 打断点。我倾向于在面试展示场景下自己实现，复杂度可控。」 |
| **Seata TC/TM/RM 部署模式** | 「拒绝了 Seata AT/TCC / Saga 编排」 | Seata 三种模式（AT/TCC/Saga）的区别？TC Server 高可用怎么做？ | 「我没有在生产环境跑过 Seata 集群，评估阶段主要看的是官方文档和社区踩坑帖——AT 模式的核心问题是 undo_log + 全局锁的性能开销（每个分支事务写完业务 SQL 还要写 undo_log，TC 协调全局锁），跟我们的本地单事务 + Outbox 事件驱动比，写路径成本和中间件依赖都高一截；而且我们的 @ConditionalOnProperty 降级模式要求 Seata TC 挂了也能起应用，TC 是单点做不到，所以就没深入部署细节。」 |
| **HNSW / IVF 向量索引原理** | 「拒绝了 Milvus/PGVector」 | HNSW 近邻搜索的 M / efConstruction 参数？余弦相似度和点积区别？ | 「我对向量检索原理主要是调研阶段的理解——HNSW 是分层可导航小世界图，M 控制每层邻居数，efConstruction 控制建图探索宽度。我们现在 SKU < 10 万，Top 50 BM25 结果再用 Java 原生 Cosine 做点积 rerank，P95 < 300ms 完全够用。真到了需要 HNSW 的规模，应该上专门的向量团队维护 Milvus，不是业务后端 Java 工程师维护 ANN 参数。」 |
| **PIT 变异测试全量耗时** | 「order 41 秒 / product 41 秒」 | 11 模块全量 PIT 要多久？CI 里跑得起吗？ | 「目前只对 domain 层注入变异，也只在 CI 的 nightly build 里跑，PR 只跑 JaCoCo + ArchUnit。product 模块 253 个变异 41 秒，order 81 个变异 41 秒——差距大是因为 product 有更复杂的状态机枚举转换，变异点位多。全量 domain 层 PIT 预估 3-5 分钟，nightly 时间窗口完全够。」 |
| **traceId 跨服务怎么传** | 「HTTP → MQ → MDC」 | 用户服务和订单服务如果拆成两个独立 JVM，traceId 怎么传？你们现在是单 JVM 模块吧？ | 「对，目前 EasyOrange 是单 JVM 多 Maven 模块部署，模块间事件驱动通过 RabbitMQ 走的是同一 Spring 上下文，所以 Brave TracingFilter 提取的 traceId 能通过 EventMetadataMessagePostProcessor 注入到 message header，消费者端再 decode 回 MDC。如果拆成多 JVM 微服务，就是在服务间的 HTTP 客户端加拦截器，把 traceId 放到 X-B3-TraceId 请求头里，走 Brave / OpenTelemetry 的标准 W3C traceparent，这套机制是通用的。」 |
| **@TokenBudget 超预算后怎么降级** | 「返回缓存最近一次结果 + 告警」 | 降级是全局开关还是按场景开关？告警推到哪里？ | 「目前 TokenBudgetExceededException 被 GlobalExceptionHandler 捕，降级逻辑是——查 Redis 缓存 `eo:ai:lastSuccess:{scope}:{userId}` 最近一次成功结果，没有的话返回 Result.fail(ResultCode.AI_BUDGET_EXCEEDED) + 业务侧提示「当前 AI 服务繁忙请稍后再试」。告警还在业务日志 WARN 级别，下一阶段打算接 Prometheus Alertmanager 推飞书 / 企微——这是故意留的 TODO，因为项目主要是展示 AI 工程化闭环，监控对接每个公司平台不一样，留接口更灵活。」 |
| **MySQL 8.4 到底用了哪些新特性** | 「MySQL 8.4 LTS」 | 8.4 跟 8.0 的区别？InnoDB 变更？ | 「项目里主要用的是 MySQL 8.x 系列的稳定能力——窗口函数在对账统计里用、CTE WITH 递归在商品分类树里用。选 8.4 是因为它是 Oracle 官方标注的 Innovation LTS，生命周期到 2032 年，比 8.0 的 EOL（2026 年 4 月）长。没有用 8.4 特有的新语法，主要是基于生命周期选型，避免刚上线就遇到 EOL 升级压力。」 |
| **RAG 分块与检索指标** | 叙事讲「RAG 完整链路：摄入管线 + hit@5/MRR」 | ✅ **已落地**：分块（500+overlap50、切点优先换行）+ 种子知识库 + 混合召回 + 引用溯源；hit@5/MRR 落 eo_retrieval_metric | 追问细节可展开 chunk 算法（`KnowledgeIngestionService.chunkContent`）与 MRR 计算（`GoldenSetEvaluator.computeReciprocalRank`），无需绕 |
| **重排模型（Reranker）** | 叙事讲「Cosine 重排」 | 用的是 Java 原生 Cosine 排序，没接 Cross-Encoder 模型（仍是演进项） | 「量级不需要模型 rerank；BGE-reranker 这类 Cross-Encoder 与 Bi-Encoder 的区别我清楚（交叉编码精度高、成本高，先粗后精两段式召回），触发条件是检索指标下滑或知识库量级上涨」 |
| **流式输出（SSE）** | 叙事讲「SSE 流式打字机」 | ✅ **已落地**：SseEmitter + ChatModel.stream，事件协议 token/sources/done/error；预算手动检查；流式调用照常落日志 | 追问细节可展开：为什么选 fetch+ReadableStream 而不是 EventSource（POST + Authorization 头）、流式与 TokenBudget AOP 的兼容处理（01 §3.1 完整应答） |
| **Agent 记忆 / 多轮对话** | 叙事讲「多轮 Agent + 记忆」 | ✅ **已落地**：Redis 会话窗口（短期）+ 用户画像表（长期）+ 单步 ReAct 工具决策 | 追问细节可展开：会话裁剪策略（最近 N 轮 + TTL 24h）、偏好提取（工具决策 JSON 的 preference 字段写入 eo_user_preference）、记忆 fail-open 语义；多步 ReAct 循环仍是演进项（01 §3.1） |
| **评测集构建 / Judge 局限** | 叙事讲「评估进 CI」 | ✅ **已落地**：30 条金标准集 + Judge 对照参考打分 + EvalGate 门禁（低于基线-0.3 卡 build）+ 反馈飞轮自动扩充；局限仍在：自评偏差、顺序/长度偏差未根治 | 追问可展开：门禁怎么接 CI（GoldenSetRegressionIT + EASYORANGE_AI_API_KEY 环境变量门控）、基线怎么维护（baselines.yaml 评审更新）、faithfulness 客观指标是演进项（01 §3.1） |

> **通用绕法公式**：「我没有深入到 X 的源码/生产部署，但评估时我关注的关键点是___，最后做出的取舍是___，所以这块我就没深入到那个程度——如果真到了那个场景，我会按___的思路去做。」→ **诚实展示思考过程 > 硬背不知道的细节**。
