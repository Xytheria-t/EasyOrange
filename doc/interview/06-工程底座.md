# DDD 核心思想轻量落地（工程底座，被追问时用）

> **用途**：DDD 是**工程底座**（工程素养证据），不是并列主线：投 AI 岗扫过即可，被追问架构或投通用 Java 后端时按本册深挖。
>
> **数字单一来源**：[doc/工程指标.md](../工程指标.md)；**结构计数**只在[「结构计数」](../工程指标.md#结构计数)区块维护，各册不复制任何结构计数。

---

> 本项目 DDD 是**「展示核心思想、拒绝过度设计」的克制落地**——在简历与口头叙事里它是**工程底座**（支撑 AI 链路的生产级要求），不是并列主线。投 AI 岗扫过即可；被追问架构 / 投通用 Java 后端时按本节深挖。
>
> 一句话定位：**DDD 六边形 + CQRS，domain → application → adapter 单向依赖**。Maven 多模块、核心聚合根 Product / Order / Payment / User、Port 接口编译期隔离、ArchUnit 规则在 CI 守分层（规则清单与条数以 `ArchitectureRulesTest` javadoc 与[结构计数](../工程指标.md#结构计数)为准）。

## 0 为什么上 DDD——驱动、收益、代价（自证不是跟风）

**驱动**（MVC 三层在本项目会怎样）：① 业务有真规则要单点守卫——商品上架的两条路径共用同一组 `validateOnline()` 不变量，「订单状态 × 支付状态」二维状态机由动作表唯一裁决，MVC 里同一不变量各写一份、改一处漏一处；② 模块边界要可执行——包结构拦不住 `import` 对方 Mapper（历史教训：order 曾直接依赖 product 的 mapper 扣库存，后来重构回 Port）；③ 外部依赖多、要可换可降级——LLM 供应商 / ES 可关（走 LIKE 兜底）/ MQ 可关，全靠条件装配；④ 领域逻辑要能纯单测——domain 零框架依赖，变异测试只对 domain 注入。

**收益（都能核验）**：不变量只写一处｜依赖方向 CI 强制（历史债用冻结规则拦住，重构移除后自动解除）｜模块边界 = 接口签名（跨模块依赖全部 `optional`，Port 目录本身就是协作地图）｜换实现 / 降级只动 adapter（ES 关走 LIKE 兜底、AI 供应商切换改 options、自研 AI 抽象换 Spring AI）｜跨模块读自持快照换解耦（订单读商品快照，商品改名删除不影响已下订单）｜演进有量化触发条件（拆独立数据源 → 重新评估 Saga，[ADR-0010](../adr/0010-order-saga-evolution-plan.md)）。

**代价（都实际付了）**：每个跨模块协作多一层 Port + 适配器样板｜模块间结构不统一（CQRS 只有部分模块、领域服务数量差异大——结构差异是领域性质的产物，写进 ADR 作评审判据）｜双层模型转换（DO ↔ 聚合根）｜定位成本（查字段谁写的要跨 Port → Adapter → Repository 三跳）。

**负收益判据（什么情况别用）**：单表 CRUD 无跨聚合不变量 → 直接 AppService + Mapper；读写比均衡 → 不上 CQRS；聚合无生命周期 → 不硬造状态机；字段无规则 → 不包 VO；**框架 / 标准库已有能力不自研抽象**（最贵的一课：AI 侧曾自研 Port / 适配器 / 装饰器，框架成熟后全删换 Spring AI——六边形不等于什么都自己包一层）。

## 1 核心思想清单（讲了能拿分的）

> 面试讲 DDD 别背概念，直接指代码。每条带落点 + 「为什么这是轻量的」——后者才是拉开差距的地方。

### 1.1 聚合根（Aggregate Root）——状态机 + 不变量内聚
- **落点**：`order/domain/aggregate/Order.java`、`payment/.../Payment.java`、`product/.../Product.java`、`user/.../User.java`
- **共性**：聚合都是**不可变对象**（字段 final，`@Builder(toBuilder = true)` 重建新实例替代原地修改），只做状态机 + 不变量，**不碰持久化、不注入外部依赖**（domain 零框架依赖由 ArchUnit 锁死）
- **状态机「只有部分聚合有」，签名还各不相同——别一勺烩**：
  - `Order`——**最完整**：单参入口 `transitionTo(动作, 原因)` 一处守卫 + 一处应用副作用；公开转换全部返回「新聚合 + 领域事件」
  - `Product`——**有状态机但目标状态驱动**（`transitionTo(目标状态)`），两条进入上架状态的路径都必须过同一组完整性校验
  - `Payment`——**没有 `transitionTo` 方法**：守卫收口在状态谓词（`canPay` / `canRefund` / …），终态转换才产事件，中间态转换直接返回裸聚合
  - `User`——**没有状态机**：只有承载不变量的变换方法（改密码 / 改头像 / 记录登录）
- **为什么轻量**：状态机只给**真生命周期**的聚合上，没有就硬造；规则只在动作表 / 状态表 / 谓词一处写；跨聚合一致性交给事件，不搞聚合内嵌反规范化

### 1.2 不变量（Invariant）只写一处
- **落点**：建单链式断言（不能认领自己、至少一件资产、金额 > 0）+ 状态合法性由动作表裁决（每个动作声明前置状态 / 目标状态 / 目标支付状态 / 错误码）
- **为什么轻量**：规则只写一处，测试直接打聚合根；不需要规则引擎 / Guard 框架。**状态裁决按模块各归其位**（订单用动作表、商品用转换表、支付用谓词）——「状态合法性由谁说了算」这一问要答得出

### 1.3 值对象（Value Object）
- **落点**：各模块的 ID 值对象、`Phone` / `Address`、跨模块共享的 ID 值对象与 `Money`（金额不落 `double`）
- **为什么轻量**：**只对有规则的字段做 VO**（ID 语义、金额精度、手机号格式），避免为 VO 而 VO 的 ceremony

### 1.4 领域事件（Domain Event）——状态转换的副产物
- **落点**：各模块 `domain/event/`，转换方法统一返回「新聚合 + 事件」；事务提交后经 **Outbox** 与业务同事务写入
- **为什么轻量**：事件是状态转换自然产生的副产物，不是到处 `new`；跨模块副作用由消费者异步触发，聚合不感知

### 1.5 工厂与重建分离
- **落点**：`createOrder(spec)`（**跑不变量**）vs `from(spec)`（**不跑不变量**，从库重建）
- **为什么轻量**：重建时库里的数据已被校验过，不重复触发不变量；参数用 record 收敛，避免长参数列表

### 1.6 仓储 + 端口（Repository & Port / 六边形）
- **落点**：读写分离的仓储（CQRS）与各类 Port 接口（锁 / 支付网关 / 库存 / 检索 / LLM）
- **为什么轻量**：domain 只依赖接口，实现全在 adapter；换实现只改 adapter，domain / application 一行不动

### 1.7 领域服务 vs 应用服务
- **落点**：领域服务（纯规则、无仓储，如敏感词过滤）vs 应用服务（**编排**：读状态 → 决定是否持久化）
- **为什么轻量**：**只有不天然属于某个聚合的规则才做领域服务**；涉及读状态 + 调仓储的编排一律放 application——分不清这两个是 DDD 面试最常见的扣分点

### 1.8 CQRS（做几个模块、两种深度）
- **落点**：product / order 有独立 ReadModel；payment / message 只做 Handler 级分离 + 独立查询仓储；范围决策见 [ADR-0002](../adr/0002-cqrs-scope-4-modules.md)
- **为什么轻量**：收益是「读多写少 + 跨聚合聚合 + 读写独立优化」；不满足就不做（admin / user）。**别把 message 说成「不做 CQRS」**——它做了 Handler 级分离，只是没有独立 ReadModel

### 1.9 防腐层 / 依赖治理（用测试守边界）
- **落点**：`ArchitectureRulesTest` 的规则在 CI 阻断违规（清单与条数以该类 javadoc 与[结构计数](../工程指标.md#结构计数)为单一来源）
- **为什么轻量**：用 ArchUnit 测试守分层，**不靠空壳架构 / 冗余包**；规则坏了 CI 直接红

## 2 刻意不做 / 轻量化取舍（防「过度设计」扣分话术）

> 面试官想听的不是你会用多少模式，而是**你懂什么时候不该用**。每条都是「我评估过、主动拒绝」。

| 没做的 | 为什么不做的理由 | 做了会怎样被扣分 |
|---|---|---|
| **Saga / 2PC / Seata AT / TCC** | 单库部署，一个本地事务把订单 / 库存 / 支付 / Outbox 全包进同一事务，比 Saga 最终一致更强（[ADR-0007](../adr/0007-order-local-tx-over-saga.md)） | 挂一个失效的状态机，观测价值低于写路径成本，典型「为了架构而架构」 |
| **全模块 CQRS** | 收益 < 维护成本（[ADR-0002](../adr/0002-cqrs-scope-4-modules.md)） | 每模块 Command/Query 双倍代码，纯负担 |
| **Specification 模式** | 支付的状态谓词不是「跨对象规则组合」，是转移谓词 | 假模式名露怯 → 已改名状态守卫 |
| **每个字段都包 VO** | 只对有规则的字段做 | ceremony，代码量膨胀 |
| **Milvus / PGVector** | SKU < 10 万，ES kNN 够用 | 向量索引 + ANN 调参一整套运维负担 |
| **Spring Cloud 微服务拆分 / RPC** | 模块化单体 + ArchUnit + Port 隔离跨模块；拆分触发条件已量化（[ADR-0010](../adr/0010-order-saga-evolution-plan.md)） | 单机演示拆微服务，分布式复杂度零收益，还答不上「为什么拆」 |
| **中间件进 K8s** | K8s 只编排无状态应用层，中间件外部化（生产用托管服务） | 被追问 PVC / 分片再平衡 / 故障恢复就答穿 |
| **托管式 Agent 循环（框架 ToolCallingAdvisor）** | 步数上限 / 循环中途预算检查 / 三口径降级插不进去（AG-4） | 生产级控制点全丢，被追问「步数怎么控制的」答不上 |
| **LLM 摘要压缩 / 多智能体编排（本仓库）** | 摘要：步数与轮数上限下收益小、成本翻倍；多智能体：分工归第二个项目（本仓库命题是「一个 agent 怎么做到生产级」） | 前者凭空翻倍成本，后者与第二项目关键词互抢 |

## 3 面试 60 秒 DDD 概括稿（被追问架构时用）

> 「项目是 DDD 六边形 + CQRS 的克制落地，它是**支撑 AI 主线的工程底座**。核心聚合根都做不可变对象：Order 状态机最完整（单一入口守卫，转换产出领域事件走 Outbox）；Product 是目标状态驱动的状态机，两条上架路径统一过同一组完整性校验；Payment 用状态谓词守卫、终态才产事件；User 没有状态机就不硬造。跨模块副作用由事件异步触发，聚合不碰持久化，领域层只依赖 Port 接口，ArchUnit 规则在 CI 守分层。

我特意做了几个轻量化取舍：**拒绝 Saga**（单库本地事务 + Outbox 比 Saga 更强，挂失效状态机是过度设计）；CQRS 只做部分模块且深度不同；值对象只对有规则的字段做；**框架已有能力不自研抽象**（AI 侧自研抽象在框架成熟后全删）。这些取舍比堆模式更能体现工程判断力。」
