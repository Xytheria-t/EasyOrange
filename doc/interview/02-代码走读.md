### 没写过代码，先读这一段

这本册子**不是教程**，是**答法卡**——它假设你已经读过一遍源码、或者至少知道这个类在解决什么问题，只负责把「面试时该怎么说、为什么这么选」压成能背的形状。所以单看它会觉得每句话都悬着：结论都在，前因都不在。

三个约定，先知道这三条就不会读岔：

1. **代码块是骨架，不是源码。** 里面的方法名（`decide` / `executeTool`）是示意名，变量名大多也是简写。**别去源码里按名字搜，搜不到。** 骨架只保留三样东西：控制流的形状、每一步的判断在哪、以及降级从哪条口子出去。真要看代码，去文件行号那行给的路径，真实方法名以源码为准。
2. **「要点」里每一条都是取舍，不是描述。** 写「锁在事务外获取」只是在描述；写「**为什么**不放在事务内」才是面试被问的。读的时候把每条后面的「因为」补出来——补不出来的，回源码看注释，源码的类注释里通常有同一句理由。
3. **「追问」是真会被问的。** 答不上来的那条就是破防点，记进 [01 §7](01-备战清单.md)。

**读到不认识的词**：整册的术语速查在 [README §五](README.md#五名词速查)。第一次见一个词先翻它，别攒着——本册默认这些词你都认识，所以不会就地解释。

**怎么用一节**：读「一句话」→ 读白话说明 → 看骨架 → 读要点 → 答追问。答完合上文档，用自己的话写 ≤10 行，不许翻。这一步是本册唯一的检验手段；[每章固定循环](README.md#每章固定循环)讲得比这里细。

### 防漂移

本册点名到类，重构会让走读静默失真。两个命令都在仓库根跑：

| 命令 | 干什么 | 红了怎么办 |
|---|---|---|
| `python3 doc/interview/check-drift.py` | **路径巡检**：核本册点名到类的源码路径还在不在 | 按提示同步改本册。改名 / 删类 / 搬包会红。 |

>
> **本册的代码块是简写速写骨架**（`decide` / `executeTool` 是示意名，真实方法名以源码为准），不逐字对齐源码。面试要讲的是控制流、降级口径和职责边界，不是逐行复现。脚本因此不比对代码块文本：重写整类后核「骨架声称的结构还在不在」（如 `ToolCallLoop` 仍是「for 循环 + 循环内预算检查 + decide → finish → execute + 四条出口」），而不是核变量名。脚本没覆盖的实现细节，靠[校准](README.md#每章固定循环)和面试前过本册兜底。

# AI 侧

## 1 多步工具循环 — ToolCallLoop

**一句话**：手写循环持有控制权——决策走原生 tool calling，工具执行、三条降级口径、步级 trace 全在自己的循环里。

**白话**：用户问「预算三千能买什么笔电」。程序不写死「先查预算再查详情」，而是每轮把当前情况发给模型，问它下一步要干什么。模型说「查在售笔电」，程序就去查，把结果拼成一条新消息塞回去；下一轮模型看到结果说「挑两个对比」，程序再执行。一轮一轮，直到模型说「够了」或者步数 / 预算撑不住。**谁决定下一步、什么时候停，是这个类说了算。** 工具只是被它调用的普通方法。

这段「问模型 → 执行 → 回填 → 再问」的循环叫**自治工具循环**，是本项目唯一的编排主线，也是整个项目里最该先读懂的一节。

行业里泛称 **agent loop**。定它是不是 agent 的**不是「用了工具」，是「下一步由谁决定」**——这里每轮问模型，所以是自治循环；这条判据跟 §4 判掉那套 4 路扇出用的是同一条。工具只是它这一版的执行手段，两者不互相定义：Workflow 里也调工具（决策在代码里，一次调用就结束），反过来纯推理的 agent loop 一个工具都不必有。

**ReAct 是它的思路源头，不是别名**——ReAct（Yao et al., ICLR 2023）靠提示词让模型交替吐 Thought / Action / Observation 纯文本、再由框架解析出动作执行，本项目走原生 tool calling，模型直接返回结构化 `tool_calls`，观察按对话协议回填。同源，不同实现。

**文件**：`easyorange-ai/.../application/chat/ToolCallLoop.java`、`.../application/chat/ToolCallLoopMetrics.java`、`.../application/support/ToolCallDecider.java`、`.../application/support/ToolLoopKernel.java`、`.../application/support/DecisionMessages.java`

**编排内核与编排器分两层**（listing 链路复用后加的）：循环机制（for 循环 / 四条出口 / 协议回填 / 步级 trace）沉在 `ToolLoopKernel`，链路差异（首轮上下文怎么拼、决策绑哪个模型与预算场景、决策失败降级动作）由 `ToolCallLoop` 注入。读本节时把两者当一个东西看——控制流一点没变，只是「买家侧口径」从循环里挪到了循环的调用方。

**骨架**（速写，方法名以源码为准）：

```java
var dispatcher = ToolDispatcher.of(toolsFactory.create(attributedUserId(input)), input.toolAllowList()); // 工具面：schema 回调 + 按名执行，累加器随实例隔离
var messages = new DecisionMessages(systemPrompt, firstUserMessage); // 首两条固定，逐轮累积
for (int round = 1; round <= maxSteps; round++) {
    if (round > 1 && budgetExhausted()) { return degraded(ToolCallLoopOutcome.BUDGET); }  // 循环中途预算检查
    var decisions = decider.decide(sessionId, messages.snapshot(), callbacks); // 原生 tool calling：发 schema、收回本轮全部 tool call
    if (decisions.isEmpty()) { return degraded(ToolCallLoopOutcome.DECISION_FAILED); } // 降级：按原始问题补检索一次
    for (var decision : decisions) {                            // 一轮内模型可并行发起多个工具
        var result = dispatcher.dispatch(decision);            // 执行在编排器，不在框架
        recordToolStep(decision, result);                       // trace 落库 + SSE step 事件
    }
    if (decisions.anyMatch(ToolCallDecision::isFinish)) { return finished(); } // finish 收敛轮无执行体，单独记一步
    messages.appendRound(decisions, observations); // 按协议回填：一条 assistant tool_calls + 一条 role=tool 观察
}
```

**读这段骨架只看三件事：**

- **循环头**：三个变量各是啥。`dispatcher` 是这次请求的工具箱，`messages` 是攒着的对话记录，`round` 是第几轮。
- **循环体四步**：问模型（`decide`）→ 执行工具（`dispatch`）→ 记一笔（`recordToolStep`）→ 回填（`appendRound`）。这个顺序别调，是模型的协议要求。
- **出口有四条**：预算耗尽、模型没给出任何决策、`finish` 收敛、步数跑满。**四条出口是本节的全部重点**——面试问「超时/失败怎么处理」，答的就是这四条分别落到什么动作。

### 要点

**1. 决策走原生 tool calling。**
工具 schema 由 `ChatTools` 的 `@Tool` 注解生成、随请求下发。`ChatModel.call` **不**自动执行工具（自动执行在 `ChatClient` 层），所以执行权和循环控制权都在编排器手里。
观察按对话协议回填——`assistant tool_calls` + `role=tool` 消息，**不是**手工拼进 user 消息。首两条消息固定不变，轮间前缀逐字稳定，才能吃到供应商的 KV cache 折扣。

**2. 一轮可以带多个工具调用。**
供应商侧并行发起时（典型是「规则 + 找货」同问），同轮全部执行。省的是**一整轮决策往返**——决策调用比工具调用贵一个量级，砍往返比并发执行工具划算。
同轮按模型给出的顺序逐个执行，因为召回累加器是实例独占的可变状态。
`finish` 与其它调用同现时以 `finish` 收敛：同轮非 finish 调用照常执行，`finish` 记在最后一个。
同轮有一个调用参数解析不了，就**整轮判决策失败**。半执行一轮会让回填的 `tool_calls` 与观察对不上，协议不合法。

**3. 三条降级口径。**

| 终止原因 | 降级动作 |
|---|---|
| 步数超限 | 用已积累的观察单次生成 |
| 循环中途预算耗尽 | 用已积累的观察单次生成 |
| 决策失败 | **按原始问题补检索一次**（不是不检索） |

补检索与工具步同口径判重，自身故障不外抛。

补检索本身也受工具白名单约束：白名单未含 `knowledge_search` 时跳过（评估的「无检索来源」臂要是照补，等于把这臂的检索来源偷偷加回来，对照立即失效）。

**4. 每步都落 trace。**
一次请求一个 `trace_id`，同时推 SSE step 事件。
**步序跨轮连续**，一轮内的并行调用各占一步——挤进同一个 `stepIndex` 会让两个动作在 trace 里看起来是同一步。

**5. 指标按 outcome 计数归因。**
结局是封闭枚举 `ToolCallLoopOutcome`：finished / step_limit / budget / decision_failed + error 哨兵。这是纯观测口径，**生成链路不按它分支**。
`error` 哨兵只进结局计数器，**不进轮数分布**：它没有循环出口、轮数不可知，记 0 会把「平均步数」的均值往 0 拽——而故障爆发恰恰是最需要读这条曲线的时候。
指标实现在 `ToolCallLoopMetrics`：构造期按枚举全集预注册（tag 是时序契约，`rate(...)` 告警从 t=0 就有效），热路径只做 `EnumMap` 查找。
工具 tag 集只收 6 个可执行工具 + `unknown` 兜底（`finish` 无执行体，它的分布由 `loop{outcome=finished}` 计）。
分位数走直方图分桶而非客户端 quantile，因为多副本下要由 PromQL 聚合。

**6. 失败的工具结果也进观察**，模型可以据此换参数重试。**不吞异常。**

**7. 编排器依赖收敛 13 → 8。**
判据不是数字变小，是**每个构造器参数都能说清它服务哪件事**。

两次抽取各解决一个具体问题：

- **工具面装配**（规则检索 / 在售资产检索 / 资产详情 / 偏好写入，4 → 1，收进 `ChatToolsFactory`）。这四个在编排器里各自只被消费一次，唯一去处是 `new ChatTools(...)`。让编排器为一次 `new` 承担四个依赖，等于把「工具面由谁组装」焊死在循环控制里——加一个工具的协作方就要改循环的构造器。
- **决策动作**（模型调用 / 路由选型 / 参数反序列化，3 → 1，收进 `ToolCallDecider`）。它们只服务于「决定调哪个工具」这一个动作。摊在编排器构造器上，会让「循环控制」和「一次模型调用的技术细节」共用一张依赖清单。

剩下 8 个各自只服务一件事：首轮 system prompt、工具面、决策、步级 trace、预算切断、步数上限、`trace_id` 来源、循环与工具指标。
`IdGenerator` 虽只被调一次，但它就是 `trace_id` 的来源。跟 tracePort 拆开会得到「谁生成 id」这种无处安放的问题。

**再往下拆就只剩把参数打包成 record。** 13 变 8 而味道没消，那种改法不做。

### 追问

**「步数上限怎么定？」**
可配。取值兼顾「多文档对比够用」和「成本 / 延迟可控」。到上限不是报错，是降级生成。

**「为什么不用递归？」**
显式 for 循环 + 显式状态更好加预算检查和终止原因分类。

**「并行调用为什么不真并发执行？」**
省的是决策往返（同轮少一次模型调用）。工具执行本身是毫秒级检索。而并发写召回累加器要额外加锁，收益不抵复杂度。

**「观察太长怎么办？」**
工具结果有文本转换器压成紧凑观察——列表类工具截断到前 3 条，并回总命中数，模型据此判断信息够不够。

**「这就是 ReAct 吧？」**
是同源思路，不同实现载体。ReAct 用提示词拼文本，本节用原生 tool calling——模型返回结构化 `tool_calls`，不需要正则去抠动作，也就不会出现「文本没解析出来」这种失败态（决策失败在本项目是独立 outcome，可分类归因）。反过来，ReAct 那套让模型先写一段 Thought 再动手的形态，在原生 tool calling 下已经被 provider 内置了，没必要自己拼。

**「决策调用每轮重发全部上下文不亏吗？」**
亏的部分只有新增的观察。消息序列跨轮累积、前缀逐字不变，供应商 KV cache 折扣吃得到。而且观察是工具压缩后的摘要，不会随轮数线性膨胀。

**「依赖抽出去会不会变成隐式全局状态？」**
不会。`ChatToolsFactory` 和 `ToolCallDecider` 都是无状态单例，每次循环拿到的仍是独立实例。
`ChatTools` 的召回累加器仍是实例独占的可变状态。机器主体返回 null 的画像归属判定仍留在编排器——同一口径还管 trace 的 `user_id`，拆开会出现两处各判一次的漂移面。

**延伸**：[04 AG-2 / AG-4](04-速答.md) · [07 §4.1](07-怎么说.md) · [05 题 2](05-设计题与手撕.md) 手撕工具循环骨架

> **读完上面再来：为什么只有这一种编排。** 常见做法是同时做「固定流程」和「让模型自己决定」两套。判据只有一条——**这件事的流程能不能提前写死**。本项目的活儿正好分两半：搜索页的筛选排序能写死，用普通代码就拿到了确定性和超时控制；Agent 页的多轮找货取决于用户问什么，写不死。**能写死的那半用不着编排范式，写不死的那半固定流程表达不了**，所以只留循环这一条。细节见 [§4](#4-编排范式取舍--为什么不做-workflow)。被问「两种为什么都要」时的答法见 [Q3](03-模拟题库.md)。
>
> 上面骨架里三个看着任性的选择（用显式 `for` 不递归、预算检查塞在循环中途、`finish` 做成一个真工具而不是返回值），都是为「控制权自持」付的代价——框架托管的循环里插不进这三条。读完 §4 再回来看这三处就通了。

## 2 工具面 — ChatTools

**一句话**：工具面按性质分层，计算类工具是让循环「真的多步」的关键，写入与收敛独立成工具，装配与工具定义分开。

**白话**：§1 的循环每轮把工具清单发给模型，模型从清单里挑。这份清单就是这个类——7 个方法，每个方法就是一个工具，模型看到的是它们的 JSON Schema（名字 + 参数说明 + 返回什么），看不到方法体。所以**设计工具面就是在设计「模型能想到什么」**：清单越杂，模型越容易挑错。

**文件**：`easyorange-ai/.../application/chat/ChatTools.java`（工具名与编排器共用常量）、`.../application/chat/ChatToolsFactory.java`（装配）

### 要点

**1. 按性质分四层。**

| 层 | 数量 | 内容 |
|---|---|---|
| 检索 | 3 | 规则知识 / 在售资产 / 资产详情 |
| 计算 | 2 | 行情统计 / 多件逐维比对。**纯 JDK，零模型调用** |
| 写入 | 1 | 长期偏好 |
| 收敛 | 1 | finish |

**2. 计算类让步骤产生依赖。**
没有计算工具，循环只是换关键词重试。有了它，第 N 步真的消费第 N-1 步的输出。

**3. 写入工具独立成工具。**
偏好写入从「收敛轮参数」拆出来。挂在收敛轮上时，三条降级路径下偏好会静默丢失。

**4. 每个工具首参是 `thought`**（本步理由）。落 trace、供前端展示与排障。详情 / 比对类工具的 ID 参数要求取自前一步观察。

**5. 装配在 `ChatToolsFactory`。**
它只做「四个协作方 → 一份 `ChatTools` 实例」，**不加工**。
归属用户由编排器判定后传入——机器主体返回 null 的口径留在编排器，因为同一口径还管 trace 的 `user_id`，拆开会出现两处各判一次的漂移面。
每次循环一份新实例，是 `ChatTools` 自己的并发要求（召回累加器是实例独占的可变状态），**不是工厂的策略**。

**6. 卖家侧发布链路同构复用本节。**
`ListingTools`（[§5](#5-发布助手--autolistingappservice)）不另起一套：循环走 §1 的 `ToolLoopKernel`，工具名与本节的四个**字面同名**，观察文案与 60% 冗余判据共用 `RetrievalObservations`；多出的 `list_categories` 锚分类约束。

### 追问

**「工具太多会怎样？」**
决策空间和误选率上升，schema 也占 token。所以工具要正交——检索 / 计算 / 写入 / 收敛各司其职。

**「工具失败怎么处理？」**
失败收敛成「失败观察 → 模型换参数重试」。**「工具执行失败就整体报错」是错的。**

## 3 会话与上下文 — AiChatAppService / ChatContextTrimmer / ChatSessionStore

**一句话**：轮数窗口 + token 裁剪两道治理，裁剪保最新一条，历史按原始角色传，记忆读写 fail-open，身份显式传参，缓存按用户分桶。

**白话**：§1 讲的是「一次请求内怎么转」。这一节讲「请求之间怎么接上」——用户上一轮说了什么、他偏好什么，全都要拼进这一轮的 prompt 里。麻烦在于模型有**上下文长度上限**（超了直接报错），塞多了又烧钱，所以要在发出去之前先裁。这个类就是管「读记忆 → 裁 → 调 §1 的循环 → 生成回答 → 存回去」这一整条链路的。

`fail-open` 是本册的高频词：**依赖挂了的时候选择放行**（照常跑，降级），而不是拒绝（直接报错）。`stale` 指「上次的结果」，供应商挂了就返回它。

**文件**：`easyorange-ai/.../application/chat/AiChatAppService.java`（缓存 / 记忆 / 降级 / 生成的编排）、`ChatPromptAssembler.java`（生成 prompt 装配）、`ChatContextTrimmer.java`、`.../adapter/outbound/cache/ChatSessionStore.java`

### 要点

**1. 短期与长期记忆。**

- **短期**：Redis List 会话窗口，TTL 24h，裁剪到最近 N 轮。一轮对话一次写入，不会留下「只有提问没有回答」的半轮记忆。
  键绑定 `userId`——`sessionId` 由前端生成、可伪造，绑定后他人的 sessionId 在请求方名下查无记忆，**防水平越权**。
- **长期**：用户画像表，跨会话，由独立工具写入。

**2. 上下文两道治理。**

- 轮数窗口（存储侧）
- 估算 token 裁剪（注入侧）。`TokenEstimator` 的口径是 CJK 0.7 / 其余 0.3，预算可配。

裁剪点**唯一**，决策与生成两条装配路径共用。**从最新向前保留连续窗口**，单条超预算仍保最新一条。

**3. 生成时历史按原始角色传多消息。**
由 `ChatPromptAssembler` 装配，**不压进当前 user 消息**。跨轮前缀稳定才能命中供应商上下文缓存折扣。

**4. 降级与串行化。**

- 供应商故障 → 返回 stale 旧回答。
- 记忆读写 → fail-open。
- 空回答 → 显式抛 B8002（AI_UNAVAILABLE），**不再落 500**。
- 客户端中途离开 → 中断轮的半截回答**照落会话历史**（刷新后追问不丢上下文），按中断静默收尾，**不进降级率**。
- **同会话并发串行化**：per-session 分布式锁（Redisson）覆盖 load → loop → save 全程。后到请求排队到前一轮落盘之后。等待超时按「会话处理中」业务提示返回，**不伪装成降级**。

**5. 身份显式传参 + 缓存按用户分桶。**

流式回答跑在另一个线程上，`SecurityContextHolder` 的 ThreadLocal 不会跟过去。所以身份由 Controller 在 servlet 线程解析后，**显式传进服务层**（不让流式线程去读安全上下文）。缺失即 401。

> 身份是硬前置。静默退化会让画像、偏好、trace 归因悄悄失效。

语义缓存与 stale 兜底的 key 都带用户维度。回答里注入了该用户的画像和历史，共享桶会把一个人的答案返给另一个人。

无登录态的机器调用方（评估跑批）走显式机器主体 `machine`：会话与缓存照常按主体隔离，画像在写侧拒收——**评估不被历史偏好污染**。

**6. 语义缓存两条路径同源。**
embed 一次、命中回放、未命中写回。

- 非流式：查缓存 → 生成 → 写缓存。
- 流式：同样先查。命中就把缓存回答按固定块回放成 token 事件并重放 sources（前端协议不变、无 step 事件）。未命中则生成成功后把完整回答（含 sources）写回。

此前流式完全绕过缓存，而流式是前端唯一路径——缓存在真实主路径上零流量，命中率口径失真。

预算闸门仍在缓存查找**之前**（与非流式切面位置同位），超限用户收到预算提示而非缓存回答。

### 追问

**「为什么不用向量召回历史？」**
会话窗口小、轮数受限，召回收益低于复杂度。

**「摘要压缩呢？」**
**有意不做。** 步数与轮数上限下收益小，每轮多一次模型调用直接翻倍成本。

**「按用户分桶不是降低命中率吗？」**
是，但这是**修正确性不是调优**。共享桶串的是个性化内容，属于信息泄露，不该拿命中率换。

**「缓存命中为什么不补打字机延迟？」**
缓存命中的价值就是快。人为加延迟是造出来的不诚实。

## 4 编排范式取舍 — 为什么不做 Workflow

**一句话**：Workflow 的收益区（流程能预写死）和本项目需要模型决策的活儿不重叠——能预写死的那半用普通代码就拿到了确定性，写不死的那半 Workflow 表达不了，所以不做。

**两个词先说清**：

- **编排范式** = 「多步任务按什么顺序走」的选择。两种极端：**Workflow**（流程写死在代码里，A 走完走 B）和**自治循环**（每一步问模型，顺序由模型定）。中间还有一堆变体。
- **收益区** = 一个方案「在什么情况下才划算」。Workflow 的收益是确定性、超时可整体设、成本可预测——**前提是流程固定**。流程一变，它不只没好处，还多一层僵硬的成本。

这一节没有类可读，它是一道**判断题**：面试官问「为什么不做另一种」，答的就是这里。§1 结尾那段是它的浓缩版，展开就是下面这两小节。

### 为什么不做

Workflow 式（路径写死）换来三样东西：确定性强、可整体设超时、成本可预测。代价是流程外的分支直接僵住。

**判据是流程能不能预写死。** 本项目的活正好分两半：

| 活儿 | 流程能写死吗 | 用什么实现 |
|---|---|---|
| 搜索页：facets / 筛选 / 排序 / 分页 | 能，本来就不需要模型决策 | 普通代码，确定性和超时白拿 |
| Agent 页：多轮找货、要不要再检索、要不要比较 | 不能，取决于用户意图 | 自治循环（§1） |

两头都不占 Workflow 的位置：**它的收益区已经被普通代码覆盖，它的代价区正好落在唯一需要模型决策的地方。**

「成本可预测」也不是 Workflow 独有。步数上限 + 循环中途预算检查 + 按场景限流（§7）把这三件事都做了，不必靠选范式来买。

### 那为什么曾经做过又删了

搜索页曾有一套 4 路并行扇出，核查后判定不是 Agentic——四路里三路是本地规则，唯一那路 LLM 生成的 30 字摘要既不回流检索也不改排序，整节删除。

**判「不是 Agentic」的三条硬指标**

1. 输出是否**回流检索链路**？
2. 是否**改变排序 / 结果**？
3. **下一步由谁决定**？

三条全否就是包装。**四路逐条对上去，三路是硬编码**：标签（折扣 > 10%、图片 ≥ 3 张）、市场分析（当前页前 5 条的 min / max / avg）、猜你想问（模板拼 3 个问题，点击只是重跑搜索）。剩下那路意图识别才是 LLM，产出一句摘要就结束，检索与排序都没碰。拿模型当格式化器不叫编排。

> **原实现**：`AiSearchEnhancerAdapter` + `adapter/outbound/tool/` 下 6 个工具类，工具注册表 + `CompletableFuture` 并行 + 整体超时保留部分结果。已随搜索页「AI 智能搜索」整体删除，**源码中不再存在**——面试只讲删除理由，不背实现。

### 删掉之后留下的

真正有价值的 kNN + BM25 + RRF 混合召回（§8）此前被藏在这个壳里，删除后独立成链路——搜索页的结构化检索和 Agent 页的对话式找货从此不再互相拖累。

**延伸**：[04 AG-1](04-速答.md) · [05 §3](05-设计题与手撕.md) 设计题对照 · [07 §4.1 Q1](07-怎么说.md) 现场口径

## 5 发布助手 — AutoListingAppService

**一句话**：卖家侧的自治链路——视觉预识别 → 多步工具循环（查禁售 / 召回同类 / 行情定价）→ 生成上架表单；编排内核与 §1 共用，注入的只是首轮上下文与降级口径。

**白话**：这是**第二条 AI 主线**（第一条是 §1 的对话式找货）。§1 那节的判据在这里同样成立——**这件事的流程能不能提前写死**：一个卖家拍 9 张二手相机照片说「挂上去卖」，真正该做的序列是「识别品名成色 → 查该品类是否禁售 → 取同类在售行情定价格带 → 起草 → 自检」，每一步的输入都依赖上一步的输出，「价格填错了」只有查完行情才能发现。**买家侧可以「一次检索定结果」，发布侧不行**——这就是两条主线一软一硬的分界。

`多模态` = 一个模型同时处理文字和图片。图片进轮的方式是个设计判断：**决策轮是纯文本快模型，吃不到图片**，所以先做一次视觉预识别，把画面转成结构化线索（品名 / 品类 / 成色 / 可见细节）进循环首轮；最终生成再带**原图**调视觉模型——「只写图片中可见的内容」这条硬约束靠看真图，不吃二手转述。把图片直接塞进决策消息等于强迫决策模型换成视觉模型，9 张图 × 最多 6 轮全量重发，成本治理直接作废。

**文件**：`easyorange-ai/.../application/listing/AutoListingAppService.java`、`.../application/listing/ListingTools.java`（工具面，5 个 `@Tool`）、`.../application/listing/ListingPromptAssembler.java`

**关键代码**：

```java
var clues = recognizeClues(dataUrls);              // 视觉预识别：画面 → 结构化线索（识别不出显式失败）
var loop = runToolLoop(clues, ...);                // 编排内核：knowledge_search → product_search → market_price_stats → finish
return generateListing(loop, dataUrls);            // 带原图 + 观察块生成表单；行情缺失 price 置 null 留给卖家
```

### 要点

**1. 工具面与买家侧同名同义，机制单一来源。**
`knowledge_search` / `product_search` / `market_price_stats` / `finish` 与 ChatTools 的四个工具**同名**（golden-set 的 expected_tools、前端 STEP_LABELS、trace 的工具列只认一份词汇，字面一致性有测试钉住）；判重与 60% 冗余收敛收在 `RetrievalObservations`，两条链路同一份判据。`list_categories` 是发布链路独有的第 5 个工具——分类约束锚在它身上。

**2. 决策失败的降级动作是 no-op，和 chat 不同型。**
chat 决策失败要补检索一次（怕「检索链路失效被伪装成无需检索」）；发布链路的失败态就是「行情缺失 → price 置 null 留给卖家」，这是**设计内的降级**，强塞一次猜测关键词的检索只会给生成喂噪声。

**3. 识别与生成失败一律显式报错，循环内的降级不报错。**
线索识别 / 取图 / 生成失败 → B8002，没有「部分可用」的表单；步数 / 预算超限、决策失败 → 已积累观察照常进生成。**模板缺失不进降级**（`require` 在方法最前，抛 IllegalStateException）——那是部署期配置错误，报「AI 暂时不可用」会把它藏起来。

**4. 预算与记账：成本归业务链路，模型归职责。**
决策调用走 `chat_tool` 场景的快模型（决策是纯路由任务），但记账进 `auto_listing` 场景预算——供应商账单按业务线归因，模型选型按任务性质归因，两者解耦。循环中途的日预算判定式仍单点在 `TokenBudgetPolicy`，配置优先、注解兜底。

**5. SSE 流式入口**：`/api/ai/auto-listing/stream` 逐步推 step 事件（工具步可视化），done 带表单 JSON；无 token / sources 事件——发布产出是结构化表单不是散文。

### 追问

**「原来不是砍成一次调用了吗，怎么又改回多步？」**
一次调用是「图片 → 表单」的直通翻译，它**答不了**「这个价格行不行」「这个品类能不能挂」——答案在平台数据里，不在图片里。原来砍掉多步砍的是「同一批产出的重复调用」（估值 / 文案各调一次），现在加回来的是「每步输入依赖上一步输出」的查证链，两回事。

**「用户拍糊了 / 模型认错品名怎么办？」**
这是**辅助生成不是自动提交**：识别错了用户改表单；价格不可信的兜底是「无行情 → price 为 null」，错误能在提交前被用户纠正。

**「预识别认错品类，后面检索全歪，怎么不纠偏？」**
决策器 prompt 允许按线索跳步，且冗余收敛会阻止它在同一批噪声上打转；终局由卖家确认。为这种低频场景加「识别置信度分流」是旁挂增强，删掉循环照跑的才是主链路。

## 6 MCP 对外工具面 — PlatformMcpTools

**一句话**：把公开只读检索能力按 MCP 协议暴露给外部 client，信任边界靠两级暴露划分。

**白话**：§1 的工具面是**自己**的模型用。能不能让别的程序（比如 Cursor）也调上这套检索能力——这就是 MCP 干的事：把工具按一套标准协议暴露出去，对方 client 直接连上 `/mcp` 就能调。

这一节的全部重点是**信任边界**：外部程序没有「当前用户是谁」这个概念，所以凡是跟具体用户相关的（订单、偏好、写操作）一律不暴露，只给公开的只读检索。

**文件**：`easyorange-ai/.../adapter/inbound/mcp/PlatformMcpTools.java`

### 要点

**1. `@McpTool` + streamable HTTP**，端点 `/mcp`。4 个**公开只读**工具：资产检索 / 资产详情 / 类目浏览 / 平台规则知识。复用既有的检索与详情服务，**不重写查询**。

**2. 两级暴露的信任边界。**
外部 client **无用户上下文**，所以不暴露订单 / 个人信息 / 写路径。与 Agent 内部工具面各自独立，**鉴权假设不共用**。

**3. 匿名可达但纳入统一限流 + 防重豁免。**
JSON-RPC 重试复用请求体属协议内合法行为，所以要豁免。工具调用计数进指标。

**4. 踩坑**：`protocol` 属性**必须显式配置**。条件装配读 Environment，属性默认值不生效，缺省时端点整个不装配。

### 追问

**「为什么是只读？」**
外部 client 没有用户身份，任何写路径都缺鉴权上下文。

**「和内部工具什么关系？」**
两级暴露。内部工具面按循环需要设计，对外面按「公开数据 + 最小能力」设计。

## 7 AI 治理切面 — TokenBudgetAspect + AiRateLimitInterceptor + AiCallRecorder

**一句话**：注解声明契约、配置覆盖运行期、切面只检查、记账按真实用量；限流按场景令牌桶 + fail-open。

**白话**：模型调用要花钱、要花算力，所以每个场景（找货 / 发布 / 评估）都得有**日预算**和**每分钟次数上限**。这一节是横切面（AOP）——它不改业务代码，在每个被标注的方法前后自动插检查和记账。

`切面 / AOP` = 在方法调用前后自动织入的横切逻辑，本项目用它做三件事：预算前置检查、按场景限流、调用记账。**它只做前置检查，记账另有一个类**——这个分法是本节第一要点。

**文件**：`easyorange-ai/.../adapter/outbound/budget/TokenBudgetAspect.java`、`.../adapter/inbound/web/AiRateLimitInterceptor.java`、`.../application/support/AiCallRecorder.java`、`.../application/support/AiModelSupport.java`、`.../application/support/ChatBudgetGuard.java`

**关键代码**：

```java
// 预算：切面只做前置检查，记账在 AiCallRecorder（全工程唯一写 TokenBudgetStorePort 的地方）
@Around("@annotation(tokenBudget)")
// 累计已用 + maxTokensPerCall > dailyTokenLimit → 抛异常走统一降级
// 调用后：取 ChatResponse 的 usage metadata，有真实 input/output 按真实值累加

// 限流：令牌桶按场景
boolean allowed = distributedRateLimiter.tryAcquire(bucketKey, scope.getRatePerMinute(), 60);
// 超限 → 429；Redis 异常 → fail-open 放行
```

### 要点

**1. 职责二分。**

| 角色 | 职责 |
|---|---|
| 注解 | 声明场景与日预算（**编译期契约**） |
| yaml | 覆盖注解默认值（**运行期旋钮**） |
| 切面 | **只做前置检查** |
| `AiCallRecorder` | **按真实用量记账** |

记账口径：有真实 input / output 就按真实值累加；不回报（embedding / 流式未带 usage）才退化为估算。
**失败不记账**——估算会在故障期虚烧日预算，恢复后把场景锁死。
scoped 调用把场景 `maxTokensPerCall` 真下发为 per-request `max_tokens`，生成长度在供应商侧封顶。

**2. 流式的特殊性。**
流式在结束前就返回，AOP 拦不住。所以服务层要手动执行同一套前置检查。

**3. 限流。**
按 `AiCallScope` 场景配速率，key 按用户（未登录按 IP），超限 429。stale 兜底**不在这里**，在服务层。

### 追问

**「超预算的用户看到什么？」**
业务提示「今日 AI 调用预算已用尽」/ 流式转 SSE error。

**「多实例预算怎么办？」**
存储两版按配置切换：内存 / Redis 原子累加。

## 8 检索链路 — RrfFusion + QueryEmbeddingAdapter + ES 适配器

**一句话**：一次查询、两路独立召回、按排名融合。开关是 `aiEnhanced`（GET 参数），后端默认关；真实流量上前端搜索页默认打开。

**白话**：用户搜「便宜笔电」。**一路按意思找**（语义路，把文字转成向量，找意思相近的，不管字面一不一样），**一路按字面找**（BM25，「便宜笔电」四个字挨个匹配）。两路各出一份排序，然后合并。

合并不能直接加分数——一路的分数是 0~1 的相似度，一路是 BM25 的几十上百，量纲不一样，加起来就是垃圾。所以只合并**名次**：A 排第 1 就记 1 分，第 2 记 2 分，两路的分加起来重排。这就是 RRF。`kNN` = 按向量距离找最近的 N 条，`BM25` = 按词面匹配打分。

**文件**：`easyorange-ai/.../domain/model/RrfFusion.java`、`.../adapter/outbound/QueryEmbeddingAdapter.java`、`easyorange-application/.../elasticsearch/ElasticsearchProductSearchQueryAdapter.java`

**关键代码**：

```java
// 端口在 product、实现在 ai（方向不反转）
List<Float> embedding = aiModelSupport.embed(embeddingModel, AiCallScope.SEMANTIC, keyword);
// ES：kNN(nameEmbedding) 与 BM25(multi_match) 各查一次 → RrfFusion.fuse(k=60) → 按页切片
// 索引侧：best-effort 写 nameEmbedding（失败降级 null 不阻塞索引）
```

### 要点

**1. 两路独立召回 + 排名融合。**
同请求里写「knn + query」拿不到各自排名——ES 会内部合成分数。
而余弦和 BM25 **量纲不可比**。所以只有排名能融。

**2. 降级链。**
单路失败 → 退化为另一路。两路都空 → 才回落单路查询。**供应商抖动不该把检索打成 500。**

**3. `num_candidates` 必须 ≥ k**，否则 ES 拒收整个请求。候选池下限保前几页稳定，随页码增长保深翻页不空。

**4. 两个口径要答准。**
显式排序 → 退化为单路。`total` → `max(BM25 总命中, 融合后条数)`：BM25 路是唯一有全量语义的口径，但它不含语义路补进的召回，只报它会出现「共 0 件却列着 N 张卡、翻页控件消失」的口径裂缝。

**5. ES 装配由条件开关控制。**
关闭时走 LIKE 兜底，健康检查**显式标注**（不静默降级）。

### 追问

**「为什么不用 Milvus？」**（本节是这个判断的唯一出处，别处只引不抄）
量不够。SKU < 10 万，ES 自带 kNN（底层 HNSW）够用，ANN 运维 ROI 为负。

**「10 万这个数哪来的？」**
按目标量级**估算**，不是实测——项目不对外运营，没有真实 SKU 统计。所以不写「我们有 8 万 SKU」，只说「这个量级 ES 够用，再高一个数量级才值得上独立向量库」。**分界线本身比具体数字重要**：过线的判据是「索引构建 + ANN 调参 + 监控这套运维值不值」，不是那个整数。

**「融合的 k 取值有影响吗？」**
平滑常数。k 越小，头部越强势。

**「为什么不给用户一个『纯语义』模式？」**
kNN 缺相似度下限时，在小语料上会召回全库——纯 kNN 反而更差。给的是「语义 / 字面」开关（关掉即纯 BM25），不是让用户在两路召回算法里二选一。

**「调完 topK / RRF 的 k，怎么知道调好了？」**
靠管理端「检索质量回看」读 `eo_retrieval_metric` 的历史批次（兑现 ADR-0012）：批次级 hit@5 / MRR 趋势 + 点批次下钻到用例级明细（哪几条没中、查询长什么样、gold 是谁）。缺了明细只剩一条数字，参数调整就是盲调。

三条口径：hit@5 与 MRR 的**分母都是该批次全部用例数**（未命中用例 `rr=0` 也进分母，剔掉它们等于把指标算成「命中的那些的平均」）；两条评测线按 `case_id` 前缀分列（`retr-` 真实 embedding / `asset-` 合成向量，语料空间不同、混算均值不可解释）；落表**只记融合腿**，单腿属消融日志不入库。空表返回空列表而非造一条 0% 批次——「还没跑过评测」与「跑了全没命中」在看板上必须分得开。

**延伸**：[04 RAG-1 / RAG-4 / RAG-5](04-速答.md) · [05 题 1](05-设计题与手撕.md) 手撕 RRF

## 9 评估闭环 — GoldenSetEvaluator + AiJudge + EvalGate

**一句话**：金标准集 + Judge 对照 + 检索指标 + 路由准确率，四道门禁。阈值全在 yaml、缺键报错。

**白话**：改了 prompt 之后，回答是变好了还是变差了？没有标准答案——好答案不止一个。本节的做法是：**人工标一批标准答案**（金标准集），改完 prompt 跑一遍，**用另一个模型当打分员**（`LLM-as-Judge`）对比参考打分。分数跌破阈值，CI 直接让构建失败。

这就是「**评估闭环进 CI**」——不是跑一次给人看，是**卡在流水线里，改坏了提交不上去**。

四条门禁里第三条（路由准确率）最容易被问：它不看答案对不对，**只看模型有没有挑对工具**。因为答案能靠知识库蒙对，选错工具只有单看路径才量得到。

**文件**：`easyorange-ai/.../application/eval/GoldenSetEvaluator.java`、`AiJudge`、`eval/baselines.yaml`、`.github/workflows/ai-eval.yml`

### 要点

**1. 金标准集分两类用例。**
生成类走 Judge 对照参考打分。检索类跑 hit@5 / MRR 落表。

**2. 第三类：路由质量。**
chat 用例可标 `expected_tools`（期望模型走过的工具）。评估时**只跑工具循环、不看生成**，比对实际 `toolPath` 算准确率。

> 为什么单独量：答案能靠知识库兜底答对，**选错工具只有独立看路径才量得到**。与生成分门禁互补，不是重复。

判据是「期望工具都在路径里」，**不比顺序与次数**——多查一步不算走错。
标注只给「正确路径唯一」的用例。「该不该检索」本身有多种合理走法的（比如「能推荐买什么数码吗」可以先反问预算，也可以直接检索）就不标。

**3. 四道门禁。**
`GoldenSetRegressionIT` 三个 `@Test` 承载四道门禁，低于阈值即卡 build。覆盖率先行（与分数门禁同方法内），另两个各一道。

| # | 门禁 | 判据 |
|---|---|---|
| ① | 均分 | 低于「基线 − 容忍度」失败 |
| ② | **评审覆盖率** | 低于下限失败 |
| ③ | 检索 hit@5 | 低于下限失败 |
| ④ | 路由准确率 | 低于下限失败。**容差取 0** |

- ② 为什么必要：防「幸存者平均」——大面积评审失败时均分已失真，**排在分数门禁之前判**。
- ③ 为什么必要：语料含同域干扰文档，命中不再是必然，hit@5 掉档即召回退化。
- ④ 为什么容差取 0：这是**下限不是基线**。路由错一步就直接答错，给容忍带等于把回归藏起来。

**4. 阈值全在 yaml，键缺失加载期报错。**
门禁静默放松比加载失败危险。
`expected_tools` 的取值在加载期对 `ChatTools` 的工具名强校验——工具改名后 yaml 里的旧名字直接炸，而不是静默评成「路由走错」。
调基线不动 Java。

**5. 按需 dispatch。**
要打真实模型调用，所以不进 PR 路径、不做定时空跑。**历史小语料时代的数字不可引用。**

**6. 双臂对照（按需，不进门禁）—「RAG 到底有没有用」。**
门禁只能回答「有没有变差」，回答不了「值不值得」。`evaluateRagArmComparison` 拿同一批 chat 用例跑两臂：**唯一变量是检索来源**——有检索臂挂全量工具面，无检索臂工具白名单只留 `finish`，模型拿不到任何检索工具的 schema，只能凭自身知识答。

消融变量只落在 `ToolCallLoop.Input` 的工具白名单上（`ToolDispatcher.of` 按名过滤回调列表），编排、生成、Judge 口径两臂完全同构。

> **报配对差分，不报两臂绝对分**：同用例两臂评分高度相关，独立样本口径会把用例难度的方差算进组间差；配对差把它消掉。绝对分因 Judge 与被评模型同源带自评偏差，**不可对外引用**——但偏差在两臂同向抵消，所以配对差可用。

**实测（2026-10-02，22 条 chat 用例）**：有检索臂 3.95 · 无检索臂 3.36，**配对差分均值 +0.5909**（标准误 0.3760）。方向为正，**但差分标准差 1.76 大于均值，单轮未达统计显著**——要下强结论须多轮取均值。

**为什么 IT 不钉差分符号**：差分是正是负是**结论不是门禁**。这批规则问答若模型自身知识已覆盖，差分趋零甚至为负都是真实结论；钉死符号等于把结论写成断言，换个模型就假红。IT 只断言两臂都评上了分（差分可算的前提）。

### 追问

**「Judge 靠谱吗？」**
自评 / 顺序偏差未根治，所以**只作回归门禁、不作对外质量证据**。

**「配对差分显著吗？」**
这批 +0.59 约合 1.6 倍标准误，**单轮不算显著**（差分标准差 1.76 > 均值）。要下强结论得跑多轮取均值——单轮数字只能支撑「方向为正」。

**「覆盖率门禁为什么必要？」**
评审大面积失败时均分失真。

**「为什么路由评估只跑循环不跑生成？」**
它量的是选路，生成那一步的结论属于生成分。少一次生成调用，这条线才是「为路由单独付的钱」，而不是把生成分重跑一遍。

**「怎么防 prompt 退化？」**
改 prompt 后跑一次评测对比基线。

## 10 LLM 可观测 — ChatModelContentObservationFilter + OTel 桥

**一句话**：OTel 桥把 Spring AI 的 Observation 送到 Langfuse，用属性键补 prompt / completion。单条 trace 内每步的 token / 延迟 / 成本可见。

**白话**：模型调用出了问题（「答得不对」「太慢了」「太贵了」），光看日志是没用的——**日志里根本没有模型实际收到的 prompt**。所以要接可观测：每次模型调用记录完整输入、完整输出、花了多少 token、耗时多久，在 Langfuse 面板上按一次请求串起来看。

`trace` = 一次请求从头到尾的完整调用链。`Observation` = 链上的一个观测点，Spring AI 每次调模型产生一个。

**文件**：`easyorange-ai/.../adapter/outbound/llm/ChatModelContentObservationFilter.java`、`compose.yaml`（langfuse profile）

### 要点

**1. 链路。**
Spring AI Observation → Micrometer Tracing 的 OTel 桥 → OTLP → 自托管 Langfuse。

**与 Grafana 分工**：那边是**调用级指标**（成功率、延迟、降级计数），这边是 **prompt 级 trace**。

**2. 关键坑。**
Langfuse 只认 `gen_ai.prompt` / `gen_ai.completion` 这两个**属性键**。
Spring AI 的 log-prompt 开关产出的是 **span 事件**，它不消费。
所以要 Observation Filter 把 prompt / completion 拷进属性。漏配则面板 input / output 恒为 null。

**3. 成本按自定义模型价逐调用计算。**
per-token 单位，**填错一位差三个数量级**。流式用量靠末帧 usage 回报。

**4. 顺带清理。**
原链路追踪上报是死链路（依赖从未引入 + 属性名变更），服务与配置一并移除。`traceId` 传播改由 OTel 桥承担。

### 追问

**「trace 覆盖率多少？」**
链路已通、单条 trace 已验证，覆盖率**待跑量统计**（如实说）。

**「成本数从哪来？」**
模型价 × 用量。模型价是配置项。

## 11 下单链路 — OrderCommandHandler

**一句话**：先取锁 → 本地事务内建单 → 扣库存 → 建支付。失败整体回滚，拒绝 Saga。

**白话**：这是**第二个项目角色**（买家）的核心链路。库存不能超卖——两个人同时买最后一件，不能都下单成功。做法是先拿一把 Redis 锁把这件商品的行锁住，然后在一个数据库事务里把建单、扣库存、建支付一次做完；任何一步失败全部回滚。

`Saga` = 把一个大事务拆成多个小事务，失败时逐个反向补偿。本项目是**单库**，所以直接用本地事务，把 Saga 整套方案全拒了——理由见 [ADR-0007](../adr/0007-order-local-tx-over-saga.md)。

**文件**：`easyorange-order/.../application/command/OrderCommandHandler.java`

**关键代码**：

```java
public CreateOrderResult createOrder(String userId, CreateOrderCommand command) {
    return lockPort.executeWithLocks(
            buildLockKeys(command),
            LOCK_TRY_TIMEOUT_SECONDS,
            () -> transactionTemplate.execute(_ -> createOrderFlow(userId, command)));
}
```

### 要点

**1. 锁在事务外获取，事务提交 / 回滚后释放。**
获取时等待**不占数据库连接**。
提前释放会让后一个请求读到旧库存快照，**击穿防超卖**。

**2. `buildLockKeys` 按 ID 排序去重。**
防 AB-BA 死锁。

**3. 事务内顺序。**
建单 + Outbox 发事件 → 同步扣库存 → 建支付 → 卖家缓存驱逐。

**4. 任一步失败整体回滚，抛领域异常。无补偿路径。**
锁获取失败在**事务开启前**抛出，没有回滚开销。

### 追问

**「锁和事务的顺序有问题吗？」**
先拿锁再开事务、提交后再释放锁，收敛防超卖窗口。

**「库存在这里为什么同步扣，而其他副作用异步？」**
防超卖是不变量，**不能靠最终一致**。

## 12 订单状态机 — Order + OrderAction

**一句话**：状态机唯一事实来源是动作表，聚合根单一入口守卫，转换产出事件走 Outbox。

**白话**：订单不能随便改状态——`待支付` 只能变成 `已支付` 或 `已取消`，不能变成 `已退款`。**如果这些规则散在十几个 `if` 里，一定会出现某处漏判**。状态机就是把它们集中成一张表：每个动作（支付 / 取消 / 发货 / 退款）声明「从哪些状态能来、来了变成什么状态」。

`聚合根` = 一批必须永远保持一致的数据的唯一修改入口，DDD 里的说法。本项目是四个：Product / Order / Payment / User。

**文件**：`easyorange-order/.../domain/aggregate/Order.java`、`domain/enums/OrderAction.java`

**关键代码**：

```java
// 动作枚举：每个动作声明前置状态集合、目标状态、目标支付状态、错误码（状态机唯一事实来源）

CANCEL("取消", Set.of(PENDING_PAYMENT), CANCELLED, null, ...)

private Order transitionTo(OrderAction action, String reason) {
    BizRequire.requireTrue(action.canApply(status, paymentStatus), action.resultCode());
    ...应用副作用（状态 + 支付状态 + 原因 / 时间）...
}
```

### 要点

**1. 动作驱动。**
合法转换集中在动作表单点声明，聚合根只留一个入口守卫。

**2. 每个公开方法返回「新聚合 + 领域事件」。** 聚合不可变（字段 final）。

**3. 支付状态独立于订单状态。**
取消不改支付状态，支付置已付，退款置已退。

### 追问

**「为什么不用一张大状态表？」**
订单状态 × 支付状态是**二维**的。动作表每行声明两个维度的目标值，比二维矩阵更可读可测。

**「退款为什么要求支付已付？」**
支付是**不可逆的外部副作用**，状态机不能靠「订单还显示已付但钱已经退了」这种组合自洽。所以退款额外挂一条支付维守卫（`paymentGuard`），与订单维的 `sources` 分开——两维混在一起就看不出卡的是哪一维。

**延伸**：[05 题 5](05-设计题与手撕.md) 手撕状态机 · [07 §4.2](07-怎么说.md)

## 13 分布式锁 — DistributedLockPort + DistributedRedissonLockAdapter

**一句话**：Redisson 锁 watchdog 续期、事务提交后释放、按 key 排序防死锁、释放前校验持有者。

**白话**：应用是多实例部署的，§11 那把「锁住这件商品」的锁必须所有人共用一把——所以放 Redis（`Redisson` 是 Redis 的 Java 客户端），不能放 JVM 里的 `synchronized`。

本节讲的是**用分布式锁的四条纪律**，每条都对应一个真实踩过的坑：租期自动续（`watchdog`）、提交事务后才放、多个锁按固定顺序拿（防死锁）、放之前先确认是自己拿的。

**文件**：`easyorange-framework/.../lock/DistributedLockPort.java`（端口）、`.../DistributedRedissonLockAdapter.java`（实现）

**关键代码**：

```java
RLock lock = redissonClient.getLock(lockKey);
boolean locked = lock.tryLock(waitTime, -1, TimeUnit.SECONDS);  // leaseTime=-1 → watchdog 续期
// 锁在事务提交 / 回滚后释放（事务同步回调），不是 finally
```

### 要点

**1. `leaseTime=-1` → watchdog 续期。** 默认 30s 锁、每 10s 续。不必手工估算事务耗时。

**2. 释放推迟到事务提交 / 回滚后。** 提前释放会击穿防超卖。

**3. 释放前检查 `isHeldByCurrentThread()`。** 防误删他人锁。

**4. 多锁按 ID 排序逐个获取。** 打破循环等待防死锁。锁 key 按业务前缀区分。

**5. 失败语义。** 获取失败抛统一的锁异常，业务在自身边界映射为领域异常。`waitTimeout=0` 即非阻塞尝试。

### 追问

**「锁过期但业务还没完？」**
watchdog 续期不会自动过期。holder 超阈值有告警。

**「Redis 挂了锁怎么办？」**
获取失败直接抛 `LockAcquisitionException`，在用例边界映射成订单域异常。锁在事务外，失败时事务还没开。**不静默放行**——超卖保护宁可失败不可绕过。

**延伸**：[04 DIST-8](04-速答.md) · [07 §4.3](07-怎么说.md)

## 14 事件幂等 — EventIdempotencyChecker

**一句话**：`SET NX EX` 原子领取 + 失败撤销 + 业务副作用幂等，达成 exactly-once 效果。

**白话**：消息中间件只保证「至少送到一次」，同一条消息可能来两次。**消费端必须自己判重**。做法是收到消息时先在 Redis 插一个标记（`SET NX EX` = 不存在才写、同时设过期），插成功才处理，插失败说明别人正在处理或处理过，直接跳过。

**文件**：`easyorange-framework/.../event/idempotency/EventIdempotencyChecker.java`

**关键代码**：

```java
// 一条 SET NX EX 领取处理权（false = 重复 / 他人处理中）
if (idempotencyEnabled && !idempotencyChecker.tryMark(namespace, eventId)) return;
...
} catch (Exception e) {
    idempotencyChecker.unmark(namespace, eventId);   // 失败撤销标记，容器重试 / DLQ 重投可重新执行
    throw e;
}
```

### 要点

**1. `SET NX EX` 是单条原子命令，无查-写竞态**，因此**不需要分布式锁**。

**2. 标记 TTL 覆盖 DLQ 三级重试的最长窗口。**

**3. 失败撤销标记。** 宁可重试不可漏处理。
「标记后、处理完成前」崩溃的残留窗口，由业务副作用幂等兜底（库存走流水唯一键）。

**4. 命名空间隔离多消费者**监听同一事件。

### 追问

**「at-least-once + 幂等 = 精确一次？」**
是。不丢 + 重复只处理一次。

**「TTL 过期后重复怎么办？」**
事件 ID 带时间戳，超窗重放概率趋零。这是成本权衡。

**延伸**：[04 MQ-2](04-速答.md) · [07 §4.3](07-怎么说.md)

## 15 Outbox 与 DLQ — ModulithDomainEventPublisher + DlqRetryScheduler

**一句话**：同事务双写保证「业务成功 = 事件必达」，DLQ 三级重试隔离毒消息，退避分两层各自计时。

**白话**：下单成功后要通知「搜索索引更新」「给卖家发通知」。如果发消息这一步失败了，订单是不是就不该建？反过来，如果订单建了消息没发出去，消息就永远丢了。

`Outbox` = 解决这个矛盾的办法：**业务数据和「待发消息」写进同一个数据库事务**。要么都成功要么都回滚。事务提交后后台任务再把待发消息读出来发到 MQ（RabbitMQ）——发失败消息还在表里，重启接着发。
`DLQ` = 死信队列，消费失败的消息先进这里重试，重试几次还不行就隔离等人处理，免得一条坏消息把主队列堵死。

**文件**：`easyorange-framework/.../messaging/core/ModulithDomainEventPublisher.java`、`.../event/dlq/DlqRetryScheduler.java`

### 要点

**1. Outbox。**
业务 SQL 与事件表 insert **同事务双写**。提交后异步外发，成功才写完成时间。崩溃重启重发未完成事件。
业务方只调 `publish(event)`，**不知道 MQ 存在**（领域层零中间件依赖）。

**2. DLQ 三级。**
主队列消费失败 → DLQ → 调度器周期重投（未超次数）→ 转储 terminal 等人工。

**3. 退避分两层，各自计时。**
主队列监听容器的重试模板先做快重试（`max-retries=2`）。进 DLQ 后调度器**自己还有一级指数退避**：按 `x-retry-count` 取 1 / 5 / 15 分钟窗口，自死信时间（`x-death`）起算，未到期就 `basicNack(requeue=true)` 回队等下一轮扫描；≥3 次转 terminal 队列等人工。
调度器每 5 分钟扫一次是**轮询节奏，与退避时长无关**——退避到期与否由 `isBackoffDue` 判，不靠扫得勤。DLQ 监听器提取死信记录指标。

**4. 路由键自动派生。** 事件类名 → 点分路由键，新事件零配置。MQ 可关时降级为进程内。

### 追问

**「发到 MQ 失败怎么办？」**
事件留在表里（完成时间为空），后台重试 + 重启重发。at-least-once 由消费幂等兜底。

**「为什么调度器轮询而不是原生延迟队列？」**
声明式简单，且与死信语义配合。

**延伸**：[04 MQ-1 / MQ-3](04-速答.md) · [07 §4.2](07-怎么说.md)

## 16 缓存 — RedisCacheConfig

**一句话**：注解 + Redis 单层，三防收口在注解与 writer，一致性靠事件 evict，可用性靠 fail-open。

**白话**：热门商品的详情被反复查，数据库扛不住，所以在中间加一层 Redis。业务代码里加一个注解，缓存的读和写由框架包掉。

三个经典故障：**穿透**（查一个根本不存在的 id，每次都打到数据库）、**击穿**（某个 key 突然过期，成千请求同时打下去）、**雪崩**（大量 key 同一时刻过期）。本节的要点是这三个问题**分别在哪一层解决**，而不是背概念。

**文件**：`easyorange-framework/.../config/cache/RedisCacheConfig.java`（+ 属性类 + TTL 抖动 writer）

### 要点

**1. 注解驱动。** 业务侧零缓存代码，统一 cache manager（String key + JSON value）。

**2. 三防收口在注解层 + writer 层。**

| 问题 | 解法 |
|---|---|
| 穿透 | null 结果缓存 |
| 击穿 | `sync=true` 同 key 单飞 |
| 雪崩 | 写入时按比例加 TTL 抖动 |

**3. 一致性 = 写路径显式 evict + 短 TTL 兜底。**
单库单 Redis，不需要 L1 / L2 配平与广播。

**4. 可用性 = fail-open。**
集中式错误处理器吞掉 Redis 异常（读直查 DB / 写放弃缓存），替代逐点 try-catch。

### 追问

**「击穿跨实例呢？」**
诚实讲边界：单飞是 JVM 内的。跨实例残留的少量并发，由事件 evict + TTL 兜底。

**「为什么删多级缓存 / 布隆？」**
复杂度换不来可感知收益。（但要能讲教科书方案。）

**延伸**：[04 DB-6 / DB-7](04-速答.md) · [07 §4.2](07-怎么说.md)

## 17 全局异常 — GlobalExceptionHandler

**一句话**：单方法模式匹配分发 + 错误码前缀映射状态码 + 模块专属错误码。

**白话**：全项目抛的异常最后都要变成一个 HTTP 响应。如果每个类各写各的 `@RestControllerAdvice`，十几个方法散在十几个文件里，**没人说得清全局到底怎么映射的**。本节把它收进一个方法：按异常类型分派，错误码前缀决定 HTTP 状态码。

**文件**：`easyorange-framework/.../exception/GlobalExceptionHandler.java`

### 要点

**1. 模式匹配 switch** 单方法按类型分发，消除十几个 `@ExceptionHandler` 方法。**代价**：多分支表达式换来「穷尽性在一处可见」，但每加一种框架异常都得改这个方法，编译器会逼着你面对——所以 `ClientAbortException` 明明不该映射成 500，仍显式收口成空分支占位，而不是让 switch 缺一个 case。

**2. HTTP 状态码按错误码前缀自动映射**（鉴权 / 参数 / 业务 / 系统）。

**3. 规范：禁止抛非业务基类的 `RuntimeException`**，否则落 500 兜底。模块异常必须用模块专属错误码，禁止回落全局码。

**4. 领域异常每模块一个根类 + 具名工厂**（`notFound(id)` / `notOwner(id)`），不搞「一码一类」。

### 追问

**「为什么 switch 不用多方法？」**
分发逻辑收敛一处。

**「响应统一吗？」**
统一响应信封 + 自动包装。

## 18 商品状态机 — Product

**一句话**：目标状态驱动的转换表 + 两条路径共用同一组完整性不变量。

**白话**：§12 是订单的状态机，这是商品的状态机。**两者的设计不一样**——商品用「转换到目标状态」驱动（`transitionTo(目标)`），订单用「按动作」驱动（`transitionTo(动作)`）。对比这两节能看出「状态机」不是背一套模板，是要按领域实际的不变量来选。

**文件**：`easyorange-product/.../domain/aggregate/Product.java`

### 要点

**1. 转换为目标状态驱动**（`transitionTo(目标状态)`）。转换表集中声明，终态判断显式。

**2. 两条进入上架状态的路径**（审核通过 / 直接上架）都过同一组 `validateOnline()`。**禁止第三条绕过校验的路径。**

**3. 删除不改状态**，单独守卫（已售不可删，保留订单追溯）。订单完成触发的「标记售出」幂等——重复触发返回空，不重复产事件。

### 追问

**「为什么上架校验独立成方法，不进状态机表？」**
状态机表管「转换是否合法」。校验方法管「进入该状态的数据完整性**不变量**」。两类规则职责不同。

## 附：被问「这段代码有什么问题」的应答模板

面试官挑毛病时，**先承认再给方案**。用下面几个项目里真实存在的点，比硬说「没问题」可信。

| 代码 | 真实问题 | 应答 |
|---|---|---|
| 下单链路 | 锁持有时长 = 事务时长，等待超时在极端慢 SQL 下会抛「繁忙」 | 「锁与事务同生命周期安全，代价是超时上限。慢 SQL 监控兜底，压测实测远低于此」 |
| 事件幂等 | 标记已写、处理中途崩溃时，重投会判重复而跳过 | 「失败路径已撤销标记，只剩『标记后、完成前』这一窄窗口。由业务副作用幂等兜底（流水唯一键），宁可漏一次也不重复加库存」 |
| 内存预算存储 | 多实例各自记账 | 「已知技术债。多实例切 Redis 存储，接口已就位」 |
| 已删的 Workflow 扇出 | 四路并行挂在搜索页上，模型调用不回流检索也不改排序 | 「核查后判定不是 Agentic，整节删除。留下的混合召回见 §8，判据见本节」 |
| 消息幂等 | 标记 TTL 理论上可重复 | 「TTL 覆盖 DLQ 重试窗口，超窗重放概率趋零，成本权衡」 |
| Agent 循环 | 步数上限内成本不确定 | 「上限可配 + 循环中途预算检查 + 三口径降级。平均步数 / 降级率待跑量回填」 |

> **原则**：主动说出「我知道这里有 trade-off，当时选 X 是因为 Y，触发条件是 Z」，比假装完美强十倍——这正是[技术债务清单](../技术债务清单.md)的叙事价值。
