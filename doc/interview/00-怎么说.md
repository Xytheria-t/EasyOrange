## 〇、使用协议（含学习队列）

### 三个开场（AI 陪练会话用）

| 开场白 | AI 行为 |
|---|---|
| 「开始第 N 章」 | 给读码路径卡：入口文件 + 阅读顺序 + 自检问题清单，不给讲解 |
| 「拷打第 N 章」 | 当面试官连环追问两轮：模块内 + 跨链路串联；卡壳点记入破防清单 |
| 「继续破防清单」 | 只考破防点，全部答对（清零）才出关进下一章 |

### 每章固定循环

1. 拿路径卡 → 自读代码（AI 不讲解；卡住超 30 分钟才解锁讲解，讲完须复述回来）
2. 合上文档写 ≤10 行白话讲解（写不出 = 没读完，回去重读）
3. 链路内拷打 → 跨链路串联拷打 → 破防点进清单
4. 破防清零 = 出关；出关产出白话讲解并入对应册（速答 → 01 / 走读 → 03 / 设计题 → 04）

### 队列（严格顺序，AI 主线在前）

| 章 | 主题 | 出关实验 |

> **当前主攻**：模型应用工程师 / AI Agent（行 1）。投递组合：主线行 1 + 保底行 2；全栈按 JD 临时切换叙事。**架构师方向不再投（2026-09-19 定）**——架构与分布式素材全部收进「工程底座」口径（回答「底座怎么撑住 AI 主线」），不作为独立叙事主线。
>
> **选主线的 4 个过滤器**（按顺序用）：① JD 关键词哪个多选哪个；② 目标岗是 AI 应用还是交易系统；③ 实习/校招一律走 AI 应用或通用后端，别自己往架构师上引；④ **最重要——哪条追问链你能讲到第 3 层不崩就选哪条**（用 [05-模拟题库.md](05-模拟题库.md) §1/§2 自测），掌握度 > 岗位匹配度。

> **原则**：一个主线故事讲到底 + 工程底座作为支撑抛出来。不要两个方向对半开（两边都讲不深）。

### 2.3 口径纪律（简历与口头都适用）

- **能说的数字分三类**：① 结构计数（链接[工程指标](../工程指标.md#结构计数)，不背具体值）；② 机械可算的检索指标（hit@5 / MRR——语料换血后须重跑才可引用）；③ 使用侧效果（建议价采纳率，**报数必须带样本量**）
- **LLM-as-Judge 分数不作对外质量证据**：它只作 CI 回归门禁（防 prompt / 模型改动退化），对外讲质量用上面两类客观数字
- **额度依赖的跑量数字**（循环三口径：平均步数 / 降级率 / 步级延迟 p95；首字延迟；trace 覆盖率）一律标 `待补口径`：面试如实说「待补测」并给出复现命令，**不编数字**；这些是已标记搁置项，不当作「项目没做完」去反复解释
- **双项目分工**：本仓库 = 生产级**单** Agent 工程化（编排 + RAG + 评估 + MCP + 成本治理）；**多智能体编排不在这里做**——归第二个项目（Python LangGraph 多智能体编排 + 评估，经 MCP 消费本仓库 Java 工具面，跨语言系统）。被问「为什么不做多智能体」就答这条分工，不要说「没时间做」

## 三、自我介绍话术（三档时间版本）

> 原则：**开场抛钩子 → 主线讲故事 → 留一个可追问的点**。结构：`我做了一个项目叫 EasyOrange，定位是___，核心矛盾是___，我的解法是___，结果是___`。

### 3.1 30 秒钩子（简历顶部 / 自我介绍开场 / HR 电话面）

> **EasyOrange — Java AI Agent 工程化实战**。按生产级标准做 LLM Agent 工程化：**多范式工具编排（自治式多步循环 + Workflow 式并行扇出）+ RAG 检索增强 + 评估闭环进 CI + MCP 工具面 + LLM 专用可观测**——AI 链路可换供应商、可降级、可观测、可评估。工程的底座是 DDD 六边形多模块与事件驱动可靠性（Outbox + DLQ 三级重试），支撑上面这些生产级要求。

### 3.2 1 分钟版 · AI Agent / 模型应用（主线）

> 我做了 EasyOrange，定位是 **Java AI Agent 工程化实战**——项目不对外运营，但工程标准对标生产：门禁 / 降级 / 预算 / 观测机制齐备（实测数字一律以 [工程指标.md](../工程指标.md) 为准，跑量类项如实说待补测）。
>
> 编排我做的是**两种范式的对照**，这是这个项目最想讲的一点：一是**自治式多步工具循环**（`AgentLoopRunner`）——决策走原生 tool calling，模型每轮选工具、观察进下一轮决策，直到收敛；工具面按性质分四层，其中两个纯计算工具（行情统计 / 多件逐维比对）让第 N 步真的依赖第 N-1 步的输出，不然循环就只剩「换关键词重试」。二是 **Workflow 式 4 路并行扇出**（`AiSearchEnhancerAdapter`）——4 路 `CompletableFuture` 并行（1 路 LLM 意图识别 + 3 路规则计算），整体 5s 超时后保留已完成步骤的部分结果。**循环为什么自己写**：`@Tool` 只用来生成 schema，工具执行与循环控制权留在我的 runner 里——步数上限、循环中途的预算检查、按终止原因分类的降级（步数超限 / 预算耗尽 → 用已积累观察单次生成；决策失败 → 按原始问题检索一次）必须插得进去，交给框架托管就插不进。
>
> 检索侧是**真实的两路召回 + 排名融合**：摄入管线分块（500 + overlap 50、换行优先切点）→ embed → ES 索引；查询侧 kNN 与 BM25 **各查一次**，再用 RRF 按排名融合——不用分数加权是因为余弦与 BM25 分值量纲不可比。商品检索 / 知识库 / 在售资产三条链路共用同一份 `RrfFusion`，回答带 `[来源:标题]` 引用溯源。SKU < 10 万不引 Milvus，分界线讲得清。
>
> 质量侧是**评估闭环进 CI**：金标准集（生成 + 检索两类）+ `AiJudge` 对照参考打分 + `EvalGate` 双门禁（低于基线-容忍度、或评审覆盖率 < 80% 都卡 build，阈值全在 `eval/baselines.yaml`、缺键加载期报错）+ hit@5 / MRR 检索指标 + 反馈飞轮。**我对 Judge 的定位很明确**：分数只作回归门禁，不作对外的质量证据；对外讲效果用建议价采纳率这类使用侧数字。
>
> 对外能力是 **MCP 工具面**：公开只读工具经 streamable HTTP 暴露，Cursor 能直接连；与 Agent 内部工具是两级暴露，信任边界独立。可观测上自托管了 **Langfuse**，通过 OTel 桥收 Spring AI 的 Observation，单条 trace 内每步的 prompt / token / 延迟 / 成本都能看到。工程底座是 DDD 六边形多模块 + Port 编译期隔离 + 下单本地单事务（拒绝 Saga）+ Outbox 与 DLQ 三级重试。

### 3.3 1 分钟版 · 通用 Java 后端 / 被追问架构时

> 我做了 EasyOrange，一个按生产级标准落地的 **Java AI Agent 项目**——AI 是主线，但支撑它的是一套 DDD 六边形 + 事件驱动的工程底座。
>
> 模块边界靠 `Port` 接口做**编译期隔离**，ArchUnit 规则在 CI 阶段守住 DDD 分层（domain 零框架依赖、CQRS 读写分离、模块间只经端口通信），违规直接红。
>
> 下单链路我选**本地单事务 + Redisson 分布式锁 + Outbox，拒绝 Saga**（[ADR-0007](../adr/0007-order-local-tx-over-saga.md)，同样拒绝 2PC / XA / Seata AT / TCC）：锁在事务外获取（等待不占数据库连接）、事务提交后再释放，多商品按 ID 排序防死锁；事务内建单 + 发事件（Outbox 同事务原子）+ 扣库存 + 建支付，失败整体回滚、无补偿路径——单库场景下本地事务的强一致比 Saga 的最终一致更强、成本更低。
>
> 事件驱动可靠性三层：Spring Modulith Outbox（业务表 + `EVENT_PUBLICATION` 同事务写入，崩溃重启重发）→ DLQ 三级重试（调度器周期重投，超限转储 terminal 等人工）→ `EventIdempotencyChecker`（`SET NX EX` 原子领取处理权，失败撤销标记，宁可重试不可漏处理）。治理上是 ADR + ArchUnit + PIT 三板斧：每条决策记「为什么选 + 拒绝了什么」。

> 1min 版本（§3.2 或 §3.3）+ 展开一个**被拒绝方案**或**一次自我纠偏**：

## 四、高频追问应答

### 4.1 主线：AI Agent / 模型应用

**问：多范式的工具编排怎么理解？为什么两种都要？**
> 因为「谁来选下一步」这件事有两种答案，工程代价不同：
> - **Workflow 式**（`AiSearchEnhancerAdapter`）——路径写死：4 路 `CompletableFuture` 并行（1 路 LLM 意图识别 + 3 路规则计算），整体 5s 超时、单路失败降级、降级结果不进缓存。**确定性强、可整体设超时、成本可预测**；换一个查询也不改变流程。
> - **自治式**（`AgentLoopRunner`）——路径由模型逐轮决定：每轮把工具 schema 随请求下发，模型返回「调哪个工具 + 参数 + 理由」，执行后观察进下一轮，直到 finish 收敛。**能处理没预写流程的问题**，代价是步数与成本不确定，所以必须配步数上限、循环中途预算检查、按终止原因分类的降级。
> 我的口径是：**能用 Workflow 解决的不用自治**（成本可控），只有「下一步真的取决于上一步结果」时才上循环。两者在同一仓库里形成对照，这是我最想被追问的部分。

**问：多步循环具体怎么实现的？**
> `AiChatService` 装配上下文 → `AgentLoopRunner` 逐轮循环：决策 → 工具 → 观察，收敛或到上限后带引用生成回答。要点四个：
> - **决策走原生 tool calling**：工具 schema 由 `AgentTools` 的 `@Tool` / `@ToolParam` 生成随请求下发（供应商侧校验、参数名锚定，依赖编译期 `-parameters`），执行经 `ToolCallback` 回调——`ChatModel.call` 不自动执行工具，循环控制权在 runner
> - **工具面按性质分层**：检索 / 计算 / 写入 / 收敛四类。**计算类工具是关键**（行情统计、多件逐维比对，纯 JDK 零模型调用）——只有检索工具时循环的唯一意义是换关键词重试，有了计算类，第 N 步才真正消费第 N-1 步的输出
> - **三条降级口径**：步数超限、循环中途预算耗尽 → 用已积累的观察单次生成（不丢已有信息）；决策失败（模型故障 / 未返回工具调用 / 参数不可解析）→ **按原始问题检索一次**，而不是不检索——不把决策链路失效伪装成「这题本来就不需要检索」
> - **可观测**：每步落 `eo_agent_step_trace`（一次请求一个 trace_id），SSE 推 step 事件（工具 + 决策理由 + 观察）供前端步骤可视化，指标按 outcome 计数归因
> **待补口径**：平均步数 / 降级率 / 步级延迟 p95——需要真实 key 跑量，已标记搁置（复现命令在工程指标里）。

**问：为什么工具循环不交给框架托管？LangChain4j 和 Spring AI 差别在哪？**
> 工具 schema 这一层两家**一致**：LangChain4j 的 `@Tool` 和 Spring AI 的 `@Tool` 都是运行时反射生成 JSON Schema（LangChain4j 官方文档也讲参数名靠反射取、编译要加 `-parameters`），所以「谁反射谁不反射」不是我选型的理由。
> 真实取舍是**循环控制权**：两家都提供托管的工具执行循环（LangChain4j AI Services / Spring AI `ChatClient` 的 ToolCallingAdvisor）。一旦托管，**步数上限、循环中途的预算检查、按终止原因分类的降级就插不进去**——这三样正是「生产级」要能讲清楚的部分。所以我只用 `ChatModel` 这一层：发 schema、原样收回 tool call，执行与循环留在 `AgentLoopRunner`。
> 选 Spring AI 而不是 LangChain4j 是 Spring 原生决定的（`ChatModel` 是 bean、自动装配、Micrometer Observation 直连 Langfuse），符合项目的标准 API 优先原则。

**问：工具面怎么设计的？**
> `AgentTools` 是唯一落点，7 个工具分四层：
> - **检索 3**：平台规则知识库、在售资产、资产详情（详情必须取自前一步检索观察里的 ID——这是让步骤有依赖关系的第一步）
> - **计算 2**：行情统计（对已召回资产算在售件数 / 均价 / 区间）、多件逐维比对（价格 / 成色 / 地区 / 在售状态，一次替代多次详情查询）——纯 `domain/model` 里的确定性计算，零模型调用
> - **写入 1**：`remember_preference` 写用户画像（长期记忆）。**它是独立工具而不是挂在收敛轮上的参数**——挂在收敛轮上时，步数超限 / 预算耗尽 / 决策失败三条降级路径下偏好会静默丢失
> - **收敛 1**：`finish` 声明信息已足够
> 每个工具的第一个参数都是 `thought`（本步理由），落 trace 供排障与展示。工具名与编排器共用常量，不重写字面量。

**问：MCP 工具面怎么做的？信任边界怎么划？**
> Spring AI `@McpTool` + streamable HTTP，端点 `/mcp`，暴露**公开只读**的 4 个工具：在售资产检索（与站内搜索同一套两路召回 + RRF 底座）、资产详情、类目逐层浏览、平台规则知识检索。Cursor / Claude Desktop 配上 URL 就能实时查平台数据。
> **信任边界是设计出来的两级暴露**：外部 MCP client **没有用户上下文**，所以只挂公开只读数据——不暴露订单、个人信息、写路径；Agent 内部工具面（循环用的那套）与它各自独立，鉴权假设互不共用。另外匿名可达但纳入统一限流，并对 JSON-RPC 的重试特性做了防重豁免（同字节请求重发属协议内合法行为）。
> 踩过的坑：MCP server 的 `protocol` 属性**必须显式配置**——条件装配读 Environment，属性默认值不生效，缺省时端点整个不装配。

**问：Langfuse 观测了什么？和 Grafana 什么关系？**
> 两级互补：**Grafana / Prometheus 是调用级指标**（成功率、延迟、降级计数），**Langfuse 是 prompt 级 trace**。链路是 Spring AI 的 Observation → Micrometer Tracing 的 OTel 桥 → OTLP 上报自托管 Langfuse（六件套 compose profile）。
> 落地时的关键细节：Langfuse 只认 `gen_ai.prompt` / `gen_ai.completion` 这两个**属性键**，而 Spring AI 的 `log-prompt` 开关产出的是 span 事件、它不消费——所以加了一个 Observation Filter 把 prompt / completion 拷进属性里，否则面板 input/output 恒为 null。成本不是猜的：按自定义模型价逐调用计算（价格单位是 per-token，填错一位数量级就差三个数量级），流式用量靠末帧的 usage 回报。

**问：Token 预算怎么管的？**
> 职责严格二分：`@TokenBudget` 注解声明场景与日预算（编译期契约），`TokenBudgetAspect` 的 `@Around` **只做前置检查**——`累计已用 + 本次上限 > 日预算` 就抛异常走统一降级；**记账不在切面里**，在 `AiModelSupport.recordBudgetUsage`：调用后取 `ChatResponse` 的 usage metadata，**有真实 input/output 就按真实值累加**，供应商确实不回报（embedding 接口、流式未带 usage）才退化为场景配置的单次上限——估算偏高，但比「预算恒为 0、限流静默失效」安全。
> 存储两版（配置切换）：内存版与 Redis 版（`HINCRBY` 原子累加 + 日窗口 key，判定式一致），多副本部署切 Redis。yaml 可按场景覆盖注解默认值——注解是编译期契约，配置是运行期旋钮。

**问：AI 调用成本怎么核算？能出报表吗？**
> 账本与预算分开讲。**账本**：`eo_ai_call_log` 记录 scope / model / prompt_hash / 响应 / 耗时 / 成败 / token 入出 / 调用主体，`GET /api/admin/ai/cost-report` 按场景聚合调用数、token、平均耗时、失败数。**报表里为 0 的两类要主动说**：embedding（供应商不回报 usage）与流式未带 usage——记 0 不估算，为 0 不代表不花钱；语义缓存命中率仍无计数器（已知技术债）。
> **成本优化实际做了什么**：① 搜索增强从早期 3 路 LLM 收敛到 1 路 LLM + 3 路本地规则；② 删掉「建 / 改商品触发 LLM」这条白烧的消费链路；③ 发布助手收敛为拍照识别单入口，发布路径模型调用从最多 5 次降到 1 次；④ 语义缓存命中复用（阈值 0.92，**一次请求只向量化一次**——拆成 get/put 会让未命中的请求对同一问题算两遍 embedding）；⑤ 上下文窗口按 token 估算裁剪（见下一条）。
> **对外讲效果用使用侧数字**：建议价采纳率（`GET /api/admin/ai/pricing-adoption`）——建议价随创建请求落库，与资产方最终价同行可比，出采纳率 / ±10% 内 / >30% 偏离分布；**报数必须带样本量**，且口径是「建议价被接受的比例」，不等于「AI 估得准」。

**问：上下文窗口怎么治理的？为什么不做摘要压缩？**
> 两道：存储侧按轮数窗口（Redis List，TTL 24h），注入 prompt 前再按**估算 token** 裁剪（`TokenEstimator` 确定性估算，CJK 0.7 token/字、其余 0.3，偏保守高估方向；预算默认 2000，可配，≤0 关闭），裁剪点在装配历史这一处、决策与生成两条路径共用。
> 裁剪规则：从最新向前保留**连续窗口**，单条超预算仍保最新一条（永不空历史）。
> **不做 LLM 摘要压缩是主动取舍**：步数上限与轮数窗口都不大，摘要收益小，而每轮摘要多一次模型调用直接翻倍成本。指标是注入历史 token 的 p50/p95 + 裁剪触发率（待真实 key 跑量回填）。

**问：为什么框架化到 Spring AI，而不是继续自研 Port / Adapter？**
> 我做过完整评估（[ADR-0008](../adr/0008-ai-spring-ai-framework.md) 决策翻转，原 ADR-0003 的记录见[已替代决策](../adr/已替代决策.md)）：ADR-0003 决策时（2025-11）Spring AI 尚未稳定，自研 Port / Adapter + 装饰器是合理选择；Spring AI 稳定后，自研的 `LlmPort` / `VisionPort` / `CachingLlmAdapter` / `AiMetricsService` 就成了与框架重复的手写代码——**零新增自定义代码是最优方案**，删掉换框架配置即可。迁移后六个 service 直接注入 `ChatModel` / `EmbeddingModel` bean，换供应商只改 `AiModelConfig` 的 baseUrl / apiKey / model。
> 但**编排保留手写**（框架黑盒）——「编排自己写、模型调用用框架」，两类复杂度各归其位。轻量级不代表不自研，而是不为框架已有的能力自研。

**问：RAG 做到哪一步了？往深做先做什么？**
> 三条链路，一套形态：**① 商品检索**——一个入口，内部两路独立召回（BM25 `multi_match` + kNN `nameEmbedding`）→ RRF 融合；**② 知识库**——完整链路：摄入管线（解析 → 分块 500 + overlap 50、切点优先落换行 → 逐块 embed → ES 索引，best-effort + 启动补索引）+ 两路独立召回 → RRF 融合 → `[来源:标题]` 引用溯源；**③ 在售资产检索（对话式找货）**——同一套形态换语料，两路都过滤在售状态，融合共用同一份 `RrfFusion`。
> 检索质量有量化：金标准集里的检索用例跑 hit@5 / MRR 落 `eo_retrieval_metric`；语料里多数是同域干扰文档（**语料与 topK 同量级时 hit@5 恒为满分，指标就成了装饰**——这个坑踩过）。
> 还没做的是**模型 rerank**（Cross-Encoder 替代排序融合）：双塔召回要快要宽、交叉编码精排要准要窄，成本权衡讲得清，触发条件是分块数上千且 hit@5 触顶而 MRR 偏低。诚实标注演进方向，不硬上。

**问：怎么判断 AI 输出质量？**
> 分两个用途说，别混：
> - **回归门禁（内部）**：金标准集 + `AiJudge` 对照参考打分 + `EvalGate` 双门禁——均分低于「基线 − 容忍度」失败，**评审覆盖率低于下限同样失败**（否则均分只是幸存者平均，一条打 5 分就能蒙过分数门禁）。阈值全在 `eval/baselines.yaml`，**键缺失是加载期异常而不是悄悄回落默认值**（门禁静默放松比加载失败危险）。改 prompt / 换模型 / 调检索参数后手动 dispatch 评测 workflow 拿数字——单次评测要打真实模型调用，所以不进 PR 路径、也不做定时空跑。
> - **对外质量证据（不可用 Judge）**：Judge 与生成同模型有自评偏差、顺序 / 长度偏差未根治，**LLM-as-Judge 分数我只作门禁、不作对外声称**。对外用机械可算或使用侧数字：hit@5 / MRR（语料换血后须重跑）、建议价采纳率（带样本量）。
> 演进项是 faithfulness（答案与检索内容一致性）这类客观指标 + 更强 Judge 模型（场景路由已支持，改配置即可）。

**问：支持流式输出吗？设计一个流式问答？**
> **已支持**：`SseEmitter` + `ChatModel.stream(Flux)`，事件协议 step（Agent 每步：工具 + 决策理由 + 观察）/ token / sources / done / error；前端用 fetch + ReadableStream 逐帧消费——**选 fetch 而不是原生 EventSource**，因为 EventSource 只支持 GET 且不能带 Authorization 头，我们的鉴权在 localStorage。
> 四个工程点：① **预算兼容**——流式方法在流结束前就返回，AOP 拦不住，所以在 `AiChatService` 手动执行同一套预算前置检查，超限转 SSE error 降级；② **调用日志不缺流**——阻塞收流后把完整拼接结果落 `eo_ai_call_log`；③ **来源先于正文**——检索结果在生成前就绪，先推 sources 让前端先渲染来源区；④ **断流兜底**——网络异常推降级文案，前端展示错误气泡。首字延迟专项指标是标注的待补项。

**问：Agent 记忆 / 多轮对话怎么设计？**
> 短期 = Redis 会话窗口（key 按 sessionId，TTL 24h，裁剪到最近 N 轮）；长期 = 用户画像表（跨会话持久，由独立的 `remember_preference` 工具写入——**模型自主决定何时记**，不依赖收敛轮，所以三条降级路径下偏好都不会丢；聊天时注入 prompt）。推理侧就是多步循环。
> 三个细节：① 工具决策失败降级为「按原始问题检索」而不是不检索；② 生成时历史按**原始角色**传多消息（`[system, 历史 user/assistant…, 当前 user]`），不压进当前 user 消息——跨轮次前缀稳定才能命中供应商的上下文缓存折扣；③ 记忆读写 fail-open，Redis 故障不影响回答。

**问：多模态 Vision 调用跟 LLM 是一条链路吗？**
> 是，同一套 Spring AI 链路——`visionChatModel` bean（通义千问 VL）用多图 Media 构造消息识别拍照上架图片，`@TokenBudget` 单独管预算。换供应商只改 `AiModelConfig` 的 options。发布助手就是拍照识别单入口：**一次调用产出属性 + 建议价 + 标题 / 描述**，把发布路径的模型调用从最多 5 次压到 1 次。

**问：如果 LLM 供应商彻底挂了，你的系统会怎样？**
> 分层降级，答这题等于把全链路降级讲一遍：① **不依赖 LLM 的路径照常**——搜索增强里的标签 / 市场分析 / 建议问题是本地规则计算，`NaturalLanguageDetector` 也是规则判断，这些零 LLM 路径亚毫秒兜底；② **对话链路**：限流超限 → 429 直接拒绝（保护上游不被烧），供应商故障 → `AiChatService` 服务层返回 stale 旧回答，无 stale 则 unavailable 文案；③ **循环链路**：决策失败降级为按原始问题检索一次；④ **索引 / 检索链路**：ES 可关（走 LIKE 兜底，启动 WARN + 健康检查 UNKNOWN 标注）；⑤ **观测**：降级不是「静默变差」——对话降级与 RAG 降级各有自定义计数，不进计数就只剩「答得差」这一种表象。**MQ 没了应用能起，ES 没了检索降级但主链路活着**，这是工程底座给 AI 主线的承诺。
> 要主动说的缺口：**没有跨供应商容灾**——每场景单供应商，故障时降级而不是切备用模型（已知技术债，触发条件是 AI 链路进对外 SLA）。

**问：这个项目为什么不做多智能体？**
> 分工问题，不是能力问题：**本仓库的命题是「一个 agent 怎么做到生产级」**——单循环的上下文治理、工具面设计、循环降级、成本与步数上限、评估闭环，这些是单 Agent 才有的工程问题；**「多个 agent 怎么编排与评估」归第二个项目**（Python LangGraph 多智能体 + 评估为主体，经 MCP 消费本仓库的 Java 工具面，组成跨语言系统）。两边共享的正是这里暴露的 MCP 工具面——这也是我把 MCP 做进这个项目的原因之一。

### 4.2 工程底座（被追问架构时）

**问：下单为什么不用 Saga？Seata 的 AT / TCC 不是更标准吗？**
> 分两层答——**为什么拒绝 Saga**（[ADR-0007](../adr/0007-order-local-tx-over-saga.md)）和**为什么不用 Seata**（技术对比）：
>
> **（一）单库下单不用 Saga**：单库部署下，一个本地事务（显式 `TransactionTemplate`，锁在事务外）就把订单 / 库存扣减 / 支付创建 / Outbox 事件全部包进**同一事务**，任一步失败整体回滚——本地事务比 Saga 的最终一致更强、成本更低。Saga 的补偿要么与回滚重复、要么进程崩溃后无法重建。触发条件是模块拆独立数据源 / 独立部署时才重新评估。
>
> **（二）为什么不用 Seata**：① AT 模式要代理数据源 + undo_log 表 + TC/TM/RM 三角色独立部署，跟我们的 `@ConditionalOnProperty` 降级模式不兼容（RabbitMQ 没了应用能起，Seata TC 挂了直接连不上）；② TCC 每个参与方三接口（Try/Confirm/Cancel），侵入大、维护成本爆炸；③ 平台不经手资金，没有 double-spend 风险，本地事务的强一致已经覆盖；④ 2PC / XA 需要全局协调器、穿透 Port/Adapter 边界、锁等待长——这条理由现在覆盖**整个 Saga 家族**。

**问：为什么用 RabbitMQ 不用 Kafka？**
> 我评估过多种 MQ，最后按维度打分选的 Rabbit，不是不知道 Kafka（[ADR-0005](../adr/0005-messaging-rabbitmq.md)）：① **DLQ + 重试**——我们有三级重试 + 毒消息转储，RabbitMQ 的队列级 dead-letter 是声明式的，两个参数搞定；Kafka 没有「死信」概念，消费失败要自己发 dlq topic、自己调度重投、自己管位点提交，成本翻倍；② **模型匹配**——我们是 1 个事件扇出到多个独立下游（恢复库存 / 标记售出 / 审计 / 通知），Rabbit 的 Exchange → 多独立队列是原生的；Kafka 得建同样多的 consumer group，各自维护 offset + 重试；③ **成本 / 运维**——Kafka 的吞吐优势在百万级 msg/s 才显现，我们的量级单节点完全够，分区 / 副本 / lag 的运维复杂度是纯负担。④ **演进位**：MQ 选型是配置驱动的演进点，真到量级变化按 ADR 方案接即可，domain / application 层一行不动。

**问：CQRS 为什么只在 4 个模块做？**
> 见 [ADR-0002](../adr/0002-cqrs-scope-4-modules.md)。收益来自「读多写少 + 跨聚合查询 + 读写独立优化」：product（ES 全文搜索 + 列表聚合）、order（列表跨 product + payment 聚合）、payment（对账查询独立）、message（会话列表 + 未读数维度独立）满足。
> 但这 4 个**深度不同**：product / order 有独立 ReadModel；payment / message 只做 **Command/Query Handler 级分离 + 独立查询仓储**，没有独立 ReadModel。message 不做 ReadModel 是因为聊天消息读写比接近 1:1，读模型独立优化收益接近 0；favorite / user 完全不做（单表索引够 / 读写均衡）。CQRS 不是银弹，每模块拆双仓储多一倍代码量，收益 < 维护成本就坚决不做。

**问：ArchUnit 具体守了什么？CI 真的能阻断吗？**
> 规则清单以 `ArchitectureRulesTest` 的 javadoc 为单一来源（条数见[结构计数](../工程指标.md#结构计数)），核心几条：domain 白名单准入（只允许 JDK + common，零框架）；CQRS 写侧不依赖读侧、读侧不依赖写侧；业务模块间只能经 `domain.port` / `domain.valueobject` 通信（端口隔离）；每个 `*Port` 必须有适配器实现；禁止 `infrastructure` 包；domain / application 禁止反向依赖 adapter（已知历史债用 `FreezingArchRule` 冻结，重构移除后自动解除）；Controller 禁止直连 Mapper；禁止 `System.out` / `printStackTrace`；domain / application 禁依赖 `org.springframework.dao`；每模块领域异常根唯一。
> 挂在 `./mvnw test` 里，CI 上测试失败即红，PR 合不进来——**是真阻断，不是摆设**。

**问：PIT 变异测试是什么？跟 JaCoCo 区别？**
> JaCoCo 只看「代码被执行过没」——把一个 `if (a > 0)` 改成 `a >= 0`，行覆盖还是绿的，但逻辑变了。PIT 在 bytecode 里注入变异（改比较符、改返回值、删调用），再跑现有测试：测试还全绿说明这个变异**存活**，对应位置的测试没覆盖真实逻辑。
> 我们只对 domain 层做（聚合根状态机 / 领域服务 / 值对象）；JaCoCo + PIT 互补，避免写「为了覆盖率的空测试」。
> **口径要说准**：PIT 的 workflow 目前只在 nightly 跑、**只对 order 模块**、且没传阈值参数，所以它是**趋势观察 job 而不是门禁**——pom 里三个阈值属性默认 0（只出报告不阻断），本地要卡门禁得自己传（如 `-Dpit.mutationThreshold=60`）。说成「PIT 卡 CI」会被追问打穿。

**问：Outbox 怎么保证事务一致的？崩溃了真的不丢事件？**
> Spring Modulith 的 Outbox 核心是**同事务双写**：业务 SQL 与 `EVENT_PUBLICATION` 的 insert 在**同一个本地事务**里（要么都成功要么都回滚）→ 事务提交后异步外发 → 发成功才写 `completion_date` → 崩溃重启时配置项会重扫未完成事件再发一次。关键是 **at-least-once（可能重复）+ 消费者幂等** 配合：Modulith 保证不丢，幂等保证重复只处理一次。

**问：缓存三防怎么做的？为什么删掉了多级缓存？**
> 三防已落地（Spring Cache 注解 + Redis 单层）：穿透 = null 结果缓存；击穿 = `@Cacheable(sync=true)` 同 key 单飞重建；雪崩 = 写入时按比例加 TTL 随机抖动。一致性 = 写路径显式 evict + 短 TTL 兜底；可用性 = `CacheErrorHandler` fail-open（读直查 DB、写放弃本次缓存）。
> 手写的多级缓存（L1 + L2 + Pub/Sub 广播 + 负缓存哨兵）与布隆过滤器**评估后移除**：单库单 Redis 部署下，这些复杂度（L1/L2 配平、广播、哨兵）换不来可感知收益，写路径显式 evict 已保证一致性。**「评估后不用的原因」比堆功能更显判断力**——但被问多级缓存方案本身，要能讲出 L1/L2 + 广播 + 命中率的教科书答案。

### 4.3 通用高频追问

**问：Redisson 分布式锁的 watchdog 怎么工作？leaseTime 设多少？**
> 下单锁调的是三参 `tryLock(waitTime, -1, SECONDS)`——**leaseTime 传 -1 交给 Redisson watchdog 自动续期**：默认锁 30s，后台每 10s 检查是否仍由当前线程持有，是就续期回 30s，保证锁不会在流程结束前自动过期（短事务场景不用手工估算锁时长；明确不想被续期才传显式 leaseTime）。
> 另外三个细节：① 锁**释放推迟到事务提交 / 回滚之后**（事务同步回调里释放）——提前释放会让后一个请求在前一个事务尚未提交时读到旧库存快照，击穿防超卖；② 多商品锁按 ID 排序后逐个获取，防 AB-BA 死锁；③ 释放前检查 `isHeldByCurrentThread()`，防「锁已过期被他人持有」时误删别人的锁。

**问：幂等为什么用纯 SETNX 就够了？不需要「锁 + done 标记」两级吗？**
> 不需要锁——`SET NX EX` 是**一条原子命令**，同时完成「检查 key 不存在 + 写入 + 设 TTL」，不存在查-写竞态窗口；锁是给多命令序列用的。key 命名空间隔离多消费者。两个细节：① 处理**失败**时撤销标记，让重试 / 重投能重新执行——**宁可重试不可漏处理**；② 标记 TTL 覆盖 DLQ 三级重试最长窗口，进程在标记后、处理完成前崩溃的残留窗口由业务副作用幂等兜底（库存恢复走流水唯一键）。

**问：ES 检索怎么做的？为什么不引 Milvus？**
> 先说入口：**没有「语义搜索」这个独立开关**——就一个搜索框，按相关性排序时自动走两路召回。链路是查询向量化 → kNN 与 BM25 **各查一次**（同请求里「knn + query」不行，ES 会把两路分数内部合成一个分值、拿不到各自排名）→ RRF 按排名融合（余弦与 BM25 量纲不可比，只有排名能融）。两个容易被追问的口径：**显式排序退化为单路**（用户点「价格从低到高」时融合排名会和点选排序打架，只走 BM25 并保留 ES 侧排序）；**`total` 取 BM25 路的总命中**（唯一有全量语义的口径），只有词面命中为 0 而语义路召回到结果时才改报候选池大小，否则前端会出现「共找到 0 件」却列着结果。
> 不引独立向量库：SKU < 10 万，ES 自带 kNN（底层 HNSW）够用，Milvus / PGVector 引入索引构建 + ANN 调参 + 运维监控一整套东西，ROI 太低。分界线是数据规模：SKU 到百万级、向量索引成为瓶颈时再切。

**问：令牌桶和固定窗口差在哪？限流参数怎么定的？**
> 固定窗口（increment + expire）有两个问题：**窗口边界突刺**（59 秒用满、下一秒又能用满）与**原子性缺口**（两条命令非原子，需要 Lua）。Redisson 的令牌桶按「补充速率」发放，天然允许突发又无边界突刺。AI 端点按场景配置速率（`AiCallScope` + yaml），超限返回 429；**Redis 不可用时 fail-open 直接放行**——限流是保护手段，不能成为可用性单点。

**问：性能数据？压测过吗？**
> 压过只读混合流量（列表 + 分类 + 搜索），k6 脚本与阈值在 `load-tests/`；另有「限流开关对比」：默认限流下同参数压测返回 **429 而非 500**，证明限流器真实生效、后端零错误。写路径（下单 + 分布式锁）压测脚本已就位但还没跑，是标注的待办。**具体 QPS / p99 收口重测后回填**（工程指标 §2.3），不背旧数字。

**问：业务复杂度这么低，有意义吗？**
> 我特意选了 C2C 资产流转做载体，因为它刚好能承载这几条主线：跨模块一致性（拒绝 Saga → 本地单事务 + 分布式锁 + Outbox）、读多写少（CQRS + ES 检索）、实时通信（WebSocket），以及**两条真实的 AI 链路**（发布助手 / 对话式找货）——AI 链路要是没有真实业务流，就只剩 demo。
> **如果业务做复杂了**（加议价 / 阶梯降价 / 优惠券），状态机几十种转换，面试时间根本讲不完，反而侵蚀 AI 工程化的主线叙事。真正的复杂度我刻意放在 **Agent 编排 / RAG / 评估 / 成本治理**这些能拿数字、能被追问三层的地方。

| **HNSW / ANN 索引原理** | M / efConstruction 参数？余弦与点积的区别？ | 「我对向量检索原理主要是调研阶段的理解——HNSW 是分层可导航小世界图，M 控制每层邻居数，efConstruction 控制建图探索宽度。我们 SKU < 10 万，ES 自带的 kNN（底层就是 HNSW）够用，`num_candidates` 是召回候选宽度；**检索排序我做的是 RRF 排名融合，不是余弦重排**——余弦和 BM25 分值量纲不可比，只能按排名融。**余弦 vs 点积**：向量预归一化后等价，所以索引侧用 cosine 打分即可。真到要自己调 ANN 参数的规模，该由专门的向量检索团队维护，不是业务后端维护。」 |
| **traceId 跨服务怎么传** | 拆成两个独立 JVM 后怎么传？ | 「项目是单 JVM 多模块部署，模块间事件驱动走同一 Spring 上下文，traceId 通过 MDC + MQ header 传递；可观测侧已经换成 OTel 桥（原 Zipkin 上报是死链路，已删）。如果拆成多 JVM，就是在服务间 HTTP 客户端加拦截器走 W3C traceparent 标准（OTel / Brave 通用），这套机制是通用的。」 |
| **@TokenBudget 超预算后的告警** | 降级是全局还是按场景？告警推哪里？ | 「`TokenBudgetExceededException` 被全局异常处理捕获，业务侧提示「今日 AI 调用预算已用尽」，流式链路捕获后转 SSE error 事件。**告警目前只在日志 WARN 级别**，接 Alertmanager 推飞书 / 企微是留的 TODO——监控对接每个公司平台不一样，留接口更灵活。」 |
| **模型 rerank（Cross-Encoder）** | 为什么没上？ | 「我做的是 RRF 排名融合（多路召回的排名加权），没接 Cross-Encoder 精排。**排名融合解决「多路信号怎么合」，模型重排解决「候选精排精度」**；现在不做是因为余弦与 BM25 量纲不可比必须先排名融合，而语料规模小、加变量会让归因变模糊。双塔 vs 交叉编码的成本权衡我清楚（先粗后精两段式：召回要快要宽、精排要准要窄），触发条件是分块数上千且 hit@5 触顶而 MRR 偏低。」 |
| **faithfulness / 自评偏差** | Judge 的局限怎么处理？ | 「门禁是『均分 + 评审覆盖率』双判——覆盖率门禁就是防『评审大面积失败时均分退化成幸存者平均』。**局限仍在**：Judge 与生成同模型的自评偏差、顺序 / 长度偏差未根治；faithfulness（答案与检索内容一致性）客观指标是演进项。另外我给自己定了条纪律：**Judge 分数只作回归门禁，不作对外质量证据**，对外用机械可算指标或使用侧采纳率。缓解方向是换更强 Judge（场景路由已支持）+ 人工抽检。」 |
| **PIT 全量耗时 / 是否门禁** | 全模块要多久？CI 跑得起吗？ | 「只对 domain 层注入变异，全量跑一遍分钟级，nightly 窗口够用。但**当前 workflow 只对 order 模块跑 PIT、且没设阈值**——它是趋势观察 job 不是门禁，我如实讲；要全量卡门禁得先补 workflow 的阈值参数。」 |
| **学生身份的追问（实习时长 / 学业平衡）** | 能做多久？会不会影响学业？ | 「我是 2025 级软件工程本科，2029 届，目标大三进一线大厂实习。项目是课外按生产标准自驱做的，每周固定投入，学业与项目的时间边界很清楚。」**不要说**「为了找工作」——说「用生产标准自证工程能力」。（**注意口径**：简历与求职文案不写任何学生职务身份。） |
