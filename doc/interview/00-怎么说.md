4. 破防清零 = 出关；出关产出白话讲解并入 [01-怎么答.md](01-怎么答.md) 对应节

### 3.2 1 分钟版 · 模型应用工程师 / AI Agent 方向

> 我做了 EasyOrange 项目，定位是 **Java AI Agent 工程化：生产级标准的 Agent 编排 × RAG 检索增强 × 评估闭环**（项目不对外运营，工程标准对标生产——门禁 / 降级 / 预算 / 可观测机制齐备；实测数字一律以 [工程指标.md](../工程指标.md) 为准，未回填的直接说「待补测」，不报数）。
>
> 核心矛盾：LLM 调用贵且不稳定，必须限流降级 + 可观测 + 预算治理，同时 DDD 铁律要求 domain 层零框架依赖。我的解法是 **AI 基础设施全面框架化为 Spring AI**（[ADR-0008](../adr/0008-ai-spring-ai-framework.md)，Supersedes ADR-0003）——删掉自研 `LlmPort` / `VisionPort` / `CachingLlmAdapter` / `AiMetricsService`，LLM / Embedding 调用点直接注入 Spring AI `ChatModel` / `EmbeddingModel` bean（`chatModel` @Primary DeepSeek / `visionChatModel` Qwen-VL / `embeddingModel` DashScope，统一 OpenAI 兼容线协议）；保留业务级治理：`AiRateLimitInterceptor` Redisson 令牌桶按端点限流、超限返回 429；`TokenBudgetAspect` 前置检查 + `AiModelSupport` 按真实用量记账；Prompt 全部 YAML 版本化（业务 / 对话 / 搜索意图识别分文件，无 Java 硬编码兜底）。**两条 AI 主线链路——卖家「发布助手」（拍照识别单入口：一次产出属性 + 建议价 + 标题/描述，发布路径模型调用从最多 5 次降到 1 次）与买家「对话式找货」（RAG 换语料检索在售资产）——全链路 8 件套工程化**；效果侧还有不依赖 LLM 判分的数字：建议价采纳率（`GET /api/admin/ai/pricing-adoption`）。原「6 个决策点 = 4 个 LLM + 2 个规则引擎」口径保留作演进痕迹（其中的信用画像已于 2026-09-19 随功能下线删除，估值 / 文案入口因与拍照识别重复一并删除）。
>
> RAG 侧我做了**真实检索链路**：商品标题级搜索用 embedding 模型把查询转 1024 维向量，ES 同请求 kNN + BM25（索引侧 `nameEmbedding` best-effort 写入，失败降级 null 不阻塞主链路）；知识库与在售资产两侧是**两路独立召回 + RRF 排名融合**（共用同一份 `RrfFusion`，k=60）——用排名融合而不是分数融合，因为余弦与 BM25 分值量纲不可比；回答带 `[来源:标题]` 引用溯源。SKU < 10 万不引 Milvus，量级分界线讲得清楚。
>
> 质量侧我做了**评估闭环**：每次 LLM 调用落 `eo_ai_call_log`（scope/model/prompt_hash/响应/耗时/成败/token 入出，2026-09-18 起含调用主体 `subject_id`），金标准集（生成 + 检索两类用例）+ `AiJudge` 对照参考打分 + `EvalGate` 门禁（低于基线-0.3 或**评审覆盖率 < 80%** 都卡 build），检索侧跑 hit@5 / MRR 落 `eo_retrieval_metric`——AI 输出好不好从「感觉」变成「可量化、可回归、可卡门禁」。
>
> 编排侧写了**轻量工具编排**（`AiSearchEnhancerAdapter`），基于 Spring AI `ChatModel` 层（只发工具 schema、不托管执行循环）：自然语言查询走 4 路 CompletableFuture 并行（1 路 LLM 意图识别 + 3 路规则：打标签 / 市场分析 / 建议问题生成），整体 5s 超时后保留已完成步骤的部分结果（无单步超时），意图识别一路复用同一套模型 + 限流/预算链路，另三路本地计算零调用。

> **口径提醒（被追问时别说错）**：[01-怎么答.md](01-怎么答.md) §一-53 有完整边界清单——这 4 路是**固定扇出**（四路无条件全提交，模型不参与选路），不是模型自主决定的工具调用；它和对话里的多步工具循环决策是两回事。

### 3.3 1 分钟版 · Java 架构师 / 高级后端方向（已降级为追问储备）

> 我做了 EasyOrange，定位 **LLM × DDD：Java 架构工程化实战**。Maven 多模块全解耦，Port 接口做编译期隔离，ArchUnit 规则在 CI 阶段守住 DDD 分层不被破坏。
>
> 下单链路一致性我选 **本地单事务 + Redisson 分布式锁 + Outbox**，**拒绝 Saga**（见 [ADR-0007](../adr/0007-order-local-tx-over-saga.md)，同样拒绝 2PC/XA/Seata AT/TCC，原由见 [ADR-0001](../adr/0001-order-saga-vs-2pc.md) Superseded）：`OrderCommandHandler.createOrder(CreateOrderCommand)` 按 productId 排序获取分布式锁（key=`eo:order:lock:product:{productId}`，10s 是获取等待超时；持有期由 watchdog 续期、事务提交后释放，锁等待在事务外不占数据库连接）防死锁防超卖 → 事务内创建订单 + 发布 `OrderCreatedEvent`（Outbox 同事务原子）→ `ProductInventoryPort.decreaseStock()` 同步扣库存 → 创建支付记录；任一步失败事务整体回滚，抛 `OrderDomainException`（B3009），**无补偿路径**。取消/退款恢复库存、完成标记售出等跨模块副作用由 `OrderLifecycleEventConsumer` 消费订单生命周期事件异步触发。
>
> 事件驱动可靠性靠三层：① **Spring Modulith Outbox** — 业务表 + `EVENT_PUBLICATION` 表同事务原子写入，崩溃重启自动重发，不丢事件；② **DLQ 三级重试** — 消费失败进 DLQ，`DlqRetryScheduler` 每 5min 扫 + 指数退避 1/5/15min 重投，超过 max 转储 `eo.dlq.terminal` 等人工；③ **幂等** — `EventIdempotencyChecker` Redis SETNX 按 `consumerId:eventType:eventId` 去重，多消费者监听同一事件不阻塞；再加 **全链路 traceId**（HTTP → MDC → @Async → RabbitMQ header → 消费者 MDC）。
>
> 架构治理靠 ADR + ArchUnit + PIT 三板斧：ADR 决策记录每条都记「为什么选 + 拒绝了什么」，ArchUnit CI 阻断违规依赖，PIT 变异测试验证 JaCoCo 行覆盖不是假的。**Maven 多模块 / ADR 决策记录 / Port 接口 / 全量测试，Domain 层 JaCoCo 行覆盖 + 分支覆盖**（PIT 当前只对 order 模块 nightly 跑、不设阈值，是趋势观察 job，不是门禁——被问要说准）。

### 3.4 3 分钟版（深度面 / 让你主动讲项目细节时）

## 四、高频追问应答

### 4.1 模型应用工程师 / AI Agent 方向

**问：为什么框架化到 Spring AI，而不是继续用自研 Port/Adapter？**
> 我做过完整评估（[ADR-0003](../adr/0003-ai-port-adapter-decorator.md) → [ADR-0008](../adr/0008-ai-spring-ai-framework.md) 决策翻转）：
> - ADR-0003 决策时（2025-11）Spring AI 尚未稳定，自研 Port/Adapter + 装饰器是合理选择；Spring AI 稳定版 GA（2026）之后，自研 `LlmPort`/`VisionPort`/`CachingLlmAdapter`/`AiMetricsService` 就成了与框架重复的"手写代码"
> - 项目 STP 规范明确"零新增自定义代码是最优方案——删掉手写代码，换成框架配置即可"，迁移后六个 service 直接注入 `ChatModel`/`EmbeddingModel` bean，供应商切换只需改 `AiModelConfig` 的 baseUrl/apiKey/model
> - `AiSearchEnhancerAdapter` 的 4 路并行编排保留手写（框架黑盒），但意图识别那路 Tool 的 LLM 调用走框架 bean（另三路是本地规则计算）——**编排自己写、模型调用用框架**，两类复杂度各归其位

**问：RAG / 向量检索为什么不用 Milvus / PGVector？**
> （拒绝项第 5 条）量不够——现在 SKU 维度 < 10 万。Milvus/PGVector 引入向量索引构建、ANN 参数调优（HNSW ef_search / nprobe）、运维监控告警一整套东西，ROI 太低。**商品检索**用 ES 自带 kNN：`QueryEmbeddingAdapter` 用 DashScope embedding 服务（1024 维）生成查询向量，索引侧商品名 `nameEmbedding` 由 `ElasticsearchProductSearchIndexAdapter` best-effort 写入（dims=1024 与 ES `dense_vector` 映射对齐）。**三条检索链路（商品检索 / 知识库 / 在售资产）是同一套形态：两路独立召回 + RRF 排名融合**，共用同一份 `RrfFusion`（[ADR-0012](../adr/0012-rag-hybrid-retrieval-rrf.md)）。分界线是数据规模：SKU 到**百万级**、向量索引成为瓶颈时再切独立向量库。

**问：TokenBudget AOP 具体怎么管的？**
> 职责是分开的：`@TokenBudget` 注解加在 3 处调用点上（chat / semantic / auto_listing），`TokenBudgetAspect` 的 `@Around` **只做前置检查**——`累计已用 + maxTokensPerCall > dailyTokenLimit` 就抛 `TokenBudgetExceededException` 走统一降级。**记账不在切面里**，在 `AiModelSupport.recordBudgetUsage`：调用后取 `ChatResponse` 的 usage metadata，**有真实 input/output 就用真实值累加**；供应商确实不回报用量时（embedding 接口不返回 usage、流式未带 `usage`）才退化为场景配置的单次上限——估算值偏高，但比「预算永远为 0、限流静默失效」安全。`application.yaml` 的 `easyorange.ai.budget.scenarios` 可按场景热更新覆盖注解默认值（注解是编译期契约，配置是运行期旋钮）。

**问：AI 调用成本怎么核算？能出成本报表吗？**
> 预算与账本分开讲。**预算侧**：`@TokenBudget` 在 3 处调用点声明日预算（chat / semantic / auto_listing；预算场景键共 5 个，另 2 个 search_enhance / knowledge 只在 yaml 配置、无注解），切面只做前置检查，记账在 `AiModelSupport`——取 `ChatResponse` 的真实 usage，供应商不回报才退化为场景上限估算。**账本侧（2026-09-18 起）**：`eo_ai_call_log` 补了 `token_input` / `token_output` / `subject_id`（调用主体，可空）三列，带 `subjectId` 的 `callText` 重载把「这笔调用属于哪个商品」也落库；新增 `GET /api/admin/ai/cost-report?hours=24` 按场景聚合调用数 / token 入出 / 平均耗时 / 失败数（默认 24h、上限 30 天），按场景的成本排布第一次可查。**报表里为 0 的两类调用**：embedding（供应商不回报 usage）与流式（未带 usage）——记 0 不估算，报表里为 0 不代表不花钱；语义缓存命中率仍无计数器（TD-015）。
> 可讲的成本优化（无实测数字）：① 搜索增强从早期 3 路 LLM 收敛到 1 路 LLM（意图识别）+ 3 路本地规则计算；② 删掉商品事件消费者这条死链路后，不再有每次建/改商品都触发的白烧调用；③ 发布助手收敛为拍照识别单入口——独立估值 / 文案产出的字段拍照识别已一并给出，删除两个重复入口后发布路径模型调用从最多 5 次降到 1 次。

**问：多模态 Vision 调用跟 LLM 是一条链路吗？**
> 是，同一套 Spring AI 链路——`visionChatModel` bean（Qwen-VL `qwen-vl-max`，DashScope compatible-mode 线协议）用 `AiModelSupport.analyzeImages`（多图 Media + `UserMessage.builder`）识别拍照上架图片，`@TokenBudget(scope=AUTO_LISTING)` 单独管预算。**换供应商只改 `AiModelConfig` 的 options**。

**问：搜索增强的 4 路并行是怎么组织的？有 Tool 抽象吗？**
> 有，我把它做成了 **Tool Registry 模式**：`SearchTool<T>` 接口（`name() / description() / kind() / run(context)`），4 个工具由 Spring 自动收集进 `SearchToolRegistry`（构造期防重名冲突，新增工具零改动注册）——**1 路 LLM（意图识别）+ 3 路规则（标签 / 市场分析 / 建议问题）**：
> - `intent_detection`（LLM）— 意图识别，4 路里唯一打模型的一路
> - `product_tagging`（RULE）— 规则引擎打标签，零 LLM 成本亚毫秒
> - `market_analysis`（RULE）— 规则计算在售件数 / 均价 / 价格区间，零 LLM 成本
> - `question_suggestion`（RULE）— 由关键词 + 命中分类 + 价格下限派生追问模板，零 LLM 成本
>
> `AiSearchEnhancerAdapter` 从 Registry 按 name 取工具，4 路 `CompletableFuture` 并行（1 路 LLM + 3 路规则），5s 总超时，单路失败降级不影响整体。`name/description` 对齐 OpenAI Function Calling 的 function name/description 语义——**下一步若要交给模型自主选路，基于它们生成 JSON Schema 即可**。

> ⚠️ **别说成「模型自主调用工具」**：当前是固定扇出，四路无条件全提交，模型不参与选路。被问「哪个工具是模型选的」要如实答「都不选，是代码写死的并行管道」，然后讲清楚它的真实价值在单路降级 / 整体超时 / 降级结果不进缓存。详见 [01-怎么答.md](01-怎么答.md) §一-53。

**问：怎么判断 AI 输出质量？（LLM-as-Judge）**
> 我把「AI 输出质量」从感觉变成了可量化：每次 LLM/Embedding 调用经 `AiCallLogRecorder` 落一条 `eo_ai_call_log`（scope/model/prompt_hash/response/耗时/成功与否），记录失败只告警不阻塞主链路。金标准集（`eval/golden-set.yaml`）+ `AiJudge` 对照参考打分 + `EvalGate` 门禁双判：均分低于「基线 - 容忍度」失败，**评审覆盖率低于下限同样失败**（评审大面积失败时均分只是幸存者平均，1 条打 5 分就能蒙过分数门禁）。**四个阈值全在 `eval/baselines.yaml` 里**（基线 4.0 / 容忍度 0.3 / 覆盖率 0.8 / hit@5 0.5），键缺失是加载期异常而不是悄悄回落到内置默认值——门禁静默放松比加载失败危险；所以「调基线」是改 yaml + 评审，不动 Java。这样 prompt 版本或模型改动后跑一次回归就知道有没有退化。
> 另有**不依赖 LLM 判分**的效果数字：拍照识别给出的建议价随创建请求落 `eo_product.ai_suggested_price`，`GET /api/admin/ai/pricing-adoption` 出采纳率 / ±10% 内 / >30% 偏离分布——采纳率是资产方用脚投票投出来的真实反馈（只做统计，不参与定价逻辑；口径是「建议价被接受的比例」，不等于 AI 估得准，且样本量随真实发布量增长，报数字时必须带样本量）。

**问：RAG 你们现在做到哪一步了？往深做先做什么？**
> 现状（已落地三条线）：**① 商品检索**——一个入口 `GET /api/products/search`，内部两路独立召回（BM25 `multi_match name^3/description` + kNN `nameEmbedding`，查询向量由 `QueryEmbeddingAdapter` 生成 embedding 模型 1024 维）→ RRF 排名融合；**② 知识库完整链路**——文档摄入管线（`KnowledgeIngestionService` 解析→分块 500 字 + overlap 50、切点优先落换行→逐块 embed→ES `knowledge_docs` 索引，best-effort 写入 + 启动补索引重试 PENDING）+ 两路独立召回（kNN num_candidates=100；BM25 title^2/content）→ RRF 排名融合（`RrfFusion`，k=60）→ 回答带 [来源:标题] 引用溯源（`AiChatService`）；**③ 在售资产检索（对话式找货）**——同一套形态换语料：`AssetSourcingService` + `AssetRetrievalPort`（ES 实现做两路独立召回 kNN `nameEmbedding` + BM25，融合共用同一份 `RrfFusion`；两路都过滤 `ONLINE`），引用溯源从客服问答挪到找货这条交易主链路。
> 检索质量有量化：金标准集 15 条检索用例（`scope: retrieval`，gold_doc_ids 引用种子文档 kb-0001~0025 中的目标篇）跑 hit@5 / MRR，逐条落 `eo_retrieval_metric`，`RetrievalEvalScheduler` 每日回归（默认关闭）。语料 23 篇（kb-0004 / kb-0008 随功能下线删除），其中多数是同域干扰文档——语料与 topK 同量级时 hit@5 恒为满分，指标就成了装饰。
> 还没做的是 **模型 rerank**（Cross-Encoder 替代排序融合，双塔 vs 交叉编码的成本权衡我讲得清）——量级不到不需要，触发条件是检索指标下滑或知识库文档量级上涨，诚实标注演进方向。

**问：你的系统支持流式输出吗？设计一个流式问答？**
> **已支持**（AI Playground 页面落地）：`POST /api/ai/chat/stream` 用 SseEmitter + Spring AI `ChatModel.stream(Prompt)`（Flux），事件协议 step（Agent 每步：工具 + 决策理由 + 观察）/ token / sources / done / error，前端 fetch + ReadableStream 逐帧消费（选 fetch 而不是原生 EventSource，因为 EventSource 只支持 GET 且不能带 Authorization 头，我们的鉴权在 localStorage）。
> 设计时解决的工程点：**① 预算兼容**——流式方法在流结束前就返回，`@TokenBudget` AOP 拦不住，`AiChatService` 手动执行同一套预算前置检查，超限 onError 降级；**② 调用日志不缺流**——`AiModelSupport.callTextStream` 阻塞收流后把完整拼接结果落 `eo_ai_call_log`；**③ 引用来源先于正文**——检索结果在生成前就绪，先推 sources 事件让前端先渲染来源区；**④ 断流兜底**——网络异常 onError 推送降级文案，前端展示错误气泡。
> 首字延迟（streaming 首 token 时间）目前未做专项指标采集，是诚实标注的待办。

**问：Agent 记忆 / 多轮对话怎么设计？**
> **已实现**（`AiChatService`，前端 Playground 多轮会话）：**短期记忆** = Redis List 会话窗口（key `eo:chat:session:{sessionId}`，TTL 24h，裁剪到最近 N 轮，`ChatSessionStore`）；**长期记忆** = `eo_user_preference` 用户画像表（跨会话持久，finish 轮带出偏好写入，聊天时注入 prompt）；**推理** = 多步工具循环（手写 ReAct 循环在 `AgentLoopRunner`：每轮把 4 个工具的 JSON Schema 随请求发出做**原生 tool calling**，模型返回「调用哪个工具 + 参数 + 理由」→ 执行 → 观察进下一轮决策上下文，步数上限 5，finish 收敛 → 带引用生成回答）。
> 两个实现细节值得一提：① 工具决策失败（模型故障 / 未返回工具调用 / 参数不可解析）**降级为「按原始问题检索」而不是不检索**——不把决策链路失效伪装成「这题本来就不需要检索」；② 生成时历史按**原始角色**传多消息（`[system, 历史 user/assistant …, 当前 user]`），不压进当前 user 消息，跨轮次前缀稳定才能命中供应商的上下文缓存折扣。
> **循环为什么不交给 `ChatClient` 托管**：`@Tool` 注解只用来生成工具 schema（供应商侧校验 + 参数名锚定），自动执行被绕开——Spring AI 的 `ChatModel.call` 只发请求、原样返回 tool call，于是步数上限 / 循环中途预算检查 / 三口径降级（步数超限、预算耗尽、决策失败）全都显式落在自己的循环里，这正是「生产级」要能讲清楚的部分。

### 4.2 Java 架构师方向

**问：下单为什么不用 Saga？Seata 的 AT/TCC 不是更标准吗？**
> 分两层答——**为什么拒绝 Saga**（决策，见 [ADR-0007](../adr/0007-order-local-tx-over-saga.md)）和 **为什么不用 Seata**（技术对比，原 ADR-0001 结论保留）。
>
> **（一）为什么单库下单不用 Saga**：我们单库部署（MySQL），`OrderCommandHandler.createOrder(CreateOrderCommand)` 一个本地事务（`TransactionTemplate` 显式边界，锁在事务外）就把订单 / 库存扣减（`ProductInventoryPort.decreaseStock`）/ 支付创建 / Outbox 事件全部包进**同一 MySQL 事务**，任一步失败数据库整体回滚——本地事务比 Saga 的最终一致更强、成本更低。Saga 的补偿要么与回滚重复、要么在进程崩溃后无法重建。真正的演进触发条件是 product/payment 模块拆分独立数据源 / 独立部署，那时才重新评估真 Saga / 事务性 Outbox 补偿。
>
> **（二）为什么不用 Seata（知识保留）**：
> ① **Seata AT 模式** 要代理数据源 + undo_log 表 + TC/TM/RM 三角色独立部署，跟我们的 `@ConditionalOnProperty` 降级模式不兼容——RabbitMQ 没了能起应用，Seata TC 挂了直接连不上；
> ② **TCC 模式** 3× try-confirm-cancel 样板代码，每个参与模块都要写 Try/Confirm/Cancel 三个接口，侵入大、维护成本爆炸；
> ③ 我们平台不经手资金，没有 double-spend 风险，本地单事务的强一致性已经覆盖，Seata 强一致 ROI 太低；
> ④ 2PC/XA 需要全局事务协调器、穿透 Port/Adapter 边界、锁等待长——这条理由现在覆盖**整个 Saga 家族**（2PC/XA/Seata AT/TCC/Saga 编排），全都以同样理由被拒绝。

**问：为什么用 RabbitMQ 不用 Kafka？Kafka 不是更标准吗？**
> 这个问题我评估过 5 种 MQ（Rabbit / Kafka / Pulsar / NATS JetStream / Redis Streams），最后按 4 个维度打分选的 Rabbit，不是不知道 Kafka，是场景和成本都没到（见 [ADR-0005](../adr/0005-messaging-rabbitmq.md)）：
> ① **DLQ + 重试（40% 权重）Kafka 不原生**：我们有 `DlqRetryScheduler` 三级重试 + terminal 毒消息转储，RabbitMQ 的队列级 `x-dead-letter-exchange` 是声明式的，两个参数搞定；Kafka 根本没有「死信」概念，消费失败要自己手动发 dlq topic、自己调度器重投、自己配位点提交逻辑，成本翻倍；
> ② **模型（30%）不匹配**：我们是 1 个事件 → **多个独立下游**各消费各的（订单生命周期要恢复库存 / 标记售出、审计要写库、通知要发消息），RabbitMQ 的「Exchange → 多独立队列」是原生的；Kafka 得搞同样多的 consumer group，每个 group 自己维护 offset + 重试，分散难讲还容易出 bug；
> ③ **成本（20%）和运维（10%）失衡**：Kafka 高吞吐优势是百万 msg/s 才显现，我们每天几万条事件，RabbitMQ 单节点 10k msg/s 完全够——杀鸡用牛刀，分区/副本/consumer group lag 带来的运维复杂度是纯负担；
> ④ **兜底方案**：MQ 选型是配置驱动的演进位——ADR-0005 评估过 NATS/Kafka/Pulsar 的替换成本；我早期写过一版 NATS JetStream 双写副本（`@ConditionalOnProperty` 默认关闭），但从未启用属于死代码，收口时删掉了；真到量级变化那天按 ADR 方案接即可，domain/application 层一行不用动。

**问：NATS JetStream 和 Kafka 你们如果真要二选一改哪个？**
> 选 NATS。两个原因：① **DLQ 原生**（`max_deliver + discard policy=dead`，和 Rabbit 的声明式粒度最接近，现有 `DlqRetryScheduler` 最容易迁移）；② **运维最轻**（`NATS JetStream -js` 单容器 50MB 镜像，Kafka KRaft 模式单节点也重得多）。Kafka 的唯一优势是「大众认知广 + 简历好看」，但从「替换成本最低、模型最贴合」的架构视角选，肯定 NATS。

**问：CQRS 为什么只在 4 个模块做，favorite/user 不做？**
> 见 [ADR-0002](../adr/0002-cqrs-scope-4-modules.md)。CQRS 的核心收益是「读多写少 + 查询聚合跨多个聚合根 + 读写模型可以独立优化」。product（读多写少，ES 全文搜索 + 列表聚合）、order（列表页跨 product+payment 聚合）、payment（对账查询独立）、message（会话列表 + 未读数查询维度独立）这 4 个满足条件。
>
> 但这 4 个**深度不同**：product / order 有独立 ReadModel（`product/application/query/readmodel/`、`order/application/query/readmodel/OrderReadModel` + `OrderQueryRepository`），payment / message 只做 **Command/Query Handler 级分离 + 独立查询仓储**（`PaymentQueryRepository`、`MessageQueryRepository`），**没有单独的 ReadModel 类**——核验方式：全仓 `*ReadModel.java` 只存在于 product(5) / order(2)。
>
> 为什么 message 不做 ReadModel、favorite 完全不做？message 的**聊天消息本身读写比 1:1**（用户发一条对方读一条），读模型独立优化的收益接近 0，所以只用 Handler 级分离把「会话列表 / 未读数 / 历史消息」的查询维度独立出来就够了；favorite 收藏列表最多几千条，DB 单表 `WHERE user_id = ?` 加索引够用。CQRS 不是银弹，每个模块都拆 Command/Query Repository 多一倍代码量，收益 < 维护成本就坚决不做。

**问：ArchUnit 具体守了什么？你们 CI 真的能阻断吗？**
> `ArchitectureRulesTest` 的 `@ArchTest` 规则（与 `ArchitectureRulesTest.java` javadoc 同步）：
> 1. `domain` 白名单准入：只允许依赖 JDK + `common`（零框架 / 不依赖 controller / mapper / DTO，合并为 1 条）
> 2. `*CommandHandler` 不能依赖 `*QueryHandler`（CQRS 写侧不依赖读侧）
> 3. `*QueryHandler` 也不能依赖 `*CommandHandler`（CQRS 读侧不依赖写侧）
> 4. 业务模块（order/product/message/favorite）间只能通过 `*.domain.port.*` 和 `*.domain.valueobject.*` 包通信（ACL 端口隔离）
> 5. 每个 `*Port` 接口必须有 `adapter.outbound` 适配器实现（端口必有适配器，白名单已清零）
> 6. 禁止出现 `*.infrastructure.*` 包（统一用 `adapter/outbound/`）
> 7. domain/application 禁止反向依赖 adapter（`FreezingArchRule` 冻结已知历史豁免，其余零例外）
> 8. Controller 禁止直连 `mapper`（必须经由 application 服务）
> 9. 禁止 `System.out` / `System.err`（统一 SLF4J）
> 10. 禁止 `e.printStackTrace()`（统一 SLF4J）
> 11. `domain`/`application` 禁止依赖 `org.springframework.dao`（持久化技术异常必须在 adapter/outbound 内翻译）
> 12. 每个模块领域异常根唯一（直接继承 `BaseBusinessException` 的根类按模块唯一，其余语义走具名工厂）
>
> 测试挂在 `easyorange-application` 模块的 `./mvnw test` 里，CI GitHub Actions 的 backend job 只要失败就红，PR 合不进来，真能阻断。

**问：PIT 变异测试是什么？跟 JaCoCo 区别？**
> JaCoCo 行覆盖只看「代码被执行过没」，不管「测试能不能发现 bug」——把一个 `if (a > 0)` 改成 `if (a >= 0)`，JaCoCo 还是绿的，但实际上逻辑变了。PIT 在编译后的 bytecode 里注入**变异**：比如把 `<` 改成 `<=`、把 `+` 改成 `-`、把 `return x` 改成 `return null`，然后跑现有测试，如果测试还全绿，说明这个变异**没被杀掉（存活）**，对应位置的测试没覆盖到真实逻辑。
>
> 我们只对 domain 层做（聚合根状态机 / 领域服务 / 值对象），**全量跑一遍 domain 变异耗时可控**——各模块 mutation / test strength 数值收口重测后回填（见工程指标 §2.1）。JaCoCo + PIT 互补，避免写「为了覆盖率的空测试」。
>
> **口径要说准**：`pit-mutation.yml` 目前 **nightly 只跑 order 模块、且没传任何 `-Dpit.*Threshold`**，所以它是「趋势观察 job」而不是「门禁」——pom 里的阈值属性默认 0（不阻断），本地要卡门禁得自己传 `-Dpit.mutationThreshold=60 …`。说成「PIT 卡 CI」会被追问打穿。

**问：Outbox 怎么保证事务一致的？崩溃了真的不丢事件？**
> Spring Modulith 的 Outbox 实现在 `org.springframework.modulith:spring-modulith-events-core`，核心就是**同事务双写**：
> 1. 业务 Service 方法 `@Transactional` 里先写业务表（比如 INSERT eo_order）
> 2. 再把 `DomainEvent` 序列化成 JSON 写入 `EVENT_PUBLICATION` 表（事件 ID / 类型 / completion_date = null）——**这两条 SQL 在同一个本地事务里**，要么都成功要么都回滚
> 3. 事务 commit 之后，异步从 `EVENT_PUBLICATION` 表捞 `completion_date is null` 的事件，一条一条发 RabbitMQ，发成功 UPDATE completion_date = NOW()
> 4. 崩溃重启时，`spring.modulith.events.republish-outstanding-events-on-restart=true` 会重新扫所有未完成事件，再发一次
>
> 关键是**至少一次投递** + **消费者幂等**配合：Modulith 保证不丢（可能重复），`EventIdempotencyChecker` 保证重复投递也只处理一次。

### 4.3 通用高频追问

**问：Redisson 分布式锁的 watchdog 到底怎么工作的？你们锁的 leaseTime 设了多少？**
> 我们下单锁在 `DistributedRedissonLockAdapter`，调的是 `lock.tryLock(waitTime, -1, TimeUnit.SECONDS)` 三参版本——**leaseTime 传 -1，由 Redisson watchdog 自动续期**：Redisson 默认锁 30s，后台每 10s（1/3 lease）检查锁是否仍被当前线程持有，是就续期回 30s，保证锁不会在下单流程结束前自动过期。另外锁**释放推迟到事务提交/回滚之后**（`TransactionSynchronization#afterCompletion`）——若提前释放，后一个请求会在前一个事务尚未提交时读到旧库存快照，击穿防超卖（e268c59e 修复）。
> 场景差异：**短事务（我们的下单）用 watchdog（leaseTime=-1）**，不用手工估算锁时长；**明确不想被续期的场景**才传显式 leaseTime。
> 另外两个细节：① 多商品锁按 productId 排序后逐个获取，防 AB-BA 死锁；② 释放时检查 `isHeldByCurrentThread()` 再 unlock，防「锁已过期被他人持有」时误删别人的锁。

**问：EventIdempotencyChecker 幂等为什么用纯 SETNX 就够了？不需要「锁 + done 标记」两级吗？**
> 不需要锁——`SET NX EX` 是**一条原子命令**，同时完成「检查 key 不存在 + 写入 + 设 TTL」，不存在查-写竞态窗口，锁是给多命令序列用的，这里单命令就原子了。key 命名空间 `consumerId:eventType:eventId` 隔离多消费者。两个细节：① 处理**失败**时 `unmark` 撤销标记，让容器重试 / DLQ 重投能重新执行——宁可重试不可漏处理；② 标记 TTL 24h 覆盖 DLQ 三级重试最长窗口，进程在标记后、处理完成前崩溃的残留窗口由业务副作用幂等兜底（库存恢复走流水唯一键，重复投递不再叠加）。

**问：ES 语义搜索怎么做的？为什么不引入 Milvus / PGVector？**
> 先说入口：**没有「语义搜索」这个独立按钮或端点**——就一个搜索框，`keyword` 非空且按相关性排序时自动走两路召回。链路：`QueryEmbeddingAdapter` 用 DashScope embedding 服务（1024 维）把关键词转成查询向量，`ElasticsearchProductSearchQueryAdapter` 把 kNN（字段 `nameEmbedding`）与 BM25 `multi_match` **各查一次**（候选池 `max(100, page*size*2)`，`num_candidates` 取 `max(100, 2k)`——ES 会直接拒收 `num_candidates < k`），再用 `RrfFusion`（k=60）按**排名**融合；同请求里「knn + query」不行，ES 会把两路分数内部合成一个分值、拿不到各自排名，而余弦相似度与 BM25 分值是不同量纲，只有排名能融。融合后可以照常叠 AI 增强（意图识别走 LLM，标签 / 市场分析 / 追问由本地规则计算，`AiSearchEnhancerAdapter`）。为什么不用独立向量库？——SKU < 10 万，ES 自带 kNN + HNSW 索引完全够，Milvus / PGVector 引入向量索引构建 + ANN 调参 + 运维监控一整套东西，ROI 太低。真正的分界线是数据规模：SKU 到百万级、向量索引成为瓶颈时再切独立向量库。
> 两个容易被追问的取舍：**显式排序退化为单路**（用户点「价格从低到高」时融合排名会和点选的排序打架，所以只走 BM25 并保留 ES 侧排序）；**`total` 取 BM25 路的总命中**（唯一有全量语义的口径），只有词面命中为 0 而语义路召回到结果时才改报候选池大小——否则前端会出现「共找到 0 件商品」却列着 20 张卡。

**问：令牌桶和固定窗口的差异具体在哪？你们的 RRateLimiter 参数怎么定的？**
> 固定窗口（`increment+expire`）的问题：窗口边界突刺——59:59 用满 30 次，00:01 又能用 30 次，1 秒内理论上能打 60 次；且原子性缺口（increment 和 expire 两条命令非原子，需要 Lua）。Redisson `RRateLimiter` 是真正按「rate/interval 令牌补充速率」的令牌桶：`tryAcquire` 按补充速率发放，无边界突刺。我们按端点配 5-60 次/分（`AiRateLimitInterceptor` 表，最低 auto-listing 5、最高 knowledge 60），配置在 `AiCallScope` 枚举 + yaml；Redis 不可用时 fail-open 直接放行——限流是保护手段，不能成为可用性单点。

**问：Flyway 你们怎么演进的？只有初始脚本吗？**
> 不是。项目有过真实演进：`V1__init_schema.sql` 是开发阶段三次合并后的单文件完整 DDL（V1~V6、V1~V9、V2~V7 收口）——折叠过删表迁移（遗留幂等键表）、删列迁移、加列迁移，并入库存流水表、枚举码完整性修正与 AI 观测/知识库/画像表；每次收口后又按功能正常递增过一轮（收藏价格快照、任务扫描索引、库存流水、AI 用量列等）。约定：**禁止修改已执行的迁移脚本**（上线后），新增按 V{N+1} 递增；DDL 用 MySQL 原生 INPLACE 算法（非阻塞在线执行）；新增字段必须可空或有默认值。开发阶段合并迁移是项目未上线、无生产历史时的合理操作，上线后绝对禁止。

**问：性能数据？压测过吗？**
> 压过。k6 50 VUs × 30s 混合只读流量（列表 60% + 分类 20% + 搜索 20%），本地单实例开发栈：**QPS / p99 数值收口重测后回填**（详见工程指标 §2.3），量级远低于脚本阈值（p95<500ms）。另外做过限流开关对比：默认限流（200 次/60s/IP）下同参数压测返回 **429 而非 500**，证明限流器真实生效、后端零错误。写路径（下单 + 分布式锁）压测还没做，k6 脚本已就位（order-create.js），是收口待办。

**被问「业务复杂度这么低有意义吗？」（防守型话术）**
> 我同意业务本身不是重点——我特意选了 C2C 资产流转做载体，因为它刚好能完整展示 DDD 的 4 个核心聚合根（Product / Order / Payment / User）、跨模块一致性架构决策（拒绝 Saga → 本地单事务 + 分布式锁 + Outbox）、读多写少场景（CQRS）、实时通信（WebSocket）这几个架构模式。**如果业务做复杂了，比如再加议价 / 阶梯降价 / 优惠券，状态机就有几十种转换，面试时间根本讲不完**，反而侵蚀 DDD/AI 工程化的主线叙事。
>
> 真正的复杂度我刻意放在架构与 AI 工程化上：Maven 多模块 + Port 接口编译期隔离 / 拒绝 Saga 的 ADR 决策 / Outbox + DLQ 三级重试 / traceId 全链路 / LLM 调用 8 件套工程化 + ADR+ArchUnit+PIT 治理三板斧，这些才是 Java 后端 / AI Agent 岗真正关心的。

|---|---|---|
| **LangChain4j / Spring AI 源码细节** | 你是不是真的读过这俩框架源码？Tool 反射调用怎么走？ | 「我没有深入到 Spring AI 的 Bean 注册源码。工具 schema 这一层两家是一致的——LangChain4j 的 `@Tool` 和 Spring AI 的 `@Tool` 都是**运行时反射**生成 JSON Schema（LangChain4j 官方文档明说参数名靠反射取、编译要加 `-parameters`），所以「谁反射谁不反射」不是差异点，我也不拿它当理由。我真正在意的是**循环控制权**：两家都提供托管的工具执行循环（LangChain4j AI Services / Spring AI `ChatClient` 的 ToolCallingAdvisor），一旦托管，步数上限、循环中途的预算检查、按终止原因分类的降级就插不进去。所以 agent 侧我只用 `ChatModel` 这一层——把 schema 发出去、原样收回 tool call，执行与循环留在 `AgentLoopRunner`。选 Spring AI 而不是 LangChain4j 是 Spring 原生决定的（`ChatModel` 是 bean、自动装配、Micrometer Observation 直连 Langfuse），符合项目的标准 API 优先原则。」 |
| **Seata TC/TM/RM 部署模式** | Seata 三种模式的区别？TC Server 高可用怎么做？ | 「我没有在生产环境跑过 Seata 集群，评估阶段看的是官方文档和社区踩坑帖——AT 模式的核心问题是 undo_log + 全局锁的性能开销，跟我们的本地单事务 + Outbox 比，写路径成本和中间件依赖都高一截；而且我们的 `@ConditionalOnProperty` 降级模式要求 Seata TC 挂了也能起应用，TC 是单点做不到，所以没深入部署细节。」 |
| **HNSW / IVF 向量索引原理** | HNSW 的 M / efConstruction 参数？余弦相似度和点积区别？ | 「我对向量检索原理主要是调研阶段的理解——HNSW 是分层可导航小世界图，M 控制每层邻居数，efConstruction 控制建图探索宽度。我们 SKU < 10 万，规模上 ES 自带的 kNN（底层就是 HNSW）够用，`num_candidates=100` 是召回候选宽度；**检索排序我做的是 RRF 排名融合，不是余弦重排**——余弦和 BM25 分值量纲不可比，只能按排名融（ADR-0012 记录了为什么删掉原先那版余弦重排）。真到需要自己调 ANN 参数的规模，该上专门的向量团队维护 Milvus，不是业务后端 Java 工程师维护。**余弦 vs 点积**：向量预归一化后两者等价，所以 ES 索引侧用 cosine 打分即可。」 |
| **PIT 变异测试全量耗时** | 全模块 PIT 要多久？CI 里跑得起吗？ | 「目前只对 domain 层注入变异，全量跑一遍是分钟级，nightly 窗口够用。但**当前 CI 只对 order 模块跑 PIT、且没设阈值**——它是趋势观察 job 不是门禁，我如实讲；要全量卡门禁得先补 workflow 里的 `-Dpit.*Threshold`。」 |
| **traceId 跨服务怎么传** | 用户服务和订单服务拆成两个独立 JVM，traceId 怎么传？ | 「目前 EasyOrange 是单 JVM 多 Maven 模块部署，模块间事件驱动走同一 Spring 上下文，所以 Brave `TracingFilter` 提取的 traceId 能通过 `EventMetadataMessagePostProcessor` 注入 message header，消费者端再 decode 回 MDC。如果拆成多 JVM 微服务，就是在服务间 HTTP 客户端加拦截器，把 traceId 放到 `X-B3-TraceId` 请求头，走 Brave / OpenTelemetry 的标准 W3C traceparent——这套机制是通用的。」 |
| **@TokenBudget 超预算后怎么降级** | 降级是全局开关还是按场景开关？告警推到哪里？ | 「`TokenBudgetExceededException` 被 `GlobalExceptionHandler` 捕，业务侧提示「今日 AI 调用预算已用尽」；流式链路捕获后转 SSE error 事件。告警目前只在业务日志 WARN 级别，下一阶段打算接 Prometheus Alertmanager 推飞书/企微——这是故意留的 TODO，因为监控对接每个公司平台不一样，留接口更灵活。」 |
| **MySQL 到底用了哪些新特性** | 用的版本跟上一代有什么区别？InnoDB 变更？ | 「项目里用的是 MySQL 的稳定能力——窗口函数在对账统计里用、CTE WITH 递归在商品分类树里用。选型主要看**生命周期**（官方标注的 Innovation LTS 比上一代 EOL 更长），没有用版本特有的新语法，避免刚上线就遇到 EOL 升级压力。」 |
| **模型 rerank（Reranker）** | 为什么没上 Cross-Encoder？ | 「我做的是 RRF 排名融合（两路召回排名加权），没接 Cross-Encoder 模型重排。排名融合解决『多路信号怎么合』，模型重排解决『候选精排精度』；现在用 RRF 是因为余弦与 BM25 分值量纲不可比，且语料只有 23 篇、指标刚恢复判别力，加变量会让归因变模糊。Cross-Encoder 与 Bi-Encoder 的区别我清楚（交叉编码精度高、成本高，先粗后精两段式），触发条件是分块上千且 hit@5 触顶而 MRR 偏低。」 |
| **faithfulness / 自评偏差** | Judge 的局限你怎么处理？ | 「已落地的门禁是『均分 + 评审覆盖率』双判——覆盖率门禁就是防『评审大面积失败时均分退化成幸存者平均』。**局限仍在**：Judge 与生成同模型的自评偏差、顺序/长度偏差未根治；faithfulness（答案与检索内容一致性）客观指标是演进项。缓解方向是换更强的 Judge 模型（场景路由已支持，改配置即可）+ 人工抽检。」 |

### 6.2 已转「实答」的（别再当盲区绕）

以下四项早期是盲区，现已落地，**照实答即可，不要再用旧口径说「刻意不做」**：

| 主题 | 现状 |
|---|---|
| RAG 分块与检索指标 | ✅ 分块（500+overlap50、切点优先换行）+ 种子知识库 23 篇（含同域干扰）+ 两路召回 + RRF 融合 + 引用溯源（知识库与在售资产检索共用同一份 `RrfFusion`）；hit@5/MRR 落 `eo_retrieval_metric`。可展开 `KnowledgeIngestionService.chunkContent` 与 `GoldenSetEvaluator` 的 MRR 计算 |
| 流式输出（SSE） | ✅ `SseEmitter` + `ChatModel.stream`，事件协议 step/token/sources/done/error（step = Agent 每步的工具 + 决策理由 + 观察，前端步骤可视化）；预算手动前置检查；流式调用照常落日志。可展开「为什么 fetch+ReadableStream 而不是 EventSource」 |
| Agent 记忆 / 多轮对话 | ✅ Redis 会话窗口（短期）+ 画像表（长期）+ 多步工具循环（原生 tool calling）。可展开裁剪策略（最近 N 轮 + TTL 24h + token 级二次裁剪）、偏好提取（finish 轮参数带出）、记忆 fail-open |
| 评测集构建 / 门禁 | ✅ 金标准集 + Judge 对照参考打分 + `EvalGate` 双门禁 + 反馈飞轮自动扩充。可展开门禁怎么接 CI、覆盖率门禁为什么必要、基线怎么维护 |

> 补充：「首字延迟专项指标」与多步循环的三口径数字（平均步数 / 降级率 / 步级延迟 p95，待真实 key 跑量回填）仍是**明确标注的待补项**，主动说比被问出来好。

> **通用绕法公式**：「我没有深入到 X 的源码/生产部署，但评估时我关注的关键点是___，最后做出的取舍是___，所以这块我就没深入到那个程度——如果真到了那个场景，我会按___的思路去做。」→ **诚实展示思考过程 > 硬背不知道的细节**。
