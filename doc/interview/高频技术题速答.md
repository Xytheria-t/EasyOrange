## 一、Java 并发

### 1. volatile 和 synchronized 的区别？
volatile 保证**可见性 + 有序性**（禁指令重排），不保证原子性；synchronized 保证原子性 + 可见性 + 有序性。volatile 适合「一写多读」标志位（如 `AiModelSupport` 的静态 recorder 引用用的 `static volatile`——写发生在启动阶段，读在多线程调用点，volatile 保证所有线程看到最新引用）。

### 2. 线程池参数怎么定？拒绝策略有哪些？
核心参数：corePoolSize / maxPoolSize / workQueue / keepAlive / 线程工厂 / 拒绝策略。队列满 → 扩到 max → 触发拒绝策略（Abort / CallerRuns / Discard / DiscardOldest）。
✔ 项目结合：Java 21+ 后**项目统一用虚拟线程**（`ForkJoinPool.commonPool()` 跑 4 路 LLM 并行），不用自定义线程池——虚拟线程轻量到可以每任务一个，线程池调参问题被语言特性消除；唯一保留的池是 `taskScheduler`（`MdcTaskDecorator` 做 MDC 透传，poolSize=5）。

### 3. ⚠ 虚拟线程了解吗？跟平台线程什么区别？
虚拟线程是 JVM 调度的轻量线程（JDK 21 正式版），挂起时释放 carrier 线程，阻塞操作不再浪费内核线程；IO 密集型场景吞吐提升显著，CPU 密集无提升。适用：高并发 IO（Web 请求、LLM 调用、JDBC 调用）。
✔ 项目结合：Spring Boot 4 默认虚拟线程（`spring.threads.virtual.enabled=true`），`@Async` 消费者跑在虚拟线程；`AiSearchEnhancerAdapter` 4 路并行用 commonPool 的虚拟线程，`cancel(false)` 避免中断虚拟线程 carrier。
⚠ 易翻车点：虚拟线程不解决 CPU 密集问题；`synchronized` 在虚拟线程下会 pin carrier（JDK 24 已修复 pinning）；慎用 `ThreadLocal` 在长时间虚拟线程上（项目用 MDC 快照 + 清理兜底）。

### 4. ConcurrentHashMap 原理？
JDK 8+：数组 + 链表/红黑树 + **CAS + synchronized（锁桶头节点）**，`size()` 用 baseCount + CounterCell 分散计数，扩容多线程协助迁移。与 Hashtable（全局锁）和 HashMap（线程不安全）对比。
✔ 项目结合：`InMemoryTokenBudgetStore` 用 `ConcurrentHashMap` + `AtomicReference` 做日预算记账（跨日重置），跨日重置的原子性由 `compute` 保证。

### 5. ThreadLocal 会内存泄漏吗？
key 是弱引用，value 是强引用——线程池复用线程时，value 可能残留。规范：**用完 remove()**。
✔ 项目结合：MDC 是 ThreadLocal 实现的——`MdcTaskDecorator` 在主线程快照 MDC 复制到子线程，子线程 `finally` 里 `MDC.clear()` 防线程池复用泄漏；虚拟线程场景 Micrometer Tracing 自动注入。

### 6. CompletableFuture 怎么用的？超时怎么处理？
`supplyAsync` 提交任务，`allOf().get(timeout)` 聚合等待，`getNow` 拿已完成结果，`cancel(false)` 取消。
✔ 项目结合：`AiSearchEnhancerAdapter`——4 路 `CompletableFuture`（意图/标签/市场/问题）并行，5s 总超时，超时后收集已完成部分返回（intent 或 tags 任一有值即可用），`cancel(false)` 不中断虚拟线程 carrier。

## 二、JVM

### 7. 运行时数据区？
线程共享：堆（对象）、方法区/元空间（类元数据，JDK 8+ 本地内存）。线程私有：虚拟机栈（栈帧/局部变量表）、本地方法栈、程序计数器。
✔ 项目结合：无直接关系，但答完可以补一句「项目配了堆内存 + 优雅停机 + 健康检查（actuator），生产扩容靠水平扩展」。

### 8. ⚠ GC 算法和收集器？你们用哪个？
标记-清除 / 标记-复制 / 标记-整理；收集器演进：Serial → Parallel → CMS → G1（JDK 9 默认）→ ZGC（低延迟，JDK 21 支持分代 ZGC）。
✔ 项目结合：Java 25 默认 G1；压测实测 50 VU 只读接口 640 QPS、p99 13ms，JVM 指标（GC/堆）经 Prometheus 采集。答完补一句「GC 调优不是目标，先看对象分配模式」。
⚠ 易翻车点：别背 CMS 细节——G1 的 Region/可预测停顿、ZGC 的染色指针和「停顿与堆大小无关」是加分点。

### 9. 类加载机制？双亲委派为什么？
加载 → 验证 → 准备 → 解析 → 初始化；双亲委派：子加载器先委托父加载器，避免核心类被篡改（`java.lang.String` 只能由 Bootstrap 加载）。
✔ 项目结合：Spring Boot fat jar 用 **LaunchedURLClassLoader** 打破双亲委派加载嵌套 jar（BOOT-INF/classes + BOOT-INF/lib）——这是个不错的加分细节。

### 10. 线上 CPU 100% / 内存泄漏怎么排查？
CPU：`top` 找进程 → `top -Hp` 找线程 → `jstack` 转线程栈 → 定位业务线程；内存：`jmap -dump` 堆转储 + MAT 分析大对象/支配树，或 arthas `dashboard`/`heap`。
✔ 项目结合：`SlowSqlInterceptor`（MyBatis Executor 拦截器，500ms 阈值）上报慢 SQL 到 Micrometer Timer（`easyorange.sql.execution`/`easyorange.sql.slow`）——慢 SQL 是 CPU/内存问题的第一嫌疑，先用指标定位再用 jstack/jmap 深挖。

## 三、Spring / Spring Boot

### 11. IoC / AOP 原理？
IoC：BeanFactory 管理对象生命周期 + 依赖注入，解决对象创建与装配的解耦；AOP：动态代理（JDK 代理接口 / CGLIB 代理类）+ 切点/通知/织入。
✔ 项目结合：`TokenBudgetAspect`（@Around 注解切面，预算检查+记账）、`AuditLogAspect`（写操作审计，事件化 Outbox 入库）。

### 12. ⚠ @Transactional 什么时候失效？这是必问题。
8 大场景：① 同类内部调用（this 调用不走代理）② 方法非 public ③ 异常被吞/被 catch ④ 抛检查异常（默认不回滚，需 rollbackFor）⑤ 传播行为错配（REQUIRES_NEW 内层提交）⑥ 数据源不支持 ⑦ 多线程线程内事务不共享 ⑧ 动态代理没生效。
✔ 项目结合：下单链路 `OrderCommandHandler.handle(CreateOrderCommand)` 显式 `@Transactional(rollbackFor = Exception.class)`——**rollbackFor 明确声明**正是踩过「检查异常不回滚」的坑后的写法；消费者侧异步处理不走事务注解，靠 EventConsumerHandler + DLQ 兜底。

### 13. Spring Boot 自动装配原理？
`@SpringBootApplication` = 配置类 + 组件扫描 + `@EnableAutoConfiguration`；`AutoConfiguration.imports` 加载自动配置类 → `@ConditionalOnXxx` 按条件装配。
✔ 项目结合：framework 模块所有配置类用 `@AutoConfiguration` + 注册进 `AutoConfiguration.imports`（不依赖隐式 ComponentScan）；`@ConditionalOnProperty(matchIfMissing=true)` 控制 RabbitMQ/ES 可选依赖——换实现只改条件配置。

### 14. Spring Security 认证流程？（本项目就是标准实现）
过滤器链：`AuthenticationFilter`（内置）→ `JwtDecoder` 验签（Nimbus）+ issuer → `JwtAuthenticationConverter` 构造 `AuthUser` → SecurityContext；授权走 `@PreAuthorize("hasRole('ADMIN')")`。
✔ 项目结合：双 Token——Access JWT（RSA 2048 签名，30min，内存）+ Refresh opaque（Redis SHA-256，HttpOnly Cookie，轮换 + 复用检测）；TokenRevocationFilter 做黑名单吊销，与 JwtDecoder 职责分离（密码学 vs 吊销状态）；STP 原则：**不手写 JWT 工具类和 Filter，全部用 oauth2ResourceServer() 标准配置**。

### 15. 循环依赖怎么解决？
构造器注入循环依赖**直接报错**（设计问题），字段/setter 注入可用三级缓存解决。
✔ 项目结合：踩过真实的坑——`RateLimitFilter` 直接注入 `List<HandlerMapping>` 触发循环依赖（WebSocket 配置链），改为 `ObjectProvider<List<HandlerMapping>>` 延迟解析打破循环。

## 四、MySQL

### 16. 索引原理？为什么 B+ 树？
B+ 树：多叉平衡树，非叶子只存索引（扇出高、层数低），叶子存数据 + 双向链表（范围查询友好）；相比 B 树全表数据只出现在叶子。
✔ 项目结合：`eo_order` 按 buyer_id/seller_id/status 建索引；慢 SQL 由 `SlowSqlInterceptor` 监控。

### 17. 索引失效场景？
最左前缀不满足、隐式类型转换、对索引列做函数/运算、LIKE '%xx' 前置通配、or 有一侧无索引、NOT IN/!=（部分优化器行为）。
✔ 项目结合：曾修复过 `CategoryMapper.countProductsByCategoryIds` 的 `IN (${ids})` 拼接——改 `<foreach>` + `#{}` 参数化，**既防 SQL 注入又保证查询计划缓存命中**（项目踩坑警示之一）。

### 18. 事务隔离级别？脏读/幻读？
读未提交（脏读）/ 读已提交（不可重复读）/ 可重复读（幻读，MVCC 解决普通快照读）/ 串行化。MySQL 默认可重复读 + 间隙锁解决幻读（当前读）。
✔ 项目结合：默认 RR 未改；项目一致性靠「本地事务 + 分布式锁」而非调隔离级别——锁已经在业务层解决了并发，DB 隔离级别保持默认即可（调级别是治标，业务锁才是治本）。

### 19. MVCC 原理？
undo log 版本链 + 隐藏列（trx_id / roll_pointer）+ ReadView（活跃事务列表），快照读基于可见性判断。当前读（for update/insert/update）走当前版本 + 锁。

### 20. 慢 SQL 怎么优化？（结合项目）
执行计划 EXPLAIN（type/rows/Extra）→ 索引优化 → 覆盖索引/索引下推 → 分批/分页优化（深分页用游标/id 定位）→ 读写分离/缓存。
✔ 项目结合：三层兜底——① 业务层：多级缓存（L1 Caffeine + L2 Redis + 负缓存）拦热点读；② 监控层：`SlowSqlInterceptor` 500ms 阈值上报 `easyorange.sql.slow` Timer；③ 数据层：覆盖索引 + 参数化查询。

## 五、Redis

### 21. 数据类型和底层结构？
String（SDS）/ List（quicklist）/ Hash（listpack/hashtable）/ Set（intset/hashtable）/ ZSet（skiplist + dict）；还有 Bitmap/HyperLogLog/Geo/Stream。

### 22. 缓存穿透/击穿/雪崩？（项目三层全做了）
穿透=查不存在（负缓存 NullValue 哨兵 30s）；击穿=热点 key 过期瞬间（Caffeine 单飞 + Redisson 跨节点锁 fail-open）；雪崩=大面积同时过期（TTL 配平 + 错峰）。
✔ 项目结合：`MultiLevelCache` 三防齐备：`l1Ttl <= l2Ttl` 构造期强制校验（L1 先过期杜绝 L2 已死 L1 仍新的窗口）+ 负缓存哨兵 + 原子单飞回源 + `easyorange.cache.requests{result}` 指标可观测。**布隆过滤器被刻意删除**（2026-07-31）——负缓存 30s 已覆盖穿透场景，Bloom 是过度设计（这个拒绝过程比堆功能更能加分）。

### 23. 持久化 RDB / AOF？
RDB 快照（fork + copy-on-write，全量，重启快）；AOF 追加日志（everysec/always，可重写压缩）。生产一般两者都开（AOF everysec 兜底）。

### 24. 分布式锁怎么做？（项目就是 Redisson）
SETNX + 过期时间（防死锁）+ 唯一 value（防误删）+ Lua 释放（原子性）。
✔ 项目结合：直接说「手写 SETNX 方案我评估过，最后用 Redisson RLock 三参 tryLock（10s 租约）」，因为 Redisson 补了：watchdog 续期（不传 lease 时）、可重入、公平锁、红锁（不需要，单点场景）；释放前 `isHeldByCurrentThread()` 检查。**为什么锁内做幂等**——见 EventIdempotencyChecker：锁保证「查-写」原子，纯 SETNX 有竞态窗口。

### 25. ⚠ 缓存一致性怎么保证？（双写一致性）
主流：Cache Aside + 先更新 DB 再删缓存 + 延迟双删/订阅 binlog（canal）。**读写并发下删缓存与写 DB 的竞态**是核心难点。
✔ 项目结合：多级缓存场景——`MultiLevelCache.evict()` 清 L1+L2 并经 **Redis Pub/Sub 广播**让其他节点清 L1（`CacheInvalidationListener`）；「回源填充不广播」——填的是新值，广播只针对陈旧值驱逐。答完补一句「强一致要上分布式锁 + 版本号，业务判断可接受最终一致才用缓存」。

### 26. 过期删除策略？
惰性删除（读时删）+ 定期删除（抽样）+ 内存淘汰（LRU/LFU/random/TTL 等 8 种）。

## 六、消息队列（RabbitMQ）

### 27. 消息怎么保证不丢失？（项目三层全做了）
生产端：confirm 模式（确认机制）；Broker：持久化（exchange/queue/message）；消费端：手动 ack + 重试。
✔ 项目结合：**Outbox 模式**是「业务事务与消息发送一致性」的正解——Spring Modulith 把事件同事务写入 `EVENT_PUBLICATION` 表，事务提交后异步外发，发送成功才写 completion_date；**崩溃重启自动重发未完成事件**（`republish-outstanding-events-on-restart`）。这比 confirm 更靠前：confirm 只保证「Broker 收到了」，Outbox 保证「业务成功 = 消息必发」。

### 28. 消息重复消费怎么解决？（项目就是标准答案）
消费端幂等。✔ 项目结合：`EventIdempotencyChecker`——Redisson 锁内「查 done 标记 → 写标记」原子操作，done 标记 24h TTL 覆盖重试窗口；异常时返回 true 宁可漏不可重（重复恢复库存是事故）。「at-least-once + 幂等 = exactly-once 效果」。

### 29. 消息积压怎么处理？
定位：队列堆积指标；处理：紧急扩容消费者 + 临时表/新队列迁移 + 定位消费慢根因（慢 SQL、下游阻塞）。✔ 项目结合：10 个消费者独占队列 + `EventMetricsService` 上报 `easyorange.events.received` 指标，积压可从指标看趋势；消费异常进 DLQ 不阻塞主队列。

### 30. 顺序消息？
RabbitMQ 天然无序（多消费者并发）；方案：单队列单消费者 / 一致性 hash 按业务 key 路由 / 客户端本地排序。
✔ 项目结合：项目**不保证跨事件顺序**——订单生命周期各事件独立处理（恢复库存/标记售出互不依赖），顺序性由业务状态机守卫（非法转换直接拒绝），这是「用领域规则替代消息顺序」的架构取舍。

### 31. RabbitMQ vs Kafka？（项目 ADR-0005 有完整评分）
4 维度：DLQ+重试（Rabbit 声明式 x-dead-letter-exchange 原生，Kafka 无死信概念）、模型（1 事件 → 多独立下游，Rabbit Exchange→多队列原生；Kafka 需多 consumer group 各维护 offset）、成本（日几万事件用不到 Kafka 百万级吞吐）、运维。**拒绝 Kafka/Pulsar/NATS/Redis Streams 的理由全部记录在 ADR-0005**——备选实现 NATS 已评估（DLQ 原生 max_deliver + dead policy）。

## 七、分布式 / 一致性

### 32. CAP / BASE？
CAP：一致性/可用性/分区容错三选二（网络分区必然存在，实际是 CP vs AP）；BASE：基本可用 + 软状态 + 最终一致。
✔ 项目结合：下单链路「本地事务 = CP（强一致），事件副作用 = BASE（最终一致）」——同一个业务两种语义分层，这是分布式设计的基本功。

### 33. ⚠ 分布式事务方案对比？（项目的核心叙事）
2PC/XA（协调者阻塞、长锁）、Seata AT（undo_log + TC 全局锁，代理数据源）、TCC（3× try/confirm/cancel 样板）、Saga（补偿编排）、本地消息表/Outbox。
✔ 项目结合：**全家族被拒**（ADR-0001 → ADR-0007）：单库场景本地事务 + 分布式锁 + Outbox 比 Saga 更强（Saga 补偿与回滚重复、崩溃后失败状态丢失）；Seata TC 单点与 fail-open 降级模式冲突；TCC 侵入大；触发演进条件：product/payment 拆独立数据源时再上真 Saga。

### 34. 幂等设计怎么做？
唯一键约束（DB unique index）、状态机幂等（已处理状态拒绝重复）、token/防重表、Redis SETNX。
✔ 项目结合：项目有**三层幂等**：① `IdempotencyKeyFilter` 协议级幂等（客户端 Idempotency-Key 头，缓存 24h 成功响应，字节级回放）② `RateLimitFilter` 防连点（3s 窗口，IP+URI+body hash）③ `EventIdempotencyChecker` 事件消费幂等。三层职责：防重放 / 防连点 / 防重复消费。

### 35. 分布式 ID？
雪花（时间+机器+序列）、UUID v7（时间有序）、美团 Leaf/滴滴 Tinyid。
✔ 项目结合：**UUID v7（RFC 9562）**——48 位毫秒时间戳 + 版本 + 随机后缀，**时间有序**（DB 索引友好，B+ 树局部性）+ 零配置零依赖；曾在 Snowflake 与 v7 间选择，v7 砍掉 workerId 分配/时钟回拨处理，代码量最小。全库 36 位 String ID + `IdType.INPUT`。

### 36. 限流算法？（项目令牌桶）
固定窗口（边界突刺+非原子）、滑动窗口（内存大）、漏桶（恒定速率，无法突发）、令牌桶（允许突发 + 平滑速率，业界主流）。
✔ 项目结合：Redisson `RRateLimiter` 令牌桶替代 increment+expire（原子化取桶/补桶）；两处限流：`RateLimitFilter`（全站 GET 200次/分/IP 本地 + 写操作 30次/分/IP Redis 分布式 + 3s 防重）+ `AiRateLimitInterceptor`（AI 端点按场景 5-30 次/分 + stale 降级）。Redis 挂了 fail-open（限流是保护不是单点）。

### 37. 熔断 / 降级？
熔断：失败率超阈值开闸（OPEN）→ 半开探测恢复（HALF_OPEN）→ 恢复 CLOSE。降级：超时降级/返回默认值/本地兜底。
✔ 项目结合：`Resilience4jConfig` 的 CircuitBreakerRegistry（COUNT_BASED 窗口 10、失败率 50%、开 60s、半开 3 次探测）包 Redis 缓存操作（记录 RedisConnectionFailureException/QueryTimeoutException），失败降级 DB 直查。AI 侧：**重试/并发隔离由 Spring AI 客户端内置**（openai-java MAX_RETRIES=2 + 连接池），自研 Bulkhead 已删（ADR-0008 框架化）。

### 38. 分布式链路追踪？（项目 traceId 全链路）
✔ 项目结合：Brave `TracingFilter` 从 HTTP 头提取 traceId → MDC → `MdcTaskDecorator` 透传 @Async → `EventMetadataMessagePostProcessor` 注入 RabbitMQ header → 消费者 `EventMetadata.from` 解码回 MDC → 日志 + Micrometer 指标统一关联。**单 JVM 多模块场景** traceId 跨进程边界只在 MQ 头传递；拆多 JVM 时走 W3C traceparent 标准（Brave/OTel 通用）。

## 八、DDD / 架构

### 39. DDD 和传统 MVC 分层区别？
MVC 按技术切（Controller/Service/DAO），业务规则散落 Service；DDD 按领域切（domain/application/adapter），**业务不变量下沉聚合根**，领域层零框架依赖，依赖方向单向向内。
✔ 项目结合：四层（aggregate/application/port/adapter）+ 11 模块 + 35 Port 编译期隔离 + ArchUnit 10 条规则 CI 守卫（domain 零 Spring 依赖、CQRS 读写隔离、业务模块只经 port/valueobject 通信、端口必有适配器、禁 infrastructure 包、domain/application 不反向依赖 adapter、Controller 不直连 mapper、禁 System.out）。

### 40. 聚合根 / 实体 / 值对象区别？
聚合根：聚合的入口 + 不变量守卫（Order/Product/User）；实体：有 ID 可变的业务对象（ProductDetail）；值对象：按值等价不可变（Money/Phone/OrderId）。
✔ 项目结合：**只对「有规则的字段」做 VO**（ID 语义、金额精度、手机号格式），不每字段包一层——避免 ceremony（DDD-核心思想轻量落地 §2 有完整取舍清单）。

### 41. CQRS 什么时候用？（项目 ADR-0002）
读多写少 + 跨聚合查询 + 读写独立优化才用。✔ 项目结合：只做 product/order/payment/message 4 个模块；message（读写 1:1）、favorite（单表索引够）**刻意不做**——收益 < 维护成本，不是银弹。

### 42. 事件驱动架构？Outbox 模式？
✔ 项目结合：领域事件 = 状态转换副产物（`Transition<Agg, Event>`），写副作用全走事件（扣库存例外——同事务同步），跨模块零同步耦合；Outbox 保证「业务成功 = 事件必达」；10 个消费者 + DLQ 三级重试 + 幂等。

### 43. 六边形架构 / 端口适配器？
领域在中心，出站/入站都是 Port 接口，Adapter 实现外围依赖。✔ 项目结合：35 Port 编译期隔离 + Adapter 集中 `easyorange-application/adapter/outbound/`，换实现（锁/支付/短信/ES）只改 adapter。

### 44. 为什么拒绝 Saga？（架构师必问，见话术集 §2.2 完整版）
单库本地事务 = 比 Saga 更强的强一致；Saga 补偿与回滚重复、崩溃状态丢失；Seata TC 单点与降级冲突；TCC 样板爆炸。触发演进：拆独立数据源。

## 九、AI / LLM

### 45. LLM 调用工程化有哪些要点？（项目的 8 件套）
限流（令牌桶）、降级（stale/兜底文案）、预算（TokenBudget）、重试（客户端内置）、超时、可观测（Spring AI Observation → Prometheus）、Prompt 版本化（YAML）、成本核算。
✔ 项目结合：AI 8 件套完整落地（README 双主线表），6 决策点全部直接注入 Spring AI `ChatModel`/`EmbeddingModel` bean（ADR-0008 框架化，删掉自研 LlmPort/CachingAdapter/AiMetricsService）。

### 46. RAG 是什么？项目怎么做？
RAG = 检索增强生成：外部知识检索 → 拼进 prompt → 生成。解决幻觉 + 知识时效。
✔ 项目结合：ES 轻量 RAG——`text-embedding-v3` 1024 维查询向量 + BM25 Top-50 + Cosine rerank 混合召回（语义 + 词法互补），索引侧 `nameEmbedding` best-effort 写入（失败降级 null 不阻塞）；**拒绝 Milvus**：SKU < 10 万，ANN 运维 ROI 为负（拒绝项第 5 条）。

### 47. Embedding 原理？
文本 → 高维向量，语义相近向量余弦距离近；训练目标让相似文本向量接近。维度选择影响检索质量与存储成本（1024 维 vs 1536 维）。

### 48. Tool Calling / Function Calling？
模型输出结构化「函数调用意图 + 参数」，系统执行后把结果回填给模型再生成。✔ 项目结合：4 路并行 Tool Calling（`SearchToolRegistry`）——工具 name/description 已对齐 Function Calling 的 JSON Schema 形态；编排手写不依赖 LangChain4j（拒绝理由：反射黑盒不可调试，见话术集 §1.2）。

### 49. Prompt 工程？
角色设定 + 明确指令 + 示例（few-shot）+ 输出格式约束（JSON）+ 边界声明。
✔ 项目结合：`PromptRegistry` + YAML 模板（6 个）版本化（模板即 system prompt，变量由服务内联 `String.format` 填充），**改 prompt 不用改代码重新部署**；`callJson` 用 `response_format=json_object` 强制 JSON。

### 50. 怎么判断 AI 输出质量？（LLM-as-Judge）
✔ 项目结合：`eo_ai_call_log` 全量记录（scope/model/prompt_hash/响应/耗时/成败）→ `AiEvalScheduler` 每天用 ChatModel 当评审员按四维打分（1-5 + 评语）→ `AVG(judge_score) GROUP BY scope` 看质量回归——prompt/模型改动后有量化对比。

## 十、通用场景题

### 51. 「你项目里最有挑战/踩过最大的坑？」
推荐两个叙事（选一个主讲）：
- **技术选型纠偏**：自研 AI Port/Adapter + 装饰器（ADR-0003）→ Spring AI 2.0 GA 后全面框架化（ADR-0008）——「承认自研与框架重复，删掉手写代码」比「从不犯错」可信
- **一致性架构决策**：Saga 上过线 → 发现单库场景补偿与回滚重复、失败状态随事务丢失 → 回退本地单事务 + 分布式锁 + Outbox（ADR-0001 → ADR-0007）——「做过决策并记录推翻过程」
- 备选技术坑：Redis 序列化器（Spring Boot 4 默认 JdkSerialization → Lua tonumber 失败 → 限流器 fail-open）——排查链条完整可讲

### 52. 「让你设计 10 倍流量怎么改？」
分层回答（架构师方向标准答案）：
1. **读写分离**：MySQL 主从 + 读库扩展，写路径不变
2. **缓存前置**：列表/详情页缓存命中率已高，加 CDN/预热
3. **多实例**：`docker compose --scale` 已验证的横向扩展路径（nginx LB + Prometheus 发现），L1 缓存广播失效已支持
4. **Redis 集群**：单点 → 哨兵/Cluster（TD-004 触发条件）
5. **跨库演进**：product/payment 拆独立数据源 → 此时重新评估真 Saga/事务性 Outbox 补偿（ADR-0007 触发条件）
6. **AI 链路**：令牌桶参数按容量调整 + 预算下调 + stale 降级兜底；`InMemoryTokenBudgetStore` 换 Redis-backed（TD-005）
7. **压测验证**：k6 从 640 QPS 目标提到 N，门禁（p95<500ms）持续断言
> 顺序要对：先横向扩容 + 缓存，**最后才拆库上 Saga**——展示「演进触发条件」思维。

### 53. 「你们为什么不用微服务？」
单 JVM 多模块：模块边界 = 编译期强制（Port + ArchUnit），**微服务的核心收益（独立部署/独立扩容/故障隔离）在单机阶段收益为零**；跨模块一致性用本地事务就能解决（微服务反而要引入 Saga/分布式事务）。触发条件：团队规模/流量/独立部署诉求达到阈值。这是 ADR-0006 的正向叙事。

### 54. 「这个项目你还会加什么？」
按 ROI 提 2-3 个（体现演进规划能力）：① 下单链路压测（写路径 + 锁）② LLM-as-Judge 数据接入 Grafana 面板（avg score by scope）③ 审计日志查询页（管理端）④ ES 从可选依赖转强依赖 + 健康检查（TD-003 触发条件）。
