## 2 设计一个 RAG 检索增强问答系统（AI 岗必考）

**① 澄清**：语料规模与类型；更新频率（决定全量重建还是增量管线）；问答场景（事实问答 / 总结归纳）；是否要引用溯源。

**② 选型**

| 环节 | 选型 | 为什么 |
|---|---|---|
| 索引 | ES kNN / 独立向量库 | **量级分界线**：百万级以下 ES 自带 HNSW 够用，再大引独立向量库 |
| 分块 | 固定长度 + overlap（简单可控）vs 语义分块（按标题 / 段落边界，质量高成本高） | chunk 太小碎片化、太大稀释相关性 |
| 检索 | **词法 + 向量混合**（两路**独立**召回）→ 排名融合（RRF，量纲无关）→ 必要时再叠模型精排 | 先粗后精两段式 |
| 生成 | ChatModel + **引用溯源** + 不可信内容包块防注入 | 答案带来源，幻觉可核验 |

**③ 难点拆解**

- **召回质量**：hit rate / MRR（可自动算）；**生成质量**：faithfulness
- **评测闭环**：金标准集 + Judge 对照 + **CI 门禁**（分数 + 评审覆盖率双判）
- **更新**：增删改 → 增量重嵌入或周期重建（按更新频率选）；**成本与延迟**：语义缓存、结果缓存、前置降级（不相关查询直接不检索）

**项目对照**：三条链路一套形态——商品检索（两路召回 + RRF）· 知识库（摄入 + 两路召回 + 融合 + 引用溯源 + 评测）· 在售资产检索（换语料，融合共用同一份实现）；差异只在有无独立向量库（[04 RAG-1](04-速答.md)）。

### 缺口与触发条件

| 缺口 | 触发条件 |
|---|---|
| 模型 rerank | 分块上千且 hit@5 触顶而 MRR 偏低 |
| 独立向量库 | 百万级分块且 kNN 延迟成为瓶颈 |

> **把「现状 + 缺口 + 触发条件」讲全，就是完整的演进规划展示**（[04 RAG-6](04-速答.md) 同款）。

## 3 设计一个 Agent 循环（AI 岗必考）

**① 澄清**：任务是开放问答还是固定流程？能接受几步？成本上限？失败时降级成什么？

**② 循环骨架**：`决策 → 工具 → 观察` 循环。**决策用原生 tool calling**——把工具 schema 随请求下发，模型返回「工具 + 参数 + 理由」。
工具执行与循环控制权**留在自己的编排器**：托管给框架则步数上限 / 中途预算 / 终止原因分类都插不进去。

**③ 工具面设计**：按性质分层（检索 / 计算 / 写入 / 收敛）。工具要正交、参数要求可校验（如 ID 必须来自上一步观察）。

> **必须有能让第 N 步依赖第 N-1 步输出的工具**，否则循环退化成换关键词重试。

**④ 控制与降级**（生产级关键）

- 步数上限（含 finish 轮）+ **循环中途预算检查**
- 按终止原因分类降级：超限 → 用已积累观察单次生成；决策失败 → 退回单次检索；工具失败也作为观察回灌，让模型换参数重试

**⑤ 可观测**：每步落 trace（工具 / 参数 / 理由 / 观察）+ 流式 step 事件；指标按 outcome 归因。**⑥ 演进**：上下文裁剪（token 估算）→ 记忆（会话窗口 + 长期画像）→ 评估集覆盖 agent 场景用例。

**项目对照**：`ToolCallLoop` + `ChatTools`（见 [02 §1 / §2](02-代码走读.md)）；被问「固定 Workflow 不够吗」的正面论证（流程能不能预写死）与已删的 4 路扇出见 [04 AG-1](04-速答.md)（[02 §4](02-代码走读.md) 有实现侧理由）。

## 4 设计一个限流器（必考）

**框架**：单机 vs 分布式 → 算法选择 → 降级策略。

1. **澄清**——按什么维度限（IP / 用户 / 接口），粒度，误杀容忍度。
2. **选型**——单机用令牌桶或本地滑动窗口；分布式用 Redis 令牌桶（单机计数器无法跨实例）。
3. **降级与演进**——限流器故障必须 **fail-open**（宁可放过不可误杀业务），且不能成为单点；固定窗口（简单但有边界突刺 + 非原子）→ 令牌桶（平滑 + 允许突发）→ Redis 集群。

**项目对照**：AI 端点按场景令牌桶 + 超限 429 + fail-open；全站 GET 走本地（单实例够）、写操作走分布式（防超卖要跨实例统一计数）；stale 旧回答兜底属**供应商故障**、在服务层，与限流是两条路径（[04 DIST-5](04-速答.md) / [04 AI-2](04-速答.md)）。

## 5 设计消息可靠投递（Outbox 必答）

**框架**：三个环节分别保可靠——生产不丢（事务一致）/ 存储不丢（持久化）/ 消费不丢（ack + 重试），最后用幂等收口。

1. **生产端一致性**（核心难点）——先发消息后提交事务则失败成孤儿，先提交再发则发失败而业务已成功。**正解是 Outbox**：业务 SQL + 事件 insert 同一本地事务 → 后台异步外发 → 发成功标记；替代方案是本地消息表 + 定时扫描。
2. **Broker 持久化 + 生产 confirm。**
3. **消费端**手动 ack + 指数退避重试 + DLQ 隔离毒消息 + **消费者幂等**（at-least-once 下重复只处理一次）。
4. **演进**——单机 → 镜像队列 / 集群；量级增大再权衡换 MQ（代价：死信、多 group 都要自建）。

**项目对照**：`Modulith Outbox`（同事务 + 崩溃重发）→ `Topic Exchange` → 消费者各自独占队列 → `DLQ 三级重试` → `SET NX EX` 幂等。

## 6 设计一个订单系统（与项目强相关）

**框架**：状态机 → 一致性（防超卖）→ 生命周期副作用 → 查询（CQRS）。

1. **状态机动作驱动**——每动作声明前置状态 / 目标状态 / 副作用，单一入口守卫，非法转换抛业务异常。比 if-else 可测可维护。
2. **防超卖**——分布式锁（按商品 key，排序获取防死锁）+ 库存乐观锁双保险。
3. **一致性**——本地单事务（订单 + 库存 + 支付 + 事件原子提交），**单库不上 Saga**，拆库才引入。
4. **副作用**——取消恢复库存 / 完成标记售出 → 事件异步（消费者幂等）。
5. **查询**——CQRS 读模型 + 列表索引。超时取消 / 自动确认走定时任务。

**项目对照**：`OrderCommandHandler`（锁在事务外 + 显式事务模板）+ 生命周期事件消费者 + 超时 / 自动确认任务。

## 7 设计缓存系统 / 短链秒杀（通用题）

### 缓存

**通用框架**：层级（L1 / L2）→ 三防 → 一致性 → 可观测；**命中率是最重要的健康指标**。教科书答案（L1 + L2 配平、Pub/Sub 广播、负缓存哨兵）见 [04 DB-6](04-速答.md)。
**项目落点**：多级缓存**刻意不做**——单库单 Redis 部署下复杂度换不来可感知收益；统一 Spring Cache 注解 + Redis 单层，三防收口在注解 + writer，一致性靠写路径 evict、可用性靠 fail-open。

> **讲清「我知道方案但评估后不用」比堆功能更显判断力。**

### 短链与秒杀

- **短链**：发号器（雪花 / 自增 + base62）→ KV 存储 → 302 跳转 → 布隆过滤非法码
- **秒杀**：提前把库存放 Redis 预扣（写只碰 Redis，MQ 异步落库）→ 限流 → 本地单飞 → 事务落库 + 对账

**与项目的对比点**：库存扣减我选**同事务强一致而非 Redis 预扣**——单库场景没有中间件一致性成本。量到百万级再改预扣 + 对账。

> **AI 岗重点：题 1 RRF + 题 2 工具循环骨架。** 每题先盖住实现自己写，写完再对比，都是 5-15 行量级。

### 题 1：RRF 排名融合（项目同款 · RAG 检索收口）

**题面**：给你多路召回的有序结果（每路按各自相关性降序），怎么合成一个总排序？

```java
/** 融合分 score(d) = Σ_r 1 / (k + rank_r(d))，rank 从 1 起，k 默认 60（Cormack et al. 2009） */
public static List<Fused> fuse(int k, List<List<String>> rankedLists) {
    Map<String, Double> scores = new LinkedHashMap<>();
    for (List<String> ranked : rankedLists) {
        for (int i = 0; i < ranked.size(); i++) {
            scores.merge(ranked.get(i), 1.0 / (k + i + 1), Double::sum);
        }
    }
    return scores.entrySet().stream()
            .sorted(Map.Entry.<String, Double>comparingByValue().reversed())
            .map(e -> new Fused(e.getKey(), e.getValue()))
            .toList();
}
```

> 完整实现见 [`RrfFusion`](../../easyorange-backend/easyorange-ai/src/main/java/com/cartethyia/easyorange/ai/domain/model/RrfFusion.java)；选型理由见 [ADR-0012](../adr/0012-rag-hybrid-retrieval-rrf.md)。

**要讲清的三点**：**为什么用排名而不是分数**（kNN 的余弦与 BM25 的相关性分**量纲不可比**，加权求和既要调参又对分布漂移敏感）· **k 是平滑常数**（压制「第 1 名 vs 第 2 名」的过度优势）· **融合解决不了什么**（融合只解决「多路信号怎么合」，用同一个余弦对稠密候选重排是单调变换、等于没排，所以必须真的有两路独立召回）。同分靠插入序 + 稳定排序保评测可复现（追问见 [04 RAG-4](04-速答.md)）。

### 题 2：工具循环骨架（项目同款 · Agent 核心）

**题面**：手写一个 agent 循环（自治式多步工具循环）——模型每轮自己决定调哪个工具，你负责执行、观察回灌、步数上限与降级。（判它是 agent 的依据是**下一步由谁决定**，不是「用了工具」；面试官爱叫它 ReAct 循环，顺着叫即可。）

```java
public Answer run(String question, int maxSteps) {
    List<StepObservation> observations = new ArrayList<>();
    for (int round = 1; round <= maxSteps; round++) {
        if (budgetExhausted()) break;                       // 循环中途预算检查（框架托管做不到）
        Decision d = decide(question, observations);         // 发工具 schema，收回 tool call
        if (d.isFinish()) break;
        StepOutcome out = executeTool(d);                    // 执行在自己手里
        observations.add(new StepObservation(d.tool(), d.input(), out.observation())); // 失败也回灌
    }
    return generate(question, observations);                 // 超限 / 预算耗尽 → 用已积累观察单次生成
}
```

**加分点（逐个讲）**：**终止原因要分类**（步数超限 / 预算耗尽 / 决策失败是三种不同的降级——前两者用已积累观察生成，决策失败退回单次检索，混成一种就没法归因）· **工具失败也进观察**（模型可换参数重试），但**决策失败不进**（那是链路故障，要走退路）；每步落 trace + 推 step 事件，否则线上只有「答得差」一种表象；上下文要裁剪（token 估算，保最新）。

**追问**：「为什么不用框架的托管循环？」→ 步数上限 / 中途预算 / 降级分类三样插不进去（`04 AG-4`）。
**追问**：「这算 ReAct 吗？」→ 同源不同实现。项目走原生 tool calling，模型回结构化 `tool_calls`，没有「文本解析不出动作」这种失败态，所以决策失败能单独分类归因；ReAct 那套先写 Thought 再动手的形态已被 provider 内置，不必自己拼。

### 题 3：实现一个令牌桶限流器（单机版）

```java
class TokenBucket {
    private final long capacity;      // 桶容量（最大突发）
    private final double ratePerSec;  // 补充速率
    private double tokens;
    private long lastRefillNanos;

    TokenBucket(long capacity, double ratePerSec) {
        this.capacity = capacity;
        this.ratePerSec = ratePerSec;
        this.tokens = capacity;
        this.lastRefillNanos = System.nanoTime();
    }

    public synchronized boolean tryAcquire() {
        long now = System.nanoTime();
        double elapsedSecs = (now - lastRefillNanos) / 1e9;
        tokens = Math.min(capacity, tokens + elapsedSecs * ratePerSec);  // 按时间补令牌
        lastRefillNanos = now;
        if (tokens >= 1) {
            tokens -= 1;
            return true;
        }
        return false;
    }
}
```

**追问延伸**：分布式版 → Redisson 令牌桶 / Lua 脚本（原子取桶补桶）。边界：`synchronized` 单机够用，多实例必须分布式。

### 题 4：实现幂等（SETNX 版）

```java
// Redis: SET key value NX EX ttl —— 成功 = 第一次，失败 = 重复
Boolean first = redisTemplate.opsForValue().setIfAbsent(key, "1", 24, TimeUnit.HOURS);
if (Boolean.TRUE.equals(first)) {
    try {
        // 第一次，执行业务
    } catch (Exception e) {
        redisTemplate.delete(key);   // 失败撤销标记，让重试 / 重投能重新执行
        throw e;
    }
} else {
    // 重复请求：跳过（事件消费）或返回上次结果（协议幂等）
}
```

**追问**：查-写竞态怎么破？→ 让「查 + 写」压成一条原子命令（`SET NX EX`），**所以不需要锁**（锁解决的是多命令序列非原子）。失败为什么撤销标记？→ 宁可重试不可漏处理。

### 题 5：实现订单状态机（动作表版，项目同款）

**先想清楚要几个维度。** 订单状态和支付状态是**两个独立维度**——`PAID` 之后可以 `SHIP` 也可以 `REFUND`，退款后订单进 `REFUNDED` 而支付维度同时翻成 `REFUNDED`。只写一维就答不出「为什么退款要求已支付」这类追问。

```java
enum OrderAction {
    PAY("支付", Set.of(PENDING_PAYMENT), PAID, PaymentStatus.PAID, ClosureKind.NONE, null),
    CANCEL("取消", Set.of(PENDING_PAYMENT), CANCELLED, null, ClosureKind.CANCEL, null),
    FORCE_CANCEL("强制取消", Set.of(PENDING_PAYMENT, PAID), CANCELLED, null, ClosureKind.CANCEL, null),
    SHIP("发货", Set.of(PAID), SHIPPED, null, ClosureKind.NONE, null),
    CONFIRM_RECEIPT("确认收货", Set.of(SHIPPED), COMPLETED, null, ClosureKind.NONE, null),
    REFUND("退款", Set.of(PAID, SHIPPED), REFUNDED, PaymentStatus.REFUNDED, ClosureKind.REFUND,
           p -> p == PaymentStatus.PAID);   // 已发货但未实付的不许退

    final String actionName;
    final Set<OrderStatus> sources;          // 订单维前置
    final OrderStatus target;
    final PaymentStatus targetPaymentStatus; // null = 支付维度不变
    final ClosureKind closureKind;           // 关闭归因：记取消字段还是退款字段
    final Predicate<PaymentStatus> paymentGuard; // 支付维额外前置；null = 无限制

    boolean canApply(OrderStatus s, PaymentStatus p) {
        return sources.contains(s) && (paymentGuard == null || paymentGuard.test(p));
    }
}

class Order {                       // 不可变聚合根：字段 final，@Builder(toBuilder = true)
    private final OrderStatus status;
    private final PaymentStatus paymentStatus;

    private Order transitionTo(OrderAction a, String reason, LocalDateTime now) {
        BizRequire.requireTrue(a.canApply(status, paymentStatus), a.resultCode());
        // 关闭类动作必须附原因——守卫与状态判定同一处收口
        BizRequire.requireTrue(a.closureKind == ClosureKind.NONE || (reason != null && !reason.isBlank()),
                a.resultCode());
        var b = toBuilder().status(a.target)
                .paymentStatus(a.targetPaymentStatus != null ? a.targetPaymentStatus : paymentStatus);
        switch (a.closureKind) {     // 取消 / 退款各归各的字段，这一维省掉就会出现「退了但写着用户取消」
            case CANCEL -> b = b.cancelReason(reason).cancelTime(now);
            case REFUND -> b = b.refundReason(reason).refundTime(now);
            case NONE -> {}
        }
        return b.build();            // 返回新实例，原对象不变
    }
    public Transition<Order, OrderPaidEvent> pay(LocalDateTime now) {
        return new Transition<>(transitionTo(OrderAction.PAY, null, now), new OrderPaidEvent(...));
    }
}
```

**要点**（每条都是追问点）

- **合法性只由 `canApply` 裁决**，聚合根不写 if-else；6 个动作的判定集中在一处，加动作不改编排代码。
- **支付前置用 `Predicate` 而不是并进 `sources`**——`sources` 是订单维集合、`paymentGuard` 是支付维条件，混在一起就看不出「退款卡的是支付维度不是订单维度」。
- **`targetPaymentStatus = null` 表示不变**，而不是让调用方自己判断，省掉一整类漏改；**抛业务异常不用 `IllegalStateException`**——走 `BizRequire.requireTrue(action.canApply(...), action.resultCode())`，错误码是 `ORDER_CANNOT_REFUND` 这类，非法转换要能被前端区分。

**面试答法**：先说两个维度，再画状态图，最后落到「合法性判定集中在一处 + 支付守卫单独成维」；注意**转换返回新实例**（不可变聚合根），公开入口再包一层 `Transition<Order, Event>` 把领域事件带出来——题 9 是这一风格的极小版。

### 题 6：手写 CompletableFuture 并行 + 超时 + 部分降级

> ⚠ **不是项目同款**。项目里唯一的 `CompletableFuture` 在缓存写入抖动（`JitterTtlRedisCacheWriter`）；那套 4 路并行扇出已随搜索页增强整节删除。讲这题只讲控制流，**别说「我们项目里就是这么做的」**。

```java
CompletableFuture<String> f1 = CompletableFuture.supplyAsync(() -> llmCall("任务1"), virtualExecutor);
CompletableFuture<String> f2 = CompletableFuture.supplyAsync(() -> ruleCompute("任务2"), virtualExecutor);

try {
    CompletableFuture.allOf(f1, f2).get(5, TimeUnit.SECONDS);
} catch (TimeoutException e) {
    // 超时：收集已完成部分，不抛错
}
String r1 = f1.getNow("默认值");   // 未完成返回默认值，不阻塞
f2.cancel(false);                 // 不中断虚拟线程载体
```

**加分点**：`getNow` 语义（不阻塞拿已完成结果）· 为什么用 `allOf` 而不用 `anyOf`（要的是「能等的都等到」，不是「最快的一个」）· 显式传虚拟线程执行器（`commonPool` 是平台线程）。

### 题 7：LRU 缓存（手撕高频）

```java
class LRUCache {
    private final LinkedHashMap<Integer, Integer> map;
    LRUCache(int capacity) {
        this.map = new LinkedHashMap<>(capacity, 0.75f, true) {   // accessOrder = true
            protected boolean removeEldestEntry(Map.Entry<Integer, Integer> eldest) {
                return size() > capacity;
            }
        };
    }
    int get(int key) { Integer v = map.get(key); return v == null ? -1 : v; }
    void put(int key, int value) { map.put(key, value); }
}
```

**追问**：手写「双向链表 + HashMap」版（不依赖 `LinkedHashMap`）也要能写。「Caffeine 的实现是 TinyLFU + 窗口」（比 LRU 更抗扫描型访问）——把面试题聊回项目的机会。

### 题 8：单例 + 双重检查（考内存可见性）

```java
class Singleton {
    private static volatile Singleton instance;   // volatile 防指令重排
    static Singleton getInstance() {
        if (instance == null) {                    // 快路径
            synchronized (Singleton.class) {       // 慢路径
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

**易翻车点**：`instance` 不 volatile 时，`new Singleton()` 的三步（分配 / 初始化 / 赋引用）可能重排，导致另一线程拿到未初始化对象。volatile 有序性的经典考题，跟项目里静态 volatile 引用的道理相通。

### 题 9：不可变状态转换（domain 层风格）

record Order2(OrderStatus status, PaymentStatus paymentStatus) {
    Order2 apply(OrderAction action) {
        // ⚠ 别写 throw new IllegalStateException——项目里非法转换要能被前端区分，

### 题 10：SQL 防注入 IN 列表（项目踩坑还原）

```java
// ❌ 禁止：IN (${ids}) 拼接（历史事故：注入 + 阻止计划缓存）
// ✅ 推荐：<script> + <foreach> + #{id} 参数化 —— 项目同款，注解式不落 XML
@Select("<script>"
        + "SELECT category_id, COUNT(*) AS product_count FROM eo_product "
        + "WHERE del_flag = 0 AND category_id IN "
        + "<foreach item='id' collection='categoryIds' open='(' separator=',' close=')'>#{id}</foreach> "
        + "GROUP BY category_id"
        + "</script>")
List<CategoryProductCount> countAllProductsByCategoryIds(@Param("categoryIds") List<String> categoryIds);
```

> 真实落点是 `CategoryMapper#countAllProductsByCategoryIds`——被追问「哪个 mapper」时按这个名字找得到。
