## 1 下单链路 — OrderCommandHandler

- **文件**：`easyorange-order/.../application/command/OrderCommandHandler.java`
- **关键代码**：
  ```java
  @Transactional(rollbackFor = Exception.class)
  public CreateOrderResult handle(CreateOrderCommand command) {
      return lockPort.executeWithLocks(buildLockKeys(command), LOCK_TRY_TIMEOUT_SECONDS, () -> createOrderFlow(command));
  }
  ```
- **实现要点**：
  1. 锁在**事务内获取、事务提交/回滚后释放**（`DistributedRedissonLockAdapter` 用 `TransactionSynchronization.afterCompletion` 延迟释放）——若在事务提交前释放，后一个请求会在前一个事务尚未提交时读到旧库存快照，击穿防超卖
  2. `buildLockKeys`：多个商品按 **productId 排序**（distinct + sorted）→ 防 AB-BA 死锁
  3. 事务内顺序：建单 + Outbox 发事件 → `decreaseStock` 同步扣库存 → `createPayment` 建支付 → 卖家缓存驱逐
  4. 任一步失败 → 数据库整体回滚（订单/库存/支付/Outbox 同事务），抛 `OrderCreationException`，**无补偿路径**
  5. 锁获取失败（10s 超时）→ 抛「资产下单繁忙」，事务回滚
- **可能的追问**：「锁和事务的顺序有问题吗？」→ 常见做法是**先拿锁再开事务**；我们是**先开事务再拿锁**（`@Transactional` 注解在 `handle()` 上，`executeWithLocks` 在方法体内）——锁在事务提交后再释放（`afterCompletion`），保证下一个请求拿到锁时前一个事务的数据已提交可见，收敛防超卖窗口（e268c59e）；代价是事务占用 DB 连接时间更长，10s 锁超时兜底
- **一句话**：单库下单 = 本地事务包住 锁 → 建单 → 扣库存 → 建支付，失败整体回滚，拒绝 Saga（ADR-0007）

## 2 订单状态机 — Order + OrderAction

- **文件**：`easyorange-order/.../domain/aggregate/Order.java`、`domain/constant/OrderAction.java`
- **关键代码**：
  ```java
  // OrderAction 枚举：每个动作声明前置状态集合、目标状态、目标支付状态、错误码（状态机唯一事实来源）
  PAY("支付", Set.of(OrderStatus.PENDING_PAYMENT), OrderStatus.PAID, PaymentStatus.PAID, ...)
  CANCEL("取消", Set.of(OrderStatus.PENDING_PAYMENT), OrderStatus.CANCELLED, null, ...)
  FORCE_CANCEL(..., Set.of(PENDING_PAYMENT, PAID), CANCELLED, ...)

  // 聚合根：所有转换经统一守卫
  private Order transitionTo(OrderAction action, String reason) {
      BizRequire.requireTrue(action.canApply(status, paymentStatus), action.resultCode());
      ...应用副作用（状态+支付状态+原因/时间）...
      return this;
  }
  ```
- **实现要点**：
  1. **动作驱动**：合法转换集中在 `OrderAction` 一张表（sources → target + targetPaymentStatus），聚合根只留 `transitionTo` 一个入口守卫
  2. 每个公开方法（`pay()/cancel()/ship()/...`）返回 `Transition<Order, XEvent>`——新聚合 + 领域事件一并产出
  3. 支付状态独立于订单状态：`CANCEL` 不改支付状态（null），`PAY` 置 PAID，`REFUND` 置 REFUNDED
  4. 聚合不可变：字段 final，转换返回新实例
- **可能的追问**：「REFUND 为什么要求支付状态已支付？」→ paymentGuard 前置条件；「为什么不用一张大状态表？」→ 订单状态 × 支付状态是二维的，动作表每行声明两个维度的目标值，比一张二维矩阵更可读可测试
- **一句话**：状态机唯一事实来源是 `OrderAction` 动作表，聚合根单一入口 `transitionTo` 守卫，转换产出事件走 Outbox

## 3 商品状态机 — Product

- **文件**：`easyorange-product/.../domain/aggregate/Product.java`、`domain/enums/ProductStatus.java`
- **关键代码**：
  ```java
  // ProductStatus.ALLOWED_TRANSITIONS：DRAFT→PENDING_REVIEW→REJECTED→ONLINE→OFFLINE→SOLD 生命周期
  approve()   { var updated = transitionTo(ProductStatus.ONLINE, "审核通过"); validateOnline(); ... }
  putOnline() { var updated = transitionTo(ProductStatus.ONLINE, "上架");     validateOnline(); ... }  // ADMIN bypass
  markAsSold()   // 订单完成事件触发
  restoreStock() // canRestoreStock() 守卫：SOLD/OFFLINE 不可恢复库存
  ```
- **实现要点**：
  1. `ALLOWED_TRANSITIONS` 集中式状态机表（AGENTS.md 有 ASCII 图），`transitionTo(target, action)` 统一守卫，终端状态 `isTerminal()` 仅 SOLD
  2. **两条进入 ONLINE 的路径**（approve / putOnline）都必须过同一组 `validateOnline()`（isComplete + hasValidPrice + hasStock）——禁止第三条绕过校验的上架路径
  3. delete 不改变 status，单独 `canDelete()` 守卫（SOLD 不可删，保留订单追溯）
- **可能的追问**：「为什么 ONLINE 校验单独抽方法而不是放状态机表？」→ 状态机表只管「转换是否合法」，`validateOnline` 管「进入 ONLINE 的**数据完整性不变量**」——两类规则职责不同，前者是转移谓词，后者是业务不变量
- **一句话**：商品生命周期 6 状态集中声明转换表，两条上架路径统一过 `validateOnline` 不变量

## 4 分布式锁 — DistributedLockPort + DistributedRedissonLockAdapter

- **文件**：`easyorange-framework/.../lock/DistributedLockPort.java`（端口接口，统一 order/payment/超时任务三处用法）、`.../lock/DistributedRedissonLockAdapter.java`（Redisson 实现、@Component("distributedLockAdapter")）
- **关键代码**（适配器内部）：
  ```java
  RLock lock = redissonClient.getLock(lockKey);
  boolean locked = lock.tryLock(waitTime, -1, TimeUnit.SECONDS);  // leaseTime=-1 → watchdog 续期
  ... // 锁在事务提交/回滚后释放（TransactionSynchronization.afterCompletion），不是 finally
  ```
- **实现要点**：
  1. **leaseTime=-1 → 由 Redisson watchdog 续期**（默认 30s 锁 + 每 10s 续期），锁不会在下单流程结束前自动过期——不必手工估算事务耗时；`RedissonConfig` 显式固定 watchdog 周期
  2. 释放推迟到事务提交/回滚之后（`TransactionSynchronization#afterCompletion`）——提前释放会让后一个请求读到旧库存快照，击穿防超卖（e268c59e）
  3. 释放前检查 `isHeldByCurrentThread()`——防止锁已过期被他人持有后误删别人的锁
  4. 多锁按 productId 排序逐个获取（`OrderCommandHandler.buildLockKeys` 排序 → `DistributedLockPort.executeWithLocks` 逐个获取），逆序释放，防 AB-BA 死锁
  5. 锁 key：`eo:order:lock:product:{productId}`（payment 用例 key=`payment:lock:...`，超时任务 key=`eo:order:lock:cancel:{orderId}`）
  6. **失败语义**：获取锁失败（等待超时/中断）抛 framework `LockAcquisitionException`——order 在 handler 边界映射为 `OrderCreationException`（B0002→400），payment 复用同一异常兜底（catch 后以统一文案重抛，RuntimeException→500）；`waitTimeout=0` 即非阻塞尝试，拿不到可自行降级
- **可能的追问**：「锁过期了业务还没完怎么办？」→ watchdog 自动续期，锁不会自动过期；holder 超阈值（60s）由适配器 warn 告警（疑似长事务卡住），业务失败整体回滚。「Redis 挂了锁怎么办？」→ Redisson 连接异常时 tryLock 抛异常走事务回滚（不静默放行——超卖保护宁可失败不可绕过）
- **一句话**：Redisson RLock leaseTime=-1 由 watchdog 续期、事务提交后释放，按 key 排序防死锁，释放前校验持有者

## 5 搜索增强 4 路并行 — AiSearchEnhancerAdapter + SearchToolRegistry

- **文件**：`easyorange-ai/.../adapter/outbound/AiSearchEnhancerAdapter.java`、`adapter/outbound/tool/`
- **关键代码**：
  ```java
  CompletableFuture.allOf(intent, tags, market, questions).get(5, TimeUnit.SECONDS);
  // 超时/异常 → collectPartialResults 收集已完成的，其余降级
  intentFuture.cancel(false);  // 不中断虚拟线程 carrier
  ```
- **实现要点**：
  1. **Tool Registry 模式**：`SearchTool<T>` 接口（name/description/kind/run），4 个工具 Spring 自动收集进注册表（构造期防重名），新增工具零改动
  2. 工具：`intent_detection`（LLM）/ `product_tagging`（规则引擎，零 LLM 亚毫秒）/ `market_analysis`（LLM，失败降级 null）/ `question_suggestion`（LLM，失败降级空列表）
  3. 并行用 `ForkJoinPool.commonPool()`（Java 21+ 虚拟线程），`cancel(false)` 不中断虚拟线程 carrier 线程
  4. 5s 总超时，部分结果也可用（intent 或 tags 任一有值即返回），Redis 5min TTL 缓存（`ai:search:enhance:{md5(keyword)}`）
  5. 前置降级：非自然语言（`NaturalLanguageDetector` 规则判断）或空商品列表 → 直接 empty，不烧 token
- **可能的追问**：「为什么用 commonPool 不自定义线程池？」→ 虚拟线程下 commonPool 已是轻量调度，自定义池是过度设计；「LLM 调用放线程池里怎么限流？」→ 每个 tool 的 LLM 调用走同一 `ChatModel` + 限流/预算链路（AiRateLimitInterceptor 在 HTTP 层，TokenBudget 在 service 层，搜索增强由限流器覆盖）
- **一句话**：4 路工具经 Registry 并行调度，单路降级 + 5s 总超时 + 结果缓存，编排手写不依赖 Agent 框架

## 6 AI 限流 + stale 降级 — AiRateLimitInterceptor + DistributedRateLimiter

- **文件**：`easyorange-ai/.../interceptor/AiRateLimitInterceptor.java`、`easyorange-framework/.../util/DistributedRateLimiter.java`
- **关键代码**：
  ```java
  boolean allowed = distributedRateLimiter.tryAcquire(bucketKey, scope.getRatePerMinute(), 60);
  // 超限 → 先查 stale 缓存（Caffeine 24h TTL）返回旧值 200；没有再返回 429
  // Redis 异常 → failOpen 放行（保护可用性，限流不能成为单点）
  ```
- **实现要点**：
  1. **Redisson RRateLimiter 令牌桶**（rate=次/分, interval=60s），原子化取桶/补桶，替代 increment+expire 固定窗口（原子性缺口 + 边界突刺）
  2. 按 `AiCallScope` 枚举分端点限流（pricing 10 / review 10 / copy 20 / auto-listing 5 / semantic 30 / qa 20 次/分），key = `ai:rl:{scope}:user:{userId}`（未登录按 IP）
  3. **超限不是 429 而是 stale 降级**：Caffeine stale 缓存（24h TTL）有值 → 返回 200 + 旧数据；没值 → 429
  4. Redis 不可用 fail-open（`easyorange.ai.rate-limit.fail-open=true`）
- **可能的追问**：「为什么用令牌桶不用滑动窗口？」→ 令牌桶天然支持突发（桶容量）+ 平滑速率；「stale 数据过期了怎么办？」→ 24h TTL + 新请求重算；「怎么区分 429 和降级？」→ 降级返回 200 + stale 数据，429 才真正拒绝
- **一句话**：Redisson 令牌桶按端点限流，超限优先返回 stale 缓存而非拒绝，Redis 挂了 fail-open

## 8 事件幂等 — EventIdempotencyChecker

- **文件**：`easyorange-framework/.../event/idempotency/EventIdempotencyChecker.java`
- **关键代码**：
  ```java
  // 两级：Redisson 锁保证「查-写」原子，Redis done 标记做去重
  RLock lock = redissonClient.getLock("eo:event:lock:" + eventType + ":" + eventId);
  lock.tryLock(0, 30, SECONDS);   // 锁内再查 done 标记
  if (!isDuplicate(eventType, eventId)) {
      redisTemplate.opsForValue().set("eo:event:done:" + type + ":" + id, "1", 24, HOURS);
  }
  ```
- **实现要点**：
  1. 纯 SETNX 的问题：**查和写不原子**（并发竞态）；锁内「查 done → 写 done」保证原子
  2. done 标记 TTL 24h，覆盖 DLQ 三级重试最长窗口（~15min）
  3. 异常时返回 true（视为已处理）——**宁可漏处理不可重复处理**（重复恢复库存是数据事故）
  4. 命名空间 `consumerId:eventType:eventId` 隔离多消费者监听同一事件
- **可能的追问**：「at-least-once + 幂等 = 精确一次？」→ 是：Modulith 保证不丢（可能重复投递），幂等保证重复只处理一次；「24h 后重复怎么办？」→ 事件 ID 带时间戳的 UUID，24h 后重放基本不可能，TTL 是成本权衡
- **一句话**：锁内查-写原子 + 24h done 标记，把 at-least-once 变成 exactly-once

## 9 多级缓存 — MultiLevelCache

- **文件**：`easyorange-framework/.../cache/MultiLevelCache.java`（+ `CacheInvalidationListener`）
- **关键代码**：
  ```java
  // L1 Caffeine → L2 Redis → DB，回源走 Supplier
  get(key, clazz, () -> repository.findDetail(id));
  // 击穿：Caffeine.get(key, fn) 原子单飞 + Redisson 跨节点锁（fail-open）
  // 穿透：null 回源 → NullValue 哨兵（L1+L2，默认 30s）
  // TTL 配平：Config 强制 l1Ttl <= l2Ttl，L1 先过期杜绝 L2 已过期 L1 仍新的窗口
  // 一致性：evict() 经 Redis Pub/Sub 广播失效其他节点 L1（回源填充不广播——填的是新值）
  ```
- **实现要点**：
  1. 三类缓存问题全覆盖：击穿（单飞+锁）、穿透（负缓存哨兵）、雪崩（TTL 错峰由配置控制）
  2. `Config` record 单一配置入口，非法 TTL 组合构造期直接抛错
  3. 可观测：`easyorange.cache.requests{result=l1_hit|l2_hit|l2_negative|load}` + 回源 Timer
- **可能的追问**：「为什么 evict 广播而 put 不广播？」→ evict 清的是**别人节点上的陈旧值**；put 填的是新值，不需要广播；「锁超时 fail-open 会不会击穿？」→ 单飞 + 负缓存双保险，锁只是跨节点去重，失败也只有一个线程回源
- **一句话**：L1 Caffeine + L2 Redis + DB 三级，击穿/穿透/雪崩三类防护 + Pub/Sub 广播失效

## 10 Outbox 发布链 — ModulithDomainEventPublisher

## 12 全局异常 — GlobalExceptionHandler

- **文件**：`easyorange-framework/.../exception/GlobalExceptionHandler.java`
- **关键代码**：
  ```java
  @ExceptionHandler(Exception.class)
  public ResponseEntity<Result<Void>> handle(Exception e) {
      return switch (e) {
          case BaseBusinessException b -> ResponseEntity.status(resolveHttpStatus(b.getCode()))...
          case AccessDeniedException _ -> response(FORBIDDEN, ...);

  ```
- **实现要点**：
  1. **Java 21 模式匹配 switch** 单方法按类型分发，消除 10+ 个 @ExceptionHandler 方法
  2. HTTP 状态码按错误码前缀自动映射：A0401→401 / A0403→403 / B→400 / C→500 / D→502；校验类错误统一 400
  3. 规范：**禁止抛非 BaseBusinessException 子类的 RuntimeException**，否则落 500 兜底
  4. 各模块异常必须用模块专属 ResultCode（如 `ProductResultCode.PRODUCT_NOT_FOUND`），禁止回退全局 B0002
- **可能的追问**：「为什么用 switch 不用多方法？」→ 分发逻辑收敛一处，新增异常类型改一个方法；「响应格式统一吗？」→ `Result<T>` 信封 + ResponseAdvice 自动包装
- **一句话**：单方法模式匹配 switch 按错误码前缀映射 HTTP 状态，业务异常统一 ResultCode

## 13 语义搜索 — SemanticSearchService

- **文件**：`easyorange-ai/.../service/SemanticSearchService.java`、`easyorange-application/.../elasticsearch/ElasticsearchProductSearchQueryAdapter.java`
- **关键代码**：
  ```java
  List<Float> embedding = AiModelSupport.embed(embeddingModel, AiCallScope.SEMANTIC, keyword);  // text-embedding-v3 1024 维
  // → ProductSearchQueryPort → ES 查询：BM25 召回 Top-50 → 查询向量 Cosine rerank → 分页
  // 索引侧：ElasticsearchProductSearchIndexAdapter 注入 ObjectProvider<EmbeddingModel> best-effort 写 nameEmbedding（失败降级 null 不阻塞索引）
  ```
- **实现要点**：
  1. 查询向量与索引维度必须一致（1024 = ES `dense_vector` 映射 dims）
  2. 混合召回：BM25 词法 + 向量 rerank，中长尾查询优于纯 kNN
  3. ES 是可选依赖（`@ConditionalOnProperty`），无 ES 降级空结果，不阻塞应用
- **可能的追问**：「为什么不用 Milvus？」→ 量不够（SKU < 10 万），ANN 运维负担 ROI 为负，见话术集拒绝项；「向量维度不匹配会怎样？」→ ES 查询直接报错，这是配置一致性最容易踩的坑
- **一句话**：text-embedding-v3 生成查询向量，BM25 + Cosine rerank 混合召回，索引侧 best-effort 写入不阻塞主链路

## 附：被问「这段代码有什么问题」的应答模板

面试官挑毛病时，**先承认再给方案**，用下面几个项目里真实存在的点（比硬说「没问题」可信）：

| 代码 | 真实问题 | 应答 |
|---|---|---|
| 下单链路 | 锁持有=事务时长，10s 超时在极端慢 SQL 下会抛「繁忙」 | 「锁与事务同生命周期是安全的代价是 10s 超时上限，慢 SQL 监控（SlowSqlInterceptor）兜底，压测实测远低于此」 |
| EventIdempotencyChecker | 异常时返回 true 会漏处理 | 「宁可漏不可重——重复恢复库存是数据事故，漏处理由 DLQ 重投兜底」 |
| InMemoryTokenBudgetStore | 多实例各自记账 | 「已知技术债 TD-005，多实例部署时换 Redis-backed，接口已就位」 |
| 搜索增强 | 每路 LLM 调用可能重复计算 prompt | 「5min Redis 缓存 + 单步降级，重复成本可控」 |
| 消息消费 | 幂等 24h TTL 理论上可重复 | 「24h 窗口内 DLQ 重试已覆盖，超窗重放概率趋零，成本权衡」 |

> 原则：**主动说出「我知道这里有 trade-off，当时选择 X 是因为 Y，触发条件 Z」**，比假装完美强十倍——这正是项目技术债务清单（doc/技术债务清单.md）的叙事价值。
