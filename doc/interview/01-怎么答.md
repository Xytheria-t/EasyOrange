# 一、高频技术题速答

> 规则：每道题「先一句话定义，再 1-2 句原理，最后接『我在项目里』」——把背诵题变成实战展示题。**AI / AG / RAG / EV 四组是主线**（投 AI 岗先过这四组），其余是工程底座与通用八股。带 `⚠` 的是容易翻车的点。

## AI — LLM 调用工程化

#### AI-1 LLM 调用工程化有哪些要点？（项目的「8 件套」）
限流、降级、预算、重试、超时、可观测、Prompt 版本化、成本核算——通用答案。
✔ 项目结合：全部落地且**框架与业务分层清晰**——框架层用 Spring AI（`ChatModel` / `EmbeddingModel` bean，[ADR-0008](../adr/0008-ai-spring-ai-framework.md) 框架化，删掉自研 Port / 装饰器 / 指标服务），业务层治理保留：`AiRateLimitInterceptor` 令牌桶按场景限流（超限 429）、`@TokenBudget` 日预算（前置检查 + 按真实用量记账）、Prompt 全 YAML 版本化（无 Java 硬编码兜底）、供应商故障 stale 兜底、调用日志 + 成本报表、语义缓存、模型路由、上下文窗口裁剪。**两条 AI 主线链路**（卖家「发布助手」拍照识别单入口 / 买家「对话式找货」RAG 检索）全链路覆盖。

#### AI-2 限流和降级怎么分工？超限用户看到什么？
✔ 项目结合：**两条路径不重叠**——限流超限 → **429 直接拒绝**（保护上游不被烧，`AiRateLimitInterceptor` 按 `AiCallScope` 场景配速率，key 按用户、未登录按 IP）；LLM 供应商故障 → `AiChatService` 服务层 **stale 旧回答**兜底，无 stale 则 unavailable 文案（保可用性）。拦截器**不承担缓存职责**（历史设计用请求体字节做缓存 key，不可靠，已移除）。**Redis 挂了 fail-open 放行**——限流是保护手段，不能成为可用性单点。降级不是静默变差：对话降级与 RAG 降级各有自定义计数指标。

#### AI-3 Token 预算怎么管的？
职责二分：`@TokenBudget` 注解声明场景 + 日预算（编译期契约），`TokenBudgetAspect` 的 `@Around` **只做前置检查**（累计已用 + 本次上限 > 日预算 → 抛异常走统一降级）；**记账在 `AiModelSupport`**：调用后取 `ChatResponse` 的 usage metadata，**有真实 input / output 就按真实值累加**，供应商不回报（embedding 接口 / 流式未带 usage）才退化为场景配置的单次上限——估算偏高，但比「预算恒为 0、限流静默失效」安全。存储两版按配置切换（内存 / Redis `HINCRBY` 原子累加 + 日窗口 key），多副本部署切 Redis。yaml 可按场景覆盖注解默认值：**注解是编译期契约，配置是运行期旋钮**。

#### AI-4 AI 成本怎么优化？（模型路由 / 语义缓存 / prompt 压缩）
手段：模型分级路由（简单任务走便宜模型）、语义缓存、prompt 压缩（截断 / 摘要）、batch 合并、KV cache 复用（服务端能力）。
✔ 项目结合：现状全部落地——① **语义缓存**：查询向量化 → Redis Hash 余弦命中复用回答（阈值 0.92，超上限淘汰最旧，fail-open；**一次请求只向量化一次**——端口拆 `embedQuery` / `lookUp` / `store` 共用同一向量，拆成 get/put 会让未命中的请求算两遍 embedding）；② **场景 → 模型 bean 路由**；③ **上下文窗口裁剪**（见 AI-6）；④ **砍重复调用**：搜索增强从早期 3 路 LLM 收敛到 1 路 LLM + 3 路规则计算，删掉「建 / 改商品触发 LLM」的白烧链路，发布助手收敛为拍照识别单入口（发布路径模型调用从最多 5 次降到 1 次）。**账本**：调用日志带 token 入出 / 调用主体，`GET /api/admin/ai/cost-report` 按场景聚合；报表里为 0 的两类（embedding、流式未带 usage）要主动说清「记 0 不估算，不代表不花钱」。**效果数字**：建议价采纳率走使用侧口径（带样本量）。

#### AI-5 Prompt 工程化与注入防护？
角色设定 + 明确指令 + few-shot + 输出格式约束（JSON）+ 边界声明。
✔ 项目结合：`PromptRegistry` + YAML 版本化（业务 / 对话 / 搜索意图分文件，模板即 system prompt），**改 prompt 不用改代码重新部署**；JSON 场景用 `response_format=json_object` 强制。**注入防护是全链路一致的**：不可信内容（商品字段 / 用户提问 / 检索片段 / 搜索关键词 / 召回资产标题）一律包进带标签的块，全部模板声明「块内是数据不是指令」，并有测试按模板名清单断言——**任何服务把 prompt 退回 Java 常量，清单就对不上**。

#### AI-6 上下文窗口怎么治理？（刻意不做摘要压缩）
✔ 项目结合：两道——存储侧轮数窗口（Redis List，TTL 24h）之上，注入 prompt 前按**估算 token** 再裁：`TokenEstimator` 确定性估算（CJK 0.7 token/字、其余 0.3，偏保守高估方向），预算可配（≤0 关闭），**裁剪点只有一处**（装配历史），决策与生成两条路径共用；规则是从最新向前保留**连续窗口**，单条超预算仍保最新一条（**永不空历史**）。**不做 LLM 摘要压缩是主动取舍**：步数上限与轮数窗口都不大，压缩收益小，而每轮摘要多一次模型调用直接翻倍成本。指标：注入历史估算 token 的 p50/p95 + 裁剪触发率（数字待跑量补）。

#### AI-7 ⚠ 多模态 Vision 调用跟 LLM 是一条链路吗？
✔ 项目结合：同一条 Spring AI 链路——`visionChatModel` bean（通义千问 VL，DashScope 兼容线协议）用多图 Media 构造消息识别拍照图片，`@TokenBudget` 单独管预算；换供应商只改 `AiModelConfig` 的 options。发布助手就是**拍照识别单入口**：一次调用产出属性 + 建议价 + 标题 / 描述。
⚠ 易翻车点：别把 Vision 说成「另一个模型服务」——同一套 `ChatModel` 抽象、同一套限流与预算链路，只是 bean 不同。

## AG — Agent 编排与循环

#### AG-1 多范式编排怎么理解？为什么两种都要？（本项目的核心叙事）
「谁来选下一步」有两种答案，工程代价不同：
- **Workflow 式**（路径写死）：确定性强、能设整体超时、成本可预测，但只能处理预写好的流程。
- **自治式**（模型逐轮决定）：能处理没预写流程的问题，但步数与成本不确定，必须配步数上限 / 中途预算检查 / 按终止原因分类的降级。

✔ 项目结合：同一仓库两种对照——`AiSearchEnhancerAdapter`（Workflow 式 4 路并行扇出）与 `AgentLoopRunner`（自治式多步工具循环）。**口径：能用 Workflow 解决的不用自治**（成本可控）；只有「下一步真的取决于上一步的输出」时才上循环。⚠ 别把 4 路扇出叫「模型自主选路」——四路无条件全提交、模型不参与选路；它的价值在单路降级 + 整体超时 + 降级结果不进缓存。

#### AG-2 ReAct / 多步工具循环怎么实现的？
ReAct = **推理（Reasoning）+ 行动（Acting）循环**：模型思考下一步 → 调工具 → 观察结果 → 再思考，直到收敛。记忆分层：短期（会话窗口）/ 长期（画像或向量记忆库）。
✔ 项目结合（`AgentLoopRunner`，四个要点）：
1. **决策走原生 tool calling**：工具 schema 由 `AgentTools` 的 `@Tool` / `@ToolParam` 生成随请求下发（供应商侧校验 + 参数名锚定，依赖编译期 `-parameters`），执行经 `ToolCallback` 回调——`ChatModel.call` **不自动执行工具**，循环与执行控制权在 runner
2. **三条降级口径**：步数超限 / 循环中途预算耗尽 → 用已积累观察**单次生成**（不丢已有信息）；决策失败（模型故障 / 未返回工具调用 / 参数不可解析）→ **按原始问题检索一次**，而不是不检索——不把决策链路失效伪装成「这题本来就不需要检索」
3. **每步可观测**：每步落 `eo_agent_step_trace`（一次请求一个 trace_id），SSE 推 step 事件（工具 + 决策理由 + 观察）供前端步骤可视化，指标按 outcome 计数归因
4. **待补口径**：平均步数 / 降级率 / 步级延迟 p95——需真实 key 跑量，如实说待补测（复现口径在工程指标）

#### AG-3 工具面怎么设计的？（工具不是越多越好）
✔ 项目结合：`AgentTools` 是唯一落点，按**性质分四层**：
- **检索 3**：平台规则知识库 / 在售资产 / 资产详情（详情必须取自前一步检索观察里的 ID——这是让步骤有依赖的第一步）
- **计算 2**：行情统计（对已召回资产算在售件数 / 均价 / 区间）、多件逐维比对（价格 / 成色 / 地区 / 在售状态，一次替代多次详情查询）——纯 `domain/model` 确定性计算，**零模型调用**
- **写入 1**：`remember_preference` 写长期画像。**独立工具而非收敛轮的参数**——挂收敛轮时，三条降级路径（步数超限 / 预算耗尽 / 决策失败）下偏好会静默丢失
- **收敛 1**：`finish` 声明信息已足够

**计算类工具是关键**：只有检索工具时，循环存在的唯一意义是换关键词重试；有了计算类，**第 N 步才真正消费第 N-1 步的输出**。每个工具第一个参数都是 `thought`（本步理由），落 trace 供排障与展示。

#### AG-4 ⚠ 循环控制权为什么不交给框架托管？LangChain4j 与 Spring AI 差别？
工具 schema 这一层**两家一致**：`@Tool` 都是**运行时反射**生成 JSON Schema（LangChain4j 官方文档也讲参数名靠反射取、编译要加 `-parameters`）——「谁反射谁不反射」不是差异点，别拿它当选型理由。
**真实取舍是循环控制权**：两家都提供托管的工具执行循环（LangChain4j AI Services / Spring AI `ChatClient` 的 ToolCallingAdvisor）；一旦托管，**步数上限、循环中途的预算检查、按终止原因分类的降级就插不进去**。所以 agent 侧只用 `ChatModel` 这一层：发 schema、原样收回 tool call，执行与循环留在 `AgentLoopRunner`。选 Spring AI 是 Spring 原生决定的（`ChatModel` 是 bean、自动装配、Micrometer Observation 直连 Langfuse）。
⚠ 别硬背框架源码——被追问 Bean 注册 / 反射细节时按「绕法」答（00 §6.1）。

#### AG-5 Agent 记忆 / 多轮对话怎么设计？
✔ 项目结合：**短期** = Redis 会话窗口（key 按 sessionId，TTL 24h，裁剪到最近 N 轮）；**长期** = 用户画像表（跨会话持久，由独立工具写入——**模型自主决定何时记**，不依赖收敛轮，所以三条降级路径下偏好都不会丢；聊天时注入 prompt）；**上下文** = 轮数窗口 + token 估算裁剪两道（AI-6）。三个细节：① 决策失败降级为「按原始问题检索」而非不检索；② 生成时历史按**原始角色**传多消息（`[system, 历史 user/assistant…, 当前 user]`），不压进当前 user 消息——跨轮次前缀稳定才能命中供应商的上下文缓存折扣；③ 记忆读写 fail-open。

#### AG-6 流式输出怎么做？（SSE vs WebSocket）
SSE：**单向**服务端推送、HTTP 协议自带、自动重连，适合 token 流；WebSocket：**双向**，适合聊天交互（消息 + 状态 + 指令）。流式工程要点：首字延迟、流中断降级、背压、与限流 / 预算的兼容。
✔ 项目结合：**已落地**（`POST /api/ai/chat/stream`）：`SseEmitter` + `ChatModel.stream`，事件协议 step / token / sources / done / error；四个工程点——① 预算手动前置检查（**流式方法在流结束前就返回，AOP 拦不住**），超限转 SSE error；② 阻塞收流后把完整拼接结果落调用日志（调用日志不缺流）；③ 来源先于正文（检索在生成前就绪，先推 sources 让前端先渲染来源区）；④ 断流 onError 推降级文案。前端选 **fetch + ReadableStream** 而非原生 EventSource（EventSource 只支持 GET 且不能带 Authorization 头，鉴权在 localStorage）。

#### AG-7 MCP 工具面怎么做的？信任边界？
MCP（Model Context Protocol）= 把工具 / 资源按 JSON-RPC 协议暴露给外部 client 的标准方式。
✔ 项目结合：Spring AI `@McpTool` + **streamable HTTP**，端点 `/mcp`，暴露**公开只读** 4 个工具：在售资产检索（与站内搜索同一套两路召回 + RRF 底座）、资产详情、类目逐层浏览、平台规则知识检索——Cursor / Claude Desktop 配上 URL 即可实时查平台数据。**信任边界是设计出来的两级暴露**：外部 client **没有用户上下文**，只挂公开只读数据（不暴露订单 / 个人信息 / 写路径）；Agent 内部工具面与它各自独立、鉴权假设不共用；匿名可达但纳入统一限流，并对 JSON-RPC 重试特性做防重豁免（同字节请求重发属协议内合法行为）。⚠ 踩坑：server 的 `protocol` 属性**必须显式配置**——条件装配读 Environment，属性默认值不生效，缺省时端点整个不装配。

## RAG — 检索增强

#### RAG-1 RAG 是什么？项目怎么做？
RAG = 检索增强生成：外部知识检索 → 拼进 prompt → 生成，解决幻觉与知识时效。
✔ 项目结合：**三条链路一套形态**——① 商品检索（两路独立召回 + 排名融合）；② 知识库（完整链路：摄入 → 两路召回 → 融合 → 引用溯源 → 评测）；③ 在售资产检索（对话式找货，换语料，**共用同一份 `RrfFusion`**，两路都过滤在售状态）。**拒绝 Milvus**：SKU < 10 万，ES 自带 kNN 够用，独立向量库的索引构建 / ANN 调参 / 运维 ROI 为负。

#### RAG-2 ⚠ RAG 全链路有哪些环节？分块策略怎么定？
环节：**文档摄入（解析 → 清洗 → 分块）→ 嵌入索引 → 检索召回 → 重排 → 生成（拼 prompt + 引用溯源）→ 评估**。
分块：固定长度 + overlap（简单可控）vs 语义分块（按标题 / 段落边界，质量高成本高）；chunk size 权衡——太小上下文碎片丢相关性，太大稀释注意力；检索层用 hit rate / MRR，生成层用 faithfulness。
✔ 项目结合：分块已落地（固定长度 + overlap，**切点优先落换行**、best-effort embed、启动补索引）；语料含**同域干扰文档**——踩过的坑是「语料与 topK 同量级时 hit@5 恒为满分，指标成了装饰」。
⚠ 易翻车点：不要把「重排」和「融合」混为一谈——融合解决多路信号怎么合（RRF），重排解决候选精排（Cross-Encoder），项目只做了前者。

#### RAG-3 Embedding 原理？
文本 → 高维向量，语义相近则向量距离近；训练目标让相似文本向量接近。维度影响检索质量与存储成本。
✔ 项目结合：查询侧 embedding 出向量做 kNN；**索引侧 best-effort 写入向量**（失败降级 null 不阻塞索引，查询侧拿不到向量则整条检索退化为纯 BM25）；向量维度必须与 ES `dense_vector` 映射的 dims 一致，**不一致查询直接报错**——这是配置一致性最容易踩的坑。

#### RAG-4 多路召回怎么合？为什么用 RRF 排名融合？
✔ 项目结合（`RrfFusion`，要讲清三点）：
1. **为什么用排名而不是分数**：kNN 的余弦相似度与 BM25 的相关性分**量纲不可比**，加权求和既要调参又对分布漂移敏感；排名是量纲无关的稳定信号
2. **k 的作用**：平滑常数压制「第 1 名 vs 第 2 名」的过度优势——k 越小头部越强势，k 越大越平均
3. **融合解决不了什么**（区分度最高）：融合只解决「多路信号怎么合」，**解决不了单路自己的排序问题**——用同一余弦对稠密候选重排是单调变换、等于没排（[ADR-0012](../adr/0012-rag-hybrid-retrieval-rrf.md) 记录了识别与删除这次无效实现）。所以**必须真的有两路独立召回**，融合才有意义
**追问延伸**：同分怎么办（插入序 + 稳定排序保证评测可复现）；ES 为什么不能同请求「knn + query」（ES 会把两路分数内部合成一个分值，拿不到各自排名）。

#### RAG-5 ES 语义搜索怎么做的？显式排序 / total 口径？
✔ 项目结合：**没有独立的「语义搜索」开关**——一个搜索入口，按相关性排序时自动两路召回（kNN + BM25 各查一次）→ 融合。两个口径要答准：① **显式排序退化为单路**（用户点「价格从低到高」时融合排名与点选排序打架，只走 BM25 并保留 ES 侧排序）；② **`total` 取 BM25 路的总命中**（唯一有全量语义的口径），只有词面命中为 0 而语义路召回到结果时才改报候选池大小——否则前端会出现「共找到 0 件」却列着结果。③ `num_candidates` 必须 ≥ k，否则 ES 直接拒收整个请求。

#### RAG-6 往深做先做什么？（现状 + 缺口 + 触发条件）
✔ 项目结合：缺口是**模型 rerank**（Cross-Encoder 替代 / 叠加排序融合）——双塔召回要快要宽、交叉编码精排要准要窄，成本权衡讲得清；触发条件是分块数上千且 hit@5 触顶而 MRR 偏低（**加变量前语料要够大，否则归因变模糊**）。独立向量库在百万级分块且 ES kNN 延迟成为瓶颈时再评估。faithfulness 这类生成层客观指标同属演进项。**把「现状 + 缺口 + 触发条件」讲全，就是一次完整的演进规划展示。**

## EV — 评估闭环

#### EV-1 怎么判断 AI 输出质量？（LLM-as-Judge 的定位与局限）
三层：① 检索层客观指标（hit rate / MRR / nDCG，可自动算）；② 生成层客观指标（faithfulness / 答案正确率，需金标准）；③ 主观分（Judge 按维度打分）。**Judge 局限**：自评偏差（Judge 与生成同模型）、顺序 / 长度偏差、打分离散不可比。
✔ 项目结合：门禁侧——金标准集（生成 + 检索两类用例）+ `AiJudge` 对照参考打分 + `EvalGate` **双门禁**（低于「基线 − 容忍度」失败，**评审覆盖率低于下限同样失败**——否则均分只是幸存者平均，一条打 5 分就能蒙过）；阈值全在 `eval/baselines.yaml`，**键缺失是加载期异常而不是悄悄回落默认值**（门禁静默放松比加载失败危险）。**定位纪律**：Judge 分数**只作回归门禁、不作对外质量证据**——对外用机械可算指标（hit@5 / MRR）或使用侧数字（建议价采纳率，带样本量）。

#### EV-2 评估体系怎么接进 CI？
✔ 项目结合：评测 workflow **按需 dispatch**——单次评测要打真实模型调用（成本不低），所以不进 PR 路径、也不做定时空跑；**改 prompt / 换模型 / 调检索参数 / 更新语料后手动 dispatch 拿数字**（起 ES + 注入真实 key）。回归用例与基线分离在 yaml，**调基线不动 Java**。**历史数字不可引用**：旧口径（小语料时代）的 Judge / hit@5 与 topK 同量级、hit@5 恒满分，不构成检索质量证据——语料换血后必须重跑。

#### EV-3 反馈飞轮怎么做的？点踩为什么不能直接当用例？
✔ 项目结合：点赞入库 → 管理端导出为金标准用例（只导「有帮助且字段非空」的行，按用例格式渲染、可直接粘贴，导出即标记）→ 人工审核合入评测集。**点踩不自动成用例**——被嫌弃的回答不能当参考标准，否则会把错答案钉成标准；点踩只统计，等人工补正确回答。这是「评估集怎么持续长大」的答案，也顺带回答了「反馈数据怎么用」。

## JAVA — 并发与 JVM

#### JAVA-1 volatile 和 synchronized 的区别？
volatile 保证**可见性 + 有序性**（禁指令重排），不保证原子性；synchronized 三性齐全。volatile 适合「一写多读」标志位。
✔ 项目结合：`AiModelSupport` 的静态 recorder 引用用 `static volatile`（写发生在启动阶段、读在多线程调用点，volatile 保证所有线程看到最新引用）。

#### JAVA-2 线程池参数怎么定？拒绝策略有哪些？
corePoolSize / maxPoolSize / workQueue / keepAlive / 线程工厂 / 拒绝策略；队列满 → 扩到 max → 触发拒绝（Abort / CallerRuns / Discard / DiscardOldest）。
✔ 项目结合：**并行扇出统一用虚拟线程**——4 路 `supplyAsync` 显式跑在虚拟线程执行器上，不用自定义线程池（虚拟线程轻量到可以每任务一个，线程池调参问题被语言特性消除）；唯一保留的池是任务调度器（MDC 透传给子线程）。

#### JAVA-3 ⚠ 虚拟线程了解吗？跟平台线程什么区别？
JVM 调度的轻量线程（JDK 21 正式），挂起时释放载体线程，阻塞不再浪费内核线程；IO 密集吞吐提升显著，CPU 密集无提升。
✔ 项目结合：Spring Boot 开启虚拟线程，`@Async` 消费者跑在虚拟线程；4 路扇出**显式传虚拟线程执行器**（`commonPool` 是平台线程且并行度 = 核数 − 1，配置开关管不到它），取消用 `cancel(false)` 不中断载体。
⚠ 易翻车点：虚拟线程不解决 CPU 密集；`synchronized` 在虚拟线程下会 pin 载体（新版 JDK 已修）；慎在长生命周期虚拟线程上用 `ThreadLocal`（项目用 MDC 快照 + 清理兜底）。

#### JAVA-4 ConcurrentHashMap 原理？
数组 + 链表 / 红黑树 + **CAS + 锁桶头**，`size()` 用 baseCount + CounterCell 分散计数，扩容多线程协助迁移。
✔ 项目结合：内存版预算存储用 `ConcurrentHashMap` + 原子引用做日预算记账，跨日重置的原子性由 `compute` 保证。

#### JAVA-5 ThreadLocal 会内存泄漏吗？
key 弱引用、value 强引用——线程池复用线程时 value 可能残留。规范：**用完 remove()**。
✔ 项目结合：MDC 就是 ThreadLocal——主线程快照复制到子线程，子线程 `finally` 清理防线程池复用泄漏。

#### JAVA-6 CompletableFuture 怎么用的？超时怎么处理？
`supplyAsync` 提交、`allOf().get(timeout)` 聚合等待、`getNow` 拿已完成结果、`cancel(false)` 取消（不中断）。
✔ 项目结合：工作流式扇出——4 路并行（1 路 LLM + 3 路规则），**整体 5s 超时后收集已完成的部分结果**（任一关键路有值即可用），`cancel(false)` 不中断虚拟线程载体。追问：为什么不用 `anyOf`（要的是「能等的都等到」，不是「最快的一个」）。

#### JAVA-7 运行时数据区 / 类加载？
线程共享：堆、方法区（元空间，JDK 8+ 本地内存）；线程私有：虚拟机栈、本地方法栈、PC。类加载：加载 → 验证 → 准备 → 解析 → 初始化；双亲委派避免核心类被篡改。
✔ 项目结合：Spring Boot fat jar 用 `LaunchedURLClassLoader` **打破双亲委派**加载嵌套 jar（`BOOT-INF/classes` + `BOOT-INF/lib`）——不错的加分细节。

#### JAVA-8 ⚠ GC 算法与收集器？你们用哪个？
标记-清除 / 复制 / 整理；收集器演进 Serial → Parallel → CMS → G1（JDK 9 默认）→ ZGC（低延迟，分代 ZGC）。
✔ 项目结合：容器内显式指定 G1（非 ZGC）；GC / 堆指标经 Prometheus 采集。答完补一句「GC 调优不是目标，先看对象分配模式」——**别背 CMS 细节**，G1 的 Region / 可预测停顿与 ZGC 的停顿与堆大小无关才是加分点。

#### JAVA-9 线上 CPU 100% / 内存泄漏怎么排查？
CPU：`top` → `top -Hp` → `jstack` 定位业务线程；内存：`jmap -dump` + MAT 分析大对象 / 支配树，或 arthas。
✔ 项目结合：慢 SQL 拦截器（MyBatis 执行器拦截、阈值上报）把慢查询先变成指标——**慢 SQL 常是 CPU / 内存问题的第一嫌疑**，先用指标定位再用 jstack / jmap 深挖。

## SPRING — Spring / 事务 / 安全

#### SPRING-1 IoC / AOP 原理？
IoC：容器管理生命周期 + 依赖注入；AOP：动态代理（JDK 代理接口 / CGLIB 代理类）+ 切点 / 通知 / 织入。
✔ 项目结合：预算切面（前置检查）、审计切面（写操作审计经 Outbox 入库）、限流拦截器。

#### SPRING-2 ⚠ @Transactional 什么时候失效？（必问题）
八类：同类内部调用（this 不走代理）、方法非 public、异常被吞、抛检查异常（默认不回滚，需 `rollbackFor`）、传播行为错配、数据源不支持、多线程不共享事务、动态代理没生效。
✔ 项目结合：订单状态流转显式 `@Transactional(rollbackFor = Exception.class)`——**正是踩过「检查异常不回滚」的坑后的写法**；下单链路因为要把锁留在事务外，改用显式事务模板控制边界。

#### SPRING-3 Spring Boot 自动装配原理？
`@SpringBootApplication` = 配置类 + 组件扫描 + `@EnableAutoConfiguration`；自动配置类经 imports 清单加载 → `@ConditionalOnXxx` 按条件装配。
✔ 项目结合：框架模块配置类用 `@AutoConfiguration` + 注册 imports（不依赖隐式扫描）；`@ConditionalOnProperty` 控制可选依赖（MQ / ES 可关，关掉走降级实现）——**换实现只改条件配置**。

#### SPRING-4 Spring Security 认证流程？（项目就是标准实现）
过滤器链：认证过滤器 → JWT 验签 + issuer 校验 → 转换为认证主体 → SecurityContext；授权走注解。
✔ 项目结合：双 Token——Access JWT（RSA 签名，短时效，内存）+ Refresh opaque（Redis 存哈希，HttpOnly Cookie，轮换 + 复用检测）；吊销走独立过滤器，与验签职责分离（密码学 vs 吊销状态）。**标准 API 优先**：不手写 JWT 工具类和 Filter，全部走 `oauth2ResourceServer()` 标准配置。

#### SPRING-5 循环依赖怎么解决？
构造器注入循环依赖**直接报错**（设计问题）；字段 / setter 注入可用三级缓存解决。
✔ 项目结合：踩过真实的坑——过滤器直接注入 `List<HandlerMapping>` 触发循环依赖（WebSocket 配置链），改为 `ObjectProvider` 延迟解析打破。

#### SPRING-6 全局异常怎么统一处理？
✔ 项目结合：单一入口用**模式匹配 switch** 按异常类型分发（消除十几个 `@ExceptionHandler` 方法），HTTP 状态码按错误码前缀自动映射；规范是**禁止抛非业务基类的 RuntimeException**（否则落 500 兜底），模块用专属错误码不回落全局码。详见 §三 全局异常。

## DB — MySQL 与缓存

#### DB-1 索引原理？为什么 B+ 树？
多叉平衡树，非叶子只存索引（扇出高、层数低），叶子存数据 + 双向链表（范围查询友好）；相比 B 树，数据只在叶子出现。
✔ 项目结合：订单按买家 / 卖家 / 状态建索引；慢 SQL 走拦截器监控。

#### DB-2 索引失效场景？
最左前缀不满足、隐式类型转换、对索引列做函数 / 运算、`LIKE '%xx'` 前置通配、`or` 有一侧无索引、`NOT IN` / `!=`（部分优化器行为）。
✔ 项目结合：曾修过 `IN (${ids})` 字符串拼接——改参数化 `<foreach>` + `#{}`，**既防注入又保证查询计划缓存命中**。

#### DB-3 事务隔离级别？脏读 / 幻读？
读未提交（脏读）/ 读已提交（不可重复读）/ 可重复读（幻读，MVCC 解决普通快照读）/ 串行化；MySQL 默认 RR + 间隙锁解决当前读幻读。
✔ 项目结合：默认 RR 未改——一致性靠「本地事务 + 分布式锁」在业务层解决，**调级别是治标，业务锁才是治本**。

#### DB-4 MVCC 原理？
undo log 版本链 + 隐藏列（事务 ID / 回滚指针）+ ReadView（活跃事务列表），快照读按可见性判断；当前读走当前版本 + 锁。

#### DB-5 慢 SQL 怎么优化？
EXPLAIN（type / rows / Extra）→ 索引优化 → 覆盖索引 / 索引下推 → 分批 / 游标分页 → 读写分离 / 缓存。
✔ 项目结合：三层兜底——① 业务层缓存拦热点读；② 监控层慢 SQL 拦截器（阈值上报指标）；③ 数据层覆盖索引 + 参数化查询。

#### DB-6 缓存穿透 / 击穿 / 雪崩？（先答三防，再答项目为什么简化）
穿透 = 查不存在（负缓存 / 布隆）；击穿 = 热点 key 过期瞬间（单飞 / 锁）；雪崩 = 大面积同时过期（TTL 错峰 / 随机化）。
✔ 项目结合：**三防已落地**（Spring Cache 注解 + Redis 单层）——穿透 = null 结果缓存（一致性由写路径事件 evict 关窗口）；击穿 = `@Cacheable(sync=true)` 同 key 单飞重建；雪崩 = 写入时按比例给 TTL 加随机抖动；可用性 = `CacheErrorHandler` fail-open。**布隆过滤器与手写多级缓存已移除**——单库单 Redis 部署下复杂度换不来可感知收益（**「评估后不用」比堆功能加分**，但要知道多级缓存的教科书方案）。

#### DB-7 缓存一致性怎么保证？持久化与过期策略？
一致性主流：Cache Aside + 先更新 DB 再删缓存 + 延迟双删 / 订阅 binlog；**读写并发下「删缓存 vs 写 DB」的竞态**是核心难点。Redis 持久化：RDB 快照（fork + COW，重启快）/ AOF 追加（everysec 兜底），生产一般都开。过期：惰性删除 + 定期抽样 + 内存淘汰。
✔ 项目结合：写路径显式失效（领域事件触发注解式 evict，key 精确）+ 短 TTL 兜底；**无本地 L1 层**，单 Redis 天然没有「多节点 L1 广播」问题。答完补一句「强一致要上分布式锁 + 版本号，业务接受最终一致才用缓存」。

#### DB-8 Redis 数据类型与底层结构？项目里用了哪些？
String（SDS）/ List（quicklist）/ Hash（listpack / hashtable）/ Set（intset / hashtable）/ ZSet（skiplist + dict）；另有 Bitmap / HyperLogLog / Geo / Stream。
✔ 项目结合（按用途列，别只背数据结构）：① 缓存（Spring Cache，String key + JSON value）；② 会话窗口（List，带 TTL）；③ 令牌桶限流（Redisson 的 Lua 原子取桶 / 补桶）；④ 事件消费幂等（String + `SET NX EX`）；⑤ 分布式锁（Hash 结构存持有者 + 重入计数）；⑥ 预算记账（Hash `HINCRBY` 原子累加 + 日窗口 key）；⑦ 语义缓存（Hash 存 query 向量 + 回答，遍历算余弦）。**踩过的坑**：默认 JDK 序列化器让 Lua 里 `tonumber` 取不到值 → 限流器静默 fail-open，统一 `GenericJacksonJsonRedisSerializer` 后解决。

## MQ — 消息与事件

#### MQ-1 消息怎么保证不丢失？（项目三层全做）
生产端 confirm、Broker 持久化、消费端手动 ack + 重试。
✔ 项目结合：**Outbox 比 confirm 更靠前**——业务表与事件表**同事务写入**，事务提交后异步外发，发送成功才标记完成，崩溃重启重发未完成事件。confirm 只保证「Broker 收到了」，Outbox 保证「**业务成功 = 消息必发**」。

#### MQ-2 消息重复消费怎么解决？（项目就是标准答案）
消费端幂等。✔ 项目结合：`SET NX EX` **一条原子命令**领取处理权（key 命名空间 = 消费者 + 事件类型 + 事件 ID，TTL 覆盖三级重试窗口）——单命令即原子，不存在「查标记 → 写标记」的竞态，**所以不需要分布式锁**；领取失败即判重复跳过。处理失败**撤销标记**再抛，让容器重试 / 重投能重新执行——宁可重试不可漏处理。第二道是业务副作用本身幂等（库存走流水唯一键）。「at-least-once + 幂等 = exactly-once 效果」。

#### MQ-3 消息积压怎么处理？
定位（队列深度指标）→ 紧急扩容消费者 / 临时队列迁移 → 找消费慢根因（慢 SQL、下游阻塞）。✔ 项目结合：消费者各自独占队列，消费异常进 DLQ **不阻塞主队列**，积压可从指标看趋势。

#### MQ-4 顺序消息？
RabbitMQ 天然无序（多消费者并发）；方案：单队列单消费者 / 一致性 hash 按业务键路由 / 客户端排序。
✔ 项目结合：**刻意不保证跨事件顺序**——订单生命周期各事件独立处理（恢复库存 / 标记售出互不依赖），顺序性由**业务状态机守卫**（非法转换直接拒绝）。这是「用领域规则替代消息顺序」的取舍。

#### MQ-5 RabbitMQ vs Kafka？（ADR 有完整评分）
✔ 项目结合：① **DLQ + 重试**：Rabbit 的队列级死信是声明式的，Kafka 没有死信概念、要自己发 dlq topic + 调度重投 + 管位点，成本翻倍；② **模型匹配**：1 事件扇出到多独立下游，Rabbit 的「Exchange → 多独立队列」原生，Kafka 要建同样多 consumer group 各自维护 offset + 重试；③ **成本 / 运维**：Kafka 吞吐优势在百万级才显现，我们量级单节点够，分区 / 副本 / lag 运维是纯负担；④ **真要换优先级 NATS JetStream**（有原生 `max_deliver` + `discard policy=dead`，声明粒度最接近 Rabbit，替换成本最低），且 MQ 选型是 Port 抽象下的配置位，domain / application 层不用动。**拒绝理由与评分权重都在 ADR-0005 里，不是偏好。**

## DIST — 分布式与一致性

#### DIST-1 CAP / BASE？
CAP 三选二（分区容错必然存在，实际是 CP vs AP）；BASE = 基本可用 + 软状态 + 最终一致。
✔ 项目结合：下单「本地事务 = CP（强一致），事件副作用 = BASE（最终一致）」——同一业务两种语义分层，是分布式设计基本功。

#### DIST-2 ⚠ 分布式事务方案对比？（工程底座核心叙事）
2PC / XA（协调者阻塞、长锁）、Seata AT（undo_log + 全局锁、代理数据源）、TCC（3× try/confirm/cancel 样板）、Saga（补偿编排）、本地消息表 / Outbox。
✔ 项目结合：**全家族被拒**（[ADR-0001](../adr/0001-order-saga-vs-2pc.md) → [ADR-0007](../adr/0007-order-local-tx-over-saga.md)）：单库场景本地事务 + 分布式锁 + Outbox 比 Saga 更强（补偿与回滚重复、崩溃后状态丢失）；Seata TC 单点与 fail-open 降级模式冲突；TCC 侵入大；2PC / XA 需全局协调器 + 锁等待长。触发演进条件是模块拆独立数据源 / 独立部署。
⚠ 被追问 Seata 部署细节（TC/TM/RM 高可用）时按「绕法」答：没在生产跑过，评估阶段的核心关注点是 undo_log + 全局锁的写路径成本与中间件单点。

#### DIST-3 幂等设计怎么做？
唯一键约束、状态机幂等（已处理状态拒绝重复）、token / 防重表、Redis SETNX。
✔ 项目结合：**三层幂等各司其职**——① 协议级幂等（客户端幂等键，缓存成功响应字节级回放）；② 防连点（短窗口 + 方法 + 请求体 hash，**不缓存响应**）；③ 事件消费幂等（`SET NX EX` 领取处理权）。**防重放 / 防连点 / 防重复消费**三件事不要混着讲。

#### DIST-4 分布式 ID？
雪花（时间 + 机器 + 序列）、UUID v7（时间有序）、各家发号器。
✔ 项目结合：**UUID v7**——时间戳前缀保证**索引局部性**（B+ 树写入友好），零配置零依赖；在 Snowflake 与 v7 之间选了 v7，砍掉机器号分配与时钟回拨处理。不选自增的关键理由是**聚合 ID 必须先于 INSERT 存在**（决策全文 [ADR-0011](../adr/0011-uuid-v7-primary-key.md)）。

#### DIST-5 限流算法？（项目令牌桶）
固定窗口（边界突刺 + 非原子）、滑动窗口（内存大）、漏桶（恒定速率）、令牌桶（允许突发 + 平滑）。
✔ 项目结合：两处限流——全站 GET 走本地固定窗口（单实例够）、写操作走 Redisson 分布式令牌桶（跨实例统一计数，防超卖）；AI 端点按场景令牌桶（超限 429）。**Redis 挂了 fail-open**（限流不是单点）。

#### DIST-6 熔断 / 降级？
熔断：失败率超阈值开闸 → 半开探测 → 恢复；降级：超时 / 默认值 / 本地兜底。
✔ 项目结合：**先给通用框架再讲取舍**——自研熔断已随缓存重构移除，缓存降级统一由 `CacheErrorHandler` fail-open 承担（集中一处替代逐点 try-catch）。AI 侧重试与并发隔离由框架客户端内置（自研舱壁已删，ADR-0008 框架化）。缺口主动说：**无跨供应商容灾**（每场景单供应商，故障时降级而非切备用模型，已知技术债）。

#### DIST-7 分布式链路追踪？
✔ 项目结合：traceId 从 HTTP 头提取 → MDC → 异步任务装饰器透传 → 消息 header 注入 → 消费者解码回 MDC，日志与指标统一关联；**可观测出口已换成 OTel 桥 → Langfuse**（原 Zipkin 上报是死链路，已删）。单 JVM 多模块场景跨进程边界只在 MQ 头传递；拆多 JVM 走 W3C traceparent 标准。

#### DIST-8 分布式锁怎么做？（项目就是 Redisson）
手写方案三件套：`SET NX` + 过期时间（防死锁）+ 唯一 value（防误删）+ Lua 释放（原子）。
✔ 项目结合：**手写版本评估过，最后用 Redisson**——补上了 watchdog 续期（不传 leaseTime 时）、可重入、公平锁；我们用的是三参 `tryLock(waitTime, -1, SECONDS)`，**leaseTime=-1 交给 watchdog 续期，waitTime 只是获取锁的等待超时**；释放前检查 `isHeldByCurrentThread()` 防误删；**锁的释放推迟到事务提交 / 回滚之后**（提前释放会让后一个请求读到旧库存快照）；多商品锁按 ID 排序获取防 AB-BA 死锁。**「锁内做幂等」要分清**——`SET NX EX` 单命令原子所以不需要锁，需要锁的是「查-写」多命令序列。详见 §三-12。

## DDD — 架构落地

#### DDD-1 DDD 和传统 MVC 分层区别？
MVC 按技术切（Controller / Service / DAO），业务规则散落 Service；DDD 按领域切（domain / application / adapter），**不变量下沉聚合根**，领域层零框架依赖，依赖方向单向向内。
✔ 项目结合：四层 + Maven 多模块 + Port 接口编译期隔离 + ArchUnit 规则 CI 守卫（规则清单以 `ArchitectureRulesTest` javadoc 为单一来源，条数见[结构计数](../工程指标.md#结构计数)）。

#### DDD-2 聚合根 / 实体 / 值对象区别？
聚合根：聚合入口 + 不变量守卫；实体：有 ID 可变；值对象：按值等价不可变。
✔ 项目结合：**只对「有规则的字段」做 VO**（ID 语义、金额精度、手机号格式），不每字段包一层——避免 ceremony。聚合根不可变（`@Builder(toBuilder = true)` 重建新实例），状态转换返回「新聚合 + 领域事件」。

#### DDD-3 CQRS 什么时候用？
读多写少 + 跨聚合查询 + 读写独立优化才用。✔ 项目结合：只在 product / order / payment / message 做，且**深度不同**——product / order 有独立 ReadModel，payment / message 只做 Handler 级分离 + 独立查询仓储（聊天消息读写比接近 1:1，读模型收益接近 0）；favorite（单表索引够）/ user（读写均衡）**刻意不做**（[ADR-0002](../adr/0002-cqrs-scope-4-modules.md)）。

#### DDD-4 事件驱动架构？Outbox 模式？
✔ 项目结合：领域事件 = 状态转换的副产物（`Transition<聚合, 事件>` 一并产出），跨模块零同步耦合；Outbox 保证「业务成功 = 事件必达」；消费侧 DLQ 三级重试 + 幂等收口。**扣库存是刻意的例外**（同事务同步扣），因为它是防超卖的不变量、不能靠最终一致。

#### DDD-5 六边形架构 / 端口适配器？
领域在中心，出站 / 入站都是 Port 接口，Adapter 实现外围依赖。
✔ 项目结合：Port 编译期隔离（跨模块依赖全部 `optional`，边界靠编译期而非约定），换实现（锁 / 支付 / 短信 / ES / AI 供应商）只改 adapter。**六边形不等于什么都自己包一层**——最贵的一课是 AI 侧曾自研 Port / 适配器 / 装饰器，框架成熟后全部删掉换 Spring AI。

#### DDD-6 为什么拒绝 Saga？（被追问架构必答）
单库本地事务 = 比 Saga 更强的强一致；Saga 补偿与回滚重复、崩溃状态丢失；Seata TC 单点与降级冲突；TCC 样板爆炸。触发演进：拆独立数据源 / 独立部署。完整应答见 [00-怎么说.md §4.2](00-怎么说.md)。

## S — 通用场景题

#### S-1 「你项目里最有挑战 / 踩过最大的坑？」
推荐两个叙事（选一个主讲，第三个备选）：
- **技术选型纠偏**：自研 AI Port / Adapter + 装饰器 → 框架成熟后全面框架化（ADR-0003 → 0008）——「承认自研与框架重复，删掉手写代码」比「从不犯错」可信
- **一致性架构决策**：Saga 上过线 → 发现单库场景补偿与回滚重复、失败状态随事务丢失 → 回退本地单事务 + 分布式锁 + Outbox（ADR-0001 → 0007）
- **备选技术坑**：Redis 序列化器（默认 JDK 序列化 → Lua `tonumber` 失败 → 限流器 fail-open）——排查链条完整可讲；或「余弦重排等于没排」的识别与删除（ADR-0012）

#### S-2 「让你设计 10 倍流量怎么改？」
分层回答：① 读写分离（主从 + 读库扩展）；② 缓存前置（命中率已高，加 CDN / 预热）；③ 多实例（已用 compose 多实例 + nginx LB 验证过横向扩展）；④ Redis 单点 → 哨兵 / 集群；⑤ 跨库演进：模块拆独立数据源后**此时才重新评估真 Saga**（ADR-0007 触发条件）；⑥ AI 链路：令牌桶参数按容量调整 + 预算下调 + stale 兜底 + 预算存储切 Redis；⑦ 压测持续断言门禁。
> **顺序要对**：先横向扩容 + 缓存，**最后才拆库上 Saga**——展示「演进触发条件」思维。

#### S-3 「你们为什么不用微服务？」
单 JVM 多模块：模块边界 = **编译期强制**（Port + ArchUnit）；微服务的核心收益（独立部署 / 独立扩容 / 故障隔离）在单机阶段收益为零，跨模块一致性用本地事务就能解决（微服务反而要引 Saga / 分布式事务）。触发条件：团队规模 / 流量 / 独立部署诉求到阈值（[ADR-0006](../adr/0006-module-decoupling-port-adapter-acl.md)）。

#### S-4 「这个项目你还会加什么？」
按 ROI 提 2-3 个（体现演进规划）：① 循环三口径跑量回填 + 首字延迟埋点（补测量债）；② 检索质量回归进定时 / 门禁（当前按需 dispatch）；③ 跨供应商容灾（按场景挂第二供应商 bean，触发条件是 AI 链路进 SLA）；④ Agent 演示素材落地（多步找货流式 / Cursor 连 MCP / Langfuse trace 面板）。

# 二、DDD 核心思想轻量落地（工程底座，被追问时用）

> 本项目 DDD 是**「展示核心思想、拒绝过度设计」的克制落地**——在简历与口头叙事里它是**工程底座**（支撑 AI 链路的生产级要求），不是并列主线。投 AI 岗扫过即可；被追问架构 / 投通用 Java 后端时按本节深挖。
>
> 一句话定位：**DDD 六边形 + CQRS，domain → application → adapter 单向依赖**。Maven 多模块、核心聚合根 Product / Order / Payment / User、Port 接口编译期隔离、ArchUnit 规则在 CI 守分层（规则清单与条数以 `ArchitectureRulesTest` javadoc 与[结构计数](../工程指标.md#结构计数)为准）。

## 0 为什么上 DDD——驱动、收益、代价（自证不是跟风）

**驱动**（MVC 三层在本项目会怎样）：① 业务有真规则要单点守卫——商品上架的两条路径共用同一组 `validateOnline()` 不变量，「订单状态 × 支付状态」二维状态机由动作表唯一裁决，MVC 里同一不变量各写一份、改一处漏一处；② 模块边界要可执行——包结构拦不住 `import` 对方 Mapper（历史教训：order 曾直接依赖 product 的 mapper 扣库存，后来重构回 Port）；③ 外部依赖多、要可换可降级——LLM 供应商 / ES 可关（走 LIKE 兜底）/ MQ 可关，全靠条件装配；④ 领域逻辑要能纯单测——domain 零框架依赖，变异测试只对 domain 注入。

**收益（都能核验）**：不变量只写一处｜依赖方向 CI 强制（历史债用冻结规则拦住，重构移除后自动解除）｜模块边界 = 接口签名（跨模块依赖全部 `optional`，Port 目录本身就是协作地图）｜换实现 / 降级只动 adapter（ES 关走 LIKE 兜底、AI 供应商切换改 options、自研 AI 抽象换 Spring AI）｜跨模块读自持快照换解耦（订单读商品快照，商品改名删除不影响已下订单）｜演进有量化触发条件（拆独立数据源 → 重新评估 Saga，[ADR-0010](../adr/0010-order-saga-evolution-plan.md)）。

**代价（都实际付了）**：每个跨模块协作多一层 Port + 适配器样板｜模块间结构不统一（CQRS 只有部分模块、领域服务数量差异大——结构差异是领域性质的产物，写进 ADR 作评审判据）｜双层模型转换（DO ↔ 聚合根）｜定位成本（查字段谁写的要跨 Port → Adapter → Repository 三跳）。

**负收益判据（什么情况别用）**：单表 CRUD 无跨聚合不变量 → 直接 AppService + Mapper；读写比均衡 → 不上 CQRS；聚合无生命周期 → 不硬造状态机；字段无规则 → 不包 VO；**框架 / 标准库已有能力不自研抽象**（最贵的一课：AI 侧曾自研 Port / 适配器 / 装饰器，框架成熟后全删换 Spring AI——六边形不等于什么都自己包一层）。

## 1 核心思想清单（讲了能拿分的）

> 面试讲 DDD 别背概念，直接指代码。每条带落点 + 「为什么这是轻量的」——后者才是拉开差距的地方。

### 1.1 聚合根（Aggregate Root）——状态机 + 不变量内聚
- **落点**：`order/domain/aggregate/Order.java`、`payment/.../Payment.java`、`product/.../Product.java`、`user/.../User.java`
- **共性**：聚合都是**不可变对象**（字段 final，`@Builder(toBuilder = true)` 重建新实例替代原地修改），只做状态机 + 不变量，**不碰持久化、不注入外部依赖**（domain 零框架依赖由 ArchUnit 锁死）
- **状态机「只有部分聚合有」，签名还各不相同——别一勺烩**：
  - `Order`——**最完整**：单参入口 `transitionTo(动作, 原因)` 一处守卫 + 一处应用副作用；公开转换全部返回「新聚合 + 领域事件」
  - `Product`——**有状态机但目标状态驱动**（`transitionTo(目标状态)`），两条进入上架状态的路径都必须过同一组完整性校验
  - `Payment`——**没有 `transitionTo` 方法**：守卫收口在状态谓词（`canPay` / `canRefund` / …），终态转换才产事件，中间态转换直接返回裸聚合
  - `User`——**没有状态机**：只有承载不变量的变换方法（改密码 / 改头像 / 记录登录）
- **为什么轻量**：状态机只给**真生命周期**的聚合上，没有就硬造；规则只在动作表 / 状态表 / 谓词一处写；跨聚合一致性交给事件，不搞聚合内嵌反规范化

### 1.2 不变量（Invariant）只写一处
- **落点**：建单链式断言（不能认领自己、至少一件资产、金额 > 0）+ 状态合法性由动作表裁决（每个动作声明前置状态 / 目标状态 / 目标支付状态 / 错误码）
- **为什么轻量**：规则只写一处，测试直接打聚合根；不需要规则引擎 / Guard 框架。**状态裁决按模块各归其位**（订单用动作表、商品用转换表、支付用谓词）——「状态合法性由谁说了算」这一问要答得出

### 1.3 值对象（Value Object）
- **落点**：各模块的 ID 值对象、`Phone` / `Address`、跨模块共享的 ID 值对象与 `Money`（金额不落 `double`）
- **为什么轻量**：**只对有规则的字段做 VO**（ID 语义、金额精度、手机号格式），避免为 VO 而 VO 的 ceremony

### 1.4 领域事件（Domain Event）——状态转换的副产物
- **落点**：各模块 `domain/event/`，转换方法统一返回「新聚合 + 事件」；事务提交后经 **Outbox** 与业务同事务写入
- **为什么轻量**：事件是状态转换自然产生的副产物，不是到处 `new`；跨模块副作用由消费者异步触发，聚合不感知

### 1.5 工厂与重建分离
- **落点**：`createOrder(spec)`（**跑不变量**）vs `from(spec)`（**不跑不变量**，从库重建）
- **为什么轻量**：重建时库里的数据已被校验过，不重复触发不变量；参数用 record 收敛，避免长参数列表

### 1.6 仓储 + 端口（Repository & Port / 六边形）
- **落点**：读写分离的仓储（CQRS）与各类 Port 接口（锁 / 支付网关 / 库存 / 检索 / LLM）
- **为什么轻量**：domain 只依赖接口，实现全在 adapter；换实现只改 adapter，domain / application 一行不动

### 1.7 领域服务 vs 应用服务
- **落点**：领域服务（纯规则、无仓储，如敏感词过滤）vs 应用服务（**编排**：读状态 → 决定是否持久化）
- **为什么轻量**：**只有不天然属于某个聚合的规则才做领域服务**；涉及读状态 + 调仓储的编排一律放 application——分不清这两个是 DDD 面试最常见的扣分点

### 1.8 CQRS（做几个模块、两种深度）
- **落点**：product / order 有独立 ReadModel；payment / message 只做 Handler 级分离 + 独立查询仓储；范围决策见 [ADR-0002](../adr/0002-cqrs-scope-4-modules.md)
- **为什么轻量**：收益是「读多写少 + 跨聚合聚合 + 读写独立优化」；不满足就不做（favorite / user）。**别把 message 说成「不做 CQRS」**——它做了 Handler 级分离，只是没有独立 ReadModel

### 1.9 防腐层 / 依赖治理（用测试守边界）
- **落点**：`ArchitectureRulesTest` 的规则在 CI 阻断违规（清单与条数以该类 javadoc 与[结构计数](../工程指标.md#结构计数)为单一来源）
- **为什么轻量**：用 ArchUnit 测试守分层，**不靠空壳架构 / 冗余包**；规则坏了 CI 直接红

## 2 刻意不做 / 轻量化取舍（防「过度设计」扣分话术）

> 面试官想听的不是你会用多少模式，而是**你懂什么时候不该用**。每条都是「我评估过、主动拒绝」。

| 没做的 | 为什么不做的理由 | 做了会怎样被扣分 |
|---|---|---|
| **Saga / 2PC / Seata AT / TCC** | 单库部署，一个本地事务把订单 / 库存 / 支付 / Outbox 全包进同一事务，比 Saga 最终一致更强（[ADR-0007](../adr/0007-order-local-tx-over-saga.md)） | 挂一个失效的状态机，观测价值低于写路径成本，典型「为了架构而架构」 |
| **全模块 CQRS** | 收益 < 维护成本（[ADR-0002](../adr/0002-cqrs-scope-4-modules.md)） | 每模块 Command/Query 双倍代码，纯负担 |
| **Specification 模式** | 支付的状态谓词不是「跨对象规则组合」，是转移谓词 | 假模式名露怯 → 已改名状态守卫 |
| **每个字段都包 VO** | 只对有规则的字段做 | ceremony，代码量膨胀 |
| **Milvus / PGVector** | SKU < 10 万，ES kNN 够用 | 向量索引 + ANN 调参一整套运维负担 |
| **Spring Cloud 微服务拆分 / RPC** | 模块化单体 + ArchUnit + Port 隔离跨模块；拆分触发条件已量化（[ADR-0010](../adr/0010-order-saga-evolution-plan.md)） | 单机演示拆微服务，分布式复杂度零收益，还答不上「为什么拆」 |
| **中间件进 K8s** | K8s 只编排无状态应用层，中间件外部化（生产用托管服务） | 被追问 PVC / 分片再平衡 / 故障恢复就答穿 |
| **托管式 Agent 循环（框架 ToolCallingAdvisor）** | 步数上限 / 循环中途预算检查 / 三口径降级插不进去（AG-4） | 生产级控制点全丢，被追问「步数怎么控制的」答不上 |
| **LLM 摘要压缩 / 多智能体编排（本仓库）** | 摘要：步数与轮数上限下收益小、成本翻倍；多智能体：分工归第二个项目（本仓库命题是「一个 agent 怎么做到生产级」） | 前者凭空翻倍成本，后者与第二项目关键词互抢 |

## 3 面试 60 秒 DDD 概括稿（被追问架构时用）

> 「项目是 DDD 六边形 + CQRS 的克制落地，它是**支撑 AI 主线的工程底座**。核心聚合根都做不可变对象：Order 状态机最完整（单一入口守卫，转换产出领域事件走 Outbox）；Product 是目标状态驱动的状态机，两条上架路径统一过同一组完整性校验；Payment 用状态谓词守卫、终态才产事件；User 没有状态机就不硬造。跨模块副作用由事件异步触发，聚合不碰持久化，领域层只依赖 Port 接口，ArchUnit 规则在 CI 守分层。

我特意做了几个轻量化取舍：**拒绝 Saga**（单库本地事务 + Outbox 比 Saga 更强，挂失效状态机是过度设计）；CQRS 只做部分模块且深度不同；值对象只对有规则的字段做；**框架已有能力不自研抽象**（AI 侧自研抽象在框架成熟后全删）。这些取舍比堆模式更能体现工程判断力。」

## 1 多步工具循环 — AgentLoopRunner

- **文件**：`easyorange-ai/.../application/service/AgentLoopRunner.java`
- **关键代码**：
  ```java
  for (int round = 1; round <= maxSteps; round++) {
      var decision = decide(prompt, callbacksByName);   // 原生 tool calling：发 schema、收回 tool call
      if (decision.isFinish()) { break; }
      if (budgetExhausted()) { outcome = OUTCOME_BUDGET; break; }   // 循环中途预算检查
      var outcome = executeTool(decision, callbacksByName);         // 执行在 runner，不在框架
      observations.add(new StepObservation(decision.tool(), toolInput, outcome.observation()));
  }
  ```
- **实现要点**：
  1. **决策走原生 tool calling**：schema 由 `AgentTools` 的 `@Tool` 注解生成随请求下发，`ChatModel.call` 不自动执行工具（自动执行在 `ChatClient` 层）——执行与循环控制权在 runner
  2. **三条降级口径**：步数超限 / 预算耗尽 → 用已积累观察单次生成；决策失败 → 按原始问题检索一次（**不是不检索**）
  3. **每步落 trace**（一次请求一个 trace_id）+ SSE step 事件；指标按 outcome 计数（finished / step_limit / budget / decision_failed）归因
  4. 失败的工具结果**也进观察**（模型可据此换参数重试），不吞异常
- **可能的追问**：「步数上限怎么定？」→ 可配，取值兼顾「多文档对比够用」与「成本 / 延迟可控」；到上限不是报错而是降级生成。「为什么不用递归？」→ 显式 for 循环 + 显式状态更好加预算检查与终止原因分类。「观察太长怎么办？」→ 工具结果有文本转换器压成紧凑观察（列表类工具截断 + 提示可分页）
- **一句话**：手写循环持有控制权——原生 tool calling 决策、runner 执行工具、三条降级口径与步级 trace 都在自己的循环里

## 2 工具面 — AgentTools

- **文件**：`easyorange-ai/.../application/service/AgentTools.java`（工具名与编排器共用常量）
- **实现要点**：
  1. **按性质分四层**：检索 3（规则知识 / 在售资产 / 资产详情）+ 计算 2（行情统计 / 多件逐维比对，纯 JDK 零模型调用）+ 写入 1（长期偏好）+ 收敛 1
  2. **计算类让步骤产生依赖**：没有它，循环只是换关键词重试；有了它，第 N 步真的消费第 N-1 步的输出
  3. **写入工具独立**：偏好写入从「收敛轮参数」拆成独立工具——挂在收敛轮时，三条降级路径下会静默丢失
  4. 每个工具首参是 `thought`（本步理由）→ 落 trace、供前端展示与排障；详情 / 比对类工具的 ID 参数要求取自前一步观察

- **一句话**：工具面按性质分层，计算类工具是让循环「真的多步」的关键，写入与收敛独立成工具

  1. **锁在事务外获取**（等待不占数据库连接）、**事务提交 / 回滚后释放**——提前释放会让后一个请求读到旧库存快照，击穿防超卖
  2. `buildLockKeys`：多商品按 ID **排序去重** → 防 AB-BA 死锁
  3. 事务内顺序：建单 + Outbox 发事件 → 同步扣库存 → 建支付 → 卖家缓存驱逐
  4. 任一步失败整体回滚，抛领域异常（**无补偿路径**）；锁获取失败在事务开启前抛出（无回滚开销）
- **可能的追问**：「锁和事务的顺序有问题吗？」→ 先拿锁再开事务、提交后再释放锁，收敛防超卖窗口；「库存在这里为什么同步扣而同其他副作用异步？」→ 防超卖是不变量，不能靠最终一致
- **一句话**：先取锁 → 本地事务内建单 → 扣库存 → 建支付，失败整体回滚，拒绝 Saga（ADR-0007）

## 11 订单状态机 — Order + OrderAction

- **文件**：`easyorange-order/.../domain/aggregate/Order.java`、`domain/constant/OrderAction.java`
- **关键代码**：
  ```java
  // 动作枚举：每个动作声明前置状态集合、目标状态、目标支付状态、错误码（状态机唯一事实来源）

  CANCEL("取消", Set.of(PENDING_PAYMENT), CANCELLED, null, ...)
  ```

- **实现要点**：

- **一句话**：状态机唯一事实来源是动作表，聚合根单一入口守卫，转换产出事件走 Outbox

## 12 分布式锁 — DistributedLockPort + DistributedRedissonLockAdapter

- **文件**：`easyorange-framework/.../lock/DistributedLockPort.java`（端口）、`.../DistributedRedissonLockAdapter.java`（实现）
- **关键代码**：
  ```java
  RLock lock = redissonClient.getLock(lockKey);
  boolean locked = lock.tryLock(waitTime, -1, TimeUnit.SECONDS);  // leaseTime=-1 → watchdog 续期
  // 锁在事务提交 / 回滚后释放（事务同步回调），不是 finally
  ```
- **实现要点**：
  1. `leaseTime=-1` → watchdog 续期（默认 30s 锁、每 10s 续），**不必手工估算事务耗时**
  2. **释放推迟到事务提交 / 回滚后**——提前释放会击穿防超卖
  3. 释放前检查 `isHeldByCurrentThread()`，防误删他人锁
  4. 多锁按 ID 排序逐个获取（打破循环等待防死锁）；锁 key 按业务前缀区分
  5. 失败语义：获取失败抛统一的锁异常，业务在自身边界映射为领域异常；`waitTimeout=0` 即非阻塞尝试
- **可能的追问**：「锁过期业务还没完？」→ watchdog 续期不会自动过期；holder 超阈值有告警；「Redis 挂了锁怎么办？」→ 连接异常时获取失败走事务回滚（**不静默放行**——超卖保护宁可失败不可绕过）
- **一句话**：Redisson 锁 watchdog 续期、事务提交后释放、按 key 排序防死锁、释放前校验持有者

## 13 事件幂等 — EventIdempotencyChecker

- **文件**：`easyorange-framework/.../event/idempotency/EventIdempotencyChecker.java`
- **关键代码**：
  ```java
  // 一条 SET NX EX 领取处理权（false = 重复 / 他人处理中）
  if (idempotencyEnabled && !idempotencyChecker.tryMark(namespace, eventId)) return;
  ...
  } catch (Exception e) {
      idempotencyChecker.unmark(namespace, eventId);   // 失败撤销标记，容器重试 / DLQ 重投可重新执行
      throw e;
  }
  ```
- **实现要点**：
  1. `SET NX EX` 是单条原子命令，**无查-写竞态**，因此不需要分布式锁
  2. 标记 TTL 覆盖 DLQ 三级重试最长窗口
  3. **失败撤销标记**（宁可重试不可漏处理）；「标记后、处理完成前」崩溃的残留窗口由业务副作用幂等兜底（库存走流水唯一键）
  4. 命名空间隔离多消费者监听同一事件
- **可能的追问**：「at-least-once + 幂等 = 精确一次？」→ 是（不丢 + 重复只处理一次）；「TTL 过期后重复怎么办？」→ 事件 ID 带时间戳，超窗重放概率趋零，是成本权衡
- **一句话**：`SET NX EX` 原子领取 + 失败撤销 + 业务副作用幂等，达成 exactly-once 效果

## 14 Outbox 与 DLQ — ModulithDomainEventPublisher + DlqRetryScheduler

- **文件**：`easyorange-framework/.../messaging/core/ModulithDomainEventPublisher.java`、`.../event/dlq/DlqRetryScheduler.java`
- **实现要点**：
  1. **Outbox**：业务 SQL 与事件表 insert **同事务双写**，提交后异步外发，成功才写完成时间；崩溃重启重发未完成事件；业务方只 `publish(event)`，不知道 MQ 存在（领域层零中间件依赖）
  2. **DLQ 三级**：主队列消费失败 → DLQ → 调度器周期重投（未超次数）→ 转储 terminal 等人工
  3. 退避由主队列重试模板承担，DLQ 层固定周期，**职责分离**；DLQ 监听器提取死信记录指标
  4. 路由键自动派生（事件类名 → 点分路由键），新事件零配置；MQ 可关时降级为进程内
- **可能的追问**：「发到 MQ 失败怎么办？」→ 事件留在表里（完成时间为空），后台重试 + 重启重发，at-least-once 由消费幂等兜底；「为什么调度器轮询而不是原生延迟队列？」→ 声明式简单 + 与死信语义配合
- **一句话**：同事务双写保证「业务成功 = 事件必达」，DLQ 三级重试隔离毒消息，退避与轮询职责分离

## 15 缓存 — RedisCacheConfig

- **文件**：`easyorange-framework/.../config/cache/RedisCacheConfig.java`（+ 属性类 + TTL 抖动 writer）
- **实现要点**：
  1. **注解驱动**：业务侧零缓存代码，统一 cache manager（String key + JSON value）
  2. **三防收口在注解层 + writer 层**：穿透 = null 结果缓存；击穿 = `sync=true` 同 key 单飞；雪崩 = 写入时按比例加 TTL 抖动
  3. **一致性 = 写路径显式 evict + 短 TTL 兜底**（单库单 Redis，不需要 L1/L2 配平与广播）
  4. **可用性 = fail-open**：集中式错误处理器吞掉 Redis 异常（读直查 DB / 写放弃缓存），替代逐点 try-catch
- **可能的追问**：「击穿跨实例呢？」→ 诚实讲边界：单飞是 JVM 内的，跨实例残留少量并发由事件 evict + TTL 兜底；「为什么删多级缓存 / 布隆？」→ 复杂度换不来可感知收益（但要能讲教科书方案）
- **一句话**：注解 + Redis 单层，三防收口在注解与 writer，一致性靠事件 evict，可用性靠 fail-open

## 16 全局异常 — GlobalExceptionHandler

- **文件**：`easyorange-framework/.../exception/GlobalExceptionHandler.java`

- **可能的追问**：「为什么 switch 不用多方法？」→ 分发逻辑收敛一处；「响应统一吗？」→ 统一响应信封 + 自动包装
- **一句话**：单方法模式匹配分发 + 前缀映射状态码 + 模块专属错误码

## 附：被问「这段代码有什么问题」的应答模板

面试官挑毛病时，**先承认再给方案**，用下面几个项目里真实存在的点（比硬说「没问题」可信）：

| 代码 | 真实问题 | 应答 |
|---|---|---|
| 下单链路 | 锁持有 = 事务时长，等待超时在极端慢 SQL 下会抛「繁忙」 | 「锁与事务同生命周期安全，代价是超时上限；慢 SQL 监控兜底，压测实测远低于此」 |
| 事件幂等 | 标记已写、处理中途崩溃时，重投会判重复而跳过 | 「失败路径已撤销标记，只剩『标记后、完成前』这一窄窗口；由业务副作用幂等兜底（流水唯一键），宁可漏一次也不重复加库存」 |
| 内存预算存储 | 多实例各自记账 | 「已知技术债，多实例切 Redis 存储，接口已就位」 |
| 工作流扇出 | 每路 LLM 调用可能重复计算 prompt | 「结果缓存 + 前置降级（非自然语言直接不调用），重复成本可控」 |
| 消息幂等 | 标记 TTL 理论上可重复 | 「TTL 覆盖 DLQ 重试窗口，超窗重放概率趋零，成本权衡」 |
| Agent 循环 | 步数上限内成本不确定 | 「上限可配 + 循环中途预算检查 + 三口径降级；平均步数 / 降级率待跑量回填」 |

> 原则：**主动说出「我知道这里有 trade-off，当时选择 X 是因为 Y，触发条件 Z」**，比假装完美强十倍——这正是 [技术债务清单](../技术债务清单.md) 的叙事价值。

# 四、系统设计题（答题框架 + 项目参考答案）

> 任何设计题都按「澄清需求 → 选型与架构 → 核心难点 + 演进路径」三步答，先框架后细节，控制 3-5 分钟。**RAG 与 Agent 循环是 AI 岗必考**，其余按 JD 取用。

## 1 系统设计答题框架（万能三步）

1. **澄清需求 + 估算规模**（QPS / 数据量 / 读写比 / 一致性要求）
2. **选型与架构**（数据模型 / 存储 / 缓存 / 消息 / 一致性方案）——每个选型给一句「为什么」
3. **核心难点拆解**（并发 / 一致性 / 幂等 / 可用性 / 成本）+ **演进路径**（触发条件）

## 2 设计一个 RAG 检索增强问答系统（AI 岗必考）

**答**：
1. **澄清**：语料规模与类型（结构化 / 非结构化）、更新频率（决定全量重建 vs 增量管线）、问答场景（事实问答 / 总结归纳）、是否要引用溯源
2. **选型**：
   - 索引：ES kNN / 独立向量库——**量级分界线**（百万级以下 ES 自带 HNSW 够用，再大引独立向量库）
   - 分块：固定长度 + overlap（简单可控）vs 语义分块（按标题 / 段落边界，质量高成本高）；chunk size 权衡——太小碎片化、太大稀释相关性
   - 检索：**词法 + 向量混合**（两路**独立**召回）→ 排名融合（RRF，量纲无关）→ 必要时再叠模型精排（先粗后精两段式）
   - 生成：ChatModel + **引用溯源**（答案带来源，幻觉可核验）+ 不可信内容包块防注入
3. **难点拆解**：
   - 召回质量：hit rate / MRR（可自动算）
   - 生成质量：faithfulness（答案与检索内容一致性）
   - 评测闭环：金标准集 + Judge 对照 + **CI 门禁**（分数 + 评审覆盖率双判）
   - 更新：增删改 → 增量重嵌入或周期重建（按更新频率选）
   - 成本与延迟：语义缓存、结果缓存、前置降级（不相关查询直接不检索）

**项目对照**：三条链路一套形态——商品检索（两路召回 + RRF，无独立向量库、无「语义搜索」开关）｜知识库（摄入管线 + 两路召回 + 融合 + 引用溯源 + 评测）｜在售资产检索（换语料，融合共用同一份实现）。**缺口与触发条件**：模型 rerank 待「分块上千且 hit@5 触顶而 MRR 偏低」；独立向量库待百万级分块且 kNN 延迟成为瓶颈。把「现状 + 缺口 + 触发条件」讲全，就是完整的演进规划展示。

## 3 设计一个 Agent 工具循环（AI 岗必考）

**答**：
1. **澄清**：任务是开放问答还是固定流程？能接受几步？成本上限？失败时要降级成什么？
2. **循环骨架**：`决策 → 工具 → 观察` 循环；**决策用原生 tool calling**（把工具 schema 随请求下发，模型返回「工具 + 参数 + 理由」）；工具执行与循环控制权**留在自己的 runner**——托管给框架则步数上限 / 中途预算 / 终止原因分类都插不进去
3. **工具面设计**：按性质分层（检索 / 计算 / 写入 / 收敛）；**必须有能让第 N 步依赖第 N-1 步输出的工具**（否则循环退化成换关键词重试）；工具要正交、参数要求可校验（如 ID 必须来自上一步观察）
4. **控制与降级**（生产级关键）：步数上限（含 finish 轮）+ **循环中途预算检查** + 按终止原因分类降级（超限 → 用已积累观察单次生成；决策失败 → 退回单次检索）；工具失败也作为观察回灌，让模型换参数重试
5. **可观测**：每步落 trace（工具 / 参数 / 理由 / 观察）+ 流式 step 事件；指标按 outcome 归因
6. **演进**：上下文裁剪（token 估算）→ 记忆（会话窗口 + 长期画像）→ 评估集覆盖 agent 场景用例

**项目对照**：`AgentLoopRunner` + `AgentTools`（见 §三-1/2）；对照项是**同一仓库里的 Workflow 式扇出**（`AiSearchEnhancerAdapter`）——「能用固定流程解决的不用自治循环，成本可控」。

## 4 设计一个限流器（必考）
**框架**：单机 vs 分布式 → 算法选择 → 降级策略。
**答**：① 澄清（按什么维度限：IP / 用户 / 接口，粒度，误杀容忍度）；② 选型：单机用令牌桶或本地滑动窗口，分布式用 Redis 令牌桶（单机计数器无法跨实例）；③ **限流器故障必须 fail-open**（宁可放过不可误杀业务），且不能成为单点；④ 演进：固定窗口（简单但有边界突刺 + 非原子）→ 令牌桶（平滑 + 允许突发）→ Redis 集群。
**项目对照**：AI 端点按场景令牌桶 + 超限 429 + fail-open；全站 GET 走本地（单实例够）、写操作走分布式（防超卖要跨实例统一计数）。stale 旧回答兜底属供应商故障、在服务层，与限流是两条路径。

## 5 设计消息可靠投递（Outbox 必答）
**框架**：三个环节分别保可靠——生产不丢（事务一致）/ 存储不丢（持久化）/ 消费不丢（ack + 重试），最后用幂等收口。
**答**：① **生产端一致性**（核心难点）：先发消息后提交事务 → 事务失败消息成孤儿；先提交再发 → 发失败业务已成功。正解 **Outbox**：业务 SQL + 事件 insert 同一本地事务 → 后台异步外发 → 发成功标记。替代：本地消息表 + 定时扫描。② Broker 持久化 + 生产 confirm。③ 消费端手动 ack + 指数退避重试 + DLQ 隔离毒消息 + **消费者幂等**（at-least-once 下重复只处理一次）。④ 演进：单机 → 镜像队列 / 集群；量级增大再权衡换 MQ（代价：死信、多 group 都要自建）。
**项目对照**：Modulith Outbox（同事务 + 崩溃重发）→ Topic Exchange → 消费者各自独占队列 → DLQ 三级重试 → `SET NX EX` 幂等。

## 6 设计一个订单系统（与项目强相关）
**框架**：状态机 → 一致性（防超卖）→ 生命周期副作用 → 查询（CQRS）。
**答**：① **状态机动作驱动**（每动作声明前置状态 / 目标状态 / 副作用），单一入口守卫，非法转换抛业务异常——比 if-else 可测可维护；② **防超卖**：分布式锁（按商品 key，排序获取防死锁）+ 库存乐观锁双保险；③ **一致性**：本地单事务（订单 + 库存 + 支付 + 事件原子提交），**单库不上 Saga**，拆库才引入；④ **副作用**：取消恢复库存 / 完成标记售出 → 事件异步（消费者幂等）；⑤ **查询**：CQRS 读模型 + 列表索引；超时取消 / 自动确认走定时任务。
**项目对照**：`OrderCommandHandler`（锁在事务外 + 显式事务模板）+ 生命周期事件消费者 + 超时 / 自动确认任务。

## 7 设计缓存系统 / 短链秒杀（通用题）
**缓存**：通用框架 = 层级（L1 / L2）→ 三防 → 一致性 → 可观测（**命中率是缓存最重要的健康指标**）；教科书答案要会讲 L1 + L2 配平、Pub/Sub 广播、负缓存哨兵。**项目落点**：多级缓存刻意不做——单库单 Redis 部署下复杂度换不来可感知收益，统一 Spring Cache 注解 + Redis 单层，三防收口在注解 + writer，一致性靠写路径 evict、可用性靠 fail-open。**讲清「我知道方案但评估后不用」比堆功能更显判断力**。
**短链**：发号器（雪花 / 自增 + base62）→ KV 存储 → 302 跳转 → 布隆过滤非法码。**秒杀**：提前把库存放 Redis 预扣（写只碰 Redis，MQ 异步落库）→ 限流 → 本地单飞 → 事务落库 + 对账。**与项目的对比点**：库存扣减我选**同事务强一致而非 Redis 预扣**——单库场景没有中间件一致性成本；量到百万级再改预扣 + 对账。「我知道另一种方案但不用的原因」最加分。

## 题 1：RRF 排名融合（项目同款 · RAG 检索收口）

**题面**：给你多路召回的有序结果（每路按各自相关性降序），怎么合成一个总排序？

```java
/** 融合分 score(d) = Σ_r 1 / (k + rank_r(d))，rank 从 1 起，k 默认 60（Cormack et al. 2009） */
public static List<Fused> fuse(int k, List<List<String>> rankedLists) {
    Map<String, Double> scores = new LinkedHashMap<>();
    for (List<String> ranked : rankedLists) {
        for (int i = 0; i < ranked.size(); i++) {
            scores.merge(ranked.get(i), 1.0 / (k + i + 1), Double::sum);
        }
    }
    return scores.entrySet().stream()
            .sorted(Map.Entry.<String, Double>comparingByValue().reversed())
            .map(e -> new Fused(e.getKey(), e.getValue()))
            .toList();
}
```

> 完整实现见 [`RrfFusion`](../../easyorange-backend/easyorange-ai/src/main/java/com/cartethyia/easyorange/ai/domain/model/RrfFusion.java)；选型理由见 [ADR-0012](../adr/0012-rag-hybrid-retrieval-rrf.md)。

**要讲清的三点**（这才是面试官想听的）：
1. **为什么用排名而不是分数**：kNN 的余弦与 BM25 的相关性分**量纲不可比**，加权求和既要调参又对分布漂移敏感；排名是量纲无关的稳定信号
2. **k 的作用**：平滑常数，压制「第 1 名 vs 第 2 名」的过度优势——k 越小头部越强势，k 越大越平均
3. **融合解决不了什么**：融合只解决「多路信号怎么合」，**解决不了单路自己的排序**——用同一个余弦对稠密候选重排是单调变换、等于没排；所以必须真的有两路独立召回
**追问延伸**：① 同分怎么办（依赖插入序 + 稳定排序，让评测可复现）② RRF 与 cross-encoder 精排的区别（融合合多路信号、零额外推理；精排提精度但要加一次模型调用，触发条件是分块上千且 hit@5 触顶而 MRR 偏低）

## 题 2：ReAct 工具循环骨架（项目同款 · Agent 核心）

**题面**：手写一个 agent 工具循环——模型每轮选工具，你负责执行、观察回灌、步数上限与降级。

```java
public Answer run(String question, int maxSteps) {
    List<StepObservation> observations = new ArrayList<>();
    for (int round = 1; round <= maxSteps; round++) {
        if (budgetExhausted()) break;                       // 循环中途预算检查（框架托管做不到）
        Decision d = decide(question, observations);         // 发工具 schema，收回 tool call
        if (d.isFinish()) break;
        StepOutcome out = executeTool(d);                    // 执行在自己手里
        observations.add(new StepObservation(d.tool(), d.input(), out.observation())); // 失败也回灌
    }
    return generate(question, observations);                 // 超限 / 预算耗尽 → 用已积累观察单次生成
}
```

> **加分点（逐个讲）**：① **终止原因要分类**——步数超限 / 预算耗尽 / 决策失败是三种不同的降级（前两者用已积累观察生成，决策失败退回单次检索），混成一种就没法归因；② **工具失败也进观察**（模型可换参数重试），但**决策失败不进**（那是链路故障，要走退路）；③ 每步落 trace + 推 step 事件，否则线上只有「答得差」一种表象；④ 上下文要裁剪（token 估算，保最新）。
> **追问**：「为什么不用框架的托管循环？」→ 步数上限 / 中途预算 / 降级分类三样插不进去（AG-4）。

## 题 3：实现一个令牌桶限流器（单机版）

```java
class TokenBucket {
    private final long capacity;      // 桶容量（最大突发）
    private final double ratePerSec;  // 补充速率
    private double tokens;
    private long lastRefillNanos;

    TokenBucket(long capacity, double ratePerSec) {
        this.capacity = capacity;
        this.ratePerSec = ratePerSec;
        this.tokens = capacity;
        this.lastRefillNanos = System.nanoTime();
    }

    public synchronized boolean tryAcquire() {
        long now = System.nanoTime();
        double elapsedSecs = (now - lastRefillNanos) / 1e9;
        tokens = Math.min(capacity, tokens + elapsedSecs * ratePerSec);  // 按时间补令牌
        lastRefillNanos = now;
        if (tokens >= 1) {
            tokens -= 1;
            return true;
        }
        return false;
    }
}
```

> 追问延伸：分布式版 → Redisson 令牌桶 / Lua 脚本（原子取桶补桶）；边界：`synchronized` 单机够用，多实例必须分布式。

## 题 5：实现订单状态机（动作表版，项目同款）

```java
enum OrderAction {
    PAY(Set.of(OrderStatus.PENDING_PAYMENT), OrderStatus.PAID),
    CANCEL(Set.of(OrderStatus.PENDING_PAYMENT), OrderStatus.CANCELLED),
    SHIP(Set.of(OrderStatus.PAID), OrderStatus.SHIPPED),
    CONFIRM_RECEIPT(Set.of(OrderStatus.SHIPPED), OrderStatus.COMPLETED);

    final Set<OrderStatus> sources;
    final OrderStatus target;
    OrderAction(Set<OrderStatus> sources, OrderStatus target) {
        this.sources = sources; this.target = target;
    }
    boolean canApply(OrderStatus current) { return sources.contains(current); }
}

class Order {
    private OrderStatus status;
    private Order transitionTo(OrderAction action) {
        if (!action.canApply(status)) throw new IllegalStateException("非法转换: " + status + " -> " + action);
        this.status = action.target;   // 副作用集中一处
        return this;
    }
    public Order pay()    { return transitionTo(OrderAction.PAY); }
    public Order cancel() { return transitionTo(OrderAction.CANCEL); }
}
```

> 加分：加支付状态二维（目标支付状态字段）；「非法转换抛异常」对应项目 `BizRequire.requireTrue(action.canApply(...), action.resultCode())`；不可变版让转换返回新实例（题 9）。

```java
class LRUCache {
    private final LinkedHashMap<Integer, Integer> map;
    LRUCache(int capacity) {
        this.map = new LinkedHashMap<>(capacity, 0.75f, true) {   // accessOrder = true

            }
```

## 题 8：单例 + 双重检查（考内存可见性）

```java
class Singleton {
    private static volatile Singleton instance;   // volatile 防指令重排
    static Singleton getInstance() {
        if (instance == null) {                    // 快路径
            synchronized (Singleton.class) {       // 慢路径
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

> 易翻车点：`instance` 不 volatile 时，`new Singleton()` 的三步（分配 / 初始化 / 赋引用）可能重排导致另一线程拿到未初始化对象——volatile 有序性的经典考题，跟项目里静态 volatile 引用的道理相通。

> HR 面不是技术面——**每个答案 1-2 分钟，用 STAR 结构**（情境-任务-行动-结果），结果尽量带数字；**学生身份下不要套用社招话术**（不提「前东家」「离职原因」）。

**H1 自我介绍（HR 版，30 秒）**
→ 参考：00 §3.1（开场抛钩子：定位 + 两条链路 + 底座）

**H2 为什么做这个项目？**
→ STAR：看到「AI 应用工程化落地难」（模型能调通、但限流 / 降级 / 预算 / 评估 / 观测一片空白）→ 自己定两条业务主线 + 一套生产级标准 → 单人完成后端 + 前端 → 门禁、降级、评测、观测齐备。**不要**说「为了找工作」——说「用生产标准自证工程能力」。

→ 推荐叙事（选一）：技术选型推翻重来（自研 AI 抽象 → Spring AI 框架化，ADR-0003 → 0008）；一致性架构回退（Saga → 本地事务 + Outbox，ADR-0001 → 0007）；余弦重排等于没排的识别与删除（ADR-0012）。

**H4 怎么评价自己？短板是什么？**

**H5 你是学生，怎么平衡学业与项目？能实习多久？**
