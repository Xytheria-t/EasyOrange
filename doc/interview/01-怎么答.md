# 一、高频技术题速答（59 题）

> 规则：每道题「先一句话定义，再 1-2 句原理，最后接『我在项目里』」——把背诵题变成实战展示题。面试前把「✔ 项目结合」标出的过一遍；带 `⚠` 的是容易翻车的点。

### Java 并发

#### 1. volatile 和 synchronized 的区别？
volatile 保证**可见性 + 有序性**（禁指令重排），不保证原子性；synchronized 保证原子性 + 可见性 + 有序性。volatile 适合「一写多读」标志位（如 `AiModelSupport` 的静态 recorder 引用用的 `static volatile`——写发生在启动阶段，读在多线程调用点，volatile 保证所有线程看到最新引用）。

#### 2. 线程池参数怎么定？拒绝策略有哪些？
核心参数：corePoolSize / maxPoolSize / workQueue / keepAlive / 线程工厂 / 拒绝策略。队列满 → 扩到 max → 触发拒绝策略（Abort / CallerRuns / Discard / DiscardOldest）。
✔ 项目结合：**项目统一用虚拟线程**（4 路并行——1 路 LLM + 3 路规则——`supplyAsync` 显式跑在 `SearchTool.VIRTUAL` 虚拟线程执行器上），不用自定义线程池——虚拟线程轻量到可以每任务一个，线程池调参问题被语言特性消除；唯一保留的池是 `taskScheduler`（`MdcTaskDecorator` 做 MDC 透传，poolSize=5）。

#### 3. ⚠ 虚拟线程了解吗？跟平台线程什么区别？
虚拟线程是 JVM 调度的轻量线程（JDK 21 正式版），挂起时释放 carrier 线程，阻塞操作不再浪费内核线程；IO 密集型场景吞吐提升显著，CPU 密集无提升。适用：高并发 IO（Web 请求、LLM 调用、JDBC 调用）。
✔ 项目结合：Spring Boot 4 默认虚拟线程（`spring.threads.virtual.enabled=true`），`@Async` 消费者跑在虚拟线程；`AiSearchEnhancerAdapter` 4 路并行显式传虚拟线程执行器（commonPool 是平台线程，`spring.threads.virtual.enabled` 管不到），`cancel(false)` 避免中断 carrier。
⚠ 易翻车点：虚拟线程不解决 CPU 密集问题；`synchronized` 在虚拟线程下会 pin carrier（JDK 24 已修复 pinning）；慎用 `ThreadLocal` 在长时间虚拟线程上（项目用 MDC 快照 + 清理兜底）。

#### 4. ConcurrentHashMap 原理？
JDK 8+：数组 + 链表/红黑树 + **CAS + synchronized（锁桶头节点）**，`size()` 用 baseCount + CounterCell 分散计数，扩容多线程协助迁移。与 Hashtable（全局锁）和 HashMap（线程不安全）对比。
✔ 项目结合：`InMemoryTokenBudgetStore` 用 `ConcurrentHashMap` + `AtomicReference` 做日预算记账（跨日重置），跨日重置的原子性由 `compute` 保证。

#### 5. ThreadLocal 会内存泄漏吗？
key 是弱引用，value 是强引用——线程池复用线程时，value 可能残留。规范：**用完 remove()**。
✔ 项目结合：MDC 是 ThreadLocal 实现的——`MdcTaskDecorator` 在主线程快照 MDC 复制到子线程，子线程 `finally` 里 `MDC.clear()` 防线程池复用泄漏；虚拟线程场景 Micrometer Tracing 自动注入。

#### 6. CompletableFuture 怎么用的？超时怎么处理？
`supplyAsync` 提交任务，`allOf().get(timeout)` 聚合等待，`getNow` 拿已完成结果，`cancel(false)` 取消。
✔ 项目结合：`AiSearchEnhancerAdapter`——4 路 `CompletableFuture`（意图/标签/市场/问题）并行，5s 总超时，超时后收集已完成部分返回（intent 或 tags 任一有值即可用），`cancel(false)` 不中断虚拟线程 carrier。

### JVM

#### 7. 运行时数据区？
线程共享：堆（对象）、方法区/元空间（类元数据，JDK 8+ 本地内存）。线程私有：虚拟机栈（栈帧/局部变量表）、本地方法栈、程序计数器。
✔ 项目结合：无直接关系，但答完可以补一句「项目配了堆内存 + 优雅停机 + 健康检查（actuator），生产扩容靠水平扩展」。

#### 8. ⚠ GC 算法和收集器？你们用哪个？
标记-清除 / 标记-复制 / 标记-整理；收集器演进：Serial → Parallel → CMS → G1（JDK 9 默认）→ ZGC（低延迟，JDK 21 支持分代 ZGC）。
✔ 项目结合：Java 25 默认 G1；压测实测 50 VU 混合只读 1,025 QPS、p99 52.6ms，JVM 指标（GC/堆）经 Prometheus 采集。答完补一句「GC 调优不是目标，先看对象分配模式」。
⚠ 易翻车点：别背 CMS 细节——G1 的 Region/可预测停顿、ZGC 的染色指针和「停顿与堆大小无关」是加分点。

#### 9. 类加载机制？双亲委派为什么？
加载 → 验证 → 准备 → 解析 → 初始化；双亲委派：子加载器先委托父加载器，避免核心类被篡改（`java.lang.String` 只能由 Bootstrap 加载）。
✔ 项目结合：Spring Boot fat jar 用 **LaunchedURLClassLoader** 打破双亲委派加载嵌套 jar（BOOT-INF/classes + BOOT-INF/lib）——这是个不错的加分细节。

#### 10. 线上 CPU 100% / 内存泄漏怎么排查？
CPU：`top` 找进程 → `top -Hp` 找线程 → `jstack` 转线程栈 → 定位业务线程；内存：`jmap -dump` 堆转储 + MAT 分析大对象/支配树，或 arthas `dashboard`/`heap`。
✔ 项目结合：`SlowSqlInterceptor`（MyBatis Executor 拦截器，500ms 阈值）上报慢 SQL 到 Micrometer Timer（`easyorange.sql.execution`/`easyorange.sql.slow`）——慢 SQL 是 CPU/内存问题的第一嫌疑，先用指标定位再用 jstack/jmap 深挖。

### Spring / Spring Boot

#### 11. IoC / AOP 原理？
IoC：BeanFactory 管理对象生命周期 + 依赖注入，解决对象创建与装配的解耦；AOP：动态代理（JDK 代理接口 / CGLIB 代理类）+ 切点/通知/织入。
✔ 项目结合：`TokenBudgetAspect`（@Around 注解切面，预算检查+记账）、`AuditLogAspect`（写操作审计，事件化 Outbox 入库）。

#### 12. ⚠ @Transactional 什么时候失效？这是必问题。
8 大场景：① 同类内部调用（this 调用不走代理）② 方法非 public ③ 异常被吞/被 catch ④ 抛检查异常（默认不回滚，需 rollbackFor）⑤ 传播行为错配（REQUIRES_NEW 内层提交）⑥ 数据源不支持 ⑦ 多线程线程内事务不共享 ⑧ 动态代理没生效。
✔ 项目结合：订单状态流转（`OrderCommandHandler.cancelOrder` / `shipOrder` / `refundOrder`…）显式 `@Transactional(rollbackFor = Exception.class)`——**rollbackFor 明确声明**正是踩过「检查异常不回滚」的坑后的写法；下单链路因为要把锁留在事务外，改用 `TransactionTemplate` 显式控制事务边界；消费者侧异步处理不走事务注解，靠 EventConsumerHandler + DLQ 兜底。

#### 13. Spring Boot 自动装配原理？
`@SpringBootApplication` = 配置类 + 组件扫描 + `@EnableAutoConfiguration`；`AutoConfiguration.imports` 加载自动配置类 → `@ConditionalOnXxx` 按条件装配。
✔ 项目结合：framework 模块所有配置类用 `@AutoConfiguration` + 注册进 `AutoConfiguration.imports`（不依赖隐式 ComponentScan）；`@ConditionalOnProperty(matchIfMissing=true)` 控制 RabbitMQ/ES 可选依赖——换实现只改条件配置。

#### 14. Spring Security 认证流程？（本项目就是标准实现）
过滤器链：`AuthenticationFilter`（内置）→ `JwtDecoder` 验签（Nimbus）+ issuer → `JwtAuthenticationConverter` 构造 `AuthUser` → SecurityContext；授权走 `@PreAuthorize("hasRole('ADMIN')")`。
✔ 项目结合：双 Token——Access JWT（RSA 2048 签名，30min，内存）+ Refresh opaque（Redis SHA-256，HttpOnly Cookie，轮换 + 复用检测）；TokenRevocationFilter 做黑名单吊销，与 JwtDecoder 职责分离（密码学 vs 吊销状态）；STP 原则：**不手写 JWT 工具类和 Filter，全部用 oauth2ResourceServer() 标准配置**。

#### 15. 循环依赖怎么解决？
构造器注入循环依赖**直接报错**（设计问题），字段/setter 注入可用三级缓存解决。
✔ 项目结合：踩过真实的坑——`RateLimitFilter` 直接注入 `List<HandlerMapping>` 触发循环依赖（WebSocket 配置链），改为 `ObjectProvider<List<HandlerMapping>>` 延迟解析打破循环。

### MySQL

#### 16. 索引原理？为什么 B+ 树？
B+ 树：多叉平衡树，非叶子只存索引（扇出高、层数低），叶子存数据 + 双向链表（范围查询友好）；相比 B 树全表数据只出现在叶子。
✔ 项目结合：`eo_order` 按 buyer_id/seller_id/status 建索引；慢 SQL 由 `SlowSqlInterceptor` 监控。

#### 17. 索引失效场景？
最左前缀不满足、隐式类型转换、对索引列做函数/运算、LIKE '%xx' 前置通配、or 有一侧无索引、NOT IN/!=（部分优化器行为）。
✔ 项目结合：曾修复过 `CategoryMapper.countProductsByCategoryIds` 的 `IN (${ids})` 拼接——改 `<foreach>` + `#{}` 参数化，**既防 SQL 注入又保证查询计划缓存命中**（项目踩坑警示之一）。

#### 18. 事务隔离级别？脏读/幻读？
读未提交（脏读）/ 读已提交（不可重复读）/ 可重复读（幻读，MVCC 解决普通快照读）/ 串行化。MySQL 默认可重复读 + 间隙锁解决幻读（当前读）。
✔ 项目结合：默认 RR 未改；项目一致性靠「本地事务 + 分布式锁」而非调隔离级别——锁已经在业务层解决了并发，DB 隔离级别保持默认即可（调级别是治标，业务锁才是治本）。

#### 19. MVCC 原理？
undo log 版本链 + 隐藏列（trx_id / roll_pointer）+ ReadView（活跃事务列表），快照读基于可见性判断。当前读（for update/insert/update）走当前版本 + 锁。

#### 20. 慢 SQL 怎么优化？（结合项目）
执行计划 EXPLAIN（type/rows/Extra）→ 索引优化 → 覆盖索引/索引下推 → 分批/分页优化（深分页用游标/id 定位）→ 读写分离/缓存。
✔ 项目结合：三层兜底——① 业务层：Spring Cache 注解 + Redis 单层（`@Cacheable` 拦热点读，统一短 TTL + 写路径显式 evict，Redis 故障 fail-open 直查 DB）；② 监控层：`SlowSqlInterceptor` 500ms 阈值上报 `easyorange.sql.slow` Timer；③ 数据层：覆盖索引 + 参数化查询。

### Redis

#### 21. 数据类型和底层结构？
String（SDS）/ List（quicklist）/ Hash（listpack/hashtable）/ Set（intset/hashtable）/ ZSet（skiplist + dict）；还有 Bitmap/HyperLogLog/Geo/Stream。

#### 22. 缓存穿透/击穿/雪崩？（先答三防，再答项目为什么简化）
穿透=查不存在（负缓存/布隆过滤）；击穿=热点 key 过期瞬间（单飞/锁）；雪崩=大面积同时过期（TTL 错峰/随机化）。
✔ 项目结合：**三防已落地**（Spring Cache 注解 + Redis 单层）——穿透：null 结果缓存，一致性由写路径事件 evict 关窗口；击穿：`@Cacheable(sync=true)` 同 key 单飞重建；雪崩：`JitterTtlRedisCacheWriter` 写入时按比例加 TTL 随机抖动；可用性 `CacheErrorHandler` fail-open 兜底。布隆过滤器与手写多级缓存（L1/L2 + 负缓存哨兵 + Pub/Sub 广播）均已移除——单库单 Redis 部署下复杂度换不来可感知收益，STP 优先（「评估后不用」的拒绝叙事比堆功能加分）。

#### 23. 持久化 RDB / AOF？
RDB 快照（fork + copy-on-write，全量，重启快）；AOF 追加日志（everysec/always，可重写压缩）。生产一般两者都开（AOF everysec 兜底）。

#### 24. 分布式锁怎么做？（项目就是 Redisson）
SETNX + 过期时间（防死锁）+ 唯一 value（防误删）+ Lua 释放（原子性）。
✔ 项目结合：直接说「手写 SETNX 方案我评估过，最后用 Redisson RLock 三参 `tryLock(waitTime, -1, SECONDS)`——**leaseTime 传 -1 由 watchdog 续期，10s 只是获取锁的等待超时**」，因为 Redisson 补了：watchdog 续期（不传 lease 时）、可重入、公平锁、红锁（不需要，单点场景）；释放前 `isHeldByCurrentThread()` 检查。**为什么锁内做幂等**——见 EventIdempotencyChecker：锁保证「查-写」原子，纯 SETNX 有竞态窗口。

#### 25. ⚠ 缓存一致性怎么保证？（双写一致性）
主流：Cache Aside + 先更新 DB 再删缓存 + 延迟双删/订阅 binlog（canal）。**读写并发下删缓存与写 DB 的竞态**是核心难点。
✔ 项目结合：Cache Aside + **写路径显式失效**——商品/分类写操作后经领域事件触发 `@CacheEvict`（注解式，key 精确失效），统一短 TTL 兜底（30m）；无本地 L1 层，单 Redis 天然无「多节点 L1 广播」问题（手写多级缓存 + Pub/Sub 广播已移除）。答完补一句「强一致要上分布式锁 + 版本号，业务判断可接受最终一致才用缓存」。

#### 26. 过期删除策略？
惰性删除（读时删）+ 定期删除（抽样）+ 内存淘汰（LRU/LFU/random/TTL 等 8 种）。

### 消息队列（RabbitMQ）

#### 27. 消息怎么保证不丢失？（项目三层全做了）
生产端：confirm 模式（确认机制）；Broker：持久化（exchange/queue/message）；消费端：手动 ack + 重试。
✔ 项目结合：**Outbox 模式**是「业务事务与消息发送一致性」的正解——Spring Modulith 把事件同事务写入 `EVENT_PUBLICATION` 表，事务提交后异步外发，发送成功才写 completion_date；**崩溃重启自动重发未完成事件**（`republish-outstanding-events-on-restart`）。这比 confirm 更靠前：confirm 只保证「Broker 收到了」，Outbox 保证「业务成功 = 消息必发」。

#### 28. 消息重复消费怎么解决？（项目就是标准答案）
消费端幂等。✔ 项目结合：`EventIdempotencyChecker`——`SET NX EX` **一条原子命令**领取处理权（key = `eo:event:done:{consumerId}:{eventType}:{eventId}`，TTL 24h 覆盖 DLQ 三级重试窗口），单命令即原子，所以不存在「查 done 标记 → 写标记」的查-写竞态，也无需分布式锁；领取失败即判重复直接跳过。**处理失败时 `unmark` 撤销标记再抛，让容器重试 / DLQ 重投能重新执行——宁可重试不可漏处理**。重复投递的第二道是业务副作用本身幂等：库存走流水唯一键（同一订单只扣一次、只恢复一次），不依赖消息层去重。「at-least-once + 幂等 = exactly-once 效果」。

#### 29. 消息积压怎么处理？
定位：队列堆积指标；处理：紧急扩容消费者 + 临时表/新队列迁移 + 定位消费慢根因（慢 SQL、下游阻塞）。✔ 项目结合：9 个消费者独占队列 + `EventMetricsService` 上报 `easyorange.events.received` 指标，积压可从指标看趋势；消费异常进 DLQ 不阻塞主队列。

#### 30. 顺序消息？
RabbitMQ 天然无序（多消费者并发）；方案：单队列单消费者 / 一致性 hash 按业务 key 路由 / 客户端本地排序。
✔ 项目结合：项目**不保证跨事件顺序**——订单生命周期各事件独立处理（恢复库存/标记售出互不依赖），顺序性由业务状态机守卫（非法转换直接拒绝），这是「用领域规则替代消息顺序」的架构取舍。

#### 31. RabbitMQ vs Kafka？（项目 ADR-0005 有完整评分）
4 维度：DLQ+重试（Rabbit 声明式 x-dead-letter-exchange 原生，Kafka 无死信概念）、模型（1 事件 → 多独立下游，Rabbit Exchange→多队列原生；Kafka 需多 consumer group 各维护 offset）、成本（日几万事件用不到 Kafka 百万级吞吐）、运维。**拒绝 Kafka/Pulsar/NATS/Redis Streams 的理由全部记录在 ADR-0005**——备选实现 NATS 已评估（DLQ 原生 max_deliver + dead policy）。

### 分布式 / 一致性

#### 32. CAP / BASE？
CAP：一致性/可用性/分区容错三选二（网络分区必然存在，实际是 CP vs AP）；BASE：基本可用 + 软状态 + 最终一致。
✔ 项目结合：下单链路「本地事务 = CP（强一致），事件副作用 = BASE（最终一致）」——同一个业务两种语义分层，这是分布式设计的基本功。

#### 33. ⚠ 分布式事务方案对比？（项目的核心叙事）
2PC/XA（协调者阻塞、长锁）、Seata AT（undo_log + TC 全局锁，代理数据源）、TCC（3× try/confirm/cancel 样板）、Saga（补偿编排）、本地消息表/Outbox。
✔ 项目结合：**全家族被拒**（ADR-0001 → ADR-0007）：单库场景本地事务 + 分布式锁 + Outbox 比 Saga 更强（Saga 补偿与回滚重复、崩溃后失败状态丢失）；Seata TC 单点与 fail-open 降级模式冲突；TCC 侵入大；触发演进条件：product/payment 拆独立数据源时再上真 Saga。

#### 34. 幂等设计怎么做？
唯一键约束（DB unique index）、状态机幂等（已处理状态拒绝重复）、token/防重表、Redis SETNX。
✔ 项目结合：项目有**三层幂等**：① `IdempotencyKeyFilter` 协议级幂等（客户端 Idempotency-Key 头，缓存 24h 成功响应，字节级回放）② `RateLimitFilter` 防连点（3s 窗口，IP+方法+URI+body hash）③ `EventIdempotencyChecker` 事件消费幂等。三层职责：防重放 / 防连点 / 防重复消费。

#### 35. 分布式 ID？
雪花（时间+机器+序列）、UUID v7（时间有序）、美团 Leaf/滴滴 Tinyid。
✔ 项目结合：**UUID v7（RFC 9562）**——48 位毫秒时间戳 + 版本 + 随机后缀，**时间有序**（DB 索引友好，B+ 树局部性）+ 零配置零依赖；曾在 Snowflake 与 v7 间选择，v7 砍掉 workerId 分配/时钟回拨处理，代码量最小。全库 36 位 String ID + `IdType.INPUT`。订单号是主键派生值（`ORD` + 订单 ID），无独立发号器；不选自增的关键理由是聚合 ID 必须先于 INSERT 存在（决策全文见 [ADR-0011](../adr/0011-uuid-v7-primary-key.md)）。

#### 36. 限流算法？（项目令牌桶）
固定窗口（边界突刺+非原子）、滑动窗口（内存大）、漏桶（恒定速率，无法突发）、令牌桶（允许突发 + 平滑速率，业界主流）。
✔ 项目结合：Redisson `RRateLimiter` 令牌桶替代 increment+expire（原子化取桶/补桶）；两处限流：`RateLimitFilter`（全站 GET 200次/分/IP 本地 + 写操作 30次/分/IP Redis 分布式 + 3s 防重）+ `AiRateLimitInterceptor`（AI 端点按场景 5-30 次/分，超限 429）。Redis 挂了 fail-open（限流是保护不是单点）。

#### 37. 熔断 / 降级？
熔断：失败率超阈值开闸（OPEN）→ 半开探测恢复（HALF_OPEN）→ 恢复 CLOSE。降级：超时降级/返回默认值/本地兜底。
✔ 项目结合：**先给通用框架，再讲项目取舍**——自研熔断（Resilience4j CircuitBreakerRegistry 包 Redis 操作）已随缓存重构移除，缓存降级统一由 `CacheErrorHandler` fail-open 承担（读直查 DB / 写放弃缓存，集中一处替代逐点 try-catch）。AI 侧：**重试/并发隔离由 Spring AI 客户端内置**（openai-java MAX_RETRIES=2 + 连接池），自研 Bulkhead 已删（ADR-0008 框架化）。答完补一句「单库单 Redis 部署下熔断收益有限，fail-open + 短 TTL 已覆盖，量级上来再引熔断」。

#### 38. 分布式链路追踪？（项目 traceId 全链路）
✔ 项目结合：Brave `TracingFilter` 从 HTTP 头提取 traceId → MDC → `MdcTaskDecorator` 透传 @Async → `EventMetadataMessagePostProcessor` 注入 RabbitMQ header → 消费者 `EventMetadata.from` 解码回 MDC → 日志 + Micrometer 指标统一关联。**单 JVM 多模块场景** traceId 跨进程边界只在 MQ 头传递；拆多 JVM 时走 W3C traceparent 标准（Brave/OTel 通用）。

### DDD / 架构

#### 39. DDD 和传统 MVC 分层区别？
MVC 按技术切（Controller/Service/DAO），业务规则散落 Service；DDD 按领域切（domain/application/adapter），**业务不变量下沉聚合根**，领域层零框架依赖，依赖方向单向向内。
✔ 项目结合：四层（aggregate/application/port/adapter）+ 11 模块 + 49 个 Port 接口编译期隔离 + ArchUnit 12 条规则 CI 守卫（domain 零 Spring 依赖、CQRS 读写隔离、业务模块只经 port/valueobject 通信、端口必有适配器、禁 infrastructure 包、domain/application 不反向依赖 adapter、Controller 不直连 mapper、禁 System.out、domain/application 禁 org.springframework.dao）。

#### 40. 聚合根 / 实体 / 值对象区别？
聚合根：聚合的入口 + 不变量守卫（Order/Product/User）；实体：有 ID 可变的业务对象（ProductDetail）；值对象：按值等价不可变（Money/Phone/OrderId）。
✔ 项目结合：**只对「有规则的字段」做 VO**（ID 语义、金额精度、手机号格式），不每字段包一层——避免 ceremony（[01-怎么答.md §一-2](01-怎么答.md) 有完整取舍清单）。

#### 41. CQRS 什么时候用？（项目 ADR-0002）
读多写少 + 跨聚合查询 + 读写独立优化才用。✔ 项目结合：只做 product/order/payment/message 4 个模块；message（读写 1:1）、favorite（单表索引够）**刻意不做**——收益 < 维护成本，不是银弹。

#### 42. 事件驱动架构？Outbox 模式？
✔ 项目结合：领域事件 = 状态转换副产物（`Transition<Agg, Event>`），写副作用全走事件（扣库存例外——同事务同步），跨模块零同步耦合；Outbox 保证「业务成功 = 事件必达」；9 个消费者 + DLQ 三级重试 + 幂等。

#### 43. 六边形架构 / 端口适配器？
领域在中心，出站/入站都是 Port 接口，Adapter 实现外围依赖。✔ 项目结合：49 个 Port 接口编译期隔离 + Adapter 集中 `easyorange-application/adapter/outbound/`，换实现（锁/支付/短信/ES）只改 adapter。

#### 44. 为什么拒绝 Saga？（架构师必问，[00-怎么说.md §3.2](00-怎么说.md) 完整版）
单库本地事务 = 比 Saga 更强的强一致；Saga 补偿与回滚重复、崩溃状态丢失；Seata TC 单点与降级冲突；TCC 样板爆炸。触发演进：拆独立数据源。

### AI / LLM

#### 45. LLM 调用工程化有哪些要点？（项目的 8 件套）
限流（令牌桶）、降级（stale/兜底文案）、预算（TokenBudget）、重试（客户端内置）、超时、可观测（Spring AI Observation → Prometheus）、Prompt 版本化（YAML）、成本核算。
✔ 项目结合：AI 8 件套完整落地（README 双主线表），两条 AI 主线链路——卖家「发布助手」（拍照识别单入口：一次产出属性 + 建议价 + 标题/描述，独立估值 / 文案入口已删除，发布路径模型调用从最多 5 次降到 1 次）与买家「对话式找货」（RAG 换语料检索在售资产）——全部直接注入 Spring AI `ChatModel`/`EmbeddingModel` bean（ADR-0008 框架化，删掉自研 LlmPort/CachingAdapter/AiMetricsService）；2026-09-18 起调用日志补 token 入出 / 调用主体列，成本可按场景出报表（`GET /api/admin/ai/cost-report`）；建议价采纳率另出效果报表（`GET /api/admin/ai/pricing-adoption`）。原口径「6 个决策点 = 4 个 LLM 驱动 + 2 个规则引擎」作演进痕迹保留（其中的信用画像已于 2026-09-19 随功能下线删除）。

#### 46. RAG 是什么？项目怎么做？
RAG = 检索增强生成：外部知识检索 → 拼进 prompt → 生成。解决幻觉 + 知识时效。
✔ 项目结合：分三层——**商品检索**也是两路独立召回 + 排名融合（`QueryEmbeddingAdapter` 出 1024 维查询向量 → kNN `nameEmbedding` 与 BM25 `multi_match` **各查一次** → `RrfFusion`；索引侧 `nameEmbedding` best-effort 写入，失败降级 null 不阻塞，查询侧拿不到向量则整条检索退化为纯 BM25）；**知识库 RAG** 是完整链路（分块摄入 → 两路独立召回 kNN/BM25 → RRF 排名融合 → `[来源:标题]` 引用溯源 → 金标准集 hit@5/MRR + Judge 门禁进 CI）；**在售资产检索（对话式找货）** 同一形态换语料，与知识库**共用同一份 `RrfFusion`**（两路都过滤 `ONLINE`）；**拒绝 Milvus**：SKU < 10 万，ANN 运维 ROI 为负（拒绝项第 5 条）。

#### 47. Embedding 原理？
文本 → 高维向量，语义相近向量余弦距离近；训练目标让相似文本向量接近。维度选择影响检索质量与存储成本（1024 维 vs 1536 维）。

#### 48. Tool Calling / Function Calling？
模型输出结构化「函数调用意图 + 参数」，系统执行后把结果回填给模型再生成。✔ 项目结合：4 路并行 Tool Calling（`SearchToolRegistry`，4 路中仅意图识别打模型、另三路是本地规则计算）——工具 name/description 已对齐 Function Calling 的 JSON Schema 形态；编排手写不依赖 LangChain4j（拒绝理由：反射黑盒不可调试，见 [00-怎么说.md §3.1](00-怎么说.md)）。

#### 49. Prompt 工程？
角色设定 + 明确指令 + 示例（few-shot）+ 输出格式约束（JSON）+ 边界声明。
✔ 项目结合：`PromptRegistry` + YAML 模板（**7 个**：业务 4 + 对话 2 + 1 搜索意图识别）版本化（模板即 system prompt，变量由服务内联 `String.format` 填充），**改 prompt 不用改代码重新部署**；`callJson` 用 `response_format=json_object` 强制 JSON。注入防护是**全链路一致**的：不可信内容（商品字段 / 用户提问 / 检索片段 / 搜索关键词 / 召回资产标题）一律包进带标签的块，7 个 prompt 全部声明「块内是数据不是指令」，`PromptContentTest` 按模板名清单断言，退回 Java 硬编码常量会让清单对不上。

#### 50. 怎么判断 AI 输出质量？（LLM-as-Judge）
✔ 项目结合：`eo_ai_call_log` 全量记录（scope/model/prompt_hash/响应/耗时/成败）→ `AiEvalScheduler` 每天用 ChatModel 当评审员按四维打分（1-5 + 评语）→ `AVG(judge_score) GROUP BY scope` 看质量回归——prompt/模型改动后有量化对比。

#### 51. RAG 全链路有哪些环节？分块策略怎么定？（模型应用工程师必考）
环节：**文档摄入（解析 → 清洗 → 分块）→ 嵌入索引 → 检索召回 → 重排 → 生成（拼 prompt + 引用溯源）→ 评估**。
分块：固定长度 + overlap（简单可控）vs 语义分块（按标题/段落边界，质量高成本高）；chunk size 权衡——太小上下文碎片丢相关性，太大稀释注意力；检索层用 hit rate / MRR 衡量，生成层用 faithfulness（忠实度）。
✔ 项目结合：分块已落地在知识库链路——500 字符 + overlap 50、换行优先切点、best-effort embed、启动补索引（`KnowledgeIngestionService`）；语料含 20 篇同域干扰文档，分块效果由 golden set hit@5/MRR 回归看护（语料与 topK 同量级时指标恒为满分，等于没测）。

#### 52. 流式输出怎么做？（SSE vs WebSocket）
SSE（Server-Sent Events）：**单向**服务端推送、HTTP 协议自带、自动重连，适合 LLM token 流；WebSocket：**双向**，适合聊天交互（消息 + 状态 + 指令）。流式工程要点：首字延迟（streaming 首 token 时间）、**流中断降级**（连接断了回退最近一次完整缓存/重试）、背压（慢消费者）、流式调用与限流 / 预算兼容。
✔ 项目结合：**已落地**——`POST /api/ai/chat/stream` 用 SseEmitter + `ChatModel.stream(Flux)`，事件协议 token / sources / done / error；工程点是预算手动前置检查（AOP 拦不住流式返回）、流式调用照常落 `eo_ai_call_log`、来源先于正文、断流 onError 降级；首字延迟专项指标是标注的演进项（详见 00 §4.1 流式应答与 §6.2 实答清单）。

#### 53. Agent 记忆 / ReAct 是什么？
ReAct = **推理（Reasoning）+ 行动（Acting）循环**：模型思考下一步 → 调工具 → 观察结果 → 再思考，直到任务完成。记忆分层：**短期**（会话窗口，Redis TTL，最近 N 轮消息 + 工具结果）/ **长期**（向量记忆库或用户画像表，按相关性召回）。
✔ 项目结合：分两块说清楚，别混。① **搜索增强的 4 路是固定扇出**——四路无条件全提交、模型不参与选路，所以别叫它 Tool Calling（那是模型产出 `tool_calls` 的专有含义），它的价值在单路降级 + 整体 5s 超时 + 降级结果不进缓存；② **对话侧才有真正的模型决策**：单步 ReAct（工具决策器输出 JSON 决定是否检索 + 顺带抽偏好），已落地，多步 ReAct 循环是演进项。`SearchTool` 的 name/description 语义对齐 Function Calling schema——**将来要交给模型自主选路，基于它们生成 JSON Schema 即可**。

#### 54. LLM 评估体系怎么建？（评测集 / LLM-as-Judge 局限）
三层：① 检索层客观指标（hit rate / MRR / nDCG，可自动算）② 生成层客观指标（faithfulness / 答案正确率，金标准集人工标注）③ 主观分（LLM-as-Judge 按维度打分）。**Judge 局限**：自评偏差（Judge 与生成同模型）、顺序 / 长度偏差、打分离散不可比——解法：客观指标为主、Judge 为辅 + prompt/模型改动 A/B 对比 + 分数进 CI 门禁。
✔ 项目结合：现状 = 金标准集 35 条（20 生成 + 15 检索）+ Judge 打分 + EvalGate 基线/覆盖率双门禁卡 build（阈值全在 `eval/baselines.yaml`，缺键加载期报错，调基线不动 Java）+ hit@5/MRR 检索指标；演进 = faithfulness 客观指标（答案与检索内容一致性）。

#### 55. AI 成本怎么优化？（模型路由 / 语义缓存 / prompt 压缩）
手段：**模型分级路由**（简单任务走快/便宜模型，复杂走强模型）、**语义缓存**（相同语义查询命中缓存，embedding 相似度判重）、prompt 压缩（截断历史/摘要）、batch 合并、KV cache 复用（服务端能力）。
✔ 项目结合：现状 = TokenBudget 日预算 + 限流 + 语义缓存（余弦 0.92 命中复用，fail-open；端口拆 `embedQuery`/`lookUp`/`store`，**一次请求只向量化一次**——拆成 get/put 会让未命中的请求对同一问题算两遍 embedding）+ 场景→模型 bean 路由，全部落地。

### 通用场景题

#### 56. 「你项目里最有挑战/踩过最大的坑？」
推荐两个叙事（选一个主讲）：
- **技术选型纠偏**：自研 AI Port/Adapter + 装饰器（ADR-0003）→ Spring AI 2.0 GA 后全面框架化（ADR-0008）——「承认自研与框架重复，删掉手写代码」比「从不犯错」可信
- **一致性架构决策**：Saga 上过线 → 发现单库场景补偿与回滚重复、失败状态随事务丢失 → 回退本地单事务 + 分布式锁 + Outbox（ADR-0001 → ADR-0007）——「做过决策并记录推翻过程」
- 备选技术坑：Redis 序列化器（Spring Boot 4 默认 JdkSerialization → Lua tonumber 失败 → 限流器 fail-open）——排查链条完整可讲

#### 57. 「让你设计 10 倍流量怎么改？」
分层回答（架构师方向标准答案）：
1. **读写分离**：MySQL 主从 + 读库扩展，写路径不变
2. **缓存前置**：列表/详情页缓存命中率已高，加 CDN/预热
3. **多实例**：`docker compose --scale` 已验证的横向扩展路径（nginx LB + Prometheus 发现），L1 缓存广播失效已支持
4. **Redis 集群**：单点 → 哨兵/Cluster（TD-004 触发条件）
5. **跨库演进**：product/payment 拆独立数据源 → 此时重新评估真 Saga/事务性 Outbox 补偿（ADR-0007 触发条件）
6. **AI 链路**：令牌桶参数按容量调整 + 预算下调 + stale 降级兜底；`InMemoryTokenBudgetStore` 换 Redis-backed（TD-005）
7. **压测验证**：k6 从基线（混合只读实测 1,025 QPS）继续向上压，门禁（p95<500ms）持续断言
> 顺序要对：先横向扩容 + 缓存，**最后才拆库上 Saga**——展示「演进触发条件」思维。

#### 58. 「你们为什么不用微服务？」
单 JVM 多模块：模块边界 = 编译期强制（Port + ArchUnit），**微服务的核心收益（独立部署/独立扩容/故障隔离）在单机阶段收益为零**；跨模块一致性用本地事务就能解决（微服务反而要引入 Saga/分布式事务）。触发条件：团队规模/流量/独立部署诉求达到阈值。这是 ADR-0006 的正向叙事。

#### 59. 「这个项目你还会加什么？」
按 ROI 提 2-3 个（体现演进规划能力）：① 下单链路压测（写路径 + 锁）② LLM-as-Judge 数据接入 Grafana 面板（avg score by scope）③ 审计日志查询页（管理端）④ 检索质量进 CI 门禁（`GoldenSetRegressionIT` 目前按需 dispatch，ES 召回路径无定时回归，见 TD-003）。

# 二、DDD 核心思想轻量落地（面试版）

> 本项目 DDD 是**「展示核心思想、拒绝过度设计」的克制落地**。每个核心思想 → 具体文件落点 → 为什么这样是轻量的。与 [00-怎么说.md](00-怎么说.md) 互补——那边是「通用叙事 + 高频追问」，这边是「DDD 专项清单 + 取舍话术」。
>
> 本部分回答「怎么做」（§1-3）与「为什么上 DDD」（§0）。
>
> 一句话定位：**DDD 六边形 + CQRS，domain → application → adapter 单向依赖**。11 个 Maven 模块、4 个核心聚合根（Product / Order / Payment / User）、49 个 Port 接口编译期隔离、ArchUnit 12 条规则在 CI 守分层不被破坏（与 `ArchitectureRulesTest` 自身 javadoc 同步）。代码里的聚合根不止 4 个，另有 `Favorite` / `Message` / `OfflineMessage` 三个简单聚合——只有不可变快照字段 + 所有权校验、无状态机，不占讲点。

## 0 为什么上 DDD——驱动、收益、代价（自证不是跟风）

**驱动**（MVC 三层在本项目会怎样）：① 业务有真规则要单点守卫——商品 6 状态两条上架路径（`approve` / `putOnline`）共用 `validateOnline()`、订单「订单状态 × 支付状态」二维状态机由 `OrderAction` 动作表唯一裁决，MVC 里同一条不变量各写一份、改一处漏一处；② 模块边界要可执行——包结构拦不住 `import` 对方 Mapper（历史教训：order 曾直接依赖 product 的 mapper 扣库存，后来才重构回 Port）；③ 外部依赖多要可换可降级——LLM 三供应商 / ES 可关（走 LIKE 兜底）/ MQ 可关，全仓 26 处 `@ConditionalOnProperty` 条件装配，MVC 里换供应商 = 改业务代码；④ 领域逻辑要能纯单测——domain 零框架依赖，PIT 只对 domain 注入变异（765 个变异约 3 分钟）。

**收益（都能核验）**：不变量只写一处（建单 `BizRequire` 链 + `OrderAction.canApply`；支付状态判断收口 6 个谓词）｜依赖方向 CI 强制（ArchUnit 12 条在 `./mvnw test` 内，历史债用 `FreezingArchRule` 冻结不新增）｜模块边界 = 接口签名（49 个 Port + 跨模块 Maven 依赖全 `<optional>true</optional>`，Port 目录本身就是模块协作地图）｜换实现 / 降级只动 adapter（ES 关闭走 LIKE 兜底、AI 供应商切换改 `AiModelConfig` options、手写多级缓存整体换 Spring Cache 单层、自研 AI Port 换 Spring AI）｜跨模块读自持快照换解耦（订单读 `eo_order_item.product_snapshot`，商品改名删除不影响已下订单）｜演进有量化触发条件（拆独立数据源 → 重新评估 Saga，[ADR-0010](../adr/0010-order-saga-evolution-plan.md)，订单写 QPS > 5k/s）。

**代价（都实际付了）**：每个跨模块协作多一层 Port + 适配器样板（接受，适配器按域分子包降低导航成本）｜模块间结构不统一（CQRS 只有 4 个模块、领域服务数量 product=1 / user=7 / 其余 0——结构差异是领域性质的产物，写进 ADR-0002 / 0009 作评审判据）｜双层模型转换（DO ↔ 聚合根，CQRS 读模型字段漂移靠 code review）｜定位成本（查「这个字段谁写的」要跨 Port → Adapter → Repository 三跳）。

**负收益判据**（什么情况别用）：单表 CRUD 无跨聚合不变量 → 直接 AppService + Mapper（favorite 就是这样）；读写比均衡 → 不上 CQRS（user）；聚合无生命周期 → 不硬造状态机（User）；字段无规则 → 不包 VO；**框架 / 标准库已有能力不自研抽象**（最贵的一课：AI 侧曾自研 Port / 适配器 / 装饰器，框架成熟后全部删掉换 Spring AI——六边形不等于什么都自己包一层，[ADR-0003](../adr/0003-ai-port-adapter-decorator.md) → [ADR-0008](../adr/0008-ai-spring-ai-framework.md)）。

## 1 核心思想清单（讲了能拿分的）

> 面试讲 DDD，别背概念，直接指代码。下面每一条都带落点文件 + 「为什么这是轻量的」——后者才是拉开差距的地方。

### 1.1 聚合根（Aggregate Root）——状态机 + 不变量内聚
- **落点**：`order/domain/aggregate/Order.java`、`payment/domain/aggregate/Payment.java`、`product/domain/aggregate/Product.java`、`user/domain/aggregate/User.java`
- **共性（先说）**：4 个聚合都是**不可变对象**，字段全 `final`，用 `@Builder(toBuilder = true)`「重建新实例」代替原地修改；聚合只做状态机 + 不变量，**不碰持久化、不注入外部依赖**（`domain` 层零框架依赖由 ArchUnit 锁死，见 1.9）。
- **状态机「只有部分聚合有」，签名还各不相同——别一勺烩**：
  - `Order`（订单）——**状态机最完整**：`private Order transitionTo(OrderAction action, String reason)`（一处校验合法性 + 一处应用副作用，见 `Order.java:248`）；公开转换 `pay()/cancel(reason)/forceCancel/ship()/confirmReceipt()/refund(reason)` 全部返回 `Transition<Order, XxxEvent>`（新聚合 + 领域事件一并产出）。
  - `Product`（商品）——**有状态机但签名不同**：`private Product transitionTo(ProductStatus target)`（**单参、目标状态驱动**，见 `Product.java:163`；曾带 `String action` 动作说明参数，因仅用于拼错误消息属语义噪音，已去掉，错误消息改为由「当前→目标」状态 desc 生成）；`approve()/reject()/putOnline()/takeOffline()` 返回 `Transition<Product, XxxEvent>`，`markAsSold()` 幂等返回 `Optional<Transition<...>>`（订单完成链路重复触发时返回空，不重复产事件）。
  - `Payment`（支付）——**没有 `transitionTo` 方法**：守卫收口 `PaymentStatusGuard` 的 6 个状态谓词（`canPay/canRefund/canClose/canFail/canConfirmPay/canConfirmRefund`），`withStatus()`/`withRefundResult()` 只内置字段副作用（`cancelPay()/cancelRefund()` 也已从内联判断改走谓词，全类无一处散写状态判断）；**终态转换**（`create()/confirmPay()/refund()`）返回 `Transition<Payment, XxxEvent>`，**中间态转换**（`preparePay()→PAYING`、`cancelPay()→PENDING`、`prepareRefund()→REFUNDING`、`cancelRefund()→SUCCESS`）**直接返回裸 `Payment`、不产事件**。
  - `User`（用户）——**没有状态机**：`status` 仅在 `create()` 置为 `NORMAL`，之后不再转换；只有 `updateContactInfo()/changePassword()/changeAvatar()/recordLogin()/assignId()` 这类 toBuilder 变换方法（承载业务不变量，不产领域事件）。
- **为什么轻量**：状态机只给**真正有状态生命周期**的聚合上（Order / Product 强状态、Payment 中等），User 没有状态机就不硬造；规则只在「动作表 / 状态机表 / Guard」写一处，不散在应用层。跨聚合一致性交给事件（见 1.4），不搞聚合内嵌反规范化——聚合保持小而纯。

### 1.2 不变量（Invariant）只写一处
- **落点**：`Order.createOrder()` 里 `BizRequire` 链——不能认领自己、必须有至少一件资产、金额必须 > 0；状态合法性由 `OrderAction.canApply(status, paymentStatus)` 裁决（`OrderAction.java:96`，每个动作声明 `sources/target/targetPaymentStatus/closureKind/resultCode/paymentGuard`）。
- **为什么轻量**：规则**只写一处**，测试直接打聚合根（`Payment` 聚合根测试 75 个全绿）。不需要额外规则引擎 / Guard 框架，`BizRequire` 一个静态方法就够。状态裁决按模块各归其位：**Order 用 `OrderAction` 动作表、Product 用 `ProductStatus.ALLOWED_TRANSITIONS` 表、Payment 用 `PaymentStatusGuard` 谓词**——「状态合法性由谁说了算」这一问要能答出来。

### 1.3 值对象（Value Object）——按值等价的不可变类型
- **落点**：`OrderId` / `UserId` / `Phone` / `Address` / `OrderNo`（`order/domain/valueobject/`）、`common/domain/ProductId.java`（跨模块共享的 `ProductId` 在 common，不在 order 的 valueobject 包里）、`common/domain/Money.java`（金额不落 `double`，用 `BigDecimal` 避免精度坑）。
- **为什么轻量**：**只对「有规则」的字段做 VO**（ID 的语义、金额的精度、手机号格式），不把每个字段都包一层——避免为了 VO 而 VO 的 ceremony。

### 1.4 领域事件（Domain Event）——状态转换的副产物
- **落点**：`OrderCreatedEvent` / `OrderPaidEvent` / `OrderCancelledEvent`…（order 模块 `domain/event/`），状态转换方法统一返回 `Transition<Agg, Event>`；事务提交后经 **Outbox** 与业务同事务一写（Spring Modulith）。
- **为什么轻量**：事件是「状态转换自然产生的副产物」，不是到处 `new` 事件。跨模块副作用（扣库存、恢复库存、标记售出）由消费者异步触发，聚合不感知。

### 1.5 工厂与重建分离（Factory vs Reconstruction）
- **落点**：`Order.createOrder(spec)`（**跑不变量**）vs `Order.from(spec)`（**不跑不变量**，直接从库重建）。
- **为什么轻量**：明确「新对象 vs 从库重建」两条路径——重建时库里的数据已被校验过，不再重复触发不变量，性能与正确性都对。参数用 record spec 收敛，避免长参数列表。

### 1.6 仓储 + 端口（Repository & Port / 六边形）
- **落点**：`OrderRepository` + `OrderQueryRepository`（CQRS 读写分离，见 1.8）、`DistributedLockPort` / `PaymentGatewayPort` / `ProductInventoryPort`…（**49 个 Port 接口** 编译期隔离）。
- **为什么轻量**：domain 只依赖接口，实现全部放 adapter。依赖方向单向（domain → application → adapter），换实现（Redis/Mem 锁、Rabbit 总线）只改 adapter，domain/application 一行不动。

### 1.7 领域服务 vs 应用服务（Domain vs Application Service）
- **落点**：领域服务 `message/domain/service/SensitiveWordFilterService.java`（纯规则、无仓储）；应用服务 `message/application/service/OfflineMessageStoreService.java`（**编排**：读在线状态 → 决定是否持久化）。
- **为什么轻量**：**只有不天然属于某个聚合的规则才做领域服务**；涉及读状态 + 调仓储的编排一律放 application。分不清这两个，是 DDD 面试最常见的扣分点。

### 1.8 CQRS（读写分离——4 个模块，两种深度）
- **落点**：`OrderReadModel` / `OrderQueryRepository`（`order/application/query/readmodel/`）、product 的 `application/query/readmodel/`；范围决策见 [ADR-0002](../adr/0002-cqrs-scope-4-modules.md)。
- **为什么轻量**：CQRS 收益是「读多写少 + 跨聚合聚合 + 读写模型独立优化」。**只在 product / order / payment / message 四个模块做，但深度不同**：
  - **有独立 ReadModel（类型级读写分离）**：product（`application/query/readmodel/` 下 5 个 ReadModel）、order（`application/query/readmodel/OrderReadModel`）——ES 全文搜索 / 订单列表跨聚合分页这类复杂查询收益最明显；
  - **只有 Command/Query Handler 级分离（无独立 ReadModel）**：payment、message——`*CommandHandler` / `*QueryHandler` 分文件 + 独立查询仓储（`MessageQueryRepository`），满足「写侧不依赖读侧」的 ArchUnit 守卫，但查询侧与写侧差异没那么大，就不再造 ReadModel；
  - **刻意不做**：favorite（单表索引够用）、user（读写比均衡）——收益 < 维护成本。
  - **注意别把 message 说成「不做 CQRS」**：它做了 Handler 级读写分离，只是没有独立 ReadModel（聊天消息读写比 1:1，读模型独立优化的收益接近 0）。

### 1.9 防腐层 / 依赖治理（用测试守边界）
- **落点**：`ArchitectureRulesTest` 的 `@ArchTest` 规则在 CI 阻断违规（规则条数与清单以该类 javadoc 为单一来源；逐条清单见 [00-怎么说.md §4.2](00-怎么说.md)）。
- **为什么轻量**：用 ArchUnit 测试守分层，**不靠空壳架构 / 冗余包**。规则坏了 CI 直接红，PR 合不进来。

## 2 刻意不做 / 轻量化取舍（防「过度设计」扣分话术）

> 面试官真正想听的，不是你会用多少个 DDD 模式，而是**你懂什么时候不该用**。下面每条都是「我评估过、主动拒绝」的决策。

| 没做的 | 为什么不做的理由 | 做了会怎样被扣分 |
|---|---|---|
| **Saga / 2PC / Seata AT/TCC** | 单库部署，一个本地 `@Transactional` 就把订单/扣库存/Outbox 全包进同一事务，比 Saga 最终一致更强（[ADR-0007](../adr/0007-order-local-tx-over-saga.md)） | 挂一个**失效的状态机**，观测价值低于写路径成本，典型「为了架构而架构」 |
| **全模块 CQRS** | 收益 < 维护成本（[ADR-0002](../adr/0002-cqrs-scope-4-modules.md)） | 每模块 Command/Query 双倍代码，纯负担 |
| **Specification 模式** | 支付的状态谓词不是「跨对象业务规则组合」，是转移谓词 | 假模式名露怯 → 已改名 `PaymentStatusGuard` |
| **每个字段都包 VO** | 只对有规则的字段做（ID/金额/手机号） | ceremony，代码量膨胀 |
| **Milvus / PGVector** | SKU < 10 万，ES kNN 够用 | 向量索引 + ANN 调参一整套运维负担 |
| **聚合内嵌反规范化** | 跨聚合一致性交给事件 + Outbox | 聚合膨胀，单点改死 |
| **Spring Cloud 微服务拆分 / RPC** | 模块化单体 + ArchUnit 12 条依赖规则 + 49 个 Port 接口/ACL 隔离跨模块；拆分触发条件已量化在 [ADR-0010](../adr/0010-order-saga-evolution-plan.md)（order 写 QPS>5k/s） | 单机演示拆微服务，分布式复杂度零收益，还答不上「为什么拆」 |
| **中间件进 K8s（ES/MySQL/Redis/MQ）** | K8s 只编排无状态应用层（Deployment/HPA/PDB），中间件外部化——生产用托管服务，demo overlay 才有 StatefulSet | 被追问 PVC 数据卷 / 分片再平衡 / 故障恢复，答穿 |
| **AutoGen / CrewAI（Python Agent 框架）** | 技术栈一致性：Spring AI 2.0 框架化（[ADR-0008](../adr/0008-ai-spring-ai-framework.md)），4 工具单步编排场景自研轻量编排零框架债 | Java 项目嵌 Python 运行时，职责边界答不清 |

## 3 面试 60 秒 DDD 概括稿

> 直接把下面这段背下来，临场改写即可。

「这个项目是 DDD 六边形 + CQRS 的克制落地。核心是 4 个聚合根——Order、Payment、Product、User，都是不可变对象。**Order 走最完整的状态机**：单一入口 `transitionTo(action, reason)` 守卫，返回 `Transition<事件>` 发领域事件；Product 也有状态机（单参 `transitionTo(target)`，目标状态驱动）；Payment 用 `PaymentStatusGuard` 谓词守卫、终态才产事件；User 没有状态机，只有不变量方法。跨模块副作用（扣库存 / 恢复库存 / 标记售出）由事件 + Outbox 异步触发，聚合不碰持久化。领域层只依赖 Port 接口，49 个 Port 接口编译期隔离，ArchUnit 12 条规则在 CI 守分层。

我特意做了几个**轻量化取舍**：首先是**拒绝 Saga**——单库部署下本地事务 + Outbox 比 Saga 更强，挂个失效状态机是过度设计；二是 CQRS 只做 4 个模块（product/order 有 ReadModel、payment/message 是 Handler 级），收益小于成本就不做；三是值对象只对有规则的字段做。这些取舍比堆 DDD 模式更能体现架构判断力。」

## 1 下单链路 — OrderCommandHandler

- **文件**：`easyorange-order/.../application/command/OrderCommandHandler.java`
- **关键代码**：
  ```java
  public CreateOrderResult createOrder(String userId, CreateOrderCommand command) {
      return lockPort.executeWithLocks(
              buildLockKeys(command),
              LOCK_TRY_TIMEOUT_SECONDS,
              () -> transactionTemplate.execute(_ -> createOrderFlow(userId, command)));
  }
  ```
- **实现要点**：
  1. 锁在**事务外获取**（tryLock 等待不占数据库连接）、**事务提交/回滚后释放**（`DistributedRedissonLockAdapter` 用 `TransactionSynchronization.afterCompletion` 延迟释放）——若在事务提交前释放，后一个请求会在前一个事务尚未提交时读到旧库存快照，击穿防超卖
  2. `buildLockKeys`：多个商品按 **productId 排序**（distinct + sorted）→ 防 AB-BA 死锁
  3. 事务内顺序：建单 + Outbox 发事件 → `decreaseStock` 同步扣库存 → `createPayment` 建支付 → 卖家缓存驱逐
  4. 任一步失败 → 数据库整体回滚（订单/库存/支付/Outbox 同事务），抛 `OrderDomainException`（B3009），**无补偿路径**
  5. 锁获取失败（10s 超时）→ 抛「资产下单繁忙」，此时事务尚未开启（无回滚开销）
- **可能的追问**：「锁和事务的顺序有问题吗？」→ **先拿锁再开事务**（`executeWithLocks` 包裹 `transactionTemplate.execute`，tryLock 等待发生在事务开启之前，最长 10s 不占数据库连接）——锁在事务提交后再释放（`afterCompletion`），保证下一个请求拿到锁时前一个事务的数据已提交可见，收敛防超卖窗口
- **一句话**：单库下单 = 先取锁 → 本地事务内 建单 → 扣库存 → 建支付，失败整体回滚，拒绝 Saga（ADR-0007）

## 2 订单状态机 — Order + OrderAction

- **文件**：`easyorange-order/.../domain/aggregate/Order.java`、`domain/constant/OrderAction.java`
- **关键代码**：
  ```java
  // OrderAction 枚举：每个动作声明前置状态集合、目标状态、目标支付状态、错误码（状态机唯一事实来源）
  PAY("支付", Set.of(OrderStatus.PENDING_PAYMENT), OrderStatus.PAID, PaymentStatus.PAID, ...)
  CANCEL("取消", Set.of(OrderStatus.PENDING_PAYMENT), OrderStatus.CANCELLED, null, ...)
  FORCE_CANCEL(..., Set.of(PENDING_PAYMENT, PAID), CANCELLED, ...)

  // 聚合根：所有转换经统一守卫
  private Order transitionTo(OrderAction action, String reason) {
      BizRequire.requireTrue(action.canApply(status, paymentStatus), action.resultCode());
      ...应用副作用（状态+支付状态+原因/时间）...
      return this;
  }
  ```
- **实现要点**：
  1. **动作驱动**：合法转换集中在 `OrderAction` 一张表（sources → target + targetPaymentStatus），聚合根只留 `transitionTo` 一个入口守卫
  2. 每个公开方法（`pay()/cancel()/ship()/...`）返回 `Transition<Order, XEvent>`——新聚合 + 领域事件一并产出
  3. 支付状态独立于订单状态：`CANCEL` 不改支付状态（null），`PAY` 置 PAID，`REFUND` 置 REFUNDED
  4. 聚合不可变：字段 final，转换返回新实例

## 4 分布式锁 — DistributedLockPort + DistributedRedissonLockAdapter

- **文件**：`easyorange-framework/.../lock/DistributedLockPort.java`（端口接口，统一 order/payment/超时任务三处用法）、`.../lock/DistributedRedissonLockAdapter.java`（Redisson 实现、@Component("distributedLockAdapter")）
- **关键代码**（适配器内部）：
  ```java
  RLock lock = redissonClient.getLock(lockKey);
  boolean locked = lock.tryLock(waitTime, -1, TimeUnit.SECONDS);  // leaseTime=-1 → watchdog 续期
  ... // 锁在事务提交/回滚后释放（TransactionSynchronization.afterCompletion），不是 finally
  ```
- **实现要点**：
  1. **leaseTime=-1 → 由 Redisson watchdog 续期**（默认 30s 锁 + 每 10s 续期），锁不会在下单流程结束前自动过期——不必手工估算事务耗时；`RedissonConfig` 显式固定 watchdog 周期
  2. 释放推迟到事务提交/回滚之后（`TransactionSynchronization#afterCompletion`）——提前释放会让后一个请求读到旧库存快照，击穿防超卖（e268c59e）
  3. 释放前检查 `isHeldByCurrentThread()`——防止锁已过期被他人持有后误删别人的锁
  4. 多锁按 productId 排序逐个获取（`OrderCommandHandler.buildLockKeys` 排序 → `DistributedLockPort.executeWithLocks` 逐个获取）——防 AB-BA 死锁靠的是这个统一的加锁顺序（打破循环等待）；逆序释放只是栈式回退惯例，与死锁无关
  5. 锁 key：`eo:order:lock:product:{productId}`（payment 用例 key=`payment:lock:...`，超时任务 key=`eo:order:lock:cancel:{orderId}`）
  6. **失败语义**：获取锁失败（等待超时/中断）抛 framework `LockAcquisitionException`——order 在 handler 边界映射为 `OrderDomainException`（B3009→400），payment 复用同一异常兜底（catch 后以统一文案重抛，RuntimeException→500）；`waitTimeout=0` 即非阻塞尝试，拿不到可自行降级
- **可能的追问**：「锁过期了业务还没完怎么办？」→ watchdog 自动续期，锁不会自动过期；holder 超阈值（60s）由适配器 warn 告警（疑似长事务卡住），业务失败整体回滚。「Redis 挂了锁怎么办？」→ Redisson 连接异常时 tryLock 抛异常走事务回滚（不静默放行——超卖保护宁可失败不可绕过）
- **一句话**：Redisson RLock leaseTime=-1 由 watchdog 续期、事务提交后释放，按 key 排序防死锁，释放前校验持有者

- **一句话**：`SET NX EX` 原子领取处理权 + 24h done 标记 + 失败撤销，配合业务副作用幂等（库存流水唯一键）达成 exactly-once 效果

  ```java
  // → ES：kNN(nameEmbedding) 与 BM25(multi_match name^3/description) 各查一次 → RrfFusion.fuse(k=60) → 按页切片
  // 索引侧：ElasticsearchProductSearchIndexAdapter 注入 ObjectProvider<EmbeddingModel> best-effort 写 nameEmbedding（失败降级 null 不阻塞索引）
  ```
- **实现要点**：
  1. 查询向量与索引维度必须一致（1024 = ES `dense_vector` 映射 dims）
  2. **两路独立召回 + 排名融合**：同请求里「knn + query」不行 —— ES 会把两路分数按内部规则合成一个分值，拿不到各自排名；余弦相似度与 BM25 分值量纲不可比，只有排名能融。与知识库、在售资产检索**共用同一份 `RrfFusion`**
  3. 单路失败退化为另一路（`runLeg` catch 返回空路），两路都空才回落到单路查询 —— 供应商抖动不该把检索打成 500
  4. `num_candidates` 必须 ≥ `k`，否则 ES 直接拒收整个请求（`illegal_argument_exception`）；候选池取 `max(100, page*size*2)`，下限保证前几页排序稳定，随页码增长保证深翻页不空
  5. **显式排序退化为单路**（价格 / 最新 / 热度）：融合排名会和用户点选的排序打架
  6. ES 装配由 `@ConditionalOnProperty` 控制（prod / dev 显式开启，it 与裸跑基文件关闭），关闭时降级不阻塞应用；生产侧由 `ProdSearchGuard` 强制开启，不接受 RAG 静默降级
- **可能的追问**：「为什么不用 Milvus？」→ 量不够（SKU < 10 万），ANN 运维负担 ROI 为负，见 [00-怎么说.md §3.1/§3.3](00-怎么说.md) 拒绝项应答；「向量维度不匹配会怎样？」→ ES 查询直接报错，这是配置一致性最容易踩的坑；「为什么没有独立的语义搜索入口/开关？」→ 两路召回是**一个检索**的两个腿，让用户选检索算法没有语义（用户不知道「语义搜索」是什么），而且独立端点会缺少 facets / 排序 / 筛选，能力反而更弱
- **一句话**：一次查询、两路召回、排名融合 —— 语义能力是默认生效的，不是用户要手动打开的开关

# 四、系统设计题（6 题 · 答题框架 + 项目参考答案）

> 任何设计题都按「澄清需求 → 选型与架构 → 核心难点 + 演进路径」三步答，先框架后细节，控制 3-5 分钟。

## 1 系统设计答题框架（万能三步）

1. **澄清需求 + 估算规模**（QPS / 数据量 / 读写比 / 一致性要求）
2. **选型与架构**（数据模型 / 存储选型 / 缓存 / 消息 / 一致性方案）——每个选型给一句「为什么」
3. **核心难点拆解**（并发 / 一致性 / 幂等 / 可用性）+ **演进路径**（触发条件）

## 2 设计题 1：设计一个限流器（必考）

**框架**：单机 vs 分布式 → 算法选择 → 降级策略。

**答**：
1. 澄清：按什么维度限（IP/用户/接口）、粒度、误杀容忍度
2. 选型：
   - 单机：Guava RateLimiter（令牌桶）或本地滑动窗口
   - 分布式：Redis 令牌桶（Redisson RRateLimiter）——原子取桶/补桶，单机计数器无法跨实例
3. 降级：限流器本身故障必须 **fail-open**（宁可放过不可误杀业务），且限流器不能成为单点
4. 演进：单实例 → Redis 集群；算法：固定窗口（简单但有边界突刺）→ 令牌桶（平滑 + 允许突发）

**项目对照**：`AiRateLimitInterceptor` 就是分布式令牌桶 + 超限 429 + fail-open（stale 旧回答兜底在 AiChatService 服务层，不在拦截器）；`RateLimitFilter` 是 GET 本地（单实例够）写操作分布式。两套并存的原因：写操作防超卖需要跨实例统一计数，GET 限流本地即可。

## 3 设计题 2：设计消息可靠投递（Outbox 必答）

**框架**：三个环节分别保可靠——生产不丢（事务一致性）/ 存储不丢（持久化）/ 消费不丢（ack + 重试），最后用幂等收口。

**答**：
1. **生产端一致性**（核心难点）：先发消息后提交事务 → 事务失败消息成了孤儿；先提交再发 → 发消息失败业务已成功。正解 **Outbox 模式**：业务 SQL + 事件 INSERT 同一本地事务 → 后台异步外发 → 发成功标记。替代：本地消息表 + 定时扫描。
2. **Broker**：持久化（queue/message durable）+ 生产 confirm
3. **消费端**：手动 ack + 失败重试（指数退避）+ DLQ 隔离毒消息 + **消费者幂等**（at-least-once 语义下重复投递只处理一次）
4. 演进：单机 RabbitMQ → 镜像队列/集群；量级增大换 Kafka（代价：死信、多 group 都要自建）

**项目对照**：Spring Modulith Outbox（EVENT_PUBLICATION 同事务 + 崩溃重发）→ RabbitMQ Topic Exchange → 9 消费者独占队列 → DLQ 三级重试（5min 周期，<3 次重投，毒消息转储 eo.dlq.terminal）→ `EventIdempotencyChecker` 幂等。

## 4 设计题 3：设计一个订单系统（与项目强相关）

**框架**：状态机 → 一致性（防超卖）→ 生命周期副作用 → 查询（CQRS）。

**答**：
1. **状态机**：动作驱动（每动作声明 sources/target/副作用），单一入口守卫，非法转换抛业务异常——比「if-else 状态判断」可测可维护（对照：项目 `OrderAction` 枚举 + `transitionTo`）
2. **防超卖**：分布式锁（按商品 key）+ 库存乐观锁（version）双保险；锁排序防死锁
3. **一致性**：本地单事务（订单 + 库存 + 支付 + Outbox 事件原子提交），**单库不上 Saga**；拆库才引入
4. **副作用**：取消恢复库存/完成标记售出 → 事件异步（消费者幂等）
5. **查询**：CQRS 读模型 + 列表索引；超时取消/自动确认 → 定时任务扫描

**项目对照**：`OrderCommandHandler`（事务 + `DistributedRedissonLockAdapter` 锁 + `ProductInventoryPort.decreaseStock`）+ `OrderLifecycleEventConsumer` + `OrderTimeoutTask/OrderAutoConfirmTask`。

## 5 设计题 4：设计短链 / 秒杀（选一个通用题）

**短链**：发号器（雪花/自增 + base62）→ 存储（KV）→ 302 跳转 → 布隆过滤非法码。
**秒杀**：**提前把库存放 Redis 预扣**（写请求只碰 Redis，MQ 异步落库）→ 令牌桶/信号量限流 → 本地单飞 → 事务落库 + 最终一致对账。**不要**：DB 行锁扛所有写。

> 秒杀题与项目的关联点：预扣方案的风险是「Redis 扣了 DB 没扣成」——项目下单链路反过来（锁 + 事务 + 同库扣减），可对比讲「库存扣减我选择同事务强一致而非 Redis 预扣最终一致，因为单库场景没有中间件一致性成本；如果量到百万级再改预扣 + 对账」。这种「我知道另一种方案但不用的原因」最加分。

## 6 设计题 5：设计缓存系统（先答通用框架，再答项目现状）

**通用框架**：层级（L1 本地 / L2 分布式）→ 三防（穿透/击穿/雪崩）→ 一致性 → 可观测。
**答**：先给教科书框架——L1 Caffeine + L2 Redis；负缓存哨兵防穿透；Caffeine 原子单飞 + 跨节点锁防击穿；TTL 配平（l1 ≤ l2）防雪崩窗口；evict 时 Pub/Sub 广播失效其他节点 L1；指标：命中率——**命中率是缓存系统最重要的健康指标**。
**项目落点**：多级缓存**刻意不做**——手写 MultiLevelCache（L1 Caffeine + L2 Redis + Pub/Sub 广播 + 负缓存）已移除，统一 Spring Cache 注解 + Redis 单层，三防收口在注解层 + writer 层：null 结果缓存防穿透、`@Cacheable(sync=true)` 同 key 单飞防击穿、`JitterTtlRedisCacheWriter` TTL 抖动防雪崩；写路径显式 `@CacheEvict` 保一致性、`CacheErrorHandler` fail-open 保可用。理由：单库单 Redis 部署下，多级缓存的复杂度（L1/L2 配平、广播、哨兵）换不来可感知的收益；把「我知道多级缓存方案但评估后不用的原因」讲清楚比堆功能更显工程判断力。

## 7 设计题 6：设计一个 RAG 检索增强问答系统（模型应用工程师必考）

**框架**（按万能三步）：澄清需求（语料规模/类型/更新频率/问答场景）→ 选型（索引库/分块策略/检索方式/生成模型）→ 核心难点（分块、召回质量、评估、更新）。

**答**：
1. **澄清**：语料规模与类型（结构化 / 非结构化文档）、更新频率（决定全量重建 vs 增量 pipeline）、问答场景（事实问答 / 总结归纳）
2. **选型**：
   - 索引：ES kNN / Milvus / PGVector——**量级分界线**（< 100 万 ES 自带 HNSW 够用，再大引独立向量库）
   - 分块：固定长度 + overlap（简单可控）vs 语义分块（按标题/段落边界，质量高成本高）；chunk size 权衡——太小上下文碎片、太大稀释相关性
   - 检索：BM25 词法 + 向量召回**混合** → rerank 收口（先粗后精两段式：召回层要快要宽，重排层要准要窄）
   - 生成：ChatModel + **引用溯源**（答案带来源，幻觉可核验）
3. **难点拆解**：
   - 召回质量：hit rate / MRR（检索层客观指标，自动算）
   - 生成质量：faithfulness（忠实度——答案与检索内容一致性）
   - 评测闭环：金标准集 + LLM-as-Judge + CI 门禁（防 prompt/模型改动质量回归）
   - 更新：文档增删改 → 增量重嵌入（或周期全量重建，按更新频率选）

**项目对照**：分三层讲才准确。
① **商品检索**（`QueryEmbeddingAdapter` + `ElasticsearchProductSearchQueryAdapter`）：也是**两路独立召回（kNN `nameEmbedding` / BM25）+ RRF 排名融合**，查询向量 text-embedding-v3 1024 维；一个入口、无独立向量库、无「语义搜索」开关，SKU < 10 万够用。
② **知识库 RAG**（`KnowledgeRetrievalService`）：已有文档摄入管线（分块 500+overlap50 → embed → ES `knowledge_docs`）+ **两路独立召回（kNN / BM25）+ RRF 排名融合**（`RrfFusion`，k=60）+ 金标准集评测（35 条：20 生成 + 15 检索，hit@5/MRR 落 `eo_retrieval_metric`）+ Judge 分数门禁进 CI。
③ **在售资产检索（对话式找货）**（`AssetSourcingService` + `AssetRetrievalPort`）：与知识库**共用同一份 `RrfFusion`**、两路都过滤 `ONLINE`——RAG 的形态（双路独立召回 + 排名融合 + 引用溯源 + 评测口径）一行没改，换的是语料与落点。
**缺口与触发条件**：缺 cross-encoder / 模型级 rerank（当前是排名融合而非语义重排，且语料仅 23 篇、评测集刚恢复判别力，加变量会让归因变模糊）；触发条件是分块上到千级、hit@5 触顶（≥95%）而 MRR 偏低；独立向量库则在百万级分块且 ES kNN 延迟成为瓶颈时再评估。把「现状 + 缺口 + 触发条件」讲全，就是一次完整的演进规划展示。

## 题 1：实现一个令牌桶限流器（单机版）

```java
// 经典实现：synchronized + 补令牌
class TokenBucket {
    private final long capacity;      // 桶容量（最大突发）
    private final double ratePerSec;  // 补充速率
    private double tokens;
    private long lastRefillNanos;

    TokenBucket(long capacity, double ratePerSec) {
        this.capacity = capacity;
        this.ratePerSec = ratePerSec;
        this.tokens = capacity;
        this.lastRefillNanos = System.nanoTime();
    }

    public synchronized boolean tryAcquire() {
        long now = System.nanoTime();
        double elapsedSecs = (now - lastRefillNanos) / 1e9;
        tokens = Math.min(capacity, tokens + elapsedSecs * ratePerSec);  // 按时间补令牌
        lastRefillNanos = now;
        if (tokens >= 1) {
            tokens -= 1;
            return true;
        }
        return false;
    }
}
```

> 面试追问延伸：分布式版 → Redisson RRateLimiter / Lua 脚本（`redis.call('EVAL')` 原子取桶补桶）；边界：`synchronized` 单机够用，多实例必须分布式。

## 题 3：实现订单状态机（动作表版，项目同款）

```java
enum OrderStatus { PENDING_PAYMENT, PAID, SHIPPED, COMPLETED, CANCELLED, REFUNDED }

// 动作：前置状态集合 → 目标状态（项目 OrderAction 的真实形态）
enum OrderAction {
    PAY(Set.of(OrderStatus.PENDING_PAYMENT), OrderStatus.PAID),
    CANCEL(Set.of(OrderStatus.PENDING_PAYMENT), OrderStatus.CANCELLED),
    SHIP(Set.of(OrderStatus.PAID), OrderStatus.SHIPPED),
    CONFIRM_RECEIPT(Set.of(OrderStatus.SHIPPED), OrderStatus.COMPLETED);

    final Set<OrderStatus> sources;
    final OrderStatus target;
    OrderAction(Set<OrderStatus> sources, OrderStatus target) {
        this.sources = sources; this.target = target;
    }
    boolean canApply(OrderStatus current) { return sources.contains(current); }
}

class Order {
    private OrderStatus status;
    private Order transitionTo(OrderAction action) {
        if (!action.canApply(status)) throw new IllegalStateException("非法转换: " + status + " -> " + action);
        this.status = action.target;   // 副作用集中一处
        return this;
    }
    public Order pay()     { return transitionTo(OrderAction.PAY); }
    public Order cancel()  { return transitionTo(OrderAction.CANCEL); }
}
```

> 加分：加支付状态二维（targetPaymentStatus 字段）；「非法转换抛异常」对应项目 `BizRequire.requireTrue(action.canApply(...), action.resultCode())`。

## 题 5：LRU 缓存（手撕高频，与 Caffeine imageProcessCache 驱逐策略关联）

```java
class LRUCache {
    // LinkedHashMap 一版搞定（accessOrder=true 按访问序）
    private final LinkedHashMap<Integer, Integer> map;
    LRUCache(int capacity) {
        this.map = new LinkedHashMap<>(capacity, 0.75f, true) {
            protected boolean removeEldestEntry(Map.Entry<Integer, Integer> eldest) {
                return size() > capacity;
            }
        };
    }
    int get(int key) {
        Integer v = map.get(key);
        return v == null ? -1 : v;
    }
    void put(int key, int value) {
        map.put(key, value);   // 超容量自动淘汰最久未用
    }
}
```

> 追问：手写双向链表 + HashMap 版本（不依赖 LinkedHashMap）也要能写；「Caffeine 的实现是 TinyLFU + 窗口」（比 LRU 更抗扫描型访问）——这是把面试题聊回项目的机会。

## 题 7：单例 + 双重检查（考内存可见性）

```java
class Singleton {
    private static volatile Singleton instance;   // volatile 防指令重排
    static Singleton getInstance() {
        if (instance == null) {                    // 快路径
            synchronized (Singleton.class) {       // 慢路径
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

> 易翻车点：`instance` 不 volatile 时，`new Singleton()` 的三步（分配/初始化/赋引用）可能重排导致另一个线程拿到未初始化对象——这是 volatile 有序性的经典考题，跟项目 `AiModelSupport` 的 `static volatile` recorder 一个道理。

## 题 9：RRF 排名融合（项目同款 · RAG 检索收口）

**题面**：给你多路召回的有序结果（每路按各自相关性降序），怎么合成一个总排序？

```java
/** 融合分 score(d) = Σ_r 1 / (k + rank_r(d))，rank 从 1 起，k 默认 60（Cormack et al. 2009） */
public static List<Fused> fuse(int k, List<List<String>> rankedLists) {
    Map<String, Double> scores = new LinkedHashMap<>();
    for (List<String> ranked : rankedLists) {
        for (int i = 0; i < ranked.size(); i++) {
            scores.merge(ranked.get(i), 1.0 / (k + i + 1), Double::sum);
        }
    }
    return scores.entrySet().stream()
            .sorted(Map.Entry.<String, Double>comparingByValue().reversed())
            .map(e -> new Fused(e.getKey(), e.getValue()))
            .toList();
}
```

> 完整实现见 [`RrfFusion`](../../easyorange-backend/easyorange-ai/src/main/java/com/cartethyia/easyorange/ai/domain/model/RrfFusion.java)；选型理由见 [ADR-0012](../adr/0012-rag-hybrid-retrieval-rrf.md)。

**要讲清的三点**（这才是面试官想听的）：

1. **为什么用排名而不是分数**：kNN 的余弦相似度与 BM25 的相关性分**量纲不可比**，直接加权求和既要调参又对分布漂移敏感；排名是对量纲无关的稳定信号。这就是选 RRF 而不是「分数加权求和」的原因。
2. **k=60 的作用**：平滑常数，压制「第 1 名 vs 第 2 名」的过度优势——k 越小头部越强势，k 越大越平均。
3. **融合解决不了什么**（区分度最高的一点）：融合只能解决「多路信号怎么合」，**解决不了单路自己的排序问题**。用同一个 embedding 的同一个余弦对稠密候选重排，是单调变换、等于没排——所以这里必须真的有两路独立召回，融合才有意义。项目早期就犯过这个错，ADR-0012 记录了识别与删除的推理。

**追问延伸**：① 同分怎么办？（依赖 `LinkedHashMap` 插入序 + 稳定排序，让同一批输入每次同序，评测可复现）② RRF 和 cross-encoder 模型重排的区别？（排名融合合多路信号、零额外推理成本；cross-encoder 是候选精排、精度更高但要加一次模型调用，触发条件是分块上千且 hit@5 触顶而 MRR 偏低）
