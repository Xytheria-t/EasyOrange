# 主线四组（投 AI 岗先过）

## AG — Agent 编排与循环

> 面试现场话术见 [07 §4.1](07-怎么说.md)。

### AG-1「谁来选下一步」两种范式？项目里用哪种？

**Workflow 式**（路径写死）vs **自治式**（模型逐轮决定）。前者确定性强、可整体设超时、成本可预测；后者能处理没预写流程的问题，代价是步数与成本不确定，必须配上限与降级。
**判据一句话**：流程能预写死就别上自治；模型参与不了决策就不叫 Agent。

**✔ 项目结合**：现在**只有自治式一条主线**（`ToolCallLoop`）。**Workflow 的收益区（流程能预写死）和需要模型决策的活儿不重叠**——搜索页那条链路的流程本来就写得死，用普通代码就拿到了确定性和超时；Agent 页写不死，Workflow 表达不了。搜索页原有一套 Workflow 式 4 路并行扇出（意图识别 / 标签 / 市场分析 / 建议问题），核查后整节删除。

**判「不是 Agentic」的三条硬指标**：输出是否**回流检索链路**？是否**改变排序 / 结果**？**下一步由谁决定**？三条全否就是包装。那套实现里四路有三路是本地规则，唯一那路 LLM 生成 30 字摘要，既不回流检索也不改排序。把它当「多范式」讲会被追问到崩。

→ [02 §4](02-代码走读.md) · [07 §4.1 Q1](07-怎么说.md)

### AG-2 多步工具循环怎么实现的？（面试官叫它 ReAct）

**这条 agent loop = 推理 + 行动**：思考 → 调工具 → 观察 → 再思考，直到收敛。定它是不是 agent 的不是「用了工具」，是**下一步由谁决定**（工具只是执行手段，Workflow 里也调工具）。
ReAct（Yao et al. 2023）用提示词让模型吐文本再解析；**本项目走原生 tool calling，是它的现代实现而非别名**，被问到就顺着叫 ReAct，再补这一句。

**✔ 项目结合**（`ToolCallLoop`）：决策走**原生 tool calling**，schema 由 `@Tool` 生成随请求下发，执行与循环控制权留在编排器；**三条降级口径**——步数超限 / 循环中途预算耗尽 → 已积累观察单次生成，决策失败 → 按原始问题检索一次（**而不是不检索**）；每步落 `eo_tool_call_step_trace` + SSE step 事件，指标按 outcome 归因。

**待补口径**：平均步数 / 降级率 / 步级延迟 p95。

→ [02 §1](02-代码走读.md) · [05 题 2](05-设计题与手撕.md)

### AG-3 工具面怎么设计的？

**按性质分四层**：检索（知识库 / 在售资产 / 资产详情）· 计算（行情统计 / 多件逐维比对，**纯 JDK 零模型调用**）· 写入（`remember_preference`）· 收敛（`finish`）。

**计算类工具是关键。** 只有检索工具时，循环存在的唯一意义是换关键词重试；有了计算类，第 N 步才真正消费第 N-1 步的输出。
**写入独立成工具**，是为了让偏好不因三条降级路径静默丢失。

→ [02 §2](02-代码走读.md)

### AG-4 ⚠ 循环控制权为什么不交给框架托管？LangChain4j 与 Spring AI 差别？

**判据**：差异**不在工具 schema**（`@Tool` 两家都是**运行时反射**生成 JSON Schema，这层一致，别拿它当选型理由）；**分水岭是循环控制权**——托管的工具执行循环一旦用了，**步数上限 / 循环中途预算检查 / 按终止原因分类的降级就插不进去**。**落点**：只用 `ChatModel` 层，发 schema、原样收回 tool call。

> ⚠ 别硬背框架源码。被追问按 [07 §6.1①](07-怎么说.md) 的绕法答。

→ 话术全文 [07 §4.1 Q3](07-怎么说.md)

### AG-5 Agent 记忆 / 多轮对话怎么设计？

- **短期** = Redis 会话窗口（TTL 24h，裁最近 N 轮）
- **长期** = 用户画像表（**独立工具写入，模型自主决定何时记**，不依赖收敛轮）
- **上下文** = 轮数窗口 + token 裁剪两道

**三个细节**：决策失败降级为「按原始问题检索」；生成时历史按**原始角色**传多消息（跨轮前缀稳定才能命中供应商上下文缓存折扣）；记忆读写 fail-open。

→ [02 §3](02-代码走读.md)

### AG-6 流式输出怎么做？（SSE vs WebSocket）

**SSE**：单向 + HTTP 自带 + 适合 token 流。**WebSocket**：双向 + 适合聊天交互。工程要点：首字延迟、断流降级、背压、与限流 / 预算的兼容。

**✔ 项目结合**：`SseEmitter` + `ChatModel.stream`，事件协议 step / token / sources / done / error。**四个工程点**——**预算手动前置检查**（流式在结束前就返回，AOP 拦不住）、调用日志不缺流（阻塞收流后落 `eo_ai_call_log`）、来源先于正文、断流兜底（网络异常推降级文案）。

前端选 fetch + ReadableStream（EventSource 只支持 GET 且不能带 Authorization）。首字延迟是标注的待办。

→ [07 §4.1 Q13](07-怎么说.md)

### AG-7 MCP 工具面怎么做的？信任边界？

**MCP** = 把工具 / 资源按 JSON-RPC 协议暴露给外部 client 的标准方式。

**✔ 项目结合**：`@McpTool` + streamable HTTP（端点 `/mcp`），4 个**公开只读**工具（资产检索 / 详情 / 类目 / 平台规则知识）。

**信任边界是设计出来的两级暴露**：外部 client 无用户上下文 → 不暴露订单 / 个人信息 / 写路径。与 Agent 内部工具面各自独立，鉴权假设不共用。匿名可达 + 独立限流 + 防重豁免。

> ⚠ 坑：`protocol` 属性**必须显式配置**，否则端点整个不装配。

→ [02 §6](02-代码走读.md)

### AG-8 ⚠ 为什么不把发布收进对话 Agent，合成一个全能助手？

**判据一句话：范式按任务选，不按产品口号选。**

- **发布是结构化产出任务**：无状态、单次多模态调用、预算封顶、表单确认后落 `ai_suggestion` 快照。
- **找货是开放探索任务**：多轮、模型选工具、有记忆。

**合并的三笔代价**：① 卖家主链路从 1 次 VL 调用变成「≥2 轮文本决策 + 1 次 VL + 每轮 schema 开销」，更慢更贵，与成本 / 延迟治理叙事冲突；② 采纳率指标靠表单提交时的快照落库，挪进聊天没有落点；③ 聊天链路要长出多模态输入与写路径确认流。

> ⚠ 翻车点：「统一入口」是**产品理由不是工程理由**。被追问按 AG-1 的范式判据答。

## RAG — 检索增强

> 三条链路的话术见 [07 §4.1 Q11](07-怎么说.md)，设计题版见 [05 §2](05-设计题与手撕.md)。

### RAG-1 RAG 是什么？项目怎么做？

**RAG = 检索增强生成**：外部知识检索 → 拼进 prompt → 生成。解决幻觉与知识时效。

**✔ 项目结合：三条链路一套形态**——商品检索；知识库（**完整链路**：摄入 → 两路召回 → 融合 → 引用溯源 → 评测）；在售资产检索（对话式找货，换语料，**共用同一份 `RrfFusion`**）。

**拒绝 Milvus**：量级够用，ES 自带 kNN（底层 HNSW）即可；独立向量库的索引构建 / ANN 调参 / 运维 ROI 为负。量级口径与追问见 [02 §8](02-代码走读.md)。

### RAG-2 ⚠ 全链路有哪些环节？分块策略怎么定？

**环节**：摄入（解析 → 清洗 → 分块）→ 嵌入索引 → 召回 → 重排 → 生成（拼 prompt + 引用溯源）→ 评估。
**分块**：固定长度 + overlap（简单可控）vs 语义分块（按标题 / 段落边界）。chunk 太小碎片化丢相关性，太大稀释注意力。检索层看 hit rate / MRR，生成层看 faithfulness。

**✔ 项目结合**：固定长度 + overlap、**切点优先落换行**、best-effort embed、启动补索引。语料含**同域干扰文档**——踩过的坑：语料与 topK 同量级时 hit@5 恒为满分，指标成了装饰。

> ⚠ 别把「重排」和「融合」混为一谈。**融合合多路信号，重排是候选精排。**

### RAG-3 Embedding 原理？

文本 → 高维向量，语义相近则向量距离近；维度影响检索质量与存储成本。

**✔ 项目结合**：查询侧出向量做 kNN；**索引侧 best-effort 写入**（失败降级 null 不阻塞索引，查询侧拿不到向量则整条检索退化为纯 BM25）。向量维度必须与 ES `dense_vector` 映射的 dims 一致，**不一致查询直接报错**。

### RAG-4 多路召回怎么合？为什么用 RRF 排名融合？

**✔ 项目结合**（`RrfFusion`）三点：**用排名不用分数**——kNN 的余弦与 BM25 的相关性分**量纲不可比**，加权求和既要调参又对分布漂移敏感；**k 是平滑常数**，压制「第 1 名 vs 第 2 名」的过度优势；**融合解决不了单路自己的排序**——用同一余弦对稠密候选重排是单调变换、**等于没排**（[ADR-0012](../adr/0012-rag-hybrid-retrieval-rrf.md) 记录了识别与删除），所以**必须真的有两路独立召回**。

**追问**：同分靠插入序 + 稳定排序保评测可复现；ES 同请求「knn + query」拿不到各自排名。

→ [05 题 1](05-设计题与手撕.md) 手撕 RRF

### RAG-5 ES 语义搜索怎么做的？显式排序 / total 口径？

**✔ 项目结合：没有独立的「语义搜索」开关。** 搜索框按相关性排序时自动两路召回（kNN 与 BM25 各查一次）→ 融合。

**两个口径要答准**：

- **显式排序退化为单路**——用户点选排序与融合排名打架，只走 BM25。
- **`total` 无条件取 `max(BM25 路总命中, 融合后条数)`**。BM25 的总命中不含语义路补进来的召回，只报它前端会出现「共找到 0 件」却列着结果——所以是恒定取较大值，不是「只在词面命中为 0 时」才换口径。

另：`num_candidates` 必须 ≥ k，否则 ES 直接拒收整个请求。

### RAG-6 往深做先做什么？（现状 + 缺口 + 触发条件）

**缺口是模型 rerank**（Cross-Encoder 替代 / 叠加排序融合）：双塔召回要快要宽、交叉编码精排要准要窄。
**触发条件是分块数上千且 hit@5 触顶而 MRR 偏低**——语料不够大时加变量只会让归因变模糊。独立向量库在百万级分块且 kNN 延迟成瓶颈时再评估；faithfulness 这类生成层客观指标同属演进项。

> **把「现状 + 缺口 + 触发条件」讲全，就是完整的演进规划展示。**

## EV — 评估闭环

### EV-1 怎么判断 AI 输出质量？（Judge 的定位与局限）

| 层 | 指标 | 能否自动算 |
|---|---|---|
| 检索 | hit rate / MRR / nDCG | 能 |
| 生成 | faithfulness | 能 |
| 主观 | Judge 按维度打分 | 否，有自评 / 顺序 / 长度偏差 |

**✔ 项目结合（门禁侧）**：金标准集（生成 + 检索两类，路由线复用 chat 用例上的 `expected_tools` 标注）+ `AiJudge` 对照参考打分 + **`EvalGate` 四道门禁**。阈值全在 `eval/baselines.yaml`，**缺键是加载期异常**——门禁静默放松比加载失败危险。

**定位纪律：Judge 分数只作回归门禁、不作对外质量证据。**

→ 四道门禁逐条判据 [02 §9](02-代码走读.md) · 话术 [07 §4.1 Q12](07-怎么说.md)

### EV-2 评估体系怎么接进 CI？

**✔ 项目结合：评测 workflow 按需 dispatch。** 单次要打真实模型调用，所以不进 PR 路径、不做定时空跑；改 prompt / 换模型 / 调检索参数 / 更新语料后手动跑。调基线只改 yaml、不动 Java。

**历史数字不可引用**——小语料时代 hit@5 恒满分，不构成检索质量证据。语料换血后须重跑。

### EV-3 反馈飞轮怎么做的？点踩为什么不当用例？

**✔ 项目结合**：点赞入库 → 管理端导出为金标准用例（只导有帮助且字段非空的行，导出即标记）→ 人工审核合入评测集。

**点踩不自动成用例**——被嫌弃的回答会把错答案钉成标准。只统计待人工补正。

## AI — LLM 调用工程化

> 面试现场话术见 [07 §4.1 Q7~Q9](07-怎么说.md)。

### AI-1 LLM 调用工程化有哪些要点？（项目的八件事）

限流、降级、预算、可观测、Prompt 版本化、成本核算、缓存、路由。

**✔ 项目结合**：**框架层**用 Spring AI（`ChatModel` / `EmbeddingModel` bean，[ADR-0008](../adr/0008-ai-spring-ai-framework.md)）；**业务层治理全在**——令牌桶限流（超限 429）、`@TokenBudget` 日预算、Prompt YAML 版本化、供应商故障 stale 兜底、调用日志 + 成本报表、语义缓存、模型路由、上下文裁剪。两条 AI 主线链路全链路覆盖。

> ⚠ **别说「没有重试」——有两层，要能分清各管什么**。**应用层**只给决策调用重试一次（`ToolCallDecider`：调用故障 / 参数 JSON 不可解析才重试；「未返回工具调用」属协议层确定性响应，不重试），理由是快模型输出不稳，一次抖动丢掉整个多步能力比多付一次决策调用更贵。**客户端层**由 openai-java 内置 `maxRetries=2` + 连接池承担（见 `AiModelConfig`）。**生成侧不重试**——失败按各路径降级（对话侧 stale 兜底、发布助手显式报错）。超时是每场景的配置项（`AiProperties` 的 `timeout`），不是一套机制。

### AI-2 限流和降级怎么分工？超限用户看到什么？

**两条路径不重叠**：限流超限 → **429 直接拒绝**（保护上游不被烧）；LLM 供应商故障 → **stale 旧回答**兜底，无 stale 则 unavailable 文案（保可用性）。

拦截器不承担缓存职责。**Redis 挂了 fail-open 放行**——限流是保护手段，不能成为可用性单点。降级不是静默变差：对话与 RAG 降级各有计数（`easyorange.ai.chat.degraded` / `easyorange.ai.rag.degraded`）。

### AI-3 Token 预算怎么管的？

**职责二分**：`@TokenBudget` 注解声明场景 + 日预算（编译期契约），切面**只做前置检查**；**记账在 `AiCallRecorder`**，按供应商回报的真实 usage 累加，不回报（embedding / 流式未带 usage）才退化为场景单次上限。

**存储两版**（默认内存；多副本切 Redis `HINCRBY` + 日窗口 key），yaml 可按场景覆盖注解默认值。
四个预算场景（auto_listing / semantic / chat / knowledge）各有拦截点，chat 与 auto_listing 因为注解只能挂方法上、又各有「非流式」与「流式 / 图文生成」两个入口，拦截点比另两个场景多。

> **失败不记账**——估算会在故障期虚烧日预算、恢复后把场景锁死。

### AI-4 AI 成本怎么优化？（模型路由 / 语义缓存 / prompt 压缩）

**通用手段**：模型分级路由、语义缓存、prompt 压缩（截断 / 摘要）、batch、KV cache 复用（服务端能力）。

**✔ 项目结合**：四项手段——语义缓存（阈值 0.92，一次请求只向量化一次）、场景 → 模型 bean 路由、上下文裁剪、砍白烧链路（删掉「建 / 改商品触发 LLM」；发布助手收敛为拍照识别单入口，发布路径模型调用 **5 次 → 1 次**；搜索页四路增强整节删除）。

**命中率可观测**：`easyorange.ai.semantic.cache{outcome}` 四结局，分母只由 hit + miss 构成——bypass 没发生查找、error 是故障不是阈值信号，两者进分母会让人在故障期误调参数。

# 底座七组

## JAVA — 并发与 JVM

- **JAVA-1 volatile vs synchronized**：volatile 保证**可见性 + 有序性**（禁指令重排）、**不保证原子性**，适合「一写多读」标志位；synchronized 三性齐全。项目里「所有线程看到同一个记账端口」用**构造器注入的 final 引用**（Spring 单例的发布安全由容器 happens-before 保证），而不是 `static volatile` 单例——依赖显式可测、无隐藏全局状态。
- **JAVA-2 线程池参数 / 拒绝策略**：core / max / queue / keepAlive / 线程工厂 / 拒绝策略（Abort / CallerRuns / Discard / DiscardOldest）。项目里 **IO 密集的异步任务统一用虚拟线程**（`@Async` 消费者），线程池调参问题被语言特性消除；唯一保留的池是任务调度器（MDC 透传给子线程）。
- **JAVA-3 ⚠ 虚拟线程**：JVM 调度的轻量线程（JDK 21 正式），挂起时**释放载体线程**；IO 密集吞吐提升显著，**CPU 密集无提升**。项目 Spring Boot 开启虚拟线程、`@Async` 消费者跑在虚拟线程上；并行任务要**显式传虚拟线程执行器**（`commonPool` 是平台线程且并行度 = 核数 − 1，配置开关管不到它），取消用 `cancel(false)` 不中断载体。

  > ⚠ 易翻车点：虚拟线程**不解决 CPU 密集**；`synchronized` 在虚拟线程下会 pin 载体（新版 JDK 已修）；慎在长生命周期虚拟线程上用 `ThreadLocal`（项目用 MDC 快照 + 清理兜底）。

- **JAVA-4 ConcurrentHashMap**：数组 + 链表 / 红黑树 + **CAS + 锁桶头**；`size()` 用 `baseCount` + `CounterCell` 分散计数。项目内存版预算存储用 `ConcurrentHashMap` + 原子引用记账，跨日重置的原子性由 `compute` 保证。
- **JAVA-5 ThreadLocal 内存泄漏**：key 弱引用、value 强引用，线程池复用线程时 value 可能残留，规范是**用完 `remove()`**。项目 MDC 就是 ThreadLocal——主线程快照复制到子线程，子线程 `finally` 清理防泄漏。
- **JAVA-6 CompletableFuture**：`supplyAsync` 提交、`allOf().get(timeout)` 聚合等待、`getNow` 拿已完成结果、`cancel(false)` 取消（不中断）。项目里没有现成的扇出（那条链路已删，见 AG-1），但判据是通用的：**`anyOf` 是「最快的一个就返回」不是「能等的都等到」**。
- **JAVA-7 运行时数据区 / 类加载**：线程共享堆与方法区（元空间，JDK 8+ 本地内存），线程私有虚拟机栈 / 本地方法栈 / PC；类加载 加载 → 验证 → 准备 → 解析 → 初始化，双亲委派避免核心类被篡改。项目 fat jar 用 `LaunchedURLClassLoader` **打破双亲委派**加载嵌套 jar。
- **JAVA-8 ⚠ GC 与收集器**：标记-清除 / 复制 / 整理；Serial → Parallel → CMS → G1（JDK 9 默认）→ ZGC。项目容器内**显式指定 G1**（`Dockerfile` 的 `-XX:+UseG1GC`）：**不选 ZGC 的理由**是 G1 已是 JDK 9 起的默认值、不换就是零成本，而这里堆不大、瓶颈也不在 GC——**显式钉住只是把默认值写死，不让运行环境漂移**，真要换是可改的一个参数。

  > ⚠ **别背 CMS 细节。** 加分点是 G1 的 Region / 可预测停顿与 ZGC 的「停顿与堆大小无关」；答完补一句「GC 调优不是目标，先看对象分配模式」。

- **JAVA-9 CPU 100% / 内存泄漏排查**：CPU 走 `top` → `top -Hp` → `jstack` 定位业务线程；内存走 `jmap -dump` + MAT 或 arthas。项目慢 SQL 拦截器把慢查询先变成指标——**慢 SQL 常是 CPU / 内存问题的第一嫌疑**，先用指标定位再深挖。

## SPRING — Spring / 事务 / 安全

- **SPRING-1 IoC / AOP**：容器管生命周期 + 依赖注入；AOP 走动态代理（JDK 代理接口 / CGLIB 代理类）+ 切点 / 通知 / 织入。项目三个切面：预算前置检查、审计（写操作经 Outbox 入库）、限流拦截器。
- **SPRING-2 ⚠ @Transactional 什么时候失效（必问）**：八类——同类内部调用（this 不走代理）、方法非 public、异常被吞、抛检查异常（默认不回滚，需 `rollbackFor`）、传播行为错配、数据源不支持、多线程不共享事务、动态代理没生效。项目订单状态流转显式 `@Transactional(rollbackFor = Exception.class)`——**正是踩过「检查异常不回滚」的坑后的写法**；下单链路因为要把锁留在事务外，改用**显式事务模板**控制边界。
- **SPRING-3 自动装配**：`@SpringBootApplication` = 配置类 + 组件扫描 + `@EnableAutoConfiguration`，自动配置类经 imports 清单加载 → `@ConditionalOnXxx` 按条件装配。项目框架模块用 `@AutoConfiguration` + 注册 imports（不依赖隐式扫描），`@ConditionalOnProperty` 控制可选依赖（MQ / ES 可关，关掉走降级实现）——**换实现只改条件配置**。
- **SPRING-4 Security 认证（项目就是标准实现）**：过滤器链 = 认证过滤器 → JWT 验签 + issuer 校验 → 转换认证主体 → SecurityContext，授权走注解。项目**双 Token**：Access JWT（RSA 签名、短时效、内存）+ Refresh opaque（Redis 存哈希、HttpOnly Cookie、轮换 + 复用检测）；吊销走独立过滤器，与验签职责分离（密码学 vs 吊销状态）。**标准 API 优先**——不手写 JWT 工具类和 Filter，全走 `oauth2ResourceServer()`。
- **SPRING-5 循环依赖**：构造器注入的循环依赖**直接报错**（设计问题），字段 / setter 注入可用三级缓存解决。项目踩过真实的坑——过滤器直接注入 `List<HandlerMapping>` 触发循环依赖（WebSocket 配置链），改为 `ObjectProvider` 延迟解析打破。
- **SPRING-6 全局异常**：`@RestControllerAdvice` + `@ExceptionHandler` 做单入口，控制器只管抛，返回信封与 HTTP 状态码统一收口。项目单入口**模式匹配 switch** 分发、状态码按错误码前缀自动映射、**禁抛非业务基类的 `RuntimeException`**，模块错误码不回落全局码。

→ 完整要点 [02 §17](02-代码走读.md)

## DB — MySQL 与缓存

- **DB-1 索引 / 为什么 B+ 树**：多叉平衡树，非叶子只存索引（扇出高、层数低），叶子存数据 + 双向链表（范围查询友好）；相比 B 树，数据只在叶子出现。项目订单按买家 / 卖家 / 状态建索引。
- **DB-2 索引失效**：最左前缀不满足、隐式类型转换、对索引列做函数 / 运算、`LIKE '%xx'` 前置通配、`or` 有一侧无索引、`NOT IN` / `!=`。项目修过 `IN (${ids})` 字符串拼接——改参数化 `<foreach>` + `#{}`，**既防注入又保证查询计划缓存命中**。
- **DB-3 事务隔离级别**：读未提交（脏读）/ 读已提交（不可重复读）/ 可重复读（幻读，MVCC 解决普通快照读）/ 串行化；MySQL 默认 RR + 间隙锁解决当前读幻读。项目默认 RR 未改——一致性靠「本地事务 + 分布式锁」在业务层解决，**调级别是治标，业务锁才是治本**。
- **DB-4 MVCC**：`undo log` 版本链 + 隐藏列（事务 ID / 回滚指针）+ ReadView（活跃事务列表）判可见性；当前读走当前版本 + 锁。
- **DB-5 慢 SQL 优化**：EXPLAIN（`type` / `rows` / `Extra`）→ 索引优化 → 覆盖索引 / 索引下推 → 分批 / 游标分页 → 读写分离 / 缓存。项目**三层兜底**：业务层缓存拦热点读、监控层慢 SQL 拦截器、数据层覆盖索引 + 参数化查询。
- **DB-6 缓存穿透 / 击穿 / 雪崩**：穿透（负缓存 / 布隆）、击穿（单飞 / 锁）、雪崩（TTL 错峰 / 随机化）。项目**三防已落地**（Spring Cache 注解 + Redis 单层）：穿透缓存 null 结果、击穿 `@Cacheable(sync=true)` 同 key 单飞、雪崩写入时按比例给 TTL 加随机抖动，可用性靠 `CacheErrorHandler` fail-open，一致性由写路径事件 evict 关窗口。**布隆过滤器与手写多级缓存已移除**——单库单 Redis 部署下复杂度换不来可感知收益，**「评估后不用」比堆功能加分**，但要知道多级缓存的教科书方案。

  → 逐条解法 [02 §16](02-代码走读.md) · 话术 [07 §4.2 Q7](07-怎么说.md)

- **DB-7 缓存一致性 / 持久化与过期**：Cache Aside + 先更新 DB 再删缓存 + 延迟双删 / 订阅 binlog，**核心难点是读写并发下「删缓存 vs 写 DB」的竞态**；持久化 RDB（fork + COW）+ AOF（everysec），生产一般都开；过期是惰性删除 + 定期抽样 + 内存淘汰。项目写路径显式失效（领域事件触发注解式 evict、key 精确）+ 短 TTL 兜底，**无本地 L1 层**所以没有「多节点 L1 广播」问题；答完补一句「强一致要上分布式锁 + 版本号，业务接受最终一致才用缓存」。
- **DB-8 Redis 结构与项目用法**：String（SDS）/ List（quicklist）/ Hash（listpack / hashtable）/ Set（intset / hashtable）/ ZSet（skiplist + dict），另有 Bitmap / HyperLogLog / Geo / Stream。项目**按用途列**：缓存（String key + JSON value）、会话窗口（List + TTL）、令牌桶限流（Redisson `RRateLimiter`）、事件消费幂等（`SET NX EX`）、分布式锁（Hash 存持有者 + 重入计数）、预算记账（`HINCRBY` + 日窗口 key）、语义缓存（Hash 存 query 向量 + 回答）。

  > **踩过的坑**：key 用默认 JDK 序列化器时，Lua 脚本的 `ARGV` 传进去是二进制，`tonumber()` 返回 nil → 限流器**静默 fail-open**。修法是 **key 走 `StringRedisSerializer`**（value 走 JSON 是为了可读可调试，不是这个坑的解药）；后来限流器直接换 Redisson `RRateLimiter`，从根上不写 Lua。

## MQ — 消息与事件

- **MQ-1 消息怎么保证不丢失**：生产端 confirm、Broker 持久化、消费端手动 ack + 重试。**项目里 Outbox 比 confirm 更靠前**——业务表与事件表**同事务写入**，事务提交后异步外发，发送成功才标记完成，崩溃重启重发未完成事件。confirm 只保证「Broker 收到了」，Outbox 保证「**业务成功 = 消息必发**」。
- **MQ-2 消息重复消费**：**消费端幂等**。项目用 `SET NX EX` **一条原子命令**领取处理权（key 命名空间 = 消费者 + 事件类型 + 事件 ID，TTL 覆盖三级重试窗口）；单命令即原子，不存在「查标记 → 写标记」的竞态，**所以不需要分布式锁**。「at-least-once + 幂等 = exactly-once 效果」。

  → 领取 / 撤销 / 副作用幂等三层 [02 §14](02-代码走读.md) · 话术 [07 §4.3 Q2](07-怎么说.md)

- **MQ-3 消息积压**：定位（队列深度指标）→ 紧急扩容消费者 / 临时队列迁移 → 找消费慢根因（慢 SQL、下游阻塞）。项目消费者各自独占队列，消费异常进 DLQ **不阻塞主队列**，积压可从指标看趋势。
- **MQ-4 顺序消息**：RabbitMQ 天然无序（多消费者并发），方案有单队列单消费者 / 一致性 hash 按业务键路由 / 客户端排序。项目**刻意不保证跨事件顺序**——各事件独立处理（恢复库存 / 标记售出互不依赖），顺序性由**业务状态机守卫**（非法转换直接拒绝），这是「用领域规则替代消息顺序」的取舍。
- **MQ-5 RabbitMQ vs Kafka**：项目按**四个维度**评分（DLQ + 重试、模型匹配、成本 / 运维、演进位）；**真要换选 NATS JetStream**（原生 `max_deliver` + `discard policy=dead`，声明粒度最接近 Rabbit，替换成本最低）。MQ 选型是 Port 抽象下的配置位，domain / application 层不用动。

  → 四个维度逐条理由 [07 §4.2 Q2](07-怎么说.md) · 评分与拒绝权重 [ADR-0005](../adr/0005-messaging-rabbitmq.md)

## DIST — 分布式与一致性

- **DIST-1 CAP / BASE**：CAP 三选二（分区容错必然存在，实际是 **CP vs AP**）；BASE = 基本可用 + 软状态 + 最终一致。项目下单「本地事务 = CP（强一致），事件副作用 = BASE（最终一致）」——**同一业务两种语义分层**。

**DIST-2 ⚠ 分布式事务方案对比（工程底座核心叙事）**

| 方案 | 问题 |
|---|---|
| 2PC / XA | 协调者阻塞、长锁 |
| Seata AT | `undo_log` + 全局锁、代理数据源 |
| TCC | 3× try / confirm / cancel 样板 |
| Saga | 补偿编排 |
| 本地消息表 / Outbox | — |

**✔ 项目结合：全家族被拒**（[ADR-0007](../adr/0007-order-local-tx-over-saga.md)；原 ADR-0001 的 Saga 编排对比见[已替代决策](../adr/已替代决策.md)）。单库场景**本地事务 + 分布式锁 + Outbox** 一次收齐；**触发演进条件**是模块拆独立数据源 / 独立部署。这也是 DDD-6 拒绝 Saga 的同一判据——Saga 补偿要么与回滚重复，要么崩溃后无法重建。

> ⚠ 被追问 Seata 部署细节（TC / TM / RM 高可用）时按「绕法」答：没在生产跑过，评估阶段的核心关注点是 `undo_log` + 全局锁的写路径成本与中间件单点。

→ [07 §4.2 Q1](07-怎么说.md)

- **DIST-3 幂等设计**：唯一键约束、状态机幂等（已处理状态拒绝重复）、token / 防重表、Redis SETNX。项目**三层幂等各司其职**——协议级（客户端幂等键，缓存成功响应字节级回放）、防连点（短窗口 + 方法 + 请求体 hash，**不缓存响应**）、事件消费（`SET NX EX` 领取处理权）。**防重放 / 防连点 / 防重复消费三件事不要混着讲。**
- **DIST-4 分布式 ID**：雪花（时间 + 机器 + 序列）、UUID v7（时间有序）、各家发号器。项目选 **UUID v7**——时间戳前缀保证**索引局部性**（B+ 树写入友好），零配置零依赖，**砍掉机器号分配与时钟回拨处理**；不选自增的关键理由是**聚合 ID 必须先于 INSERT 存在**（[ADR-0011](../adr/0011-uuid-v7-primary-key.md)）。
- **DIST-5 限流算法**：固定窗口（边界突刺 + 非原子）、滑动窗口（内存大）、漏桶（恒定速率）、令牌桶（允许突发 + 平滑）。项目**两处限流**——商品浏览 GET 走本地固定窗口（单实例够）、写操作走 Redisson 分布式令牌桶（跨实例统一计数，防超卖）、AI 端点按场景令牌桶（超限 429）；**Redis 挂了 fail-open**，限流不是单点。设计题答法见 [05 §4](05-设计题与手撕.md)。
- **DIST-6 熔断 / 降级**：熔断是失败率超阈值开闸 → 半开探测 → 恢复；降级是超时 / 默认值 / 本地兜底。项目自研熔断已随缓存重构移除，缓存降级统一由 `CacheErrorHandler` fail-open 承担（集中一处替代逐点 try-catch）；AI 侧重试与并发隔离由框架客户端内置（自研舱壁已删，ADR-0008 框架化）。**缺口主动说：无跨供应商容灾**——每场景单供应商，故障时降级而非切备用模型，已知技术债。
- **DIST-7 分布式链路追踪**：项目 `traceId` 从 HTTP 头提取 → MDC → 异步任务装饰器透传 → 消息 header 注入 → 消费者解码回 MDC，日志与指标统一关联。**可观测出口已换成 OTel 桥 → Langfuse**（原 Zipkin 上报是死链路，已删）；单 JVM 多模块只在 MQ 头传，拆多 JVM 走 W3C `traceparent`。
- **DIST-8 分布式锁**：手写方案三件套是 `SET NX` + 过期时间（防死锁）+ 唯一 value（防误删）+ Lua 释放（原子）。项目**手写版本评估过，最后用 Redisson**——补上 watchdog 续期（不传 leaseTime 时）与可重入；调的是三参 `tryLock(waitTime, -1, SECONDS)`，**leaseTime=-1 交给 watchdog 续期，waitTime 只是获取锁的等待超时**。**别把「公平锁」算进来**——项目调 `getLock(key)` 非公平，全仓没有 `getFairLock`，被追问就如实说。**「锁内做幂等」要分清**——`SET NX EX` 单命令原子所以不需要锁，需要锁的是「查-写」多命令序列。

  → 落点与四个细节 [02 §13](02-代码走读.md) · 话术 [07 §4.3 Q1](07-怎么说.md)

## DDD — 架构落地

- **DDD-1 DDD 和传统 MVC 分层区别**：MVC 按技术切（Controller / Service / DAO），业务规则散落 Service；DDD 按领域切（domain / application / adapter），**不变量下沉聚合根**，领域层零框架依赖，依赖方向单向向内。项目三层 + Maven 多模块 + Port 接口编译期隔离 + ArchUnit 规则 CI 守卫（规则清单以 `ArchitectureRulesTest` javadoc 为单一来源，条数见[结构计数](../工程指标.md#结构计数)）。
- **DDD-2 聚合根 / 实体 / 值对象**：聚合根 = 聚合入口 + 不变量守卫；实体有 ID 可变；值对象按值等价不可变。项目**只对「有规则的字段」做 VO**（ID 语义、金额精度、手机号格式），不每字段包一层——避免 ceremony；聚合根不可变（`@Builder(toBuilder = true)` 重建新实例），状态转换返回「新聚合 + 领域事件」。
- **DDD-3 CQRS 什么时候用**：读多写少 + 跨聚合查询 + 读写独立优化才用。项目只在 product / order / payment / message 做且**深度不同**；admin / user 刻意不做（单表索引够 / 读写均衡）。

  → 逐模块深度与理由 [07 §4.2 Q3](07-怎么说.md) · 轻量理由 [06 §1.8](06-工程底座.md) · 范围决策 [ADR-0002](../adr/0002-cqrs-scope-4-modules.md)

- **DDD-4 事件驱动架构 / Outbox**：领域事件 = 状态转换的副产物（`Transition<聚合, 事件>` 一并产出），跨模块零同步耦合；Outbox 的写法与保证见本册 **MQ-1**，消费侧 DLQ 三级重试 + 幂等收口。**扣库存是刻意的例外**（同事务同步扣），因为它是防超卖的不变量、不能靠最终一致。
- **DDD-5 六边形架构 / 端口适配器**：领域在中心，出站 / 入站都是 Port 接口，Adapter 实现外围依赖。项目 Port 编译期隔离（跨模块依赖全部 `optional`，边界靠编译期而非约定），换实现（锁 / 支付 / 短信 / ES / AI 供应商）只改 adapter。**六边形不等于什么都自己包一层**——最贵的一课是 AI 侧曾自研 Port / 适配器 / 装饰器，框架成熟后全部删掉换 Spring AI。
- **DDD-6 为什么拒绝 Saga**：判据与触发演进同 **DIST-2**（单库部署，一个本地事务就把订单 / 库存 / 支付 / Outbox 全包进同一事务，比 Saga 的最终一致更强也更便宜）——方案对比表见本册 DIST-2。

  → 取舍表 [06 §2](06-工程底座.md) · 拒绝理由与话术 [07 §4.2 Q1](07-怎么说.md)

## S — 通用场景题

- **S-1「最有挑战 / 踩过最大的坑」**（主讲一个，第三个备选）：**技术选型纠偏**——自研 AI Port / Adapter + 装饰器 → 框架成熟后全面框架化（ADR-0003 → 0008），**「承认自研与框架重复，删掉手写代码」比「从不犯错」可信**；**一致性架构决策**——Saga 上过线 → 发现单库场景补偿与回滚重复、失败状态随事务丢失 → 回退本地单事务 + 分布式锁 + Outbox（ADR-0001 → 0007）；**备选技术坑**——Redis 序列化器（默认 JDK 序列化 → Lua `tonumber` 失败 → 限流器 fail-open，详见本册 DB-8），或「余弦重排等于没排」的识别与删除（ADR-0012）。
- **S-2「让你设计 10 倍流量怎么改」**（七步，顺序不能乱）：① 读写分离（主从 + 读库扩展）② 缓存前置（命中率已高，加 CDN / 预热）③ 多实例（已用 compose 多实例 + nginx LB 验证过横向扩展）④ Redis 单点 → 哨兵 / 集群 ⑤ 跨库演进：模块拆独立数据源后**此时才重新评估真 Saga**（ADR-0007 触发条件）⑥ AI 链路：令牌桶参数按容量调整 + 预算下调 + stale 兜底 + 预算存储切 Redis ⑦ 压测持续断言门禁。**顺序要对**：先横向扩容 + 缓存，**最后才拆库上 Saga**——展示「演进触发条件」思维。
- **S-3「你们为什么不用微服务」**：单 JVM 多模块，模块边界 = **编译期强制**（Port + ArchUnit）。微服务的核心收益（独立部署 / 独立扩容 / 故障隔离）在单机阶段收益为零，跨模块一致性用本地事务就能解决（微服务反而要引 Saga / 分布式事务）；**触发条件**是团队规模 / 流量 / 独立部署诉求到阈值（[ADR-0006](../adr/0006-module-decoupling-port-adapter-acl.md)）。
- **S-4「这个项目你还会加什么」**（按 ROI 提 2-3 个，体现演进规划）：循环三口径跑量回填 + 首字延迟埋点（补测量债）；检索质量回归进定时 / 门禁（当前按需 dispatch）；跨供应商容灾（按场景挂第二供应商 bean，触发条件是 AI 链路进 SLA）；Agent 演示素材落地（多步找货流式 / Cursor 连 MCP / Langfuse trace 面板）。
