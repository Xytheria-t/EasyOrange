# 一、DDD 核心思想轻量落地（面试版）

> 本项目 DDD 是**「展示核心思想、拒绝过度设计」的克制落地**。每个核心思想 → 具体文件落点 → 为什么这样是轻量的。与 [01-话术与总纲.md](01-话术与总纲.md) 互补——那边是「通用叙事 + 高频追问」，这边是「DDD 专项清单 + 取舍话术」。
>
> 一句话定位：**DDD 六边形 + CQRS，domain → application → adapter 单向依赖**。11 个 Maven 模块、4 个核心聚合根（Product / Order / Payment / User）、35 个 Port 接口编译期隔离、ArchUnit 10 条规则在 CI 守分层不被破坏（注意：老口径写 11，实际代码与 `ArchitectureRulesTest` 自身 javadoc 都是 10）。代码里的聚合根不止 4 个，另有 `Favorite` / `Message` / `OfflineMessage` 三个简单聚合——只有不可变快照字段 + 所有权校验、无状态机，不占讲点。

## 1 核心思想清单（讲了能拿分的）

> 面试讲 DDD，别背概念，直接指代码。下面每一条都带落点文件 + 「为什么这是轻量的」——后者才是拉开差距的地方。

### 1.1 聚合根（Aggregate Root）——状态机 + 不变量内聚
- **落点**：`order/domain/aggregate/Order.java`、`payment/domain/aggregate/Payment.java`、`product/domain/aggregate/Product.java`、`user/domain/aggregate/User.java`
- **共性（先说）**：4 个聚合都是**不可变对象**，字段全 `final`，用 `@Builder(toBuilder = true)`「重建新实例」代替原地修改；聚合只做状态机 + 不变量，**不碰持久化、不注入外部依赖**（`domain` 层零框架依赖由 ArchUnit 锁死，见 1.9）。
- **状态机「只有部分聚合有」，签名还各不相同——别一勺烩**：
  - `Order`（订单）——**状态机最完整**：`private Order transitionTo(OrderAction action, String reason)`（一处校验合法性 + 一处应用副作用，见 `Order.java:248`）；公开转换 `pay()/cancel(reason)/forceCancel/ship()/confirmReceipt()/refund(reason)` 全部返回 `Transition<Order, XxxEvent>`（新聚合 + 领域事件一并产出）。
  - `Product`（商品）——**有状态机但签名不同**：`private Product transitionTo(ProductStatus target)`（**单参、目标状态驱动**，见 `Product.java:163`；曾带 `String action` 动作说明参数，因仅用于拼错误消息属语义噪音，已去掉，错误消息改为由「当前→目标」状态 desc 生成）；`approve()/reject()/putOnline()/takeOffline()` 返回 `Transition<Product, XxxEvent>`，`markAsSold()` 幂等返回 `Optional<Transition<...>>`（订单完成链路重复触发时返回空，不重复产事件）。
  - `Payment`（支付）——**没有 `transitionTo` 方法**：守卫收口 `PaymentStatusGuard` 的 6 个状态谓词（`canPay/canRefund/canClose/canFail/canConfirmPay/canConfirmRefund`），`withStatus()`/`withRefundResult()` 只内置字段副作用（`cancelPay()/cancelRefund()` 也已从内联判断改走谓词，全类无一处散写状态判断）；**终态转换**（`create()/confirmPay()/refund()`）返回 `Transition<Payment, XxxEvent>`，**中间态转换**（`preparePay()→PAYING`、`cancelPay()→PENDING`、`prepareRefund()→REFUNDING`、`cancelRefund()→SUCCESS`）**直接返回裸 `Payment`、不产事件**。
  - `User`（用户）——**没有状态机**：`status` 仅在 `create()` 置为 `NORMAL`，之后不再转换；只有 `updateContactInfo()/changePassword()/changeAvatar()/recordLogin()/assignId()` 这类 toBuilder 变换方法（承载业务不变量，不产领域事件）。
- **为什么轻量**：状态机只给**真正有状态生命周期**的聚合上（Order / Product 强状态、Payment 中等），User 没有状态机就不硬造；规则只在「动作表 / 状态机表 / Guard」写一处，不散在应用层。跨聚合一致性交给事件（见 1.4），不搞聚合内嵌反规范化——聚合保持小而纯。

### 1.2 不变量（Invariant）只写一处
- **落点**：`Order.createOrder()` 里 `BizRequire` 链——不能认领自己、必须有至少一件资产、金额必须 > 0；状态合法性由 `OrderAction.canApply(status, paymentStatus)` 裁决（`OrderAction.java:96`，每个动作声明 `sources/target/targetPaymentStatus/closureKind/resultCode/paymentGuard`）。
- **为什么轻量**：规则**只写一处**，测试直接打聚合根（`Payment` 聚合根测试 75 个全绿）。不需要额外规则引擎 / Guard 框架，`BizRequire` 一个静态方法就够。状态裁决按模块各归其位：**Order 用 `OrderAction` 动作表、Product 用 `ProductStatus.ALLOWED_TRANSITIONS` 表、Payment 用 `PaymentStatusGuard` 谓词**——「状态合法性由谁说了算」这一问要能答出来。

### 1.3 值对象（Value Object）——按值等价的不可变类型
- **落点**：`OrderId` / `UserId` / `Phone` / `Address` / `OrderNo`（`order/domain/valueobject/`）、`common/domain/ProductId.java`（跨模块共享的 `ProductId` 在 common，不在 order 的 valueobject 包里）、`common/domain/Money.java`（金额不落 `double`，用 `BigDecimal` 避免精度坑）。
- **为什么轻量**：**只对「有规则」的字段做 VO**（ID 的语义、金额的精度、手机号格式），不把每个字段都包一层——避免为了 VO 而 VO 的 ceremony。

### 1.4 领域事件（Domain Event）——状态转换的副产物
- **落点**：`OrderCreatedEvent` / `OrderPaidEvent` / `OrderCancelledEvent`…（order 模块 `domain/event/`），状态转换方法统一返回 `Transition<Agg, Event>`；事务提交后经 **Outbox** 与业务同事务一写（Spring Modulith）。
- **为什么轻量**：事件是「状态转换自然产生的副产物」，不是到处 `new` 事件。跨模块副作用（扣库存、恢复库存、标记售出）由消费者异步触发，聚合不感知。

### 1.5 工厂与重建分离（Factory vs Reconstruction）
- **落点**：`Order.createOrder(spec)`（**跑不变量**）vs `Order.from(spec)`（**不跑不变量**，直接从库重建）。
- **为什么轻量**：明确「新对象 vs 从库重建」两条路径——重建时库里的数据已被校验过，不再重复触发不变量，性能与正确性都对。参数用 record spec 收敛，避免长参数列表。

### 1.6 仓储 + 端口（Repository & Port / 六边形）
- **落点**：`OrderRepository` + `OrderQueryRepository`（CQRS 读写分离，见 1.8）、`DistributedLockPort` / `PaymentGatewayPort` / `ProductQueryPort`…（**35 个 Port** 编译期隔离）。
- **为什么轻量**：domain 只依赖接口，实现全部放 adapter。依赖方向单向（domain → application → adapter），换实现（Redis/Mem 锁、Rabbit/NATS 总线）只改 adapter，domain/application 一行不动。

### 1.7 领域服务 vs 应用服务（Domain vs Application Service）
- **落点**：领域服务 `message/domain/service/SensitiveWordFilterService.java`（纯规则、无仓储）；应用服务 `message/application/service/OfflineMessageStoreService.java`（**编排**：读在线状态 → 决定是否持久化）。
- **为什么轻量**：**只有不天然属于某个聚合的规则才做领域服务**；涉及读状态 + 调仓储的编排一律放 application。分不清这两个，是 DDD 面试最常见的扣分点。

### 1.8 CQRS（读写分离——4 个模块，两种深度）
- **落点**：`OrderReadModel` / `OrderQueryRepository`（`order/application/query/readmodel/`）、product 的 `application/query/readmodel/`；范围决策见 [ADR-0002](../adr/0002-cqrs-scope-4-modules.md)。
- **为什么轻量**：CQRS 收益是「读多写少 + 跨聚合聚合 + 读写模型独立优化」。**只在 product / order / payment / message 四个模块做，但深度不同**：
  - **有独立 ReadModel（类型级读写分离）**：product（`application/query/readmodel/` 下 5 个 ReadModel）、order（`application/query/readmodel/OrderReadModel`）——ES 全文搜索 / 订单列表跨聚合分页这类复杂查询收益最明显；
  - **只有 Command/Query Handler 级分离（无独立 ReadModel）**：payment、message——`*CommandHandler` / `*QueryHandler` 分文件 + 独立查询仓储（`MessageQueryRepository`），满足「写侧不依赖读侧」的 ArchUnit 守卫，但查询侧与写侧差异没那么大，就不再造 ReadModel；
  - **刻意不做**：favorite（单表索引够用）、user（读写比均衡）——收益 < 维护成本。
  - **注意别把 message 说成「不做 CQRS」**：它做了 Handler 级读写分离，只是没有独立 ReadModel（聊天消息读写比 1:1，读模型独立优化的收益接近 0）。

### 1.9 防腐层 / 依赖治理（用测试守边界）
- **落点**：`ArchitectureRulesTest` **10 条 @ArchTest** 在 CI 阻断（⚠️ 老口径写 11，代码与文件 javadoc 都是 10）：
  ① domain 白名单准入：`domain` 只允许依赖 JDK + `common`（禁框架 / 禁 web / 禁 DTO，合并为 1 条）；
  ②③ CQRS 读写双向隔离：`*CommandHandler` 不依赖 `*QueryHandler`，`*QueryHandler` 也不依赖 `*CommandHandler`；
  ④ 业务模块间只经 `domain.port.*` / `domain.valueobject.*` 通信（覆盖 order/product/message/favorite 四模块）；
  ⑤ 每个 `*Port` 接口必须有 `adapter.outbound` 实现（白名单已清零）；
  ⑥ 禁止 `*.infrastructure.*` 包；
  ⑦ `domain`/`application` 不反向依赖 adapter（已用 `FreezingArchRule` 冻结已知历史豁免）；
  ⑧ Controller 不直连 mapper；
  ⑨ 禁 `System.out` / `System.err`；
  ⑩ 禁 `e.printStackTrace()`。
- **为什么轻量**：用 ArchUnit 测试守分层，**不靠空壳架构 / 冗余包**。规则坏了 CI 直接红，PR 合不进来。

## 2 刻意不做 / 轻量化取舍（防「过度设计」扣分话术）

> 面试官真正想听的，不是你会用多少个 DDD 模式，而是**你懂什么时候不该用**。下面每条都是「我评估过、主动拒绝」的决策。

| 没做的 | 为什么不做的理由 | 做了会怎样被扣分 |
|---|---|---|
| **Saga / 2PC / Seata AT/TCC** | 单库部署，一个本地 `@Transactional` 就把订单/扣库存/Outbox 全包进同一事务，比 Saga 最终一致更强（[ADR-0007](../adr/0007-order-local-tx-over-saga.md)） | 挂一个**失效的状态机**，观测价值低于写路径成本，典型「为了架构而架构」 |
| **全模块 CQRS** | 收益 < 维护成本（[ADR-0002](../adr/0002-cqrs-scope-4-modules.md)） | 每模块 Command/Query 双倍代码，纯负担 |
| **Specification 模式** | 支付的状态谓词不是「跨对象业务规则组合」，是转移谓词 | 假模式名露怯 → 已改名 `PaymentStatusGuard` |
| **每个字段都包 VO** | 只对有规则的字段做（ID/金额/手机号） | ceremony，代码量膨胀 |
| **Milvus / PGVector** | SKU < 10 万，ES kNN 够用 | 向量索引 + ANN 调参一整套运维负担 |
| **聚合内嵌反规范化** | 跨聚合一致性交给事件 + Outbox | 聚合膨胀，单点改死 |

## 3 本次 DDD 轻量化清理（审计记录 2026-08）

> 过程记录（changelog 性质）：面试讲 §2 取舍清单即可；这些清理细节是「被追问最近在项目里做过什么」时的素材。

1. **`PaymentSpecification` → `PaymentStatusGuard`**（`payment/domain/aggregate/`）
   - 原包名 `specification/` 撞「Specification 模式」名，但实际只是支付状态转移谓词，且与订单模块 `OrderAction.canApply` 角色重复。改名 + 移包，去掉假抽象名。
2. **`OfflineMessageStoreService` 从 `domain/service` → `application/service`**
   - 它包了个 repository 做「在线判断 → 持久化」，是应用层编排，不是纯领域规则。移出后 `domain/service` 只剩纯领域服务 `SensitiveWordFilterService`，领域/应用职责分清。
3. **`SensitiveWordFilterService` 注释统一中文**
   - 消除模块内中英混用，与全项目一致。
4. **聚合状态机守卫签名对齐**（Order / Product / Payment，2026-08）
   - `Product.transitionTo` 去掉仅为拼错误消息的 `String action` 参数，改单参 `transitionTo(target)`；错误消息由「当前 → 目标」状态 desc 生成，信息量更高。
   - `Payment.cancelPay()/cancelRefund()` 内联 `PaymentStatus.equals(status)` 改走 `canConfirmPay()/canConfirmRefund()` 谓词，守卫单一来源收口 `PaymentStatusGuard`。
   - 消除 Order/Product 同名私有 `transitionTo` 参数反序的观感噪音；意图性差异保留（Order 动作表驱动 / Product 目标状态驱动 / Payment 谓词），各归其位。

## 4 面试 60 秒 DDD 概括稿

> 直接把下面这段背下来，临场改写即可。

「这个项目是 DDD 六边形 + CQRS 的克制落地。核心是 4 个聚合根——Order、Payment、Product、User，都是不可变对象。**Order 走最完整的状态机**：单一入口 `transitionTo(action, reason)` 守卫，返回 `Transition<事件>` 发领域事件；Product 也有状态机（单参 `transitionTo(target)`，目标状态驱动）；Payment 用 `PaymentStatusGuard` 谓词守卫、终态才产事件；User 没有状态机，只有不变量方法。跨模块副作用（扣库存 / 恢复库存 / 标记售出）由事件 + Outbox 异步触发，聚合不碰持久化。领域层只依赖 Port 接口，35 个 Port 编译期隔离，ArchUnit 10 条规则在 CI 守分层。

我特意做了几个**轻量化取舍**：首先是**拒绝 Saga**——单库部署下本地事务 + Outbox 比 Saga 更强，挂个失效状态机是过度设计；二是 CQRS 只做 4 个模块（product/order 有 ReadModel、payment/message 是 Handler 级），收益小于成本就不做；三是值对象只对有规则的字段做。这些取舍比堆 DDD 模式更能体现架构判断力。」

## 1 下单链路 — OrderCommandHandler

- **文件**：`easyorange-order/.../application/command/OrderCommandHandler.java`
- **关键代码**：
  ```java
  @Transactional(rollbackFor = Exception.class)
  public CreateOrderResult handle(CreateOrderCommand command) {
      return lockPort.executeWithLocks(buildLockKeys(command), LOCK_TRY_TIMEOUT_SECONDS, () -> createOrderFlow(command));
  }
  ```
- **实现要点**：
  1. 锁在**事务内获取、事务提交/回滚后释放**（`DistributedRedissonLockAdapter` 用 `TransactionSynchronization.afterCompletion` 延迟释放）——若在事务提交前释放，后一个请求会在前一个事务尚未提交时读到旧库存快照，击穿防超卖
  2. `buildLockKeys`：多个商品按 **productId 排序**（distinct + sorted）→ 防 AB-BA 死锁
  3. 事务内顺序：建单 + Outbox 发事件 → `decreaseStock` 同步扣库存 → `createPayment` 建支付 → 卖家缓存驱逐
  4. 任一步失败 → 数据库整体回滚（订单/库存/支付/Outbox 同事务），抛 `OrderCreationException`，**无补偿路径**
  5. 锁获取失败（10s 超时）→ 抛「资产下单繁忙」，事务回滚
- **可能的追问**：「锁和事务的顺序有问题吗？」→ 常见做法是**先拿锁再开事务**；我们是**先开事务再拿锁**（`@Transactional` 注解在 `handle()` 上，`executeWithLocks` 在方法体内）——锁在事务提交后再释放（`afterCompletion`），保证下一个请求拿到锁时前一个事务的数据已提交可见，收敛防超卖窗口（e268c59e）；代价是事务占用 DB 连接时间更长，10s 锁超时兜底
- **一句话**：单库下单 = 本地事务包住 锁 → 建单 → 扣库存 → 建支付，失败整体回滚，拒绝 Saga（ADR-0007）

## 2 订单状态机 — Order + OrderAction

- **文件**：`easyorange-order/.../domain/aggregate/Order.java`、`domain/constant/OrderAction.java`
- **关键代码**：
  ```java
  // OrderAction 枚举：每个动作声明前置状态集合、目标状态、目标支付状态、错误码（状态机唯一事实来源）
  PAY("支付", Set.of(OrderStatus.PENDING_PAYMENT), OrderStatus.PAID, PaymentStatus.PAID, ...)
  CANCEL("取消", Set.of(OrderStatus.PENDING_PAYMENT), OrderStatus.CANCELLED, null, ...)
  FORCE_CANCEL(..., Set.of(PENDING_PAYMENT, PAID), CANCELLED, ...)

  // 聚合根：所有转换经统一守卫
  private Order transitionTo(OrderAction action, String reason) {
      BizRequire.requireTrue(action.canApply(status, paymentStatus), action.resultCode());
      ...应用副作用（状态+支付状态+原因/时间）...
      return this;
  }
  ```
- **实现要点**：

## 4 分布式锁 — DistributedLockPort + DistributedRedissonLockAdapter

- **文件**：`easyorange-framework/.../lock/DistributedLockPort.java`（端口接口，统一 order/payment/超时任务三处用法）、`.../lock/DistributedRedissonLockAdapter.java`（Redisson 实现、@Component("distributedLockAdapter")）
- **关键代码**（适配器内部）：
  ```java
  RLock lock = redissonClient.getLock(lockKey);
  boolean locked = lock.tryLock(waitTime, -1, TimeUnit.SECONDS);  // leaseTime=-1 → watchdog 续期
  ... // 锁在事务提交/回滚后释放（TransactionSynchronization.afterCompletion），不是 finally
  ```
- **实现要点**：
  1. **leaseTime=-1 → 由 Redisson watchdog 续期**（默认 30s 锁 + 每 10s 续期），锁不会在下单流程结束前自动过期——不必手工估算事务耗时；`RedissonConfig` 显式固定 watchdog 周期
  2. 释放推迟到事务提交/回滚之后（`TransactionSynchronization#afterCompletion`）——提前释放会让后一个请求读到旧库存快照，击穿防超卖（e268c59e）
  3. 释放前检查 `isHeldByCurrentThread()`——防止锁已过期被他人持有后误删别人的锁
  4. 多锁按 productId 排序逐个获取（`OrderCommandHandler.buildLockKeys` 排序 → `DistributedLockPort.executeWithLocks` 逐个获取），逆序释放，防 AB-BA 死锁
  5. 锁 key：`eo:order:lock:product:{productId}`（payment 用例 key=`payment:lock:...`，超时任务 key=`eo:order:lock:cancel:{orderId}`）
  6. **失败语义**：获取锁失败（等待超时/中断）抛 framework `LockAcquisitionException`——order 在 handler 边界映射为 `OrderCreationException`（B0002→400），payment 复用同一异常兜底（catch 后以统一文案重抛，RuntimeException→500）；`waitTimeout=0` 即非阻塞尝试，拿不到可自行降级
- **可能的追问**：「锁过期了业务还没完怎么办？」→ watchdog 自动续期，锁不会自动过期；holder 超阈值（60s）由适配器 warn 告警（疑似长事务卡住），业务失败整体回滚。「Redis 挂了锁怎么办？」→ Redisson 连接异常时 tryLock 抛异常走事务回滚（不静默放行——超卖保护宁可失败不可绕过）
- **一句话**：Redisson RLock leaseTime=-1 由 watchdog 续期、事务提交后释放，按 key 排序防死锁，释放前校验持有者

## 8 事件幂等 — EventIdempotencyChecker

- **文件**：`easyorange-framework/.../event/idempotency/EventIdempotencyChecker.java`
- **关键代码**：
  ```java
  // 两级：Redisson 锁保证「查-写」原子，Redis done 标记做去重
  RLock lock = redissonClient.getLock("eo:event:lock:" + eventType + ":" + eventId);
  lock.tryLock(0, 30, SECONDS);   // 锁内再查 done 标记
  if (!isDuplicate(eventType, eventId)) {
      redisTemplate.opsForValue().set("eo:event:done:" + type + ":" + id, "1", 24, HOURS);
  }
  ```
- **实现要点**：
  1. `SET NX EX` 是单条原子命令，「检查 + 写入 + TTL」一步完成，**无查-写竞态**，无需再加分布式锁（锁解决的是多命令非原子，这里不适用）
  2. done 标记 TTL 24h，覆盖 DLQ 三级重试最长窗口（快速 3 次 + 退避 1/5/15min ≈ 20min）
  3. 处理失败时 `unmark` 撤销标记，容器重试 / DLQ 重投可重新执行——**宁可重试不可漏处理**；标记后处理前崩溃的残留窗口由业务副作用幂等（条件更新）兜底
  4. 命名空间 `consumerId:eventType:eventId` 隔离多消费者监听同一事件
- **可能的追问**：「at-least-once + 幂等 = 精确一次？」→ 是：Modulith 保证不丢（可能重复投递），幂等保证重复只处理一次；「24h 后重复怎么办？」→ 事件 ID 带时间戳的 UUID，24h 后重放基本不可能，TTL 是成本权衡
- **一句话**：锁内查-写原子 + 24h done 标记，把 at-least-once 变成 exactly-once

| 搜索增强 | 每路 LLM 调用可能重复计算 prompt | 「5min Redis 缓存 + 单步降级，重复成本可控」 |
| 消息消费 | 幂等 24h TTL 理论上可重复 | 「24h 窗口内 DLQ 重试已覆盖，超窗重放概率趋零，成本权衡」 |

> 原则：**主动说出「我知道这里有 trade-off，当时选择 X 是因为 Y，触发条件 Z」**，比假装完美强十倍——这正是项目技术债务清单（[doc/技术债务清单.md](../技术债务清单.md)）的叙事价值。

# 三、系统设计题（6 题 · 答题框架 + 项目参考答案）

> 任何设计题都按「澄清需求 → 选型与架构 → 核心难点 + 演进路径」三步答，先框架后细节，控制 3-5 分钟。

## 1 系统设计答题框架（万能三步）

1. **澄清需求 + 估算规模**（QPS / 数据量 / 读写比 / 一致性要求）
2. **选型与架构**（数据模型 / 存储选型 / 缓存 / 消息 / 一致性方案）——每个选型给一句「为什么」
3. **核心难点拆解**（并发 / 一致性 / 幂等 / 可用性）+ **演进路径**（触发条件）

## 2 设计题 1：设计一个限流器（必考）

**框架**：单机 vs 分布式 → 算法选择 → 降级策略。

**答**：
1. 澄清：按什么维度限（IP/用户/接口）、粒度、误杀容忍度
2. 选型：
   - 单机：Guava RateLimiter（令牌桶）或本地滑动窗口
   - 分布式：Redis 令牌桶（Redisson RRateLimiter）——原子取桶/补桶，单机计数器无法跨实例
3. 降级：限流器本身故障必须 **fail-open**（宁可放过不可误杀业务），且限流器不能成为单点
4. 演进：单实例 → Redis 集群；算法：固定窗口（简单但有边界突刺）→ 令牌桶（平滑 + 允许突发）

**项目对照**：`AiRateLimitInterceptor` 就是分布式令牌桶 + stale 降级（超限返回缓存旧值而非 429）+ fail-open；`RateLimitFilter` 是 GET 本地（单实例够）写操作分布式。两套并存的原因：写操作防超卖需要跨实例统一计数，GET 限流本地即可。

## 3 设计题 2：设计消息可靠投递（Outbox 必答）

**框架**：三个环节分别保可靠——生产不丢（事务一致性）/ 存储不丢（持久化）/ 消费不丢（ack + 重试），最后用幂等收口。

**答**：
1. **生产端一致性**（核心难点）：先发消息后提交事务 → 事务失败消息成了孤儿；先提交再发 → 发消息失败业务已成功。正解 **Outbox 模式**：业务 SQL + 事件 INSERT 同一本地事务 → 后台异步外发 → 发成功标记。替代：本地消息表 + 定时扫描。
2. **Broker**：持久化（queue/message durable）+ 生产 confirm
3. **消费端**：手动 ack + 失败重试（指数退避）+ DLQ 隔离毒消息 + **消费者幂等**（at-least-once 语义下重复投递只处理一次）
4. 演进：单机 RabbitMQ → 镜像队列/集群；量级增大换 Kafka（代价：死信、多 group 都要自建）

**项目对照**：Spring Modulith Outbox（EVENT_PUBLICATION 同事务 + 崩溃重发）→ RabbitMQ Topic Exchange → 10 消费者独占队列 → DLQ 三级重试（5min 周期，<3 次重投，毒消息转储 eo.dlq.terminal）→ `EventIdempotencyChecker` 幂等。

## 4 设计题 3：设计一个订单系统（与项目强相关）

**框架**：状态机 → 一致性（防超卖）→ 生命周期副作用 → 查询（CQRS）。

**答**：
1. **状态机**：动作驱动（每动作声明 sources/target/副作用），单一入口守卫，非法转换抛业务异常——比「if-else 状态判断」可测可维护（对照：项目 `OrderAction` 枚举 + `transitionTo`）
2. **防超卖**：分布式锁（按商品 key）+ 库存乐观锁（version）双保险；锁排序防死锁
3. **一致性**：本地单事务（订单 + 库存 + 支付 + Outbox 事件原子提交），**单库不上 Saga**；拆库才引入
4. **副作用**：取消恢复库存/完成标记售出 → 事件异步（消费者幂等）
5. **查询**：CQRS 读模型 + 列表索引；超时取消/自动确认 → 定时任务扫描

**项目对照**：`OrderCommandHandler`（事务 + `DistributedRedissonLockAdapter` 锁 + `ProductInventoryPort.decreaseStock`）+ `OrderLifecycleEventConsumer` + `OrderTimeoutTask/OrderAutoConfirmTask`。

## 5 设计题 4：设计短链 / 秒杀（选一个通用题）

**短链**：发号器（雪花/自增 + base62）→ 存储（KV）→ 302 跳转 → 布隆过滤非法码。
**秒杀**：**提前把库存放 Redis 预扣**（写请求只碰 Redis，MQ 异步落库）→ 令牌桶/信号量限流 → 本地单飞 → 事务落库 + 最终一致对账。**不要**：DB 行锁扛所有写。

> 秒杀题与项目的关联点：预扣方案的风险是「Redis 扣了 DB 没扣成」——项目下单链路反过来（锁 + 事务 + 同库扣减），可对比讲「库存扣减我选择同事务强一致而非 Redis 预扣最终一致，因为单库场景没有中间件一致性成本；如果量到百万级再改预扣 + 对账」。这种「我知道另一种方案但不用的原因」最加分。

## 6 设计题 5：设计缓存系统（先答通用框架，再答项目现状）

**通用框架**：层级（L1 本地 / L2 分布式）→ 三防（穿透/击穿/雪崩）→ 一致性 → 可观测。
**答**：先给教科书框架——L1 Caffeine + L2 Redis；负缓存哨兵防穿透；Caffeine 原子单飞 + 跨节点锁防击穿；TTL 配平（l1 ≤ l2）防雪崩窗口；evict 时 Pub/Sub 广播失效其他节点 L1；指标：命中率——**命中率是缓存系统最重要的健康指标**。
**项目落点**：我们**刻意不做多级缓存**——手写 MultiLevelCache（L1 Caffeine + L2 Redis + Pub/Sub 广播 + 负缓存）已于 2026-08-13 移除，统一 Spring Cache 注解 + Redis 单层：写路径显式 `@CacheEvict` 保一致性、统一短 TTL 兜底、`CacheErrorHandler` fail-open 保可用。理由：单库单 Redis 部署下，多级缓存的复杂度（L1/L2 配平、广播、哨兵）换不来可感知的收益；把「我知道多级缓存方案但评估后不用的原因」讲清楚比堆功能更显工程判断力。

## 7 设计题 6：设计一个 RAG 检索增强问答系统（模型应用工程师必考）

**框架**（按万能三步）：澄清需求（语料规模/类型/更新频率/问答场景）→ 选型（索引库/分块策略/检索方式/生成模型）→ 核心难点（分块、召回质量、评估、更新）。

**答**：
1. **澄清**：语料规模与类型（结构化 / 非结构化文档）、更新频率（决定全量重建 vs 增量 pipeline）、问答场景（事实问答 / 总结归纳）
2. **选型**：
   - 索引：ES kNN / Milvus / PGVector——**量级分界线**（< 100 万 ES 自带 HNSW 够用，再大引独立向量库）
   - 分块：固定长度 + overlap（简单可控）vs 语义分块（按标题/段落边界，质量高成本高）；chunk size 权衡——太小上下文碎片、太大稀释相关性
   - 检索：BM25 词法 + 向量召回**混合** → rerank 收口（先粗后精两段式：召回层要快要宽，重排层要准要窄）
   - 生成：ChatModel + **引用溯源**（答案带来源，幻觉可核验）
3. **难点拆解**：
   - 召回质量：hit rate / MRR（检索层客观指标，自动算）
   - 生成质量：faithfulness（忠实度——答案与检索内容一致性）
   - 评测闭环：金标准集 + LLM-as-Judge + CI 门禁（防 prompt/模型改动质量回归）
   - 更新：文档增删改 → 增量重嵌入（或周期全量重建，按更新频率选）

**项目对照**：现状是**商品标题级轻量 RAG**（`SemanticSearchService`：text-embedding-v3 1024 维 + ES kNN + BM25 混合召回 Top-50 + Java 原生 Cosine 重排，SKU < 10 万不引独立向量库）；缺失的是文档摄入管线（分块）、模型 rerank、评测集——**演进触发条件**：引入文档型知识库（商品详情 / 平台规则问答）时先加分块管线 + 评测集，量到百万级再考虑独立向量库。把「现状 + 缺口 + 触发条件」讲全，就是一次完整的演进规划展示。

## 题 1：实现一个令牌桶限流器（单机版）

```java
// 经典实现：synchronized + 补令牌
class TokenBucket {
    private final long capacity;      // 桶容量（最大突发）
    private final double ratePerSec;  // 补充速率
    private double tokens;
    private long lastRefillNanos;

    TokenBucket(long capacity, double ratePerSec) {
        this.capacity = capacity;
        this.ratePerSec = ratePerSec;
        this.tokens = capacity;
        this.lastRefillNanos = System.nanoTime();
    }

    public synchronized boolean tryAcquire() {
        long now = System.nanoTime();
        double elapsedSecs = (now - lastRefillNanos) / 1e9;
        tokens = Math.min(capacity, tokens + elapsedSecs * ratePerSec);  // 按时间补令牌
        lastRefillNanos = now;
        if (tokens >= 1) {
            tokens -= 1;
            return true;
        }
        return false;
    }
}
```

> 面试追问延伸：分布式版 → Redisson RRateLimiter / Lua 脚本（`redis.call('EVAL')` 原子取桶补桶）；边界：`synchronized` 单机够用，多实例必须分布式。

## 题 3：实现订单状态机（动作表版，项目同款）

```java
enum OrderStatus { PENDING_PAYMENT, PAID, SHIPPED, COMPLETED, CANCELLED, REFUNDED }

// 动作：前置状态集合 → 目标状态（项目 OrderAction 的真实形态）
enum OrderAction {
    PAY(Set.of(OrderStatus.PENDING_PAYMENT), OrderStatus.PAID),
    CANCEL(Set.of(OrderStatus.PENDING_PAYMENT), OrderStatus.CANCELLED),
    SHIP(Set.of(OrderStatus.PAID), OrderStatus.SHIPPED),
    CONFIRM_RECEIPT(Set.of(OrderStatus.SHIPPED), OrderStatus.COMPLETED);

    final Set<OrderStatus> sources;
    final OrderStatus target;
    OrderAction(Set<OrderStatus> sources, OrderStatus target) {
        this.sources = sources; this.target = target;
    }
    boolean canApply(OrderStatus current) { return sources.contains(current); }
}

class Order {
    private OrderStatus status;
    private Order transitionTo(OrderAction action) {
        if (!action.canApply(status)) throw new IllegalStateException("非法转换: " + status + " -> " + action);
        this.status = action.target;   // 副作用集中一处
        return this;
    }
    public Order pay()     { return transitionTo(OrderAction.PAY); }
    public Order cancel()  { return transitionTo(OrderAction.CANCEL); }
}
```

> 加分：加支付状态二维（targetPaymentStatus 字段）；「非法转换抛异常」对应项目 `BizRequire.requireTrue(action.canApply(...), action.resultCode())`。

## 题 5：LRU 缓存（手撕高频，与 Caffeine imageProcessCache 驱逐策略关联）

```java
class LRUCache {
    // LinkedHashMap 一版搞定（accessOrder=true 按访问序）
    private final LinkedHashMap<Integer, Integer> map;
    LRUCache(int capacity) {
        this.map = new LinkedHashMap<>(capacity, 0.75f, true) {
            protected boolean removeEldestEntry(Map.Entry<Integer, Integer> eldest) {
                return size() > capacity;
            }
        };
    }
    int get(int key) {
        Integer v = map.get(key);
        return v == null ? -1 : v;
    }
    void put(int key, int value) {
        map.put(key, value);   // 超容量自动淘汰最久未用
    }
}
```

> 追问：手写双向链表 + HashMap 版本（不依赖 LinkedHashMap）也要能写；「Caffeine 的实现是 TinyLFU + 窗口」（比 LRU 更抗扫描型访问）——这是把面试题聊回项目的机会。

## 题 7：单例 + 双重检查（考内存可见性）

```java
class Singleton {
    private static volatile Singleton instance;   // volatile 防指令重排
    static Singleton getInstance() {
        if (instance == null) {                    // 快路径
            synchronized (Singleton.class) {       // 慢路径
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

> 易翻车点：`instance` 不 volatile 时，`new Singleton()` 的三步（分配/初始化/赋引用）可能重排导致另一个线程拿到未初始化对象——这是 volatile 有序性的经典考题，跟项目 `AiModelSupport` 的 `static volatile` recorder 一个道理。

## 题 9：余弦相似度重排（项目同款 · RAG 检索收口）

```java
// 项目 SemanticSearchService 的 rerank 形态：BM25 召回 Top-50 → 查询向量 Cosine 排序取 Top-N
record Scored(String doc, double score) {}

double cosine(List<Float> q, List<Float> d) {
    double dot = 0, nq = 0, nd = 0;
    for (int i = 0; i < q.size(); i++) {
        dot += q.get(i) * d.get(i);
        nq += q.get(i) * q.get(i);
        nd += d.get(i) * d.get(i);
    }
    return dot / (Math.sqrt(nq) * Math.sqrt(nd));  // 归一化点积
}
```

> 加分：讲**两段式召回**——先 BM25 词法召回（要快要宽）再向量重排（要准要窄）；向量预归一化后余弦 = 点积，归一化因子可缓存。追问延伸：模型 rerank（Cross-Encoder）与 Cosine 的区别——双塔 Bi-Encoder（向量提前算好，快）vs 交叉编码（query 与 doc 拼接过模型，准但贵），量级不够时 Cosine 够用（01 §五 有绕法）。
