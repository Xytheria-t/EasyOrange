## 1 多步工具循环 — AgentLoopRunner

- **文件**：`easyorange-ai/.../application/service/AgentLoopRunner.java`
- **关键代码**：
  ```java
  for (int round = 1; round <= maxSteps; round++) {
      var decision = decide(prompt, callbacksByName);   // 原生 tool calling：发 schema、收回 tool call
      if (decision.isFinish()) { break; }
      if (budgetExhausted()) { outcome = OUTCOME_BUDGET; break; }   // 循环中途预算检查
      var outcome = executeTool(decision, callbacksByName);         // 执行在 runner，不在框架
      observations.add(new StepObservation(decision.tool(), toolInput, outcome.observation()));
  }
  ```
- **实现要点**：
  1. **决策走原生 tool calling**：schema 由 `AgentTools` 的 `@Tool` 注解生成随请求下发，`ChatModel.call` 不自动执行工具（自动执行在 `ChatClient` 层）——执行与循环控制权在 runner
  2. **三条降级口径**：步数超限 / 预算耗尽 → 用已积累观察单次生成；决策失败 → 按原始问题检索一次（**不是不检索**）
  3. **每步落 trace**（一次请求一个 trace_id）+ SSE step 事件；指标按 outcome 计数（finished / step_limit / budget / decision_failed）归因
  4. 失败的工具结果**也进观察**（模型可据此换参数重试），不吞异常
- **可能的追问**：「步数上限怎么定？」→ 可配，取值兼顾「多文档对比够用」与「成本 / 延迟可控」；到上限不是报错而是降级生成。「为什么不用递归？」→ 显式 for 循环 + 显式状态更好加预算检查与终止原因分类。「观察太长怎么办？」→ 工具结果有文本转换器压成紧凑观察（列表类工具截断 + 提示可分页）
- **一句话**：手写循环持有控制权——原生 tool calling 决策、runner 执行工具、三条降级口径与步级 trace 都在自己的循环里

## 2 工具面 — AgentTools

- **文件**：`easyorange-ai/.../application/service/AgentTools.java`（工具名与编排器共用常量）
- **实现要点**：
  1. **按性质分四层**：检索 3（规则知识 / 在售资产 / 资产详情）+ 计算 2（行情统计 / 多件逐维比对，纯 JDK 零模型调用）+ 写入 1（长期偏好）+ 收敛 1
  2. **计算类让步骤产生依赖**：没有它，循环只是换关键词重试；有了它，第 N 步真的消费第 N-1 步的输出
  3. **写入工具独立**：偏好写入从「收敛轮参数」拆成独立工具——挂在收敛轮时，三条降级路径下会静默丢失
  4. 每个工具首参是 `thought`（本步理由）→ 落 trace、供前端展示与排障；详情 / 比对类工具的 ID 参数要求取自前一步观察
- **可能的追问**：「工具太多会怎样？」→ 决策空间与误选率上升，且 schema 占 token；所以工具要正交（检索 vs 计算 vs 写入 vs 收敛各司其职）。「工具失败怎么处理？」→ 失败收敛为「失败观察 → 模型换参数重试」，「工具执行失败就整体报错」是错的
- **一句话**：工具面按性质分层，计算类工具是让循环「真的多步」的关键，写入与收敛独立成工具

## 3 会话与上下文 — AiChatService / ChatContextTrimmer / ChatSessionStore

- **文件**：`easyorange-ai/.../application/service/AiChatService.java`、`ChatContextTrimmer.java`、`.../adapter/outbound/cache/ChatSessionStore.java`
- **实现要点**：
  1. **短期记忆**：Redis List 会话窗口（TTL 24h，裁剪到最近 N 轮）；**长期记忆**：用户画像表（跨会话，由独立工具写入）
  2. **上下文两道治理**：轮数窗口（存储侧）+ 估算 token 裁剪（注入侧，`TokenEstimator` CJK 0.7 / 其余 0.3，预算可配）；裁剪点唯一，决策与生成两条装配共用；**从最新向前保留连续窗口，单条超预算仍保最新一条**
  3. **生成时历史按原始角色传多消息**（不压进当前 user 消息）——跨轮前缀稳定才能命中供应商上下文缓存折扣
  4. 降级：供应商故障 → stale 旧回答；记忆读写 fail-open
- **可能的追问**：「为什么不用向量召回历史？」→ 会话窗口小、轮数受限，召回收益低于复杂度；「摘要压缩呢？」→ 有意不做（步数与轮数上限下收益小、每轮多一次模型调用）
- **一句话**：轮数窗口 + token 裁剪两道、裁剪保最新、历史按原始角色传、记忆读写 fail-open

## 4 工作流式扇出 — AiSearchEnhancerAdapter + SearchToolRegistry

- **文件**：`easyorange-ai/.../adapter/outbound/AiSearchEnhancerAdapter.java`、`.../tool/`
- **关键代码**：
  ```java
  CompletableFuture.allOf(intent, tags, market, questions).get(5, TimeUnit.SECONDS);
  // 超时 / 异常 → 收集已完成的部分结果，其余降级
  ```

- **实现要点**：
  1. **Tool Registry 模式**：工具接口（name / description / kind / run）+ Spring 自动收集进注册表（构造期防重名），新增工具零改动注册
  2. **只有一路打模型**：意图识别走 LLM，标签 / 市场分析 / 建议问题全为本地规则计算（零供应商调用、亚毫秒）
  3. 并行 `supplyAsync` **显式传虚拟线程执行器**（`commonPool` 是平台线程且并行度 = 核数 − 1，配置开关管不到它），`cancel(false)` 不中断载体
  4. **整体 5s 超时**，部分结果可用（关键路任一有值即返回），结果缓存；前置降级：非自然语言或空结果集**直接不烧 token**
  5. 与 §1 的对照：这是**固定扇出**（四路无条件全提交、模型不选路），不是 tool calling 语义
- **可能的追问**：「为什么不用 commonPool？」→ 平台线程会被秒级 LLM 阻塞占死；「为什么不要自定义池？」→ 虚拟线程轻量到每任务一个，自定义池是过度设计；「这算 Agent 吗？」→ 算 Workflow 式编排，与自治循环是两种范式（AG-1）
- **一句话**：工具注册表 + 虚拟线程并行 + 整体超时保留部分结果；一路 LLM 三路规则，模型不参与选路

## 5 MCP 对外工具面 — PlatformMcpTools

- **文件**：`easyorange-ai/.../adapter/inbound/mcp/PlatformMcpTools.java`
- **实现要点**：
  1. `@McpTool` + streamable HTTP（端点 `/mcp`），4 个**公开只读**工具：资产检索 / 资产详情 / 类目浏览 / 平台规则知识——复用既有的检索与详情服务，不重写查询
  2. **两级暴露的信任边界**：外部 client 无用户上下文 → 不暴露订单 / 个人信息 / 写路径；与 Agent 内部工具面各自独立，鉴权假设不共用
  3. 匿名可达但纳入统一限流 + 防重豁免（JSON-RPC 重试复用请求体属协议内合法行为）；工具调用计数进指标
  4. 踩坑：`protocol` 属性**必须显式配置**（条件装配读 Environment，属性默认值不生效，缺省时端点整个不装配）
- **可能的追问**：「为什么是只读？」→ 外部 client 没有用户身份，任何写路径都缺鉴权上下文；「和内部工具的关系？」→ 两级暴露，内部工具面按循环需要设计，对外面按「公开数据 + 最小能力」设计
- **一句话**：把公开只读检索能力按 MCP 协议暴露给外部 client，信任边界靠两级暴露划分

- **关键代码**：

- **一句话**：一次查询、两路独立召回、按排名融合；语义能力默认生效，不是手动开关

## 9 LLM 可观测 — ChatModelContentObservationFilter + OTel 桥

- **文件**：`easyorange-ai/.../config/ChatModelContentObservationFilter.java`、`compose.yaml`（langfuse profile）
- **实现要点**：
  1. 链路：Spring AI Observation → Micrometer Tracing 的 OTel 桥 → OTLP → 自托管 Langfuse；**与 Grafana 分工**（那边是调用级指标，这边是 prompt 级 trace）
  2. **关键坑**：Langfuse 只认 `gen_ai.prompt` / `gen_ai.completion` 两个**属性键**；Spring AI 的 log-prompt 开关产出的是 span 事件、它不消费——所以要 Observation Filter 把 prompt / completion 拷进属性，漏配则面板 input/output 恒为 null
  3. 成本按自定义模型价逐调用计算（per-token 单位，填错一位差三个数量级）；流式用量靠末帧 usage 回报
  4. 顺带清理：原链路追踪上报是死链路（依赖从未引入 + 属性名变更），服务与配置一并移除，traceId 传播改由 OTel 桥承担
- **可能的追问**：「trace 覆盖率多少？」→ 链路已通、单条 trace 已验证，覆盖率待跑量统计（如实说）；「成本数从哪来？」→ 模型价 × 用量，模型价是配置项
- **一句话**：OTel 桥把 Spring AI 的 Observation 送到 Langfuse，用属性键补 prompt / completion，单条 trace 内每步的 token / 延迟 / 成本可见

## 10 下单链路 — OrderCommandHandler

- **文件**：`easyorange-order/.../application/command/OrderCommandHandler.java`
- **关键代码**：
  ```java
  public CreateOrderResult createOrder(String userId, CreateOrderCommand command) {
      return lockPort.executeWithLocks(
              buildLockKeys(command),
              LOCK_TRY_TIMEOUT_SECONDS,
              () -> transactionTemplate.execute(_ -> createOrderFlow(userId, command)));
  }
  ```
- **实现要点**：
  1. **锁在事务外获取**（等待不占数据库连接）、**事务提交 / 回滚后释放**——提前释放会让后一个请求读到旧库存快照，击穿防超卖
  2. `buildLockKeys`：多商品按 ID **排序去重** → 防 AB-BA 死锁
  3. 事务内顺序：建单 + Outbox 发事件 → 同步扣库存 → 建支付 → 卖家缓存驱逐
  4. 任一步失败整体回滚，抛领域异常（**无补偿路径**）；锁获取失败在事务开启前抛出（无回滚开销）
- **可能的追问**：「锁和事务的顺序有问题吗？」→ 先拿锁再开事务、提交后再释放锁，收敛防超卖窗口；「库存在这里为什么同步扣而同其他副作用异步？」→ 防超卖是不变量，不能靠最终一致
- **一句话**：先取锁 → 本地事务内建单 → 扣库存 → 建支付，失败整体回滚，拒绝 Saga（ADR-0007）

  1. **动作驱动**：合法转换集中在动作表单点声明，聚合根只留一个入口守卫
  2. 每个公开方法返回「新聚合 + 领域事件」；聚合不可变（字段 final）
  3. 支付状态独立于订单状态：取消不改支付状态、支付置已付、退款置已退
- **可能的追问**：「为什么不用一张大状态表？」→ 订单状态 × 支付状态是**二维**的，动作表每行声明两个维度目标值，比二维矩阵更可读可测；「退款为什么要求支付已付？」→ 支付前置守卫
- **一句话**：状态机唯一事实来源是动作表，聚合根单一入口守卫，转换产出事件走 Outbox

## 12 分布式锁 — DistributedLockPort + DistributedRedissonLockAdapter

- **文件**：`easyorange-framework/.../lock/DistributedLockPort.java`（端口）、`.../DistributedRedissonLockAdapter.java`（实现）
- **关键代码**：
  ```java
  RLock lock = redissonClient.getLock(lockKey);
  boolean locked = lock.tryLock(waitTime, -1, TimeUnit.SECONDS);  // leaseTime=-1 → watchdog 续期
  // 锁在事务提交 / 回滚后释放（事务同步回调），不是 finally
  ```
- **实现要点**：
  1. `leaseTime=-1` → watchdog 续期（默认 30s 锁、每 10s 续），**不必手工估算事务耗时**
  2. **释放推迟到事务提交 / 回滚后**——提前释放会击穿防超卖
  3. 释放前检查 `isHeldByCurrentThread()`，防误删他人锁
  4. 多锁按 ID 排序逐个获取（打破循环等待防死锁）；锁 key 按业务前缀区分
  5. 失败语义：获取失败抛统一的锁异常，业务在自身边界映射为领域异常；`waitTimeout=0` 即非阻塞尝试
- **可能的追问**：「锁过期业务还没完？」→ watchdog 续期不会自动过期；holder 超阈值有告警；「Redis 挂了锁怎么办？」→ 连接异常时获取失败走事务回滚（**不静默放行**——超卖保护宁可失败不可绕过）
- **一句话**：Redisson 锁 watchdog 续期、事务提交后释放、按 key 排序防死锁、释放前校验持有者

## 13 事件幂等 — EventIdempotencyChecker

- **文件**：`easyorange-framework/.../event/idempotency/EventIdempotencyChecker.java`
- **关键代码**：
  ```java
  // 一条 SET NX EX 领取处理权（false = 重复 / 他人处理中）
  if (idempotencyEnabled && !idempotencyChecker.tryMark(namespace, eventId)) return;
  ...
  } catch (Exception e) {
      idempotencyChecker.unmark(namespace, eventId);   // 失败撤销标记，容器重试 / DLQ 重投可重新执行
      throw e;
  }
  ```
- **实现要点**：
  1. `SET NX EX` 是单条原子命令，**无查-写竞态**，因此不需要分布式锁
  2. 标记 TTL 覆盖 DLQ 三级重试最长窗口
  3. **失败撤销标记**（宁可重试不可漏处理）；「标记后、处理完成前」崩溃的残留窗口由业务副作用幂等兜底（库存走流水唯一键）
  4. 命名空间隔离多消费者监听同一事件
- **可能的追问**：「at-least-once + 幂等 = 精确一次？」→ 是（不丢 + 重复只处理一次）；「TTL 过期后重复怎么办？」→ 事件 ID 带时间戳，超窗重放概率趋零，是成本权衡
- **一句话**：`SET NX EX` 原子领取 + 失败撤销 + 业务副作用幂等，达成 exactly-once 效果

## 14 Outbox 与 DLQ — ModulithDomainEventPublisher + DlqRetryScheduler

- **文件**：`easyorange-framework/.../messaging/core/ModulithDomainEventPublisher.java`、`.../event/dlq/DlqRetryScheduler.java`
- **实现要点**：
  1. **Outbox**：业务 SQL 与事件表 insert **同事务双写**，提交后异步外发，成功才写完成时间；崩溃重启重发未完成事件；业务方只 `publish(event)`，不知道 MQ 存在（领域层零中间件依赖）
  2. **DLQ 三级**：主队列消费失败 → DLQ → 调度器周期重投（未超次数）→ 转储 terminal 等人工
  3. 退避由主队列重试模板承担，DLQ 层固定周期，**职责分离**；DLQ 监听器提取死信记录指标
  4. 路由键自动派生（事件类名 → 点分路由键），新事件零配置；MQ 可关时降级为进程内
- **可能的追问**：「发到 MQ 失败怎么办？」→ 事件留在表里（完成时间为空），后台重试 + 重启重发，at-least-once 由消费幂等兜底；「为什么调度器轮询而不是原生延迟队列？」→ 声明式简单 + 与死信语义配合
- **一句话**：同事务双写保证「业务成功 = 事件必达」，DLQ 三级重试隔离毒消息，退避与轮询职责分离

## 15 缓存 — RedisCacheConfig

- **文件**：`easyorange-framework/.../config/cache/RedisCacheConfig.java`（+ 属性类 + TTL 抖动 writer）
- **实现要点**：
  1. **注解驱动**：业务侧零缓存代码，统一 cache manager（String key + JSON value）
  2. **三防收口在注解层 + writer 层**：穿透 = null 结果缓存；击穿 = `sync=true` 同 key 单飞；雪崩 = 写入时按比例加 TTL 抖动
  3. **一致性 = 写路径显式 evict + 短 TTL 兜底**（单库单 Redis，不需要 L1/L2 配平与广播）
  4. **可用性 = fail-open**：集中式错误处理器吞掉 Redis 异常（读直查 DB / 写放弃缓存），替代逐点 try-catch
- **可能的追问**：「击穿跨实例呢？」→ 诚实讲边界：单飞是 JVM 内的，跨实例残留少量并发由事件 evict + TTL 兜底；「为什么删多级缓存 / 布隆？」→ 复杂度换不来可感知收益（但要能讲教科书方案）
- **一句话**：注解 + Redis 单层，三防收口在注解与 writer，一致性靠事件 evict，可用性靠 fail-open

## 16 全局异常 — GlobalExceptionHandler

- **文件**：`easyorange-framework/.../exception/GlobalExceptionHandler.java`
- **实现要点**：
  1. **模式匹配 switch** 单方法按类型分发，消除十几个 `@ExceptionHandler` 方法
  2. HTTP 状态码按错误码前缀自动映射（鉴权 / 参数 / 业务 / 系统）
  3. 规范：**禁止抛非业务基类的 RuntimeException**（否则落 500 兜底）；模块异常必须用模块专属错误码，禁止回落全局码
  4. 领域异常每模块一个根类 + 具名工厂（`notFound(id)` / `notOwner(id)`），不搞「一码一类」
- **可能的追问**：「为什么 switch 不用多方法？」→ 分发逻辑收敛一处；「响应统一吗？」→ 统一响应信封 + 自动包装
- **一句话**：单方法模式匹配分发 + 前缀映射状态码 + 模块专属错误码

## 17 商品状态机 — Product

- **文件**：`easyorange-product/.../domain/aggregate/Product.java`
- **实现要点**：
  1. 转换为**目标状态驱动**（`transitionTo(目标状态)`），转换表集中声明；终态判断显式
  2. **两条进入上架状态的路径**（审核通过 / 直接上架）都过同一组 `validateOnline()`——**禁止第三条绕过校验的路径**
  3. 删除不改状态，单独守卫（已售不可删，保留订单追溯）；订单完成触发的「标记售出」幂等（重复触发返回空，不重复产事件）
- **可能的追问**：「为什么上架校验独立成方法而不进状态机表？」→ 状态机表管「转换是否合法」，校验方法管「进入该状态的数据完整性**不变量**」——两类规则职责不同
- **一句话**：目标状态驱动的转换表 + 两条路径共用同一组完整性不变量

## 附：被问「这段代码有什么问题」的应答模板

面试官挑毛病时，**先承认再给方案**，用下面几个项目里真实存在的点（比硬说「没问题」可信）：

| 代码 | 真实问题 | 应答 |
|---|---|---|
| 下单链路 | 锁持有 = 事务时长，等待超时在极端慢 SQL 下会抛「繁忙」 | 「锁与事务同生命周期安全，代价是超时上限；慢 SQL 监控兜底，压测实测远低于此」 |
| 事件幂等 | 标记已写、处理中途崩溃时，重投会判重复而跳过 | 「失败路径已撤销标记，只剩『标记后、完成前』这一窄窗口；由业务副作用幂等兜底（流水唯一键），宁可漏一次也不重复加库存」 |
| 内存预算存储 | 多实例各自记账 | 「已知技术债，多实例切 Redis 存储，接口已就位」 |
| 工作流扇出 | 每路 LLM 调用可能重复计算 prompt | 「结果缓存 + 前置降级（非自然语言直接不调用），重复成本可控」 |
| 消息幂等 | 标记 TTL 理论上可重复 | 「TTL 覆盖 DLQ 重试窗口，超窗重放概率趋零，成本权衡」 |
| Agent 循环 | 步数上限内成本不确定 | 「上限可配 + 循环中途预算检查 + 三口径降级；平均步数 / 降级率待跑量回填」 |

> 原则：**主动说出「我知道这里有 trade-off，当时选择 X 是因为 Y，触发条件 Z」**，比假装完美强十倍——这正是 [技术债务清单](../技术债务清单.md) 的叙事价值。
