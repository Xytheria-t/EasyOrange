# EasyOrange DDD 架构规范

本文档定义了 EasyOrange 项目的 DDD（领域驱动设计）+ 六边形架构规范。
CQRS 作为可选模式，在读写模型差异明显时引入。

> **约定**：标注 `[现状]` 的内容表示当前代码已实现；标注 `[演进]` 的内容表示架构目标，需逐步落地。

## 一、模块总览

| 模块名 | DDD 架构角色 | 核心定位 | 能放什么 |
|-----------|------------|---------|---------|
| easyorange-backend | 父工程（Parent POM） | 全局依赖 / 版本管理 | 统一依赖版本号、插件管理、模块聚合 |
| easyorange-common | 通用基础模块 | 所有模块可依赖 | 统一响应体、基础异常、通用工具类、领域事件基类、基础枚举 |
| easyorange-framework | 框架适配层 | 基础设施通用封装 | Spring/MyBatis/Redis/MQ **通用配置**、过滤器、AOP 切面、JWT 工具、全局异常处理器 |
| easyorange-message | 消息业务模块 | 站内信/通知限界上下文 | 消息实体、消息模板、离线消息、WebSocket、订阅管理 |
| easyorange-application | 启动聚合层 | 主入口 | 启动类、全局配置 |
| easyorange-user | 用户限界上下文 | 完整 DDD 业务模块 | adapter/application/domain 全分层 |
| easyorange-product | 商品限界上下文 | 完整 DDD 业务模块 | adapter/application/domain 全分层 |
| easyorange-order | 订单限界上下文 | 完整 DDD 业务模块 | adapter/application/domain 全分层 |
| easyorange-payment | 支付限界上下文 | 完整 DDD 业务模块 | adapter/application/domain 全分层 |
| easyorange-favorite | 收藏限界上下文 | 完整 DDD 业务模块 | adapter/application/domain 全分层 |

### 模块演进规划 `[演进]`

当前 `easyorange-common` 承担了技术工具和领域共享两重职责。随着业务增长，可拆分为：

| 演进后模块名 | 定位 | 内容 |
|-------------|------|------|
| easyorange-common-tech | 纯技术通用底座 | 纯 JDK 工具类、统一响应体、基础异常、纯技术常量（无框架/中间件依赖） |
| easyorange-common-domain | 领域共享内核 | 共享值对象、领域事件基类、聚合根基类、全局业务枚举 |

拆分判断标准：当 `common` 模块中领域相关代码（值对象、领域事件基类、业务枚举）占比超过 30%，或业务模块需要仅依赖领域部分而排斥技术工具时，启动拆分。

#### common 与 framework 的边界

| 维度 | common | framework |
|------|--------|-----------|
| 依赖范围 | JDK + Jackson + Spring Core（仅 HttpStatus 枚举） | 依赖 Spring 完整生态/Redis/MQ/MyBatis-Plus 等框架库 |
| 内容类型 | 基础定义、工具类、异常定义、枚举 | 配置类、过滤器、AOP 切面、安全拦截、服务实现 |
| 典型类 | `Result`、`BizRequire`、`BaseDomainEvent`、`FileSizeFormat` | `RedisConfig`、`JwtAuthenticationFilter`、`BaseDO`、`RequestUtil` |
| 是否启动 Spring 上下文 | 否（纯定义和工具） | 是（含 `@Configuration`、`@Service` 等） |

**迁移规则**：如果一个类正常运行需要 Spring 容器初始化（如注入 Bean、使用 `@Configuration`），则必须放在 `easyorange-framework`。

> **现状**：`BaseDO`、`RequestUtil`、`FileUtils` 已从 common 迁移到 framework 模块。common 模块现在仅依赖 JDK + Jackson + Spring Core（用于 HttpStatus 枚举），实现了框架依赖的最小化。

#### GlobalExceptionHandler 的定位 `[现状]`

当前 `GlobalExceptionHandler` 放在 `easyorange-framework` 中，原因是：
- 它处理的是所有模块通用的异常映射逻辑（BusinessException → HTTP 响应）
- 它依赖框架层的异常类型（Spring Security、Validation 等）
- 通过 Spring Boot 自动配置注册，所有模块自动生效

`[演进]` 如果未来需要处理模块特有的异常映射（如特定业务错误码的特殊处理），可在 `easyorange-application` 中添加补充的异常处理器，优先级高于 framework 中的通用处理器。

#### 消息模块演进规划 `[演进]`

当前消息模块同时承担了「业务消息（站内信）」和「跨模块事件通信基础设施」两重职责。随着业务增长，应拆分为：

| 演进后模块 | 定位 | 内容 |
|-----------|------|------|
| easyorange-message-infra | 跨模块事件通信基础设施 | Outbox 框架、MQ 路由/重试/死信、事件分发 |
| easyorange-notification | 通知业务限界上下文 | 站内信、消息模板、离线消息、WebSocket、订阅管理 |

**Outbox 模式** `[演进]`：当引入 `easyorange-message-infra` 时，实现事务性事件发布：

```
业务事务开始
  ├─ 写入业务数据（如 user 表）
  └─ 写入 Outbox 表（同一事务）
业务事务提交

OutboxPublisher 定时任务（独立线程）
  ├─ 扫描 status = PENDING 的 Outbox 记录
  ├─ 发送到 MQ
  ├─ 更新 status = PUBLISHED
  └─ 失败则增加 retry_count，超过阈值标记 DEAD_LETTER
```

**重要约束**：`easyorange-message-infra` 模块不得定义任何业务领域事件类。具体事件（如 `UserRegisteredEvent`、`OrderCreatedEvent`）必须在各自业务模块的 `domain/event/` 下定义。业务事件只需实现 `common` 中的 `BaseDomainEvent` 基类即可被 Outbox 框架统一处理。

- `domain/repository/` 作为特殊的出站端口，专门定义聚合根的存取接口
- 技术常量（路由前缀、缓存 Key、MQ Topic）应下沉到对应适配器层的 `constant` 子包
- `[现状]` 部分模块（如 user、order、payment）仍有 `infrastructure` 包存放基础设施工具，`[演进]` 目标是逐步迁移到 `adapter/outbound`

## 四、模块依赖铁律（必须遵守，防止耦合）

1. **easyorange-common**：所有模块可依赖，提供基础定义和工具
2. **easyorange-framework**：依赖 easyorange-common，提供框架封装
3. **easyorange-message**：依赖 easyorange-common + easyorange-framework
4. **业务模块（user/product/order/payment/favorite）**：只能依赖 easyorange-common + easyorange-framework
5. **easyorange-application**：依赖所有业务模块（仅聚合启动用）
6. **业务模块之间禁止直接依赖**：跨模块通信通过事件驱动或 RPC 调用实现
7. **强一致性跨模块场景** `[演进]`：允许通过 `adapter/outbound/rpc` 的 Feign 客户端调用，但必须在 ACL 中转换外部模型

```
依赖方向（箭头表示 "被依赖"）：

common ← framework ← message
   ↑         ↑
   └── 业务模块 (user/product/order/payment/favorite)
              ↑
       application (聚合启动)
```

## 五、DDD 领域设计规范

### 1. 聚合根设计

**聚合根职责：**

- 保证聚合内的业务不变量（Invariants）
- 作为聚合的唯一访问入口
- 通过工厂方法创建，确保创建时满足不变量

**当前实践** `[现状]`：

项目使用 Lombok `@Builder(toBuilder = true)` 实现不可变聚合根，通过 `toBuilder()` 实现返回新实例的"修改"模式：

```java
@Getter
@Builder(toBuilder = true)
public class User {
    private final Long id;
    private final String username;
    private final String password;
    private final UserProfile profile;
    private final LoginInfo loginInfo;
    private final AuditInfo auditInfo;

    public static User register(String username, String encodedPassword, String nickName) {
        Objects.requireNonNull(username, "username must not be null");
        Objects.requireNonNull(encodedPassword, "password must not be null");
        return User.builder()
            .username(username)
            .password(encodedPassword)
            .status(UserStatus.NORMAL)
            .profile(new UserProfile(null, null, null, nickName, null, null, null))
            .loginInfo(LoginInfo.initial())
            .build();
    }

    public User changePassword(String encodedNewPassword, Long operatorId) {
        Objects.requireNonNull(encodedNewPassword, "password must not be null");
        return this.toBuilder()
            .password(encodedNewPassword)
            .loginInfo(this.loginInfo.updatePasswordTime())
            .auditInfo(updateAuditInfo(operatorId))
            .build();
    }
}
```

**聚合边界规则：**

- 一个事务只能修改一个聚合根
- 聚合根通过 ID 引用其他聚合，不直接持有其他聚合的引用
- 聚合内的所有修改必须通过聚合根的方法进行
- 聚合根字段必须为 `final`，修改操作返回新实例

### 2. 值对象设计

值对象强制要求：

- **不可变**：使用 `final` 字段或 `record`
- **基于属性的相等性**：实现 `equals()` 和 `hashCode()`（record 自动实现）
- **自验证**：创建时校验业务规则
- **替换而非修改**：通过返回新实例实现"修改"

```java
public record UserProfile(
    String email,
    String phone,
    Sex sex,
    String nickName,
    String realName,
    String avatar,
    String studentId
) {
    public UserProfile updateEmail(String email) {
        return new UserProfile(email, this.phone, this.sex, this.nickName,
            this.realName, this.avatar, this.studentId);
    }

    public UserProfile updatePhone(String phone) {
        return new UserProfile(this.email, phone, this.sex, this.nickName,
            this.realName, this.avatar, this.studentId);
    }

    public UserProfile updateAvatar(String avatar) {
        return new UserProfile(this.email, this.phone, this.sex, this.nickName,
            this.realName, avatar, this.studentId);
    }
}
```

### 3. 领域服务

- **无状态**：不持有任何可变状态
- **纯业务逻辑**：不包含框架调用、数据库操作
- **多聚合协调**：当业务逻辑涉及多个聚合时使用领域服务
- **与应用层区分**：领域服务处理纯业务规则，应用层处理用例编排和事务管理

```java
public class AuthenticationDomainService {
    public void validateRegistration(User user, List<User> existingUsers) {
        if (existingUsers.stream().anyMatch(u -> u.getProfile().phone().equals(user.getProfile().phone()))) {
            throw new UserDomainException("手机号已注册");
        }
    }
}
```

### 4. 仓储设计

- **接口在 domain/repository**：定义以聚合根为操作对象的接口
- **实现在 adapter/outbound/persistence**：内部处理 DO 与聚合根的转换
- **返回聚合根，不返回 DO**：仓储的使用者只关心领域模型

```java
// domain/repository/UserRepository.java
public interface UserRepository {
    Optional<User> findById(Long id);
    User save(User user);
    void deleteById(Long id);
    Optional<User> findByUsername(String username);
}

// adapter/outbound/persistence/UserRepositoryImpl.java
public class UserRepositoryImpl implements UserRepository {
    private final UserMapper mapper;

    @Override
    public User save(User user) {
        UserEntity entity = UserAssembler.toEntity(user);
        mapper.insertOrUpdate(entity);
        return UserAssembler.toDomain(entity);
    }
}
```

### 5. 领域事件

- **事件基类**：所有领域事件继承 `common` 中的 `BaseDomainEvent`
- **事件命名**：使用过去时态（UserRegistered、OrderPaid、PasswordChanged）
- **事件内容**：仅包含必要 ID 和状态，不传输完整聚合
- **事件发布** `[现状]`：通过 `@PublishEvent` 注解 + AOP 切面实现，事务提交后异步发布

```java
// 领域事件定义
public class UserRegisteredEvent extends BaseDomainEvent {
    private final Long userId;
    private final String username;
}

// 应用服务中发布事件
@PublishEvent(type = "UserRegistered", extractor = "userRegisteredEventExtractor")
@Transactional(rollbackFor = Exception.class)
public Long register(RegisterRequest request) {
    // 业务逻辑
}
```

`[演进]` 当引入 Outbox 模式后，事件发布改为同一事务写入 Outbox 表，由 OutboxPublisher 异步发布到 MQ，保证事务一致性。

### 6. 错误码体系与异常传播

#### 错误码分层

| 错误码定义位置 | 前缀/模式 | 示例 |
|-----------|------|------|
| `common/enums/ResultCode` | 通用系统错误码 | `INTERNAL_SERVER_ERROR`、`VALIDATE_FAILED`、`FORBIDDEN`、`NOT_FOUND` |
| 各模块 `domain/enums/*ResultCode` | 模块业务错误码 | `UserResultCode`、`ProductResultCode`、`MessageResultCode` |

#### 异常继承体系

```
RuntimeException
├── BaseBusinessException (common, 业务异常基类)
│   ├── code: String          # 错误码
│   ├── message: String       # 错误消息
│   └── httpStatus: HttpStatus # HTTP 状态码
│   ├── BusinessException (common, 通用业务异常)
│   ├── ParamValidationException (common, 参数校验异常)
│   ├── FileException (common, 文件异常)
│   ├── UserBizException (user 模块)
│   ├── UserDomainException (user 模块, 领域层专用)
│   ├── ProductNotFoundException (product 模块)
│   └── ... 其他模块异常
```

**划分原则：**
- `BaseBusinessException` — 所有业务异常的基类，提供统一的 code + message + httpStatus
- `BusinessException` — 通用业务异常，用于不需要自定义子类的场景
- 各模块异常 — 继承 `BaseBusinessException`，通过错误码区分具体业务场景
- 领域层异常（如 `UserDomainException`）— 领域层专用，不含任何框架依赖

#### 异常传播路径

```
领域层 (throw UserDomainException)
  → 应用层 (无需 catch，事务自动回滚)
    → 适配层 (GlobalExceptionHandler 拦截)
      → HTTP 响应 (JSON: { "code": "VALIDATE_FAILED", "message": "用户不存在" })
```

**关键规则：**

1. **领域层抛异常**：当业务不变量被违反时，直接抛出模块级领域异常，不 try-catch
2. **应用层不吞异常**：应用服务通常不处理领域异常，让事务回滚；仅在需要自定义错误映射时 catch
3. **全局统一拦截**：`GlobalExceptionHandler` 在 `easyorange-framework` 中统一拦截，确保 API 响应格式一致
4. **RPC 异常映射** `[演进]`：跨模块 Feign 调用时，调用方需 catch FeignException 并转换为自己的业务异常，防止外部异常类型泄漏

```java
// 模块级业务异常定义
public class UserBizException extends BaseBusinessException {
    public UserBizException(String code, String message) {
        super(code, message, HttpStatus.BAD_REQUEST);
    }

    public UserBizException(String code, String message, HttpStatus httpStatus) {
        super(code, message, httpStatus);
    }
}

// 领域层使用（不含任何框架引用）
public class UserDomainException extends RuntimeException {
    public UserDomainException(String message) {
        super(message);
    }
}
```

> **注意**：避免使用 `static final` 异常实例（如 `public static final UserBizException USER_NOT_FOUND = ...`），因为所有抛出点共享同一堆栈跟踪，导致调试困难。应使用 `throw new UserBizException(...)` 每次创建新实例。

## 六、防腐层（ACL）设计 `[演进]`

当跨模块通过 RPC 调用或集成外部系统时，必须使用防腐层将外部模型转换为内部模型：

```java
// adapter/outbound/rpc/acl/OrderAcl.java
public class OrderAcl {
    private final OrderFeignClient client;

    // 外部 OrderDTO → 内部 OrderSummary 值对象
    public OrderSummary toOrderSummary(OrderDTO externalOrder) {
        return new OrderSummary(
            externalOrder.getId(),
            externalOrder.getAmount(),
            OrderStatus.from(externalOrder.getStatus())
        );
    }

    public List<OrderSummary> getRecentOrders(Long userId) {
        return client.getOrdersByUserId(userId)
            .stream()
            .map(this::toOrderSummary)
            .toList();
    }
}
```

### 跨模块 RPC 版本兼容策略

当业务模块之间通过 Feign 直接调用时（强一致性场景），必须考虑 RPC 接口的版本兼容：

**接口变更兼容规则：**

| 变更类型 | 兼容性 | 处理方式 |
|---------|--------|---------|
| 新增字段（响应体） | 向前兼容 | 调用方 ACL 忽略未知字段，使用 `@JsonIgnoreProperties(ignoreUnknown = true)` |
| 新增可选参数（请求体） | 向前兼容 | 提供方设置默认值，调用方可选传递 |
| 删除/重命名字段 | **不兼容** | 提供方必须保留旧字段并用 `@Deprecated` 标记，至少保留一个迭代周期 |
| 修改字段类型 | **不兼容** | 必须新增接口版本，旧接口保留一个迭代周期 |

**ACL 作为兼容性边界：**

ACL 层承担兼容性适配职责——当提供方接口升级时，只需要修改调用方模块的 ACL 代码，调用方上层业务逻辑不受影响。

## 九、关键细节避坑

### 1. 领域层绝对纯净

`domain` 包下的所有代码，**不能 import 任何 Spring、MyBatis、Redis 的 API**，只能依赖 JDK 和 `easyorange-common` 中的纯定义类（枚举、异常基类、事件基类等）。

### 2. 值对象不可变性

所有值对象必须不可变：
- 使用 `record` 或 `final` 字段
- 不暴露可变引用（返回防御性拷贝）
- 通过返回新实例实现"修改"

### 3. 聚合根不可变性

聚合根字段必须为 `final`，修改操作返回新实例。当前使用 Lombok `@Builder(toBuilder = true)` 模式实现。

### 4. 常量分层放置

| 常量类型 | 放置位置 | 示例 |
|---------|---------|------|
| 业务枚举 / 状态 | `domain/enums` | UserStatus、ProductStatus |
| 业务常量（非枚举） | `domain/constant` | UserConstant、ProductConstant |
| 全局共享业务枚举 | `common/enums` | ResultCode、BusinessType |
| 全局技术常量 | `common/constant` | CommonConstant |
| 框架层常量 | `framework/constant` | LoginCacheConstants |
| 模块业务错误码 | `domain/enums/*ResultCode` | UserResultCode、ProductResultCode |

**包命名规范：**

- **枚举包用复数 `enums/`**：`enum` 是 Java 关键字，不能作为包名；使用复数形式避免冲突，符合行业惯例
- **常量包用复数 `constants/`**：与 `enums/` 保持一致，语义清晰
- **枚举和常量分开存放**：枚举是类型定义，常量是静态 final 字段，分开存放便于维护和扩展

> **注意** `[现状]`：当前项目所有模块统一使用 `constant/`（单数），如 `common/constant/`、`user/constant/`、`framework/constant/` 等。`[演进]` 目标是逐步统一为 `constants/`（复数）以与 `enums/` 保持一致。

**原则：常量应紧贴其使用者所在的层，而不是放在模块根级别。**

### 5. 应用服务 vs 领域服务

| 维度 | 应用服务 | 领域服务 |
|-----|---------|---------|
| 职责 | 用例编排、事务管理、端口协调 | 纯业务规则、多聚合协调 |
| 依赖 | 依赖领域服务 + 输出端口 | 仅依赖领域模型 |
| 框架 | 可包含 @Transactional 等注解 | 绝对无框架依赖 |
| 返回值 | DTO/VO | 聚合根/值对象 |

### 6. CQRS 渐进式引入

- **早期/简单场景**：使用传统应用服务（`UserAppService`），同时处理读写
- **读写模型差异大时**：拆分为 `command/handler` 和 `query/handler`
- **复杂查询场景**：Query 侧可使用物化视图、读库副本、ES 等
- **不推荐一刀切**：简单 CRUD 场景强制 CQRS 会增加大量样板代码

### 7. DO 命名规范

- 数据库实体统一使用 `DO` 后缀或 `Entity` 后缀：`UserEntity`、`ProductDO`
- DO 仅存在于 `adapter/outbound/persistence` 包中，不得泄漏到领域层
- DO 与聚合根之间的转换在 `UserRepositoryImpl` 或 `Assembler` 中完成

### 8. 禁止 static final 异常实例

```java
// BAD — 所有抛出点共享同一堆栈跟踪，调试困难
public static final UserBizException USER_NOT_FOUND =
    new UserBizException("USER_NOT_FOUND", "用户不存在");

// GOOD — 每次创建新实例，堆栈跟踪准确
public class UserBizException extends BaseBusinessException {
    public static UserBizException notFound() {
        return new UserBizException("USER_NOT_FOUND", "用户不存在", HttpStatus.NOT_FOUND);
    }
}
```

## 十、架构设计原则

### 1. 六边形架构（端口与适配器）

- **输出端口**：定义依赖外部的接口（如仓储、事件发布、缓存），位于 `domain/port` 和 `domain/repository`
- **入站适配器**：将外部请求（REST、MQ、Job）转换为内部调用，位于 `adapter/inbound`
- **出站适配器**：将内部调用转换为外部实现（数据库、MQ、RPC），位于 `adapter/outbound`
- **输入端口（可选）**：仅当有多个实现或需要解耦时定义，单实现时直接调用应用服务（YAGNI）

### 2. DDD 分层职责

| 层 | 职责 | 依赖规则 |
|---|------|---------|
| adapter | 与外部系统交互，格式转换，实现端口 | 依赖 application、domain |
| application | 用例编排，事务管理，端口协调 | 依赖 domain |
| domain | 核心业务逻辑，领域模型，定义端口 | 仅依赖 common 中的纯定义 |

### 3. 依赖倒置原则（DIP）

- 领域层定义端口接口（`domain/port/`、`domain/repository/`）
- 适配器层实现端口接口（`adapter/outbound/`）
- 应用层通过端口接口与外部交互，不直接依赖具体实现
- `OutboundPort` 标记接口统一标识所有出站端口

### 4. 防腐层（ACL）

- 跨模块 RPC 调用必须在 ACL 中转换外部模型为内部模型
- 集成外部系统（支付、短信）也必须通过 ACL
- 防止外部模型变化污染内部领域模型
