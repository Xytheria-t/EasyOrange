# EasyOrange 模块结构

> 本文档定义**模块级分层规范**：包结构约定、模块边界规则、依赖方向。
>
> **不收录文件树**——模块内有哪些类,读代码即可（`find easyorange-backend/easyorange-<模块> -type f`）。各模块职责见 [README 模块结构表](../../README.md#模块结构),架构守卫的可执行版本见 [`ArchitectureRulesTest`](../../easyorange-backend/easyorange-application/src/test/java/com/cartethyia/easyorange/architecture/ArchitectureRulesTest.java)。

## 一、六边形分层与包结构

所有业务模块统一遵循「adapter（inbound / outbound）→ application → domain」的扁平结构：

```
<module>
├── adapter/inbound/          # 外部 → 模块：web（controller/dto/validation）、job（定时任务）
├── adapter/outbound/         # 模块 → 外部：persistence、cache、elasticsearch、scheduler、messaging
├── application/              # 用例编排：service / command / query / dto / assembler
├── domain/                   # 领域层：aggregate / valueobject / service / event / port / repository / constant / exception
└── config/                   # 模块内基础设施关注点（Bean 注册等）
```

| 约定 | 规则 |
|---|---|
| 出站端口 | 平铺在 `domain/port/`（不使用 `output/` 子包）；`domain/repository/` 是特殊出站端口，专用于聚合根存取 |
| 领域常量 | 放 `domain/constant/`；**技术常量**（路由前缀 / 缓存 Key / MQ Topic）下沉到对应适配器层 |
| 领域服务 | 不使用 `@Service` 等框架注解，由 `config/` 下的配置类手动注册 Bean |
| 领域服务依赖外部功能 | 通过端口接口抽象，由适配器层实现 |
| 已废弃 | `infrastructure/` 包（ArchUnit 对任何新建的 `infrastructure/` 包路径报错）、无分层的 `service/` / `entity/` / `dto/` 目录 |

**应用服务按职责聚合**：避免过度拆分。多个用例共享相同依赖集与事务边界时合并到同一应用服务（如 `AuthAppService` 处理注册/登录/登出/刷新/忘记密码/修改密码）；用例差异大或可能独立演进时再拆分。核心标准：**一个应用服务的构造函数变更不应强迫修改不相关的调用方**。

**DTO 分层放置**：被 `application` 层（assembler / service）和 `adapter` 层（controller）共同引用的 Response/DTO 必须放 `application/dto/`，禁止放 `adapter/inbound/web/dto/response/`——application 层依赖 adapter 层违反依赖倒置。仅 controller 单独使用的响应 DTO 可留在 adapter 层。

## 二、common 与 framework 的边界

| 维度 | common | framework |
|------|--------|-----------|
| 依赖范围 | JDK + Jackson + Spring Core/Web + MyBatis-Plus Extension + SLF4J + Jakarta Validation | Spring 完整生态 / Redis / MQ / MyBatis-Plus Starter 等框架库 |
| 内容类型 | 基础定义、工具类、异常定义、枚举 | 配置类、过滤器、AOP 切面、安全拦截、服务实现 |
| 典型类 | `Result`、`BizRequire`、`DomainEvent`、`FileSizeFormat`、`BaseDO`、`PageRequest` | `RedisConfig`、`SecurityConfig`、`RequestUtil`、`GlobalExceptionHandler` |
| 是否启动 Spring 上下文 | 否（纯定义和工具） | 是（含 `@Configuration`、`@Service` 等） |

**迁移规则**：一个类正常运行需要 Spring 容器初始化（注入 Bean、使用 `@Configuration`）→ 必须放 `easyorange-framework`。

**GlobalExceptionHandler 的定位**：放在 framework，因为它处理所有模块通用的异常映射（BusinessException → HTTP 响应）、依赖框架层异常类型（Spring Security / Validation），并经 Spring Boot 自动配置全模块生效。若未来需要模块特有的异常映射，在 `easyorange-application` 中加补充处理器（优先级高于 framework 通用处理器）。

> `PageRequest`（`common/dto/`）已是纯 JDK + Jakarta Validation 模型——只有 `jakarta.validation` 与 Lombok 导入，不含 MyBatis-Plus 分页类。**领域模型不共享 MyBatis-Plus 的 `IPage`**：分页参数在 common 定义、在 framework 的适配器层翻译成 MyBatis-Plus 分页对象。

## 三、模块依赖规则

- **依赖方向单向向内**：domain → application → adapter（domain 零框架依赖，由 ArchUnit 守卫）
- **跨模块依赖一律 `<optional>true</optional>`**：编译期隔离，跨模块调用只经 Port/ACL 适配，禁止直接依赖其他模块的领域模型或 Mapper
- **端口必有适配器**：ArchUnit 校验「定义了 Port 但无实现」的悬空端口
- **敏感操作要求 `reason` 字段**：管理端订单干预、角色切换等操作必须带理由（落到审计日志）

## 四、模块级约定

**事务**：查询方法必须标注 `@Transactional(readOnly = true)` 以启用数据库只读优化。

**缓存**：所有业务模块的缓存适配器必须遵循以下规则：

1. **端口定义在 `domain/port/`**：如 `OrderCachePort`、`ProductCachePort`
2. **实现放在 `adapter/outbound/cache/`**：如 `RedisOrderCacheAdapter`、`ProductCacheAdapter`
3. **禁用 `infrastructure/` 包**：ArchitectureRulesTest 对新建 `infrastructure/` 包路径报错
4. **技术常量下沉到适配器层**：Redis Key 前缀、过期时间等放 `adapter/outbound/cache/` 下的常量类
5. **应用层只依赖端口**：通过 `OrderCachePort` 等接口操作缓存，不直接依赖 `RedisTemplate`

**跨模块读写**：以 product 依赖 user 为例——通过 `SellerInfoPort` 端口 + `SellerInfo` 值对象隔离，适配器在 `easyorange-application` 模块实现。order 对 product / user / payment 的 Maven 依赖均为 `<optional>true</optional>`，业务逻辑完全经端口 + 适配器隔离。
