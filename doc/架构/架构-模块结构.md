#### common 与 framework 的边界

| 维度 | common | framework |
|------|--------|-----------|
| 依赖范围 | JDK + Jackson + Spring Core/Web + MyBatis-Plus Extension + SLF4J + Jakarta Validation | 依赖 Spring 完整生态/Redis/MQ/MyBatis-Plus Starter 等框架库 |
| 内容类型 | 基础定义、工具类、异常定义、枚举 | 配置类、过滤器、AOP 切面、安全拦截、服务实现 |
| 典型类 | `Result`、`BizRequire`、`DomainEvent`、`FileSizeFormat` | `RedisConfig`、`SecurityConfig`、`BaseDO`、`RequestUtil` |
| 是否启动 Spring 上下文 | 否（纯定义和工具） | 是（含 `@Configuration`、`@Service` 等） |

**迁移规则**：如果一个类正常运行需要 Spring 容器初始化（如注入 Bean、使用 `@Configuration`），则必须放在 `easyorange-framework`。

> **已知问题** `[演进]`：`PageRequest` 依赖了 `mybatis-plus-extension` 的分页类，导致 common 模块引入了 MyBatis-Plus 依赖。应将 `PageRequest` 迁移到 framework 模块，或在 common 中定义纯 JDK 分页模型，由 framework 层适配 MyBatis-Plus 分页。

#### GlobalExceptionHandler 的定位 `[现状]`

当前 `GlobalExceptionHandler` 放在 `easyorange-framework` 中，原因是：
- 它处理的是所有模块通用的异常映射逻辑（BusinessException → HTTP 响应）
- 它依赖框架层的异常类型（Spring Security、Validation 等）
- 通过 Spring Boot 自动配置注册，所有模块自动生效

`[演进]` 如果未来需要处理模块特有的异常映射（如特定业务错误码的特殊处理），可在 `easyorange-application` 中添加补充的异常处理器，优先级高于 framework 中的通用处理器。

#### 消息模块演进规划 `[演进]`

当前消息模块同时承担了「业务消息（站内信）」和「跨模块事件通信基础设施」两重职责。随着业务增长，应拆分为：

| 演进后模块 | 定位 | 内容 |
|-----------|------|------|
| easyorange-message-infra | 跨模块事件通信基础设施 | RabbitMQ Topic Exchange 路由/重试/死信、事件分发 |
| easyorange-notification | 通知业务限界上下文 | 站内信、消息模板、离线消息、WebSocket、订阅管理 |

**已演进**：领域事件已通过 Spring Modulith + RabbitMQ Topic Exchange 实现跨模块通信，废弃了旧 Outbox 和直发 RabbitMQ 模式。应用服务调用 `DomainEventPublisher.publish()` 由 `ModulithDomainEventPublisher`（`@Primary`）代理到 `ApplicationEventPublisher`，Spring Modulith 在数据库 `EVENT_PUBLICATION` 表中持久化事件（与应用事务同原子），事务提交后异步读取并发布到 `eo.domain.events` Exchange。路由键由事件类名自动派生（`ProductCreatedEvent` → `product.created`），无需手动注册。每个消费者独占队列，失败消息路由到 DLQ + 指数退避重试。at-least-once 语义 + 消费者 `EventIdempotencyChecker` 确保精确一次处理。

**包结构调整说明：**

- 去掉了 `infrastructure` 层，所有端口实现统一归入 `adapter/outbound`（纯粹的六边形架构）
- 去掉 `domain/port/input`（输入端口），当只有一个实现类时属于过度抽象（YAGNI 原则）
- `config` 包属于基础设施关注点，保留在模块根包下
- `application/service` 替代 `application/command|query`，采用传统应用服务模式；读写差异大时再拆分为 CQRS
- `domain/port/` 下放置所有出站端口接口（user 模块已移除 `OutboundPort` 标记接口，其他模块仍保留）
- 包结构采用扁平的 `domain/port/`（2026-05-27 统一移除 `output/` 子包），所有出站端口接口平铺在 `domain/port/` 下
- `domain/repository/` 作为特殊的出站端口，专门定义聚合根的存取接口
- 领域常量放在 `domain/constant/`，技术常量（路由前缀、缓存 Key、MQ Topic）应下沉到对应适配器层
- 领域服务不使用 `@Service` 等框架注解，通过 `config/` 下的配置类手动注册 Bean
- 领域服务依赖外部功能时，通过端口接口抽象，由适配器层实现
- **应用服务按职责聚合**：避免过度拆分。当多个用例共享相同的依赖集和事务边界时，合并到同一个应用服务（如 `AuthAppService` 处理注册/登录/登出/刷新/忘记密码/修改密码）。当用例差异大或可能独立演进时再拆分。核心标准：**一个应用服务的构造函数变更不应强迫修改不相关的调用方**
- **DTO 分层放置**：当 Response/DTO 被 `application` 层（assembler、service）和 `adapter` 层（controller）共同引用时，必须放在 `application/dto/` 下，禁止放在 `adapter/inbound/web/dto/response/` 中。原因是 application 层依赖 adapter 层会违反六边形架构的依赖倒置原则（DIP）。仅由 controller 单独使用的响应 DTO 可保留在 adapter 层

> **现状**：所有业务模块已统一采用扁平的 `domain/port/` 结构（2026-05-27）。`infrastructure/` 包已废弃，相关实现全部迁入 `adapter/outbound/`。
>
> **缓存统一规范**：所有业务模块的缓存适配器必须遵循以下规则：
> 1. **端口定义在 `domain/port/`**：如 `OrderCachePort`、`ProductCachePort`
> 2. **实现放在 `adapter/outbound/cache/`**：如 `RedisOrderCacheAdapter`、`ProductCacheAdapter`
> 3. **禁用 `infrastructure/` 包**：ArchitectureRulesTest 会对任何新建的 `infrastructure/` 包路径文件报错
> 4. **技术常量下沉到适配器层**：Redis Key 前缀、过期时间等放在 `adapter/outbound/cache/` 下的常量类中
> 5. **应用层只依赖端口**：通过 `OrderCachePort` 等接口操作缓存，不直接依赖 `RedisTemplate`
