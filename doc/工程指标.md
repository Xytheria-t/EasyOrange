### 4.1 🎯 AI Agent / 大模型 Java 后端方向

#### 4.1.1 1 分钟自我介绍

> 我做了 EasyOrange 项目，定位是 **LLM × DDD 工程化实战 + 轻量级 Agent 编排**。
>
> 核心矛盾：DDD 铁律要求 domain 层零框架依赖，但 LLM 调用贵且不稳定，必须多级缓存 + 限流降级 + 可观测 + 预算治理。我的解法是 Port/Adapter + 装饰器——`LlmPort` 接口在 domain 层，`@Primary` 装饰器 `CachingLlmAdapter` 包 DeepSeek 实现 L1 Caffeine + L2 Redis；`AiRateLimitInterceptor` Redisson 令牌桶按端点限流，超限返回 stale 缓存不是 429；`AiMetricsService` 把缓存命中率/LLM p99/限流计数打到 Prometheus；再加上 `@TokenBudget` AOP 日预算 + Prompt 6 个 YAML 版本化 + Resilience4j Bulkhead（8/4/16 三隔离舱），**6 个 AI 决策点全链路 8 件套工程化**。
>
> 更进一步我写了**轻量级 Agent Planner**（`AiSearchEnhancerAdapter`），没用 LangChain4j/Spring AI（避免框架反射黑盒，面试能讲清每层实现）：用户自然语言查询进来走 4 路 CompletableFuture 并行 Tool Calling——Tool 1 LLM 意图识别（找货/比价/问答）路由、Tool 2 提取商品标签、Tool 3 历史成交统计市场分析、Tool 4 LLM 自动追问建议问题，虚拟线程 `ForkJoinPool.commonPool()` 跑，单步骤 5s 超时降级不影响整体，每路 Tool 复用同一条缓存/限流/预算链路。

#### 4.1.2 高频追问应答

**问：为什么不用 LangChain4j / Spring AI？**
> 我评估过两个框架（对应 [ADR-0003](adr/0003-ai-port-adapter-with-decorator.md) 拒绝项）：
> - LangChain4j 的 `@Tool` 注解靠反射扫描 Tool 方法入参 → GPT JSON Schema 生成 → 反序列化调用，调试堆栈深、出问题要翻框架源码，升级版本经常有 breaking change（我 2026 Q1 用 1.0.0-beta2 升 beta5 时 Tool 返回 record 序列化直接报错）
> - Spring AI 的 `ChatClient` 抽象不错，但 `PromptTemplate` + `ChatMemory` 跟我们自己写的 Prompt YAML 版本化管理 + `AiRateLimitInterceptor` 限流逻辑有重叠，合并成本 > 重写
> - 最后决定手写 Tool Registry（`AiSearchEnhancerAdapter` 4 路 CompletableFuture），代码量其实只有 120 行，每一层 Tool 调用都能打断点 + 写单测，面试也能讲清实现细节，**面试展示价值 > 框架依赖价值**

**问：RAG / 向量检索为什么不用 Milvus / PGVector？**
> （拒绝项第 5 条）量不够——现在 SKU 维度 < 10 万，Milvus/PGVector 引入向量索引构建、ANN 参数调优（HNSW ef_search / nprobe）、运维监控告警一整套东西，ROI 太低。我们用**轻量 RAG 两阶段**：① ES BM25 粗召回 top 50；② Top 50 的 `EmbeddingPort.encode()` 向量跟 query 向量做点积 cosine rerank，LLM 做最终语义排序，P95 延迟 < 300ms 完全够用，等 SKU 到 500 万以上再平滑迁 Milvus。

**问：TokenBudget AOP 具体怎么管的？**
> `@TokenBudget` 注解加在 6 个 AI Service 方法上，配置 `dayBudget=100_0000` token（按场景调），Spring AOP `@Around` 切面在调用前查 Redis `eo:ai:budget:{scope}:{yyyy-MM-dd}` 日累计计数，`incrby usage_total_tokens` 原子累加，超过抛 `TokenBudgetExceededException` 走统一降级——返回 prompt 缓存最近一次成功结果 + 业务侧日志告警。切面同时把每次调用的 `usage.prompt_tokens / completion_tokens / total_tokens` 三围拆到 Prometheus `easyorange_ai_token_usage_total{scope,type}`，方便月末跟供应商对账。

**问：多模态 Vision 调用跟 LLM 是一条链路吗？**
> 是，完全复用同一条 8 件套工程化链路——`VisionPort` 接口在 domain 层，`@Primary` `CachingVisionAdapter` 包 `QwenVlVisionAdapter`（通义千问 VL），L1/L2 缓存 key 用 base64 图片 SHA-256 哈希，`@TokenBudget(scope=AUTO_LISTING_VISUAL)` 单独管预算，Bulkhead `aiVision` 并发 4（比 aiLlm 的 8 小，因为图片推理更贵）。**核心抽象一致，换供应商只加 Adapter 类**。

### 4.2 🏛 Java 架构师 / 高级后端方向

#### 4.2.1 1 分钟自我介绍

> 我做了 EasyOrange，定位 **LLM × DDD：Java 架构工程化实战**。11 个 Maven 模块全解耦，32 个 Port 接口做编译期隔离，ArchUnit 6 条规则在 CI 阶段守住 DDD 分层不被破坏。
>
> 下单链路一致性我选 **本地单事务 + Redisson 分布式锁 + Outbox**，**拒绝 Saga**（见 [ADR-0007](adr/0007-order-saga-single-tx-observability.md)，同样拒绝 2PC/XA/Seata AT/TCC，原由见 [ADR-0001](adr/0001-use-saga-over-2pc.md) Superseded）：`OrderCreationService.createOrder()` 在单一本地 `@Transactional` 内按 productId 排序获取分布式锁（key=`eo:order:lock:product:{productId}`，10s 超时）防死锁防超卖 → 创建订单 + 发布 `OrderCreatedEvent`（Outbox 同事务原子）→ `ProductOrderPort.decreaseStock()` 同步扣库存 → 创建支付记录；任一步失败事务整体回滚，抛 `OrderCreationException`，**无补偿路径**。取消/退款恢复库存、完成标记售出等跨模块副作用由 `OrderLifecycleEventConsumer` 消费订单生命周期事件异步触发。
>
> 事件驱动可靠性靠三层：① **Spring Modulith Outbox** — 业务表 + `EVENT_PUBLICATION` 表同事务原子写入，崩溃重启自动重发，不丢事件；② **DLQ 三级重试** — 消费失败进 DLQ，`DlqRetryScheduler` 每 5min 扫 + 指数退避 1/5/15min 重投，超过 max 转储 `eo.dlq.terminal` 等人工；③ **幂等** — `EventIdempotencyChecker` Redis SETNX 按 `consumerId:eventType:eventId` 去重，多消费者监听同一事件不阻塞；再加 **全链路 traceId**（HTTP → MDC → @Async → RabbitMQ header → 消费者 MDC）。
>
> 架构治理靠 ADR + ArchUnit + PIT 三板斧：6 条 ADR 每条都记「为什么选 + 拒绝了什么」，ArchUnit CI 阻断违规依赖，PIT 变异测试验证 JaCoCo 行覆盖不是假的（order 模块 mutation 70% / test strength 89%）。**11 模块 / 6 ADR / 32 Port / 2,412 测试，Domain 层 84.1% 行覆盖 + 71.5% 分支覆盖**。

#### 4.2.2 高频追问应答

**问：下单为什么不用 Saga？Seata 的 AT/TCC 不是更标准吗？**
> 分两层答——**为什么拒绝 Saga**（决策，见 [ADR-0007](adr/0007-order-saga-single-tx-observability.md)）和 **为什么不用 Seata**（技术对比，原 ADR-0001 结论保留）。
>
> **（一）为什么单库下单不用 Saga**：我们单库部署（MySQL 8.4），`OrderCreationService.createOrder()` 一个本地 `@Transactional` 就把订单 / 库存扣减（`ProductOrderPort.decreaseStock`）/ 支付创建 / Outbox 事件全部包进**同一 MySQL 事务**，任一步失败数据库整体回滚——本地事务比 Saga 的最终一致更强、成本更低。Saga 的补偿要么与回滚重复、要么在进程崩溃后无法重建，`eo_saga` 表留下的只是一行失败状态码，观测价值低于写路径成本。所以我在 [ADR-0007](adr/0007-order-saga-single-tx-observability.md) 明确**拒绝 Saga**：单库场景正确识别过度设计，比挂一个失效状态机更能体现架构判断力。真正的演进触发条件是 product/payment 模块拆分独立数据源 / 独立部署，那时才重新评估真 Saga / 事务性 Outbox 补偿。
>
> **（二）为什么不用 Seata（知识保留）**：
> ① **Seata AT 模式** 要代理数据源 + undo_log 表 + TC/TM/RM 三角色独立部署，跟我们的 `@ConditionalOnProperty RabbitMQ` 降级模式不兼容——RabbitMQ 没了能起应用，Seata TC 挂了直接连不上；
> ② **TCC 模式** 3× try-confirm-cancel 样板代码，每个参与模块都要写 Try/Confirm/Cancel 三个接口，侵入大、维护成本爆炸；
> ③ 我们平台不经手资金，没有 double-spend 风险，本地单事务的强一致已经覆盖，Seata 强一致 ROI 太低；
> ④ 2PC/XA 需要全局事务协调器、穿透 Port/Adapter 边界、锁等待长——这条理由现在覆盖**整个 Saga 家族**（2PC/XA/Seata AT/TCC/Saga 编排），全都以同样理由被拒绝。

**问：为什么用 RabbitMQ 不用 Kafka？Kafka 不是更标准吗？**
> 这个问题我评估过 5 种 MQ（Rabbit / Kafka / Pulsar / NATS JetStream / Redis Streams），最后按 4 个维度打分选的 Rabbit，不是不知道 Kafka，是场景和成本都没到（见 [ADR-0005](../doc/adr/0005-messaging-bus-select-rabbitmq-over-kafka-nats-pulsar.md)）：
> ① **DLQ + 重试（40% 权重）Kafka 不原生**：我们有 `DlqRetryScheduler` 三级重试 + terminal 毒消息转储，RabbitMQ 的队列级 `x-dead-letter-exchange` 是声明式的，两个参数搞定；Kafka 根本没有「死信」概念，消费失败要自己手动发 dlq topic、自己调度器重投、自己配位点提交逻辑，成本翻倍；
> ② **模型（30%）不匹配**：我们是 1 个事件 → 11 个独立下游各消费各的（AI 要估值、订单生命周期要恢复库存 / 标记售出、审计要写库、通知要发消息），RabbitMQ 的「Exchange → 多独立队列」是原生的；Kafka 得搞 11 个不同 consumer group，每个 group 自己维护 offset + 重试，分散难讲还容易出 bug；
> ③ **成本（20%）和运维（10%）失衡**：Kafka 高吞吐优势是百万 msg/s 才显现，我们每天几万条事件，RabbitMQ 单节点 10k msg/s 完全够——杀鸡用牛刀，分区/副本/consumer group lag 带来的运维复杂度是纯负担；
> ④ **兜底方案**：我保留了 `MessageBus` Port 抽象，NATS JetStream 做了备选实现（`@ConditionalOnProperty` 切换），真哪天量到了换 Kafka 改 Adapter 就行，domain/application 层一行不用动。

**问：NATS JetStream 和 Kafka 你们如果真要二选一改哪个？**
> 选 NATS。两个原因：① **DLQ 原生**（`max_deliver + discard policy=dead`，和 Rabbit 的声明式粒度最接近，现有 `DlqRetryScheduler` 最容易迁移）；② **运维最轻**（`nats:2.10 -js` 单容器 50MB 镜像，Kafka KRaft 模式单节点也重得多）。Kafka 的唯一优势是「大众认知广 + 简历好看」，但从「替换成本最低、模型最贴合」的架构视角选，肯定 NATS。

**问：CQRS 为什么只在 4 个模块做，message/favorite 不做？**
> 见 [ADR-0002](adr/0002-cqrs-scope-only-4-modules.md)。CQRS 的核心收益是「读多写少 + 查询聚合跨多个聚合根 + 读写模型可以独立优化」。product（读多写少，ES 全文搜索 + 列表聚合）、order（列表页跨 product+payment 聚合）、payment（对账查询独立索引）、message（消息会话列表跨用户投影）这 4 个满足条件。
>
> message 模块的聊天消息读写比 1:1，用户发一条对方读一条，读优化收益几乎为 0；favorite 收藏列表最多几千条，DB 单表 `WHERE user_id = ?` 加索引够用。CQRS 不是银弹，每个模块都拆 Command/Query Repository 多一倍代码量，收益 < 维护成本就坚决不做。

**问：ArchUnit 具体守了什么？你们 CI 真的能阻断吗？**
> `ArchitectureRulesTest` 6 条规则：
> 1. `domain` 包的类不能依赖 `org.springframework.*`（零框架依赖）
> 2. `*CommandService` 不能依赖 `*QueryRepository`，`*QueryService` 不能依赖 `*CommandRepository`（CQRS 读写分离）
> 3. 模块间只能通过 `*.port.*` 和 `*.valueobject.*` 包通信（ACL 端口隔离）
> 4. 每个 `*Port` 接口必须有 `@Component` 或 `@Primary` 的 `*Adapter` 实现（端口必有适配器）
> 5. 禁止出现 `*.infrastructure.*` 包（避免"基础设施层"大杂烩破坏六边形）
> 6. Controller 方法返回值必须是 `Result<T>` 或 `PageResult<T>`（统一响应格式）
>
> 测试挂在 `easyorange-application` 模块的 `./mvnw test` 里，CI GitHub Actions 的 build-and-test job 只要失败就红，PR 合不进来，真能阻断。

**问：PIT 变异测试是什么？跟 JaCoCo 区别？**
> JaCoCo 行覆盖只看「代码被执行过没」，不管「测试能不能发现 bug」——把一个 `if (a > 0)` 改成 `if (a >= 0)`，JaCoCo 还是绿的，但实际上逻辑变了。PIT 在编译后的 bytecode 里注入**变异**（mutations）：比如把 `<` 改成 `<=`、把 `+` 改成 `-`、把 `return x` 改成 `return null`，然后跑现有测试，如果测试还全绿，说明这个变异**没被杀掉（存活）**，对应位置的测试没覆盖到真实逻辑。
>
> 我们只对 domain 层做（聚合根状态机 / 领域服务 / 值对象），order 模块 81 个变异跑 41 秒，mutation 70%（杀掉的比例）、test strength 89%、line 81%。JaCoCo + PIT 双门禁互补，避免写「为了覆盖率的空测试」。

**问：Outbox 怎么保证事务一致的？崩溃了真的不丢事件？**
> Spring Modulith 的 Outbox 实现在 `org.springframework.modulith:spring-modulith-events-core`，核心就是**同事务双写**：
> 1. 业务 Service 方法 `@Transactional` 里先写业务表（比如 INSERT eo_order）
> 2. 再把 `DomainEvent` 序列化成 JSON 写入 `EVENT_PUBLICATION` 表（事件 ID / 类型 / completion_date = null）——**这两条 SQL 在同一个本地事务里**，要么都成功要么都回滚
> 3. 事务 commit 之后，`ApplicationListenerMethodAdapter` 异步从 `EVENT_PUBLICATION` 表捞 `completion_date is null` 的事件，一条一条发 RabbitMQ，发成功 UPDATE completion_date = NOW()
> 4. 崩溃重启时，`spring.modulith.events.republish-outstanding-events-on-restart=true` 会重新扫所有未完成事件，再发一次
>
> 关键是**至少一次投递** + **消费者幂等**配合：Modulith 保证不丢（可能重复），`EventIdempotencyChecker` 保证重复投递也只处理一次。

### 4.3 通用高频追问

**被问"业务复杂度这么低有意义吗？"（防守型话术）**
> 我同意业务本身不是重点——我特意选了 C2C 资产流转做载体，因为它刚好能完整展示 DDD 的 4 个核心聚合根（Product / Order / Payment / User）、跨模块一致性架构决策（拒绝 Saga → 本地单事务 + 分布式锁 + Outbox）、读多写少场景（CQRS）、实时通信（WebSocket）这几个架构模式。**如果业务做复杂了，比如再加议价 / 阶梯降价 / 优惠券，状态机就有几十种转换，面试时间根本讲不完**，反而侵蚀 DDD/AI 工程化的主线叙事。

> 真正的复杂度我刻意放在架构与 AI 工程化上：11 模块 + 32 Port 编译期隔离 / 拒绝 Saga 的 ADR 决策（本地单事务 + 分布式锁 + Outbox）/ Outbox + DLQ 三级重试 / traceId 全链路 / LLM 调用 8 件套工程化 + ADR+ArchUnit+PIT 治理三板斧，这些才是 Java 架构师 / AI Agent 岗真正关心的。
